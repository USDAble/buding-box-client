## 2. 逐个 PR

### `PR-1` 契约层 + 中台替身 + 客户端骨架（最小范围）

**为什么三者必须同一个 PR：** 替身是客户端的**镜像**。先写替身会发明一份契约，再写客户端又发明一份，两份必然漂移 —— 正是 `§3.8` 禁止的"同一件事两处定义"。**一份 Go 类型，两个实现**，替身才具备证明力。

> **⚠️ 实施期范围修正（2026-09-11，落代码时发现，已按此实现）。** 本节原先把 JCS + ed25519 验签列在 `PR-1`。**这是错的**：`PR-1` 的四个端点（发码 / 登录 / 刷新 / bootstrap）**没有任何签名要验** —— 需要验签的是**签名目录与策略信封**。而 bootstrap 在合同里**同时返回目录**（`中台交付包` §4.1 第 5 行：账户摘要 + 权益 + 余额 + **模型目录** + 能力矩阵 + 策略版本），所以正确做法是**把 bootstrap 收敛为「账户 + 激活 + 余额」，目录与能力矩阵留到 `PR-4`**，签名代码整体下沉到 `PR-4`。理由有二：① 让 `PR-1` 不包含本题**唯一没有现成实现**的一处，符合"先走通流程、别太复杂"；② JCS 是 RFC 8785，手写一份不合规的实现比不写更危险，它应当与目录一起一次做对。**bootstrap 不带目录是合法状态，不是错误**（`B4`：目录未就绪时选择器为空 + 不可用提示）。

**做：**

1. `internal/productclient/` —— **契约层**：`dto.go`（请求/响应类型 + 错误码常量，是字段名与错误码的**唯一 owner**）+ `client.go`（4 个端点 + 内存凭证持有者 + 401 单飞刷新与一次重放，即 `PR-1` 即已落地 `L-A6`）。
2. `internal/productclient/clienttest/` —— **中台替身**：真 HTTP handler、可编排场景、含测试码重置，**与客户端共用上面那份类型**。
3. 测试：用替身驱动客户端，覆盖 `L-A1a` `L-A2`–`L-A6` 的**客户端侧**分支（`L-A1b` 有意不实现）。

**不做（留到后续 PR）：** **JCS + ed25519 签名/验签（下沉 `PR-4`）**、模型目录与能力矩阵（`PR-4`）、网关 SSE（`PR-5`）、词库（`PR-6`）、`/api/product/*` 本地服务（`PR-2`）、前端接线、`devBackend` 拆除、可执行替身文件。

**验收：**

- 用替身跑通 `L-A2`（二次登录**不需要**激活码与盒子编号）、`L-A5`（bootstrap 回填 `boxCode`；缺失时是空值而非报错）、`L-A6`（401 单飞刷新一次 + 重放一次；刷新被拒 → 清凭证 + `ErrSessionExpired`，不重试）。
- 四个激活错误码（`activation_invalid` / `activation_code_used` / `box_code_unknown` / `box_code_mismatch`）**各自**可被触发并断言（`L-A4`）；`phone_mismatch` 亦单列。
- 同一盒子编号 + 两个不同激活码 → **两次都成功**（`L-A4` 的一对多回归）。
- 平台完全不可达 → `network_unavailable`（与上游 5xx 区分，且**不**回落本地模型源）。
- `L-A1b` 的"响应已送达但响应丢失"分支 **不实现**，登记为 `PQ25` 的未决面。

**替身的形态：**

| 项 | 定 |
| --- | --- |

| 重置 | `New()` 每次都是干净状态，等价于重置测试激活码，对应 `S-8` 要中台提供的那一项 |

**同时定死 `V-7`（首启初始化时序）** —— 此前四处未写：责任人、时刻、初值、只读盘行为。结论落在 `需求基线` `E6.4`：

- **责任人 = Go 本地服务**。`installId` 是「这台安装」的属性，而安装边界＝数据根，数据根的唯一 owner 是 `internal/datapath`；让桌面壳生成会造出**第二个路径与生命周期的 owner**（§3.8）。壳只把**系统语言**带进来一次（`PQ18`）。
- **时刻 = 首次读取时惰性创建**，不新增任何"进程启动写文件"的路径。比 §3.9.1 允许的"启动时幂等播种"更强：**没有任何一次进程启动会写文件**。
- **只读盘 / 写失败 ⇒ 内存默认值让界面可渲染 + 错误向上返回**，不阻塞启动、**不假装已持久化**。
- **与 `E6.2` 规则 4/5 的顺序**：文件**不存在**才播种；版本**超前**与文件**损坏**都**不得**进入播种路径（否则新版本或损坏数据会被空白状态悄悄替换）。

**明确的边界（本 PR 不做）**：HTTP handler、产品门、`internal/server` 的接线、凭证与 `productclient` 的对接（令牌从内存到凭证文件的搬运）。这些是 `PR-2b1` / `PR-2b2a`。

### `PR-2b1` 本地 `/api/product/*` 端点（已完成）

**做：** `internal/productruntime` 承载 5 个端点（`GET /state`、`POST /send-code`、`POST /login`、`POST /logout`、`PUT /locale`），按 [`本地API契约.md`](本地API契约.md) 的三类信封与错误码实现。

**实施期定下三件契约上的事（都已回写文档）：**

1. **信封层级由本地契约决定，不由中台决定。** 中台会在错误体里带 `field`（它把 `activation_invalid` 标成 `activationCode` 的错），但 `本地API契约.md` §3 把这四个激活失败定为**业务级**，所以实现忽略中台的 `field`。理由：用户改不动这些值（`activation_code_used` 只能找客服），落在输入框下面会误导成"改一下就能过"。层级表只有 3 个字段级 code，落在 `envelope.go` 的 `fieldLevelCodes`。

### `PR-2b2b` 产品门 + window token（✅ **已完成，2026-09-11**）

#### 机制全貌（端到端）

```
桌面壳启动 ── crypto/rand 32 字节 → hex（仅内存，一次）──┬─▶ server.Config.WindowToken
                                                      └─▶ shellURL() 拼进 webview URL ?…&window_token=…
                                                                    │
前端 adoptWindowToken()（早于任何 fetch）──▶ sessionStorage ──▶ 后续请求带 X-Octo-Window-Token
                                                                    │
后端 productAPI 的 wrapper（缝交的注册器）：配置了令牌 ⇒ 比对，失败 403 {"error":"product_gate"}
                                                                    │
前端 api.ts:56 收到该 403 ⇒ productPhase = "blocked"
```

**范围代价（登记 `D-006`）：** `P3` §5.4.3「未登录时窗口发起的请求同样不可用」在上游 `/api/*` 上不由本门覆盖 —— 真正实现它需要服务端按 `internal/productstate` 的激活态校验，而不是把窗口令牌铺到全部 `/api/*`（失败模式已实测）。

### `PR-4a` 验签核心（✅ **已落地 2026-09-11**）

> **落地结果：** `internal/productclient/{policy,signing}.go` + 替身签名能力（`internal/productclient/clienttest/sign.go`）+ `developer.json` 测试锚；14 条测试，两条钉子经变异验证会红。**实现与本文档的差异只有一处**：原计划把 `SignPolicy` 写成"不会失败"的辅助函数，实现改为**返回 error**（密钥长度不对时报错而非 panic）—— 因为替身是可执行进程，panic 会杀掉服务而不是给出可诊断的错误。详见 §6 修订。

**为什么它是打底而不是闭环。** 它不产生任何用户可见行为 —— 与 `PR-2a` 同性质。它的判据是**单元测试**：给定一段字节、一个 `keyId`、一个签名，判定"接受/拒绝"是否正确。后续 `4b`/`4c`/`4d`/`4e` 都建立在它之上。理由同 §2 `PR-1` 的范围修正：让本轮**唯一没有现成实现**的一处独立出来，一次做对。

**做：**

1. `internal/productclient/signing.go` —— **签名与验签的唯一一份实现**（§3.3 写死的约束：不得让签名方与验签方各写一份）。
   - 验签：输入 = **被签名的那段原始字节** + `keyId` + base64 签名；用 `crypto/ed25519`（**stdlib，复用，零新依赖**）对 `productprofile.TrustedKeyIDs[keyId]` 的公钥验签。
   - 签名：同一份实现对测试/替身可逆调用（替身要产出真签名）。
   - 四道校验，**任一条失败即 fail-closed**（`B2` 规则 2）：① 签名；② `keyId` 在 `trustedKeyIDs` 内；③ `audience` 等于本产品；④ 时钟窗口（`issuedAt`/`expiresAt`，含允许的偏斜），**时钟不可信时拒绝而非放行**。
2. 信封解析：`data.policy` 以 `json.RawMessage` 取出（**保留原始字节**，`encoding/json` 不重排 RawMessage 内容）+ 同级 `data.policySignature{keyId,sig}`。`policy` 内部字段（`policyVersion`/`catalog`/`capabilities`）此时只解析 `4a` 要用的那几个。

#### 第 2 步补充（开工时定下的实现级决定）

上面六处是**需求级**缺口。真去读代码又碰到八处**实现级**决定，全部记在这里 —— 计划里没写的实现选择，事后没人能判断它是有意的还是随手写的。

**① 落缓存有个会「静默写坏签名」的陷阱（已实测，不是推测）。** 需求说缓存**原始签名信封**、客户端**不做任何规范化**（`中台交付包` §4.3）。而 Go 的 `json.Marshal` 对 `json.RawMessage` 做两件事：**压缩空白**、**HTML 转义**。实测五种输入：

| 输入（`policy` 的字节） | `json.Marshal` 写出 | `Encoder` + `SetEscapeHTML(false)` | 读回是否逐字节相同 |
| --- | --- | --- | --- |
| `{"a":"x&y<z","b":1}` | `{"a":"x\u0026y\u003cz","b":1}` | 原样 | ❌ / ✅ |
| 带缩进的 `{\n "a": 1\n}` | `{"a":1}`（压缩） | `{"a":1}`（同样压缩） | ❌ / ❌ |
| 线上就是 `x\u003cy` | 原样 | 原样 | ✅ / ✅ |
| 中文 | 原样 | 原样 | ✅ / ✅ |
| `\"` 与 `\\` | 原样 | 原样 | ✅ / ✅ |

**第一行不是理论风险**：模型展示名里出现 `&` 或 `<` 完全正常（`Tools & Agents`），而 `json.Marshal` 会把签名覆盖的字节改掉 ⇒ **缓存写下来就已经验不过**，表现为"这台机器永远缓存不住目录"，且看不出原因。

**决定**：写 `catalog.json` 用 `json.Encoder` + `SetEscapeHTML(false)`；**并在写之前自检** —— 把要写的字节按读路径解析回来，`policy` 不逐字节相同就**拒绝写**并报错。即"**不写一份自己读不回来的缓存**"。第三行（平台自己缩进）因此变成一条**响亮的失败**而不是一条静默的坏缓存；修法是局部换一个 verbatim writer，已在错误值上写明。

**② `expiresAt` 取两者的较早者。** 契约给了两个时间轴：policy 的签名窗口（`issuedAt`/`expiresAt`）与目录自己的新鲜度（`catalog.ttlSec` + `issuedAt`）。`4c` 需要**一个**字段判断"离线还能不能用"，取 `min(policy.expiresAt, issuedAt + ttlSec)`（`ttlSec` 缺失或非法时不取第二项）。保守方向，且两条都成立才可用 —— 政策窗口过了要刷新，目录本身陈旧了也要刷新。

**③ 单调性的轴是 `catalog.version`，不是 `policyVersion`。** `需求基线` B2 规则 3 写的是 `catalogVersion`；两个版本是两个事实，把它们合成一个判据会让"改了策略但目录没变"被判成回滚。`policyVersion` 的消费（撤销/最小客户端版本）不归 `4b`。

**④ 缓存损坏时**单调性的比较基准随之消失**（残留缺口，写明而不是假装没有）。** 文件读不出来就没有"当前版本"可比，此时只能接受新目录 —— 否则用户被永久锁在损坏文件外面、且没有任何恢复路径。**代价**：能改本地文件的攻击者可以"先弄坏缓存再重放旧目录"。判定为可接受（能改本地文件的攻击者已在机器内），但登记在此，因为它是一个**有意的**取舍。

**⑤ 四个拒绝原因是本 PR 的交付物之一，但**不是四类错误****。** 定义 `catalogOutcome` 一个枚举：`ready` / `transport`（没到达或 5xx）/ `verification`（签名、`audience`、时钟窗口）/ `rolled_back`（签名有效但更旧）/ `unavailable`（没有信封可用，也没有可用缓存）。**`4b` 只做分类与日志，一个字的文案都不定**（`4c` 的三条降级与四种文案消费这个枚举）。平台没给信封时归 `unavailable`：用户面对的是"没有目录"，而分类是按**用户面对什么**分的，不是按**哪一层先发现**。

**⑥ 信任锚与受众走 `Deps` 字段，不 import。** 与 `ControlPlane` 同形：`productruntime` 不 import `internal/productprofile`（判据的 owner）也不 import `internal/brand`（受众 = `brandId` 的 owner），装配层把值填进 `Deps`。好处有三：owner 不变、`productruntime` 保持"只转发"、四种失败面在测试里可造。**受众的取值来源是 `brand.Load().BrandID`**（不写品牌字面量，`开发规范` §3.1 规则 2）。

**⑦ `Deps.Catalog` 为 nil 时**根本不发起拉取****（没有地方可放）。这是"装配失败也不要让登录挂掉"的边界，不是降级路径：`4b` 里拉取只有一处发起，没有缓存时拉回来也没人能用。

**⑧ 替身补三个故障开关，其中一个让 `L-A6` 第一次端到端可达。** `RefuseSessionsAfterLogin()`（登录成功但发出的令牌不被承认 ⇒ `bootstrap` 401 → 刷新被拒 ⇒ `ErrSessionExpired`）、`FailBootstrap(status, code)`（会话正常、目录拉不到）、`SetCatalogVersion(v)`（签名有效但更旧的目录）。**第一条是本 PR 顺带解决 `V-29` 的关键**：`bootstrap` 是首个 `doAuthorized` 调用，它一进 `handleLogin`，`L-A6` 的清凭证链路就从"机制在、触发点不存在"变成真的能走一遍。

**⑨ 受众一致性加一条钉子。** 替身签的 `FixturePolicyAudience` 必须等于 `brand.Load().BrandID`，否则 developer 构建**对每一份目录都验不过**，而现象读起来像"中台坏了"。与已有的"替身密钥 = developer 信任锚"钉子（`profile_key_test.go`）同一性质，同一个文件里加一条。

**⑩ 测试用的锚与受众必须是**显式值**，不能读 `productprofile.Current()`**。`Current()` 由构建标签决定，`test-production`（`PR-9` 接线）会以 `product_production` 跑同一批测试 —— 那时 `Current()` 是 production 锚（空 `trustedKeyIDs` + `.invalid` 主机），任何依赖它的测试都会以"环境不同"失败。故测试填 `clienttest.FixtureSigningPublicKey()` + `brand.Load().BrandID`，两个都是与标签无关的显式事实。

**本 PR 明确不做**：TTL 到期后的条件请求（`ETag`/`304`）与周期刷新、三条降级语义与文案、投影与前端渲染、`/catalog/models` 客户端方法 —— 前三件归 `PR-4c`，后两件归 `PR-4d`。

**开工前置**：本方案的六处缺口里 ①②③ 是**文档级改动**（`L-C1a` 的异常分支栏、`catalogstore` 的 owner 声明、§1 表已改），其余按上表执行。**代码未写，测试未红。**（*本节为开工前的方案原文，保留不改，以便对照实际落地时的偏差。*）

### `PR-4c0` `V-35` 前置拦截：网关绑定的模型名不得落到默认 sender（✅ **已完成 2026-09-13**）

**为什么会有这条 PR（不是计划里的，是手工验收逼出来的）。** `PR-4d` 的人工验收里，用户选中「布丁隐私版」发了一条消息，界面出现：

```
HTTP 400 (invalid_request_error): The supported API model names are
deepseek-flash, deepseek-v4-pro, but you passed buding-gateway::buding-privacy-1
```

> **这条报错同时证明了两件事，其中一件是好消息。** 报错里的 `buding-privacy-1` **只存在于签名目录的夹具里**（用户机器上那份 `data/chat-modes.json` 是 `buding-local-general` 等旧四项，`devBackend.ts` 的本地表也是那四项）⇒ **`PR-4d` 的投影确实端到端生效了**，选择器读的就是签名目录、复合 id 前缀也确实来自 `productprofile`。另一件是缺陷。

**第 0 步 · 粒度自检＝一条 PR。** 用户可见结果只有一个：**选了目录模型后发消息，请求不再发给第三方，而是本地说明原因。** 四段（检测点 / 拒绝 / 错误码语义 / 文案）拆不开 —— 少任一段，用户要么继续看到那个第三方 400，要么只看到沉默。

**第 1 步 · 需求分析。**

**机制（逐行核实，不是猜测）**：`internal/server/server.go` 的 `senderForSession` 是**所有回合路径的唯一解析点**（`buildAgent` 的四个调用方：REST / WS×2 / 定时任务）。前端把 `model_id = "buding-gateway::buding-privacy-1"` 发到 `PATCH /api/sessions/{id}/model`，`config.EntryByModel` 匹配不到（`config.yml` 里没有这个端点），走 `handlers.go:1373` 的最后一个分支 —— 注释原文就是"Raw model string: keep the default sender, change only the model" —— 存成 **`Model` = 复合 id、`ModelConfig` = `""`**。于是 `senderForSession` 在**第一个** fallback（`sess.ModelConfig == ""`）就把这个字符串交给了默认 sender；默认 sender 来自 `data/config.yml`（用户那台是真 DeepSeek）⇒ 就是那句 400。

**两件事是错的，第二件更重**：① 用户拿到一句看不懂的第三方报错；② **那个请求真的到了 DeepSeek**（错误是它返回的）⇒ 对话内容随该请求一起发了出去。`B4` 禁止的正是第 ② 件。

**规则（一句话）**：**默认 sender 不得收到"网关绑定"的模型名。** 要么由网关 sender 承载，要么这个回合不开。

**scope（§3.10，这一条必须写清否则会被用反）**：**所有 profile 生效，含开发构建**。这**不是** production 的 `RequiresControlPlane` 强制（那条仍归 `PR-5`，见 `V-27`）：开发构建里用 `config.yml` 当模型源是**被允许的**，但"网关绑定的 id 交给 `config.yml` 的端点"在任何 profile 下都必然失败且把内容发给第三方。护栏**只认网关前缀**，所以正常从设置里选真实端点模型的上游流程**完全不受影响**。

**落点取舍（§3.7 第 2 项，已人工确认）**：

| 方案 | 位置数 | 结论 |
| --- | --- | --- |
| **① 在 `senderForSession` 一处拒绝**（**已选**） | 1 | 唯一解析点 ⇒ 一处覆盖全部回合路径。`§4.5` 不改上游函数签名、而它返回 `(Sender, string)` 无 error ⇒ 用**拒绝型 sender**（非惯例做法，已登记） |
| ② 四个 `buildAgent` 调用点各自拦截 | 4 | 同一条规则写 4 遍，漏一个等于没做（`§3.8`） |
| ③ 只改前端 | 1 | 零上游改动，但**不权威**：队列里的消息、REST、**定时任务**仍会照发。`§3.9` 要 fail-closed，这条是 fail-open |
