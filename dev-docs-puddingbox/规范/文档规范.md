# 文档规范

> 本文件约束 `dev-docs-puddingbox/` 中新建或实质重写的 Markdown。它不改动上游 `dev-docs/`，也不要求为了格式合规而批量重写历史文档。

## 先选上游样例

设计、契约、实施和手册类新文档必须在标题下用一行 `写作参照：dev-docs/<文件名>.md` 标明最接近的上游样例。参照的是信息组织和论证方式，不是复制文字；样例本身的过期修订表或历史叙述不构成本 fork 的格式要求。长期规则与策略没有对应的上游样例时，改为在开头说明适用范围、权威来源和验证方式。

按目的选择样例：

- 产品或技术设计：`desktop-update-notice.md`、`permission-remember-design.md`。先给当前结果，写目标与非目标，按关键决策展开，以验证收尾。
- 接口、配置或数据契约：`endpoint-custom-headers-design.md`。定义边界、术语、兼容性、错误路径，逐项解释不做什么及原因。
- 实施方案或迁移：`endpoint-pr5-impl.md`。标出范围和非目标，按数据模型、读写路径、兼容性拆解为可验证的变更。
- 运维或排障手册：`relay-runbook.md`。按可执行顺序说明准备、验证、运行、升级和失败处置。

找不到合适样例时，先在 PR 说明所选结构和原因；需要新增样例类型时再修改本节。这样让写法持续对齐上游真实文档，而不是随着抽象模板漂移。

## 文件与范围

- 文件名只写主题，不编号；阅读顺序由“相关文档”链接表达。已有编号文件通常随主题重写迁移；用户明确要求去编号时，可做一次受控的纯重命名，但必须先检查并更新所有入站引用。
- 一文件一主题。新问题属于已有主题时更新原文；边界独立且能独立验证时才新建文件。
- `规范/` 只放长期规则；设计、契约、实施和手册放目录根。一次性讨论稿在结论拆入主题文档后删除。
- 文档要写当前有效事实。Git 保存修订历史，不维护版本、日期、作者或完成状态表。

## 每份文档至少回答什么

1. 读者现在能获得什么结论、能力或操作结果？
2. 范围和 `## 非目标` 是什么？设计类文档必须有该节；其他类型也必须写清不适用的范围。
3. 关键取舍、例外和被否决的方案是什么，为什么？时间敏感的决定标明日期及复审触发条件。
4. 谁是事实源，如何验证？代码引用稳定的符号名和相对链接，不使用 `file:line`。
5. 改动需求或方案后，哪些相关主题文档需要同步为当前结论？

标题表达结论或问题，例如 `## 登录态只属于当前设备`；不用“概述”“详细设计”“其它”。一个事实只在一处完整论证，其他文档只保留一句结论和链接。

维护本目录的 Markdown 链接，或在源码、脚本与 CI 中引用本目录的路径后，运行 `make docs-ref-check`。代码注释只解释约束或取舍，不保存已退休的文档路径、章节号或计划编号作为第二份索引。

## 功能进入开发前要做可追溯评审

功能文档不是“写完就视为可开发”。在不改代码的审阅阶段，按用户路径逐项核查以下问题，并把发现的缺口回写到该主题，而不是另建重复的验收台账：

- **必要性与入口：** 这个能力解决哪一个可观察的用户问题；能否合并进现有页面或接口，而非增加孤立入口、开关或文档？
- **唯一事实源：** 显示值、状态、配置和身份各由谁拥有；同一事实是否被两个页面、两个接口或两份文档分别推断？
- **边界与最小化：** 涉及外部服务、隐私或支付时，输入、自动附带的数据、持久化、重试、授权和失败后保留什么，明确禁止什么？
- **失败可行动：** 每个用户可见失败是否有稳定错误码、可执行的界面动作和不误导的降级；是否避免把内部错误、密钥或开发配置露给用户？
- **实施与验收：** 能否对应到本地 API、中台契约、状态所有者和至少一条自动或人工走查；若实现尚不存在，是否清楚标为待实现而非当前事实？

评审结果只有三种处理：保留并补足边界、合并进已有主题，或删除无独立价值的设想。通过审阅不等于实现完成；进入开发后仍必须以代码、契约夹具和真实用户路径验证。

## 长度与可读性

目标控制在约 300 行；超过 600 行时应按主题拆分，确实不能拆时在 PR 中说明原因。优先使用短段落、列表和贴近决策的示例，不用台账、流水账或重复表格填充篇幅。

## 禁止事项

- 不新增 `V-n`、`L-*`、`TODO-nn`、`P0-nn` 等人工状态编号，也不在表格中维护 ✅ / ⚠️ / 完成度。
- 不维护修订历史表，也不跨文档复制整段事实、方案或表格。
- 不留只有“已废弃”“仅供参考”的空壳；事实过期时更新或删除它。
- 新写或随当前功能修改的代码注释只解释“为什么”；不以文档路径、章节号或行号代替原因。

## 迁移历史文档

不要全仓搜索替换。功能变更或明确重写某主题时，以代码和测试核对当前事实，合并重复推理、删除过期台账，并让文档对齐最接近的上游样例；其余历史文档保持可读即可。

## 非目标

- 不替代代码评审、测试或需求澄清。
- 不约束上游 `dev-docs/`、外部需求原文或中台文档。
