## 1 结论

1. **文件是唯一真相，页面只是它的编辑器。** `data/sensitive-words.txt` 是权威；页面**不保留第二份**。
2. **导入是合并，不是覆盖。** 导入一份含重复词的列表，报告「新增 N / 跳过 M」。
3. **三层里只有用户层可写。** 内置词只读（`go:embed`），服务器词库只读（只由同步写）。
4. **热加载**：改完**下一次检测**即生效，无需发版、无需重启。

## 2 页面结构

### 2.1 两个列表

| 区块 | 内容 | 可写 |
| --- | --- | --- |
| 内置词（`builtin`） | `go:embed` 进二进制的词表 | **否**（只读展示，可折叠） |
| 我的词（`user`） | `data/sensitive-words.txt` 的内容 | **是**（增 / 删 / 改 / 导入） |

内置词默认**折叠**（`builtinOpen`）：出厂词表是用户需要"知道有什么"而不是"每天在看"的内容，默认展开会把用户自己的词挤到屏幕外。

**服务器词库（第三层）不在这个页面里** —— 它只读、且由同步流程维护，展示它会让用户以为能编辑。

### 2.2 计数与空态

- 计数：`{n} items`，每个区块各一份。
- 用户层为空：`No custom words yet`（**不是**空白区域）。
- 非空时显示「Changes take effect immediately」—— 热加载是用户最需要知道的一条，因为它决定了"我改完还要不要重启"。

## 3 文件与 API

### 3.1 文件是唯一真相

用户词的载体是 **`data/sensitive-words.txt`**（`datapath.Join`，**扁平落在数据根下**，与 `config.yml` / `mcp.json` 同级）。形态：UTF-8 文本，一行一词，`#` 开头为注释。

**规则.**

1. 页面**不得**在内存里保一份"最终词表"并在退出时写回 —— 那就是第二份真相，与用户手改文件冲突时无解。
2. 每次写操作**立刻**落到文件（`PUT`），不攒批。
3. 用户**直接手改文件**同样生效（热加载），页面下次打开读到新内容。这条是"文件即真相"的直接推论，也是它最重要的好处：批量导入一百个词时用户可以用编辑器而不是点一百次。

**为什么是扁平文件而不是数据根子目录：** 与 `config.yml` / `mcp.json` 同级，用户已经知道"数据根里的文件是可以自己改的"。放进子目录会让人以为那是程序内部文件。

### 3.2 端点契约（已落地，Go 侧待实现）

| 方法 | 路径 | 请求 | 响应 |
| --- | --- | --- | --- |
| `GET` | `/api/product/sensitive/dict` | — | `{ builtin: string[], user: string[] }` |
| `PUT` | `/api/product/sensitive/dict` | `{ user: string[] }` | `{ user: string[] }` |
| `POST` | `/api/product/sensitive/dict/import` | `{ words: string[], dryRun: bool }` | `{ added: number, skipped: number }` |

全部走产品门（`/api/product/*`，需窗口令牌）。**导出不占端点** —— 见 §5.2。

**响应回写规则：** `PUT` 返回的 `user` 是**服务端规范化后的词表**，页面用返回值刷新自己。不要乐观地用本地数组覆盖 —— 服务端会做去重与规范化，本地那份只是候选。

### 3.3 规范化与符号表（唯一实现要求）

`normalizeWord()` 的规则：Unicode 大小写折叠 + 去掉空白 + 去掉固定符号表。符号表**原文**为：

```
!"#$%&'()*+,-./:;<=>?@[\]^_`{|}~
！＂＃＄％＆＇（）＊＋，－．／：；＜＝＞？＠［＼］＾＿｀｛｜｝～
、。「」『』《》—…·
```

**刻意不用 `unicode.IsPunct`：** 它会删掉比产品契约允许的更多的字符（各类语言标点），结果是"看起来一样的词"被判成同一个 —— 误合并比漏合并更难发现。

**这份实现的作用域（关键）：** 前端这一份**只用于重复/空值预检**（`isUsableWord` / `containsWord`），**服务端在写入时权威再验一次**。原因：前端判据可被绕过，而词库是持久化数据，写进去的重复项会一直留在文件里。

**现状（`D6`，尚未满足）：** `STRIP_SYMBOLS` 是 Go 常量的**第二份定义**（注释自称"keep the two in lockstep"），而 Go 侧（`internal/sensitive/normalize.go`）**尚不存在**。§3.8 的要求是**一份类型、两个实现**或干脆一处实现 + 一致性断言。落地时的处置见 `P8` §3.5：Go 权威、前端降级为预检，并加"同一输入两边结论一致"的断言。

## 4 增 / 删 / 改

| 操作 | 规则 |
| --- | --- |
| 增 | 规范化后为空（纯符号/空白）→ 拒绝，提示 `invalid_word`；已存在 → 拒绝，提示 `duplicate_word` |
| 删 | 立即写盘（`persist`），不在本地留 tombstone |
| 改 | 就地把一行改成新词，同样过规范化与重复检查 |

**重复检查要同时查内置层与用户层**（`containsWord`）：内置层已有的词，用户层再加一遍是无效的（并集里它已经在），允许它只会让用户困惑"为什么我加的词不生效"。

## 5 导入与导出

### 5.1 导入是合并

**流程：**

1. 选文件 → 客户端 `parseDictText()` 解析（一行一词、跳 `#` 注释与空行）。
2. **`dryRun: true`** 先问服务端：`{ added, skipped }`。
3. 页面显示预览：`Will add {added} and skip {skipped} that already exist`。
4. 用户确认 → **`dryRun: false`** 真写入。

**为什么必须两步：** 导入是**合并**（`D7`），一份大词表里通常一半是重复的。直接写入的话用户唯一能看到的反馈是"文件变长了"，看不出加了哪些。dry-run 让"合并不是覆盖"这件事在界面上可见。

### 5.2 导出

**没有导出端点。** 客户端 `serializeDict()` 把用户词拼成文件格式（一行一词），然后：

| 环境 | 方式 |
| --- | --- |
| 桌面壳（`nativeShell`） | 系统保存对话框（`api.nativeSaveFile`） |
| 浏览器 | Blob + `a.download` |

**文件名固定 `sensitive-words.txt`** —— 与数据根里的实际文件名一致，所以"导出 → 编辑 → 导入"是一个自洽的往返，用户也可以直接把导出的文件放回数据根。

**为什么导出走客户端：** 导出的是**用户层**（服务器层与内置层不可写，导出它们没有意义），而这份数据已经在页面上；多加一个端点只会多一处可能与页面不同步的序列化实现。

## 6 验收

| # | 验收项 | 判据 |
| --- | --- | --- |
| 1 | 新增即刻生效 | 页面加一个词 → **下一次发送**即被拦（不发版、不重启） |
| 2 | 删除即刻生效 | 删一个词 → 下一次发送不再命中 |
| 3 | 内置层只读 | 内置词区无编辑/删除入口 |
| 4 | 重复被拒 | 加一个已存在的词（含大小写/符号变形）→ `duplicate_word` |
| 5 | 纯符号被拒 | 加 `"!!!"` → `invalid_word` |
| 6 | 手改文件生效 | 直接用编辑器改 `data/sensitive-words.txt` → 页面重开读到新内容 |
| 7 | 导入是合并且有预览 | 导入含重复词的列表 → 先报「新增 N / 跳过 M」，确认后才写入 |
| 8 | 导入往返自洽 | 导出 → 不改 → 再导入 → 报「新增 0 / 跳过 N」 |
| 9 | 导出文件名正确 | 导出文件名为 `sensitive-words.txt` |
| 10 | 服务器层不在此页 | 页面不展示服务器词库的编辑入口 |
| 11 | 无第二份真相 | 磁盘上的文件与页面显示一致（改文件后刷新页面即见） |
