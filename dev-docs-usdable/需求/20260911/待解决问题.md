### D-001 中台真实地址与验签公钥未内置（原 `PQ1`）

| 项 | 内容 |
| --- | --- |
| 状态 | **暂不解决**（等中台提供取值） |
| 对应需求 | `A1`（环境内置配置）、`C1`（内置网关端点）、`E1` |
| 重新评估 | 中台给出生产 `apiHost` / `gatewayHost` / `trustedKeyIDs` 与密钥轮换流程时 |

**为什么不解决**

要的就是三个由中台提供的外部值（生产地址两个 + 签名公钥若干），客户端自己做不了任何有意义的替代方案。在拿到之前，任何「先用一个默认地址」的写法都会把产品流量指向不确定的地方。

**当前兜底 —— 联调走 `developer` Profile**

这份配置机制本身就是为这件事准备的，不需要额外造东西：

| | `developer`（联调期用这个） | `production`（等中台给值） |
| --- | --- | --- |
| `apiHost` / `gatewayHost` | 可留空；地址从 `data/config.yml` 的一个 endpoint 配 | 编译期内置，必须非空且 `https` |
| `trustedKeyIDs` | 可空 | 必须至少一个 base64 ed25519 公钥 |
| 模型来源 | 允许 `config.yml` / 环境变量 | 只允许签名目录 + 网关 |
| 怎么构建 | 默认构建（不带 `product_production`） | 必须带 `product_production` |

所以**联调路径是**：不带标签构建 → 在 `data/config.yml` 配一个 `provider: custom`、`protocol: openai`、`base_url: <中台测试网关>` 的 endpoint → 直接联调。**不需要**等地址内置，也**不修改** `production.json` 里的 `.invalid` 占位。

**明确缺什么**

- `production` 包当前**无法启动控制面**：`Profile.ControlPlaneConfigured()` 为 `false` → 按设计**拒绝启动**（不是降级、不是回退 `localhost`）。这是有意的 fail-closed。
- 因此**不能**用 `production` 包做联调，也不能用它出正式包。
- 签名目录的**验签流程无法端到端验证**：`trustedKeyIDs` 为空时任何签名都验不过，等于没有目录。目录的验签代码可以单测，但走不通「拿真实信封验过」这条路。
- `release-config-guard` 会在出包时告警未替换的 `.invalid` 占位（只告警不阻断，内部测试包合法）。

**何时重新评估 / owner**

中台（基础设施）+ 发布负责人。拿到三个值后：填 `production.json` → 跑一次 `production` 构建 → 确认 `ControlPlaneConfigured()` 与 `HasTrustedKeys()` 都为 `true` → 删除本条登记。

**要的东西（照抄给中台即可）**

| 要什么 | 形态 | 备注 |
| --- | --- | --- |
| 生产 `apiHost` | `https://api.<域名>/v1` | 必须 `https` |
| 生产 `gatewayHost` | `https://gateway.<域名>/v1` | 可与 api 同域不同前缀 |
| `trustedKeyIDs` | `{"<keyId>": "<base64 32 字节 ed25519 公钥>"}` | 至少一个，建议两个（当前 + 下一把） |
| 密钥轮换流程 | 文档 | 必须「先并入新公钥 → 再切签名 → 最后撤旧公钥」，每步跨越一个客户端发版周期 |
| （可选）`GET /v1/meta` | 返回服务端当前有效 `keyId` 列表 | 出问题时能 5 秒确认「客户端内置的 keyId 是否已过期」 |
| 测试环境域名 | 与生产分开一套 | 防止测试包连生产 |

### D-002 `retract` 与账本终态在客户端无法接收（原 `PQ4`）

| 项 | 内容 |
| --- | --- |
| 状态 | **暂不解决**（先让内容流跑通） |
| 对应需求 | `C6`（流中安全终止）、`C7`（账本终态上屏）、`D8`（与服务端内容安全的边界） |
| 重新评估 | 中台确认 `retract` / 账本终态的**发送形态**时；或内容安全验收开始前（**不能晚于这个点**） |

**为什么不解决**

这件事本不该是问题 —— 我们**已经有两套**和大模型对接的协议适配器：`internal/provider/openai`（OpenAI `chat/completions`）与 `internal/provider/anthropic`（Anthropic Messages）。**但 `retract` 和账本终态不属于其中任何一种协议。**

**这是关键，值得说清**：问题不是「选哪个适配器」，而是——

| 事件 | OpenAI 协议有吗 | Anthropic 协议有吗 |
| --- | --- | --- |
| 正文流式增量 | 有（`choices[].delta.content`） | 有（`content_block_delta`） |
| 工具调用分片 | 有（`tool_calls[].index` 拼接） | 有（`input_json_delta`） |
| token 用量 | 有（`usage`） | 有（`message_delta.usage`） |
| **撤回已渲染的增量（`retract`）** | **没有** | **没有** |
| **账本终态（`settled` / `reversed` / …）** | **没有** | **没有** |

所以**换适配器不解决这件事**，两套都会把这两种事件丢掉。它们是中台网关**自己发明的产品事件**，必须约定一个载体，跟协议选型无关。

而且这次的丢法很隐蔽：交付包 §5.3 写的是 SSE「命名事件」形式

```text
event: retract
data: {"reason":"safety_blocked", ...}
```

而 `internal/provider/openai/stream.go:152` 是

```go
if !strings.HasPrefix(line, "data:") {
    continue
}
```

`event: retract` 这一行**被直接跳过**；下一行 `data: {...}` 里没有 `choices`，被当成空 chunk。**结果：撤回被静默忽略，用户看到未撤回的原文，且不报错。**

**当前兜底 —— 联调期只跑内容流**

**如果只是先和中台调试通过，这里零改动。** 协议选 OpenAI 兼容，用一个标准 `chat/completions` 请求（`model` = 目录 `id`），现成的 `internal/provider/openai` 端到端可用 —— **不新增任何字段、不发 `clientRequestId` / `toolPolicy`、不收 `retract` / 账本终态**，也不碰任何上游文件。

1. **协议选 OpenAI 兼容**，用 `internal/provider/openai` 直连网关。正文、工具调用、思考过程、usage 全部走现成实现，零新增解析代码。
2. **联调期的验收范围**只包含上表前三行（内容 / 工具 / usage）。`retract` 与账本终态**不在联调验收内**。
3. **必须加一条廉价的安全网（不能省）**：解析到一个「既不是已知标准字段、也不是 `[DONE]`」的顶层字段时，**报错或至少打一条 error 级日志**，不得静默 `continue`。理由：这样网关一旦真的发了 `retract`，我们会**立刻看见**，而不是安静地漏掉。约 5 行代码，但它是「静默失效」与「明确失败」的分界线（开发规范 §3.9）。
4. 联调前给中台一句请求：**调试期请不要发 `retract` / 账本终态事件**；如果发了，我们按第 3 条报错。

**明确缺什么（这段要原样带进验收）**

- **「流中安全终止」在客户端不可用。** 网关如果判定某段回复违禁并撤回，客户端**不会**移除已上屏的内容，也**不会**丢弃未执行的 streaming tool call。→ 需求 `C6` 全部未交付。
- **余额与用量不会实时更新。** 账本终态收不到，所以「只有 `settled` 才更新余额」这条链路不通；`C7` 的实时部分未交付。**兜底**：余额走 `GET /v1/credits/ledger` 主动查询（拉模式），或联调期不显示实时余额。
- **`D8`（客户端敏感词与服务端内容安全的边界）只有客户端那一层**：客户端打码有效，服务端撤回无效。两层合并不完整。
- 因此**内容安全不能作为本次联调的验收项**。这一条是安全功能，**重新评估的最晚时点是内容安全验收开始前**，不能拖到上线。

**正确的解法（等重评估时按它谈）**

保留交付包 §5.3 的**全部语义**，只把「事件名」从 `event:` 那一行挪进 `data:` 的 JSON，从而复用现成解析循环（约 20 行）：

```text
data: {"retract":{"reason":"safety_blocked","scope":{"fromDeltaIndex":7},"replacement":"该回复已被安全策略终止。"}}
data: {"usage":{"ledgerId":"led_123","state":"settled","usage":{...},"chargeMicroCredits":21800,"balanceMicroCredits":2478200}}
data: {"error":{"code":"safety_blocked","requestId":"gw_123","state":"reversed"}}
data: [DONE]
```

替代方案是另写第二个 SSE 解析器（约 200 行 + 独立测试），并会让 `reuse-guard` 失败（它明确禁止在 `internal/productclient/gateway` 出现 `bufio` / `[DONE]` / wire-format 字段）。**不建议。**

**owner**

中台（定发送形态）+ 客户端（实现接收）。**回归触发点：内容安全验收开始前。**

### D-003 请求体未携带 `clientRequestId` / `toolPolicy`，且模型标识语义未固化（原 `PQ2` + `PQ3`）

| 项 | 内容 |
| --- | --- |
| 状态 | **暂不解决**（联调期先不发这两个字段） |
| 对应需求 | `C5`（网关扩展字段的载体） |
| 重新评估 | 联调打通内容流之后、**上线前必须补**；不晚于「工具权限」与「计费 / 审计」验收开始前 |

**为什么不解决**

联调期的目标是先把**内容流**跑通，而最小路径是**零改动**：请求就是一个标准 OpenAI `chat/completions`（`model` = 目录 `id`），现成 `internal/provider/openai` 端到端可用，一个上游文件都不用碰。代价只是「暂不带这两个字段」，不影响正文、工具调用、思考过程、usage。

**当前兜底**

| | 联调期做法 | 为什么不能走别的路 |
| --- | --- | --- |
| 模型标识 | 用 `"model": "<目录 id>"` | `provider/openai` 的请求结构体里只有 `Model`（`stream.go:52`）。改名或新增 `modelId` 都要动上游文件 |
| `clientRequestId` | **不发** | 每个调用都不同，而 `Client.Headers` 是**构造期一次性设置的静态 map**（`client.go:123`），承载不了按请求变化的值 |
| `toolPolicy` | **不发** | 它是结构化对象（`{version, allowedToolIds[]}`），塞 header 要自造序列化，且长度受限 |

**明确缺什么**

- **没有 `clientRequestId` ⇒ 缺幂等键与追溯键。** 网关侧的重复计费防护、`GET /v1/ai/requests/{clientRequestId}` 这个对账入口都无从使用；一次超时重试可能被计费两次（除非网关另有去重手段）。
- **没有 `toolPolicy` ⇒ 工具白名单未下发。** 「按模型 / 按权限限制可用工具」这条需求**未交付**，网关只能用它的默认策略。这是**权限控制**，属安全面，不能长期缺位。
- **`model` 字段语义未固化。** 目录 `id`（`buding-cloud-pro`）与供应商模型名（`deepseek-chat`）共用同一个字段名，存在「网关把目录 id 当供应商模型名透传下去」的错，且很难查。**注**：模型 `id` 取值本身**一律英文 ASCII**（已拍板 2026-09-11，见 `B6`），这里的问题是**字段名**而非取值。

**上线前要问中台的（一次问清即可）**

1. 请求体里模型标识叫什么 —— 继续用 `model`（语义明确为「目录 id」）、还是新增 `modelId`？
2. `clientRequestId` 与 `toolPolicy` 放**请求体**行不行？（推荐请求体；`Idempotency-Key` 头可做可选冗余，但请求体是唯一权威）

**正确的解法**

按 [D-002](#d-002-retract-与账本终态在客户端无法接收原-pq4) 的同一处改动一并落地：给 `apiRequest` / `streamChunk` 加透传字段，打 `// OCTO-FORK:` 标记，一次改完、一次回归。

**owner**

中台（定字段名与位置）+ 客户端（实现）。

### D-004 凭证随 `data/` 可复制之后的防拷贝与泄露止损（新，2026-09-11）

| 项 | 内容 |
| --- | --- |
| 来源 | `PQ17` 拍板的**直接后果**（[`待确认问题清单.md`](待确认问题清单.md) `PQ17`、[`需求基线.md`](需求基线.md) §5.2.1） |
| 状态 | **暂不解决**（用户 2026-09-11 明确：「复制之后的安全性后面再考虑」） |
| 对应需求 | `E6` 规则 3 / 6、`E12`（设备会话与撤销） |
| 重新评估 | 上线前**至少**完成下面「本期必须做的」两条；「防拷贝」本身可更晚 |

**已拍板的前提（不在本条目讨论范围内）**

refresh token **明文存 `data/credential.json`，随 `data/` 一起复制**。这是为了保住便携 U 盘版「插上就能用」的核心体验，且**明确禁止**用机器相关密钥加密来防拷贝（那会重新引入硬件标识，违反 `E1` 规则 5）。详见 `E6` 规则 1/3/4。

**为什么不解决**

「防拷贝」要在「用户能随便换机器用」和「U 盘被复制后不能被盗用」之间做取舍，两者本质冲突；本期先保证前者。且真正的防护需要在**中台侧**做（设备绑定、异常登录风控、并发会话检测），属于中台工作包，不是客户端能单独完成的。

**本期必须做的（不算「不解决」的部分，是安全底线）**

| # | 要求 | 落在哪 |
| --- | --- | --- |
| 1 | 中台必须能**撤销单个 refresh token**（而非只能撤销整个账号） | 客服后台 + `DELETE /v1/account/sessions/{sessionId}`（合同 §4.2.4） |
| 2 | 客户端收到 401/403 后**清 `data/credential.json` 并回拦截页**，不静默继续、不无限重试 | `C2` 规则 5、`E12` 验收 |

这两条已写进 `E6` 规则 6 与 `E12`；它们**不因为本条目「暂不解决」而降级**。

**明确缺什么（暂不做的部分）**

- **U 盘被偷偷复制后，没有任何提前止损手段。** 原持有人与原副本都能用，直到有人调用客服撤销。
- **没有「设备/介质指纹」**，中台无法区分「同一份 `data/` 在两台机器上同时使用」。
- **没有并发会话检测**：同一 refresh token 从两地并发刷新，客户端只能按「单飞刷新」处理单机的并发，跨机器无感知。
- **帮助页只写一句「丢失程序目录等同账号泄露」**，没有面向用户的完整泄露处置说明（改手机号、撤销、换绑都需要客服，而客服通道本身还挂在 `PQ9` 上）。

**重新评估时要回答的**

1. 要不要在中台加**登录异常检测**（同一 token 短时间内跨 IP / 跨设备）？触发后是告警、强制重新登录、还是冻结？
2. 要不要给凭证文件加一个**与账号绑定的可轮换密钥**（加密密钥由中台下发、不依赖硬件）？—— 这条不违反「不读硬件标识」，但会引入新的启动依赖，需要单独评估。
3. 用户说明书里怎么写这段取舍（`E6` 规则 3 只要求「写一句」）？

**owner**

产品（取舍）+ 安全（防护方案）+ 中台（撤销与风控能力）。

### D-005 WebSocket 握手的窗口令牌校验未做（新，2026-09-11）

**是什么。** `L-B1b` 的请求门本轮只落在本 fork 经 `MountAPI` 缝注册的产品路由（`/api/product/*`）。`/ws` 的握手**前端已经把 `?window_token=` 带上**（`web/src/lib/product.ts:23`；浏览器 WebSocket API 不能自定义 header，所以只能走 query），但**后端不校验** —— 那个参数目前是装饰性的。

**为什么不一起做（人工决定，2026-09-11）。** 本轮先把 HTTP 请求门走通；WS 是另一条通道 —— `internal/server/auth.go:78` 已经为 `/ws` 单独开了 `?access_key=` 的口子，说明它有独立的鉴权路径，一起改会让本次改动同时触及两处鉴权语义。门也因此**改成注册器的属性**（`productAPI` vs `api`，见 `D-006` 与 `开发计划.md` §4.1 第 12 行）：WS 经 `s.api` 注册，被**结构性**排除，日后给 WS 加门必须显式改走带门注册器，不会被静默继承。

**不做会怎样。** 一个非本窗口的 loopback 进程若直接连 `/ws`，仍能收到产品事件推送（`credits_update` / `input_sensitive` / `datastore:lost` / `datastore:restored`）。注意：`/ws` 仍受 `requireAuth` 与 loopback 豁免约束，所以这不是"无鉴权"，而是"**没有窗口身份**"。

**何时必须做（写死）。** `L-F1`（产品事件）开工时，或任何"产品事件必须只到本窗口"的验收开始 —— 那条验收的前提就是 WS 侧有身份校验。

**owner**

客户端（`internal/server` 的 `/ws` 注册点 + 令牌在 query 上的传递）。

### D-006 窗口门不覆盖上游 `/api` 路由（新，2026-09-11）

**是什么。** `L-B1b` 的窗口门只覆盖本 fork 的产品路由（`/api/product/*`，经 `MountAPI` 缝注册的 5 条）。`P3` §5.4.3 要求「未登录时窗口发起的请求同样不可用」，但上游的 `/api/chat`、`/api/sessions` 等在桌面壳里**不以窗口身份为条件** —— 它们仍按上游信任模型（`requireAuth` + loopback 豁免 + access key）放行。

**为什么本轮不覆盖（人工决定，2026-09-11）。** 曾把门定为"全部 `/api/*`"，**实测后推翻**：门是请求头校验，浏览器给裸 `<img src="/api/…">` 子资源加不了 header —— 宽门把聊天图片缩略图（`GET /api/uploads/{name}`，`ChatView.svelte:2761`）与 artifact 图片（`GET /api/sessions/{id}/artifacts`）打成 `403 product_gate`；又因桌面壳 `hubAddr` 与 CLI `localServe()` 探测的默认地址同为 `127.0.0.1:8088`（`cmd/octo-desktop/main.go:62` / `cmd/octo/climessenger.go:69`），宽门还会打死 `octo` CLI 的 `send_message`。证据与取舍见 `开发计划.md` §4.1 第 12 行。

**不做会怎样。** 本机上一个非窗口的 loopback 进程（或另一个标签页）在桌面壳运行期间仍可调用上游 agent 接口。注意这不是"无鉴权"（`requireAuth` 与 access key 仍在），而是"**没有产品身份的约束**"：它不会因产品未激活/未登录而被拒。

**何时必须做（写死）。** 产品门要真正成为"界面门"（而非仅"窗口身份门"）时 —— 即任何"未激活产品不得驱动 agent"的验收开始。

**正确做法（写死，避免重走弯路）。** 服务端持有会话/激活态并在上游路由上校验，单一事实源是 `internal/productstate`；**不要**把窗口令牌铺到全部 `/api/*` —— 那个失败模式本轮已实测。

**owner**

客户端（`internal/server` 的注册器 + `internal/productruntime` 的激活态校验）。

### D-007 策略签名未用 JCS 规范化（新，2026-09-11）

**是什么。** 策略信封的签名（`data.policySignature`）**签的是 `data.policy` 值的原始 JSON 字节**，不是 RFC 8785（JCS）规范化后的字节。验签方对**收到的原始字节**验签，不做任何规范化。

**为什么不现在做（人工决定，2026-09-11：「先简单的实现……别搞太复杂；正规的做法写到待解决问题里面；目前先走通流程」）。** 两条路能达到同一安全目标，选了简单的一条。JCS 路线的**真实代价**不是代码量，而是**两份实现会漂移**：签名方（中台）与验签方（客户端）各自实现 RFC 8785，其中最危险的是**数字规范化**（要求 ECMAScript `Number::toString` 的最短往返表示），而 `policy` 里有 `ttlSec: 3600` 这类数字 ⇒ 躲不掉。漂移的表现是**最难查的一类故障**：「替身测试全绿、生产验签失败」——因为替身与客户端很可能共用同一份（错的）实现，两边一起错就互相印证。

**不做会怎样。** 与 JCS 相比，唯一失去的是**对"会重新序列化 JSON 的中间人"的鲁棒性**：任何代理若重排/重格式化 JSON，原始字节就变了，验签失败（fail-closed，**不会**误放行 —— 安全性不降级，只降可用性）。本产品客户端**直连中台**、无中间人，故当前无实际影响。

**何时必须做（写死）。** 在**任何中间人**进入链路之前 —— 反向代理、CDN、API 网关重写、或中台侧任何会重编码 JSON 的组件。届时"验签偶发失败"会成为线上问题，而它的根因（字节被重排）在现场几乎不可见。

**正确做法（写死，避免重走弯路）。** ① **`signature` 必须留在 `policy` 之外**（现为同级 `policySignature`）—— 放进 `policy` 内会迫使验签方"反序列化 → 删字段 → 重新序列化"，那正是规范化分歧的入口；② 换的只是"被签名的字节"：从原始字节改为 `JCS(policy)`，**信封形状不变**；③ JCS 实现**只写一份**，由签名方与验签方共用（`开发计划.md` §3.3 已写死此约束）；④ 必须用 RFC 8785 的**官方测试向量**验证数字规范化，不得只用自己的往返测试 —— 自测通过只证明"自己与自己一致"。

**owner**

客户端 + 中台（`internal/productclient` 的 signing 实现与 `中台交付包` §4.3 的信封定义）。
