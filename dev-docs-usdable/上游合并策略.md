## 1. 现状（必须先修的三件事）

### 1.1 仓库里没有 upstream remote

```
$ git remote -v
origin  git@…:USDAble/buding-box-client.git (fetch)
origin  git@…:USDAble/buding-box-client.git (push)
```

只有 `origin`。**没有任何指向上游 `open-octo/octo-agent` 的引用**，因此：

- 不知道当前 fork 从上游哪个 commit 分出来的；
- 不知道已经落后多少；
- 没有任何机制能发现上游修了我们也有的 bug。

Go module 路径仍是 `github.com/open-octo/octo-agent`（`go.mod`），说明这是一次直接 clone，不是 GitHub fork 关系。

**行动项 A（开工前完成）**

```bash
git remote add upstream https://github.com/open-octo/octo-agent.git
git fetch upstream --tags
# 找到分叉点并记录下来
git merge-base HEAD upstream/main
```

把 merge-base 的 commit 与日期写进本文档 §6「合并日志」的第一行。这是后续所有合并的基准点，没有它就无从谈起。

### 1.2 没有约定合并方式

**行动项 B**：本文档 §3 给出方式，评审通过后写进 `.octorules` 与 `CLAUDE.md`。

### 1.3 品牌改造已经污染了大量上游文件

`feat/brand-config-layer` 分支已把品牌配置层铺进 `i18n.ts`、`lang.go`、打包脚本、Inno Setup 等处。这些改动本身是对的，但意味着**上游合并的冲突面已经不小**，而 P1（数据根）会把它扩大到 50+ 个文件。

## 2. 一条判断原则

需求写得很清楚：**功能必须的，就不为上游兼容让步。**

但「功能必须」不等于「怎么实现都行」。同一个功能通常有多种实现方式，它们对上游合并的成本差几十倍：

| 做法 | 合并成本 |
|---|---|
| 在 50 个上游文件里各改一行 | 每次合并 50 个冲突点 |
| 加一个收口层，50 个文件机械替换成对它的调用 | 冲突仍在，但**解法是「取上游版 + 重跑替换」**，几分钟 |
| 删掉上游的某个文件 | 上游改动该文件时产生「删除 vs 修改」冲突，git 无法自动解 |
| 保留上游文件，只是让它到不了 | 零冲突 |

所以规则是：**功能不妥协，实现方式尽量选合并成本低的那一种。** 本期的两个具体体现：

- P1 用 `internal/datapath` 收口，而不是逐处改（技术方案 P1 §3.1）。
- P6 用开关隐藏 IM/MCP/Light Apps，而不是删代码 —— 这也正好是需求 §7 的要求，两者一致。

## 3. 合并方式

### 3.1 分支模型

```
upstream/main ──────●───────●───────●──────▶   上游，只读
                     \       \       \
                      ▼       ▼       ▼
main          ──●──●──◆───●───◆───●───◆──▶     我们的主干
                        ↑           ↑
                   merge 上游    merge 上游
                        
feat/xxx      ────────●──●──●──▶ PR → squash → main
```

- **上游 → 我们：用 `merge`，不用 rebase。** rebase 会重写我们已发布的历史，且 50 个文件的冲突要在每个 commit 上重解一遍。merge 只解一次。
- **我们的功能分支 → main：用 squash。** 保持主干线性可读（沿用 `.octorules` 既有约定）。
- 上游合并单独成 PR，标题固定格式 `chore(upstream): merge upstream/main @ <short-sha>`，**不夹带任何功能改动**。

### 3.2 合并节奏

| 时机 | 动作 |
|---|---|
| 每两周 | 例行 `git fetch upstream` + 查看 diff 规模，决定是否合并 |
| 每个里程碑结束后 | 必须合并一次，趁功能刚验收完、上下文还热 |
| 上游发安全修复 | 立即合并 |
| 里程碑进行中 | **不合并**，避免功能开发与合并冲突叠加 |

不要攒到半年一合 —— 冲突量随时间超线性增长。

### 3.3 合并流程

```bash
git fetch upstream
git switch -c chore/upstream-$(date +%Y%m%d) main
git merge upstream/main            # 解冲突
make fmt-check && make vet && make test
make brand-check                   # 品牌产物一致性
node scripts/datapath-guard.mjs     # P1 的数据根守卫
make desktop-portable              # P12 的产物自检
```

**四道 CI guard 是合并质量的主要保障**，它们各自守住一类最容易在合并中被悄悄破坏的东西：

| Guard | 守住什么 | 引入 |
|---|---|---|
| `brand-guard` | 上游带回写死的 Octo 品牌字面量 | 已有 |
| `datapath-guard` | 上游带回 `~/.octo` 写入。对字面量 `".octo"` **零例外** —— 产品里已经没有这条路径了（含 CLI），出现即回潮 | P1 |
| `portable-check` | 产物形态与文件属性回退 | P12 |
| Sender 能力断言测试 | 装饰器因接口变化静默降级 | P8 |

`datapath-guard` 之所以能做到零例外，是因为评审决定把 `~/.octo` 从代码里彻底删掉（含 CLI），而不是「桌面走 data/、CLI 走 ~/.octo」的双模式。双模式必须给 guard 开例外，例外一开，上游合并带回的新写入点就能从这个口子溜进来 —— 这正是当初选单一数据根的主要理由。见 `需求/2260906/技术方案/P1-便携数据根.md` §1。

第四条不是脚本而是测试，但作用相同：合并后 CI 红，就知道哪里被破坏了。

### 3.4 冲突解法速查

| 冲突类型 | 解法 |
|---|---|
| 机械替换类（P1 的路径调用点） | **取上游版本，重跑替换**。不要逐行手工合 |
| 我们新增的整块（`AccountCorner`、`ModeMenu`） | 取我们的版本，然后确认上游那块有没有新功能需要一起带 |
| `i18n.ts` 文案 | 两边各自加行，取双方。我们的键统一 `product.*` 前缀且集中在文件尾部（见 §4.2） |
| 上游重构了我们包装的函数 | 重新包一次装饰器，跑能力断言测试 |
| 上游删了我们改过的文件 | 停下来问清楚：这个功能上游是废弃了还是搬走了 |

## 4. 降低未来冲突的编码约定

这几条是本期新代码必须遵守的，目的只有一个：让下一次合并便宜。

### 4.1 新代码尽量放新文件

新增包、新增组件优先。碰上游文件时，把逻辑抽到新文件，上游文件里只留一行调用。

本期的实例：

| PR | 上游文件里只留 | 逻辑在 |
|---|---|---|
| P2 | `if f := checkX(); f != nil { fatal(f) }` | `bootstrap.go` |
| P5 | `<AccountCorner />` + `<AccountPanel />` | `AccountCorner.svelte` / `AccountPanel.svelte` |
| P6 | `visibleNav(topNav)` | `features.ts` |
| P8 | `WrapSensitive(...)` | `sensitive_sender.go` |
| P9 | `<ModeMenu />` | `ModeMenu.svelte` |
| P10 | `WrapPII(...)` | `pii_sender.go` |
| P13 | —（全部新文件） | `SensitiveDictPage.svelte` |

### 4.2 追加统一放文件尾部

`i18n.ts`、`stores.ts` 这类上游高频改动的「清单型」文件，我们的新增项**集中放文件末尾的独立区块**，用注释分隔：

```ts
// ─── OCTO-FORK: 布丁盒子产品层文案 ────────────────────────────
// 本区块以下全部是下游新增，上游没有对应项。
// 合并冲突时：保留双方，本区块整体挪到文件末尾。
"product.login.title": "…",
```

冲突就永远发生在文件尾部，而不是中间某一行。

### 4.3 所有下游改动打标记

改上游文件时，改动处加一行：

```go
// OCTO-FORK: <一句话为什么> —— see dev-docs-usdable/需求/2260906/技术方案/P8-敏感词接入.md
```

作用有三个：合并时一眼看出哪些是我们的；`grep -rn "OCTO-FORK" ` 就是完整的改动清单；新人 review 时知道这行不是上游的。

### 4.4 不删上游代码

需要「去掉」某个功能时，优先「让它到不了」而不是删。本期 IM/MCP/Light Apps（P6）、`FirstRunSetup.svelte`（P9）、自启动与自动更新（P2）全部按此处理 —— 这也正好是需求 §7 的要求。

### 4.5 不改上游的函数签名

`config.Path()`、`serveproc.PidPath()` 这类被广泛调用的函数，**只换实现不换签名**。这样上游新增的调用点合并进来就自动正确。

## 5. 什么时候可以不管上游

需求的功能要求与上游兼容冲突时，功能优先。已知的几处：

| 冲突点 | 决定 |
|---|---|
| 数据根从 `~/.octo` 改到 `data/`，且**连 CLI 一起改** | 功能必须（需求 §2.1 硬约束）。承担 P1 的高合并成本。CLI 一起改是为了让 guard 能零例外 —— 这一条是主动扩大了改动面来换取长期的守护强度，属于「实现方式的选择」而非需求要求 |
| 关掉自动更新与开机自启动 | 功能必须（需求 §5.1.2）。但用运行期开关不用删代码 |
| 输出敏感词过滤插进流式链路 | 功能必须（需求 §5.5.2）。用装饰器把成本压到最低 |
| 单实例 ID 改为 `app.puddingbox.desktop` | 功能必须（需求 §5.2.4）。已落地，一行配置 |

这些地方**不要**为了少冲突而做妥协实现。但每一处都要在技术方案里写明缓解手段 —— 「功能必须」不是放弃工程判断的理由。
