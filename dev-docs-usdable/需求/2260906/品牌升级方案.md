## 0. 一句话方案

**一个来源（`branding/brand.json` + 三个源图），两条管线（文案键插值 / 资产派生），一条命令（`make brand`），CI 全程守卫漂移。**

三条不可动摇的原则：

1. **唯一来源。** 换名字只改 `brand.json`，换 Logo 只换那三个源图，两件事都不需要动代码（§3.4 有量化演练）。
2. **路径与标识符一律英文 ASCII，永不多语言。** 只有「给人读的句子」才有中英两套值；路径、文件名、命令、协议名、端口、bundle id 全是单一 ASCII 字符串，界面上原样展示、不翻译（§2.5，CI 强制）。
3. **文案用模板变量插值，不做运行时全局替换。** 品牌名在词条里是 `{brand}`，不是被擦掉的 `Octo`（§4）。

界面上不出现 Octo 与章鱼标；`octo` 命令、Go 模块路径等兼容标识本期一律不动（`~/.octo` 作为**数据根**已按需求 §5.7 删除，见 §2.4 注）。

## 2. 已定值（不再讨论）

### 2.1 名称与文案

| 用途 | 中文（zh-CN） | 英文（en-US） | 用在 |
|---|---|---|---|
| 全称 | 布丁盒子 | Pudding Box | 窗口标题、关于页、拦截页主标题、欢迎页、版权行、导出标题 |
| 简称 | 布丁盒子 | **Pudding** | 任务栏过长、托盘提示与菜单动词、通知标题 |
| 口号 | 让本地工具、任务与智能代理，在一个工作台里协作。 | One workspace for local tools, tasks, and agents. | 拦截页副文案、关于页、落地页 |

| 版权行 | © {年} 布丁盒子工作室 | © {year} Pudding Box Studio | 关于页页脚、VERSIONINFO LegalCopyright |
| 用户协议标题 | 布丁盒子用户协议 | Pudding Box Terms of Use | 拦截页页脚、关于页 |
| 隐私政策标题 | 布丁盒子隐私政策 | Pudding Box Privacy Policy | 同上 |

中文简称与全称同值（四个字不会被裁切）；英文托盘/通知一律用 `Pudding` 以免任务栏与通知栏截断。

**语言覆盖：** 本期只保证 `zh-CN` 与 `en-US` 两套值齐全。`zh-TW` **不填中文值**，按需求 T10 落到英文分支；其它语言键本期不预填（填了就是承诺，而没人校对）。

### 2.2 系统标识符

| 项 | 值 | 说明 |
|---|---|---|
| exe 文件名 | `PuddingBox.exe` | 便携交付与安装器内均用此名 |
| CLI 可执行文件名 | `octo.exe` | **不改**，需求 §5.2.5 |
| 便携目录文件夹名 | `PuddingBox` | 纯 ASCII 无空格（C 类，§2.5）。用户看见的中文名靠窗口标题，不靠目录名 |
| 单实例 ID | `app.puddingbox.desktop` | **必改**，替换 `dev.octo-agent.desktop`（`cmd/octo-desktop/main.go`）。这是运行期锁名，改了正好达到「不与本机已装 Octo 抢窗口」的目的 |
| Windows VERSIONINFO InternalName | `pudding-box-desktop` | |
| Windows VERSIONINFO OriginalFilename | `PuddingBox.exe` | 必须与实际交付文件名一致，否则 Windows 属性页自相矛盾 |
| Windows 文件属性 产品名称 | `Pudding Box` | **固定单值，不随 UI 语言**，见 §2.2.1 |
| Windows 文件属性 文件说明 | `布丁盒子` | **固定单值，不随 UI 语言** |

#### 2.2.1 为什么文件属性只写一套

需求 §5.2「例外」条明确把 exe 文件名、文件夹名、文件属性列为不可随 UI 热切的系统字段，按固定 合同测试 处理。因此 VERSIONINFO **只写一个 translation block**（`LangDefault`），值为上表的固定值。

不要像 dev-zxy 那样写 en-US + zh-CN 两个 block —— 那会让中文 Windows 的属性页显示中文产品名、英文 Windows 显示英文产品名，恰好与「固定」相反，而且验收表逐字对不上。

### 2.3 视觉

| 项 | 值 |
|---|---|
| 标志图形 | 由设计提供的**主图源**（单张高分辨率彩色 PNG 即可起步；纯黑剪影 `logo-mono`、社交卡片 `og-card` 为可选增强），见 §5.1 与[交付说明](./品牌资产交付说明.md)。托盘剪影在无 `logo-mono.png` 时由主图 alpha 自动派生（§5.6）。研发不再自拟图形 |
| 主色 | 设计定稿时给出十六进制值，同时填入 PNG 实际色与 `brand.visual.colors.primary`，两处由 CI 保证不漂移 |
| 图形风格约束 | 不含章鱼元素；16px 下可辨；不依赖 logo 内嵌文字传达产品名；四边留 8–10% 安全边距 |

### 2.4 保持不变的兼容标识（动了会破坏已装版本）

| 标识 | 当前值 | 为什么不改 |
|---|---|---|
| Go 模块路径 | `github.com/open-octo/octo-agent` | 内部路径，用户不可见 |
| CLI 命令 | `octo` / `octo serve` | 需求 §5.2.5 |
| 配置目录 | `~/.octo` | **品牌层面不重命名**；但作为数据根已按需求 §5.7 删除（移到 `data/`），`brand.json` 里的 `configDir` 字段见本表下方注 |
| 环境变量前缀 | `OCTO_` | 品牌层面不重命名；`OCTO_DATA_ROOT` 仍作为数据根的**显式覆盖**手段保留（需求 §9.14），不与 `~/.octo` 一起删除 |
| protocol | `octo-ui` / `octo-pair` | 已发出的配对链接要继续可用 |
| Inno Setup `AppId` | `{{8F2A6B1C-…}}` | 改了会让新安装器不认旧安装，变成并存两份 |
| macOS `CFBundleIdentifier` | `dev.octo-agent.desktop` | 改了会丢失通知授权、登录项、钥匙串条目 |
| Capacitor `appId` | `dev.octo.mobile` | 改了等于换 App，商店链路与已安装用户全断 |
| 安装目录 | `%LOCALAPPDATA%\Programs\octo` | 与 AppId 同理 |

这些写入 `brand.json` 的 `identifiers.current`（当前值）与 `identifiers.future`（正式发布时的目标值），把「现在不动」和「以后要动」显式记账，避免下一个人以为是漏改。

> **`~/.octo` 的例外（2026-09-07 与数据根决策对齐）**：需求 §2.1 已定「代码里彻底删除 `~/.octo` 这条路径，CLI 也一并改」，数据根统一为 `data/`（见 `技术方案/P1-便携数据根.md` §3.2）。因此 `~/.octo` **不再作为配置目录存在**——本表与 §2.5.3 里把它列为「兼容标识」只表达「品牌上不把它重命名为 `~/.puddingbox`」，不等于它仍被使用。`brand.json` 的 `identifiers.current.configDir` 与 `identifiers.future.configDir` 这两项是纯记账、**不被任何数据路径代码消费**（数据路径统一走 `internal/datapath`），是否删除或改指向 `data/` 留待 P1 落地时一并处理，不影响本方案其余结论。

### 2.5 值的三类：什么能有多语言，什么绝对不能

这是本方案的一条结构性约束。一个值属于哪一类，决定它在 `brand.json` 里长什么样、能不能进 `copy` 段、CI 用哪条规则校验它。**分类先定，再谈实现。**

| 类 | 定义 | 在 `brand.json` 里的形态 | 举例 |
|---|---|---|---|
| **A 本地化文案** | 用户读的句子与名称，随界面语言实时切换 | 多语言 map `{"zh-CN": …, "en-US": …}` | 全称、简称、口号、版权方、版权行、协议标题、全部界面文案 |
| **B 固定显示值** | 用户能看见，但由操作系统渲染、不随界面语言热切 | **单个字符串** | Windows 文件属性的产品名称与文件说明 |
| **C 标识符与路径** | 机器读的，不是给人看的 | **单个字符串，且必须是无空格的 ASCII** | 路径、文件名、目录名、单实例 ID、bundle id、协议名、环境变量前缀、端口、配置键名、模型 id、资产文件名、URL |

#### 2.5.1 C 类硬规则（不接受例外）

1. **一律英文 ASCII，永不本地化。** 不做多语言 map，不随界面语言变，不存在中文版本。
2. 不含中文字符、不含空格、不含全角标点。
3. 大小写只用两种约定：**用户可见的可执行文件与交付目录用 PascalCase**（`PuddingBox.exe`、`PuddingBox`，随 Windows 习惯）；**仓库内资产与配置文件用小写 kebab-case**（`logo-mark.svg`、`tray-icon-template.png`、`brand.json`）。同一目录内不得只靠大小写区分两个文件 —— Windows 不区分大小写、Linux 区分，那是跨平台事故。
4. 它出现在界面上时，是**被展示的字面量**，不是可翻译文案。设置里的默认工作区中英文界面都显示 `data/workspace/` 这五个字符，不翻译成「数据/工作区」，也不插值。

#### 2.5.2 为什么要单独立这条

dev-zxy 用运行时 `replaceAll('Octo', 品牌名)` 处理文案，把 `settings.workspace_dir_desc` 里的 `~/Octo` 一起换了：英文界面变成 `~/Pudding Box`，中文界面变成 `~/布丁盒子`。一个带空格的无效路径，一个带中文的无效路径，两个都不存在。

根因不是替换逻辑写错，而是**没有把「路径」和「文案」当成两类不同的值来管**。只要这两类值混在一个池子里，任何全局处理手段都会误伤，换成插值也只是把事故概率降低而不是消除。所以要在 schema 层面把它们分开，并让 CI 结构性地拦住。

#### 2.5.3 C 类清单（本期）

| 值 | 说明 |
|---|---|
| `data/`、`data/workspace/`、`data/tmp` | 便携数据根与会话工作区。界面原样展示，不翻译 |
| `OCTO_`、`octo`、`octo serve`、`octo-ui`、`octo-pair` | 上游兼容标识，本期不改 |
| `~/.octo` | 数据根已按需求 §5.7 删除，见 §2.4 注；不再作为配置目录 |
| `PuddingBox.exe`、`PuddingBox`、`octo.exe` | 交付文件与目录名 |
| `app.puddingbox.desktop` | 单实例 ID |
| `dev.octo-agent.desktop`、`dev.octo.mobile`、Inno `AppId` | bundle id 类，本期不改 |
| `pudding-box-desktop` | VERSIONINFO InternalName |
| `%LOCALAPPDATA%\Programs\octo` | 安装目录 |
| `8088` | 固定端口 |
| `buding-local-general` 等模型 id | 需求 §5.6.3：**id 固定，展示名随语言**（展示名是 A 类） |
| `branding/` 下全部资产文件名 | kebab-case |
| i18n 键名、配置键名、JSON 字段名 | 永不本地化 |
| `links` 下全部 URL 与路由 | 含应用内路由 `/legal/terms` |

**一个容易误判的例子：** B 类的「Windows 文件说明 = `布丁盒子`」是中文，但它既不是路径也不是标识符，而是给人看的固定显示值，所以允许是中文 —— 不违反本节规则。判断标准是「谁来读」，不是「是不是中文」。

#### 2.5.4 CI 结构性强制

`brand-guard` 里加三条 schema 校验，让错误分类在提交阶段就过不去，而不是靠评审看出来：

| 规则 | 校验什么 |
|---|---|
| A 类必须是 locale map | `product.names` / `product.shortName` / `product.tagline` / `about.teamName` / `about.copyright` / `copy.*` 的每个叶子必须是 object，且**同时含 `zh-CN` 与 `en-US` 且两者非空** |
| B 类必须是单字符串 | `display.*` 下的叶子必须是 string，不能是 object（防止有人给文件属性加多语言） |
| C 类必须是无空格 ASCII | `identifiers.*` 与 `links.*` 下的叶子必须是 string 且匹配 `^[\x21-\x7E]+$`（可打印 ASCII、无空格）。这一条同时挡住「给路径加中文」和「给路径加多语言 map」 |

## 3. 架构：一个来源，两类消费

### 3.1 文件职责

```
branding/
  brand.json              ← 唯一 source of truth（文本值）。人工编辑只改这里
  source/                 ← 唯一 source of truth（图形）。设计交付物
    logo-mark.png         ← 彩色主图（必需，2048–4096 正方形）。其余全部由此派生
    logo-mono.png         ← 单色剪影（可选；缺省由主图 alpha 自动派生）
    og-card.png           ← 1200×630 社交卡片（可选；缺省沿用旧图）
  reference/              ← 设计草稿/超大原图暂存，git 忽略，不入库

cmd/generate-brand-assets/   ← 工具：source/* → 各消费端产物（无中间 assets/ 目录）
scripts/sync-branding.mjs    ← 工具二：brand.json → 各文本消费端
```

每个逻辑资产各司其职、互不重叠：`logo-mark` 派生一切方形图标（ICO / ICNS / Linux PNG），`logo-mono` 只派生 macOS 托盘 template（缺省从主图 alpha 派生，原因与局限见 §5.6），`og-card` 只派生社交预览位图（不自动合成）。`.svg` 源仍受支持（校验过的真矢量，防止嵌入位图的 SVG回归），但当前标准交付是 PNG。

### 3.2 数据流

```
                     ┌─ internal/brand/brand.json        (go:embed，桌面端 + 服务端)
                     ├─ web/src/lib/brand.config.json    (Vite import)
brand.json ──sync──> ├─ mobile/src/brand.config.json
                     ├─ landing/brand.config.json
                     ├─ cmd/octo-relay/internal/push/brand.json  (嵌套模块，独立 embed)
                     └─ packaging/windows/brand.iss      (Inno #define)

source/logo-mark.png ┐  (必需；彩色主图)
source/logo-mono.png  ┤  (可选；缺省由主图 alpha 派生)
source/og-card.png    ┘  (可选；缺省沿用旧 og-image.png)
        │
        │ generate (cmd/generate-brand-assets)
        ▼
        ├─ cmd/octo-desktop/build/windows/icon.ico
        ├─ cmd/octo-desktop/build/darwin/icon.icns
        ├─ cmd/octo-desktop/build/darwin/tray-icon.png
        ├─ cmd/octo-desktop/build/linux/icon.png
        ├─ web/public/favicon.*
        ├─ blog/public/{favicon.*,og-default.*}
        ├─ docs/public/favicon.*
        └─ landing/{favicon.*,og-image.png}
```

> 现状注：favicon 系列分发到 web/blog/docs 属 §5.5 规划的后续动作；**当前工具实际落盘范围**为 `cmd/octo-desktop/build/*` 四项 + `landing/og-image.png`（有 `og-card.png` 源时），见 §5.4 消费点表。

生成目标全部进版本库（CI 与打包不重跑图形处理，构建可复现），但用 `.gitattributes` 标 `linguist-generated=true`，让 PR 里默认折叠，评审只看 `branding/` 下的源文件。

源是 PNG（或校验过的 SVG）、产物是位图，两者都由纯 Go 确定性重采样/编码，`--check` 因此能做到「重新渲染再比对」—— 手改任何生成产物都会在提交阶段暴露。同机两次独立渲染逐字节一致（无 CGO、无 SIMD，Go 的 float64 与 PNG 编码器都是确定性的）；**跨 macOS / Linux / Windows 尚未验证**。

因此 CI 的资产检查设计成两层，逐字节比对不是唯一防线：

| 层 | 检查 | 跨平台风险 |
|---|---|---|
| **属性校验**（主防线） | 尺寸齐全、托盘图去重颜色数为 1、安全边距、无近白、favicon 体积上限 | 无。这些性质与渲染器的亚像素差异无关，且**恰好覆盖全部已知的真实事故** |
| 逐字节比对（附加） | 重新渲染与仓库产物比对 | 有。PR 2 需在三个 OS 上实测；若不可复现则降级为仅本地 `make brand && git diff --exit-code` 的纪律 |

排序是有意的：属性校验能拦下「有人手改了托盘图导致它变彩色」这类真实危害，而逐字节比对只多拦「像素级无害改动」。把可能不稳的那层放在附加位置，避免 CI 因渲染器的平台差异变成噪音源。

### 3.3 brand.json schema（`schemaVersion: 2`）

dev-zxy 的 v1 按「这个值以后会不会变」分组（`compatibility` / `futureMigration` / `platform`）。本方案改成**按值的类别分组**（§2.5 的 A / B / C），这样每一段只有一条校验规则，CI 能机械执行，人也不会往错的段里填值。

```jsonc
{
  "schemaVersion": 2,
  "brandId": "puddingbox",

  // ── A 类：本地化文案。每个叶子必须是 locale map，且 zh-CN / en-US 齐全 ──
  "product": {
    "names":     { "zh-CN": "布丁盒子", "en-US": "Pudding Box" },
    "shortName": { "zh-CN": "布丁盒子", "en-US": "Pudding" },
    "tagline":   { "zh-CN": "让本地工具、任务与智能代理，在一个工作台里协作。",
                   "en-US": "One workspace for local tools, tasks, and agents." },
```

Go 侧 `internal/brand/brand.go` 的 `Load()` / `localized()` 结构可直接沿用（`go:embed` + 三级回退：精确 locale → 语言前缀 → `en-US`），按新 schema 调整字段并追加 `ShortName(locale)`、`Identifier(key)`、`Display(platform, key)`。

### 3.4 替换演练：这套结构到底省了什么

「以后好替换」不是愿望，是可以量化验收的。三个典型场景：

**场景 A：只改名字**（例如英文名从 `Pudding Box` 换成别的拼写，或整个换中文名）

```bash

```

改动量：**1 个文件的几行 JSON，0 行代码。** 窗口标题、托盘菜单、通知、关于页、输入框待接入、导出标题、落地页、安装器显示名、Windows VERSIONINFO 全部跟着变，因为它们没有一处写死品牌名 —— 这就是 §4 那套模板变量插值的回报。

**场景 B：只换 Logo**

```bash
# 用新主图覆盖 branding/source/logo-mark.png（换风格时连同可选 logo-mono.png / og-card.png）
make brand
```

改动量：**1 个 SVG，0 行代码。** Windows ico、macOS icns 与托盘 template、Linux png、四个站点的 favicon 系列、落地页 og-image、界面内 Logo 组件全部更新，因为它们同源（§5.7）。

**场景 C：整体白标**（把产品换给另一个客户/另一条产品线）

```bash
# 1. 替换 branding/brand.json（名称、口号、版权方、色值、链接）
# 2. 替换 branding/source/ 下的三个 SVG
make brand
make brand-check   # 与 CI 同一套判断
```

改动量：**4 个源文件 + 1 条命令。**

**仍然需要改代码的边界**（写清楚，免得以后误以为"配置万能"）：

| 情况 | 为什么必须改代码 |
|---|---|
| 新增一种界面语言 | 要在 `i18n.ts` 增加词典、在 `dictFor()` 与 `resolveLang()` 增加分支 |
| 新增一个消费端（例如新开一个站点） | 要在 `sync-branding.mjs` 的 targets 表加一行 |
| 改 C 类标识符（bundle id、AppId、CLI 名） | 配置能改，但要配套迁移方案（§2.4），不是改个值就完事 |
| 新增一个需要品牌名的界面位置 | 要写词条，但**用 `{brand}` 模板变量**，不写死 |

**验收这一节：** §9「流程」部分的三条演练检查项就是对着这里写的 —— 真的换一张图、真的改一次名，看是不是只动了预期的文件。

## 4. 文案层：模板变量插值，禁止运行时替换

### 4.1 为什么不用 replaceAll（dev-zxy 的实测教训）

dev-zxy 在 `web/src/lib/i18n.ts` 和 `cmd/octo-desktop/lang.go` 里都用了「取出文案后把 `Octo` 全局替换成品牌名」。实测四类问题，全部是这个做法的必然结果，不是实现瑕疵：

| 问题 | 具体表现 |
|---|---|
| 误伤非品牌文本 | `settings.workspace_dir_desc` 里的 `~/Octo` 是**路径**，被改成 `~/Pudding Box`，给用户一个不存在的路径 |
| 中文多空格 | `"Octo 正在等待你的输入"` → `"布丁盒子 正在等待你的输入"`；`"关于 Octo"` → `"关于 布丁盒子"`；`"退出 Octo"` → `"退出 布丁盒子"`。中文排版硬伤，且验收表是逐字对的 |
| 短名无处接入 | 没有替换目标可以区分「这里该用全称」和「这里该用简称」 |
| 评审无抓手 | 翻译文件里看不出哪条含品牌词，回归靠肉眼；每次 `t()` 都全串扫描一遍，渲染热路径上纯开销 |

而需求 §5.2.1 已经写明「名称是文案键，不是写死的字符串」。运行时替换恰好是把名称写死在英文串里再擦掉。

### 4.2 Web 侧做法

词典里用模板变量，`t()` 只做插值，并对不含模板变量的词条走零分配快路径：

```ts
// web/src/lib/i18n.ts
export const t = derived(locale, ($l) => {
  const dict = dictFor($l)
  const name = brandName($l)
  const short = brandShortName($l)
  return (key: string): string => {
    const value = dict[key] ?? en[key] ?? key
    // 绝大多数词条不含模板变量，直接返回，避免每次渲染都分配新串。
    if (!value.includes('{brand')) return value
    return value.replaceAll('{brand}', name).replaceAll('{brandShort}', short)
  }
})
```

> 两个模板变量互不干扰（`{brandShort}` 里 `brand` 后面跟的是 `S` 不是 `}`，不会被 `{brand}` 匹配到），替换顺序无所谓。但如果以后新增 `{brandX}` 形式的模板变量，要检查是否存在前缀包含关系。

词条改写示例：

| 键 | 英文 | 中文 |
|---|---|---|
| 聊天输入提示字段 | `Message {brand}… (…)` | `发给{brand}…（…）` |
| `header.notif_question_body` | `{brand} is waiting for your input` | `{brand}正在等待你的输入` |
| `onboard.title` | `Welcome to {brand}` | `欢迎使用{brand}` |
| `m.about_octo` | `About {brand}` | `关于{brand}` |
| `settings.about.footer` | `{brand} · {tagline} · © {year}` | 同结构 |
| `settings.about.version_desc` | `Currently installed {brand} version` | `当前安装的{brand}版本` |
| `settings.update_desc` | `Check whether a newer version of {brand} is available.` | `检查是否有新版本的{brand}。` |
| `settings.autostart_desc` | `Start {brand} automatically when you log in to this computer` | `登录这台电脑时自动启动{brand}` |

**例外，不要插值的（C 类，见 §2.5）：** `settings.workspace_dir_desc` 里的 `~/Octo` 是**路径**不是品牌名，按需求 §5.2.2 直接改成 `data/workspace/`，中英文界面都展示这五个 ASCII 字符，不翻译、不插值。

凡是「看起来像 Octo 但其实是 C 类」的位置一律同样处理，逐一列明以便实现时核对：

| 词条里的字面量 | 它是什么 | 怎么处理 |
|---|---|---|
| `~/Octo` | 会话工作区路径 | 改成 `data/workspace/`，原样展示 |
| `~/.octo` | 配置目录 | 数据根已按需求 §5.7 删除（移到 `data/`），见 §2.4 注 |
| `octo serve` / `octo` | CLI 命令 | 保持不变 |
| `octo-ui://` / `octo-pair://` | protocol scheme | 保持不变 |
| `OCTO_*` | 环境变量名 | 保持不变 |
| `8088` | 端口 | 保持不变 |
| `octo-desktop.exe` | 上游 exe 名 | 改成 `PuddingBox.exe`（C 类换值，不是插值） |

判断口诀：**这个字符串用户会不会拿去敲进终端、粘进地址栏、或在文件管理器里找？** 会，就是 C 类，不进插值管线。

### 4.3 桌面原生侧做法（`cmd/octo-desktop/lang.go`）

去掉 dev-zxy 的反射遍历。把两个 `uiStrings` 变量改成构造函数，品牌位置在源码里可见：

```go
func enStrings(name, short string) uiStrings {
	return uiStrings{
		trayShow: "Show " + short,
		trayQuit: "Quit " + short,
		quitTitle: "Quit " + name,
		takeoverTitle: name,
		updAvailableFmt: name + " %s is available.",
		// …不含品牌的条目原样保留
	}
}

func zhStrings(name, short string) uiStrings {
	return uiStrings{
		trayShow: "显示" + name,   // 中文无空格
		trayQuit: "退出" + name,
		quitTitle: "退出" + name,
		takeoverTitle: name,
		updAvailableFmt: name + " %s 已发布。",
	}
}

func applyLang() {
	cfg := brand.Load()
	if resolveLang() == "zh" {
		s := zhStrings(cfg.Name("zh-CN"), cfg.ShortName("zh-CN"))
		active.Store(&s)
	} else {
		s := enStrings(cfg.Name("en-US"), cfg.ShortName("en-US"))
		active.Store(&s)
	}
}
```

好处：编译期就能看出哪些串带品牌；中文无空格；短名有明确位置；不需要 `reflect`。

窗口标题（`bridge.go`）、`application.Options{Name, Description}`（`main.go`）、托盘 tooltip 走同一份取值，语言切换时一起变。原生对话框跟随当前语言 —— 中文界面不能弹英文 `Quit Pudding Box`。

### 4.4 中文排版规则（写进 review checklist）

1. 中文文案里产品名与中文字符**之间不加空格**：`显示布丁盒子`、`关于布丁盒子`、`布丁盒子正在等待你的输入`。
2. 中文文案里产品名与**英文/数字**相邻时保留一个空格：`布丁盒子 v1.2.0 已发布。`
3. 英文文案照英文习惯：`Show Pudding`、`About Pudding Box`。

### 4.5 CI 守卫

新增 `brand-guard` job，七条检查全部为硬失败：

| # | 检查 | 命令 / 判据 | 拦什么 |
|---|---|---|---|
| 1 | 文案表无字面品牌名 | `rg -n '\bOcto\b' web/src/lib/i18n.ts cmd/octo-desktop/lang.go` 必须无输出 | 有人新增词条时又把品牌名写死 |
| 2 | A 类必须是 locale map | `product.*` / `about.*` / `copy.*` 叶子为 object 且 `zh-CN`、`en-US` 均非空 | 少一种语言就发版；或把文案写成单字符串 |
| 3 | B 类必须是单字符串 | `display.*` 叶子为 string，不是 object | 给 Windows 文件属性加多语言（dev-zxy 的错） |
| 4 | **C 类必须是无空格 ASCII** | `identifiers.*` / `links.*` / `visual.logo.*` 叶子为 string 且匹配 `^[\x21-\x7E]+$` | **给路径或标识符加中文、加空格、加多语言 map** |
| 5 | 配置分发未漂移 | `node scripts/sync-branding.mjs --check` | 改了 `brand.json` 忘了同步 |
| 6 | 资产未漂移 | `go run ./cmd/generate-brand-assets --check` | 换了源图忘了重新生成（dev-zxy 就出现过换资产没同步组件） |
| 7 | 格式 | `gofmt -l .` 必须无输出 | dev-zxy 因 `//go:embed` 前缺空行挂在这一项上 |

第 1 条只匹配大写词边界 `\bOcto\b`，所以小写 `octo`、`octo-ui`、`~/.octo`、`octo-desktop` 等 C 类兼容标识天然放过。

第 4 条是 §2.5 那条「路径一律英文」的落地方式。**规则写在文档里只是约定，写进 CI 才是约束** —— 有了它，「把 `data/workspace/` 翻译成中文」或「给 `exeName` 加个 `zh-CN` 键」这类改动在提交阶段就过不去，不依赖评审逐行看。

## 5. Logo 资产管线（一次生成，全仓同步）

这一节是本方案的重点：**设计只交一张图，研发跑一条命令，全平台产物与所有消费点一次到位。**

### 5.1 输入契约（设计交付给研发的东西）

完整的设计侧交付契约见独立文档 **[品牌资产交付说明](./品牌资产交付说明.md)**（可直接发给设计）。本节只记录研发需要知道的要点与判断依据。

**单主图模型（2026-09-09）**：主图是唯一必需的正式交付物；托盘剪影缺省自动派生、`og-card` 缺省沿用旧图 —— 设计**只交一张图就能让 PR 2 全绿**，其余两张是"更好看"的可选增强。

| 文件 | 规格 | 必需 |
|---|---|---|
| `branding/source/logo-mark.png` | 方形主标识，**2048–4096×2048–4096**，透明底 | **必需（唯一阻塞项）** |
| `branding/source/logo-mono.png` | 单色剪影，≥ 512×512，只用 `#000000` + 透明 | **可选**。缺省由主图 alpha 自动派生（§5.6） |
| `branding/source/og-card.png` | **1200×630**，不透明底 | **可选**。含排版文案，不自动合成，缺省沿用旧 `og-image.png` |

> **2026-09-09 决策变更：源由矢量 SVG 改为高分辨率 PNG。** 详见 [品牌资产交付说明](./品牌资产交付说明.md) §9。工具 `cmd/generate-brand-assets` 同时接受 `.svg`（优先）与 `.png`（兜底）——真矢量若日后补交，无需改脚本。单主图模型沿用同一决策：设计只交付彩色位图主图，衍生资产全部交给工具。

#### 为什么源是 PNG，不是矢量（2026-09-09 修订）

初版（2026-09-07）用三段论证「必须矢量」，后因连续四次设计交付均为 base64 嵌入位图的 SVG而推翻，逐条回应如下：

1. ~~位图喂不了主要消费点。~~ 约 10 处内联 SVG 消费点改 `<img>` 引用 PNG 即可，浏览器渲染 PNG 与 SVG 无差别，且无内联 `<defs>` id 冲突（§5.9 第 2 条正是该问题）。
2. ~~矢量源才能让 `--check` 有意义。~~ PNG 源下 `--check` 仍能「重新缩放再逐字节比对」，只失去「检测源 PNG 被手改」这一层，可接受。
3. ~~现有标识本来就是矢量。~~ 那是对**旧章鱼标识**的描述；**新布丁盒子标识的设计源文件里是位图**（四次导出都带 base64 `<image>` 即证明），拿不到真矢量。

dev-zxy 曾把 582 字节真矢量替换成 218,652 字节 base64 嵌入位图的 SVG（大 375 倍）——**所以严禁在 `.svg` 里内嵌 PNG 冒充矢量**；但**直接用 `.png` 作为源**是另一回事：`cmd/generate-brand-assets` 直接解码 PNG 缩放，不产生嵌入位图的 SVG。

#### 渲染器约束（实测，直接决定交付契约）

流水线用纯 Go 的 SVG 光栅化（`oksvg` + `rasterx`）。

**新依赖的理由**（`.octorules` 要求新增第三方依赖须在 PR 描述中说明，这里先记录）：矢量源必须被光栅化成 `.ico` / `.icns` / PNG，而 Go 标准库不解析 SVG。已有的 `golang.org/x/image` 提供光栅化器但不解析 SVG。候选与取舍：

| 方案 | 代价 | 结论 |
|---|---|---|
| `oksvg` + `rasterx` | +2 个 Go 依赖，纯 Go 无 CGO，SVG 特性支持有限 | **采用。** 与 `cmd/generate-brand-assets` 同栈，`make brand` 不需要 npm；特性缺口正好由交付契约（只用 `<path>` + 实色）覆盖 |
| Node + `@resvg/resvg-js` | +1 个 npm 依赖含预编译原生二进制，SVG 支持完整 | 不采用。会让 `make brand` 依赖 `npm install`，破坏配置层现有的「零 npm 依赖」性质 |
| 自己写 SVG 路径解析器 | 0 依赖，约 200 行，需处理弧线命令 | 不采用。重造轮子，且弧线易出错 |

`oksvg` 的特性支持实测了一遍。**正常**：`<rect>` `<circle>` `<ellipse>` `<polygon>` `<g>` `translate` `rotate` `matrix` 嵌套变换 `fill-rule=evenodd` 线性/径向渐变 `stroke` `opacity` 内联 `style=` `<clipPath>` `<use>`。**三条缺陷**：

| # | 缺陷 | 实测表现 | 处理 |
|---|---|---|---|
| 1 | `<rect>` 只写 `rx` 不写 `ry` | 圆角**静默忽略**。角点像素：只写 `rx` → `rgba(47,84,235,255)` 不透明；`rx` `ry` 都写 → `rgba(0,0,0,0)` 透明。未实现 SVG 规范「省略 `ry` 时取 `rx`」这条 | 预处理补 `ry`，**自动修** |
| 2 | `transform="scale(...)"` 简写 | 静默失效，图形不出现。等价的 `matrix(2 0 0 2 0 0)` 正常 | 预处理改写为 `matrix()`，**自动修** |
| 3 | `<text>` 活文字 | 不支持，但会打印 `Cannot process svg element text`（非静默） | 无法自动修，**交付契约要求文字转曲** |

所以交付契约只有两条硬禁止：**文字转曲**、**不得内嵌位图**。其余由预处理消化。

> **修订说明：** 初版契约写的是「所有形状必须转 `<path>`，禁用渐变/描边/clipPath」。那是只测了 `<rect rx>` 一个用例就外推的结论 —— 补测后发现根因很窄（缺陷 1 是 `ry` 缺省未实现，缺陷 2 是 `scale()` 简写解析），且两条都能自动修，故已放宽。Figma 导出的 SVG 用 `matrix()` 与 `translate()`，本来不踩缺陷 2。

缺陷 1 和 2 都是**静默失败**，所以生成工具必须**断言渲染结果**而不是信任渲染器（§5.2 第 2 条）—— 预处理漏了某种写法时，要在构建期暴露，不能等到 16px 图标上被人眼发现。

### 5.2 工具一：`cmd/generate-brand-assets`（矢量源 → 全套派生）

dev-zxy 已有一个雏形，架构可取（纯 Go、无外部依赖、ICO 存 PNG 帧、ICNS 存标准 PNG chunk，同一条命令在三个 OS 上都能跑）。本方案改成从矢量输入起步，并补齐七件事：

| # | 能力 | 说明 |
|---|---|---|
| 1 | **源文件校验 + 预处理** | 拒绝 `<text>` 与 `<image>`/`base64`（§5.1 的两条硬禁止）；`viewBox` 必须匹配约定；自动补 `<rect>` 缺省的 `ry`、把 `scale()` 改写成 `matrix()`（§5.1 缺陷 1、2） |
| 2 | **渲染结果自验** | 渲染后断言关键像素（如圆角处应透明），防止渲染器静默降级。不能只信任「没报错」—— 缺陷 1、2 都是静默失败 |
| 3 | **几何校验** | alpha 包围盒须留 8–10% 边距、居中偏差 ≤ 1%；不满足则**报错退出**并打印实际值 |
| 4 | **近白检测** | 亮度 > 0.85 且不透明的像素成片出现时报错（深色界面会露出，见 §5.1 与交付说明 §2.4） |
| 5 | **16px 可读性检查** | 缩到 16×16 后非透明像素占比 < 12% 时告警（图形过细，托盘会看不清） |
| 6 | **托盘 template 独立通道** | 有专门 `logo-mono` 源时单独渲染并断言产物只有一种颜色；没有时从主图 alpha 自动派生纯黑剪影（§5.6） |
| 7 | **`--check` 模式** | 只渲染不落盘，与仓库现有产物逐字节比对，不一致则非零退出。给 CI 用 |

保留 dev-zxy 已实现且正确的部分：`draw.CatmullRom` 缩放、手写 ICO（多帧 PNG）、手写 ICNS（`icp4/icp5/icp6/ic07…ic14` chunk）。给 `makeICO` 的帧集合补上 **24px**（需求 §5.2.4 要求 16/24/32/48/256），并给 `makeICNS` 加缺失尺寸的显式报错，别静默写出空 chunk。

派生尺寸：`1024, 512, 256, 192, 180, 152, 144, 128, 120, 96, 72, 64, 48, 32, 24, 16`。

**只生成有消费点的产物。** dev-zxy 产出了 15 个尺寸的 PNG 进仓，其中 **11 个在整个仓库里没有任何引用**。派生尺寸清单用于组装 `.ico` / `.icns` / favicon 系列，中间产物不必逐个落盘进版本库 —— 落盘清单以 §5.4 的消费点表为准。

### 5.3 工具二：`scripts/sync-branding.mjs`（分发）

沿用 dev-zxy 的实现思路（一张 targets 表 + `--check` 漂移检测），扩展为同时分发**文本配置**和**图形产物**，目标见 §3.2 与 §5.4。

两点改进：

1. **生成文件带来源标记。** JSON 加顶层 `"_generated": "branding/brand.json via scripts/sync-branding.mjs"` 字段，`.iss` 已有注释头。任何人打开生成文件都知道不该手改。
2. **降低评审噪音。** `.gitattributes` 里把所有生成目标标 `linguist-generated=true`，GitHub PR 默认折叠。dev-zxy 一次 PR 里 170 行 JSON × 7 份副本的 diff 让评审几乎无法进行。

### 5.5 favicon：不做 base64 嵌入位图的 SVG

dev-zxy 的 `pudding-box-mark.svg` 是把 1024×1024 PNG base64 塞进 `<image>` 标签的壳，**218,652 字节**，还被复制成 3 份进仓（约 650 KB）。这是净退步。

本方案的规则（源改为 PNG 后相应调整，见 §5.1 决策变更）：

- favicon 由 `logo-mark.png` 缩放为多帧 `favicon.ico`（16/32/48，PNG 帧；`web/public/` 与 `docs/public/`），`index.html` 用 `<link rel="icon" type="image/x-icon" href="/favicon.ico">`。不再保留矢量 favicon（源已是 PNG，见 §5.1 决策变更）；PWA 的 `icon-192/512`、iOS `apple-touch-icon` 属后续站点工作，需要时从同一主图补帧。
- 单个 favicon 文件 **≤ 25 KB**，由 `--check` 顺带断言。
- **明确禁止**把位图 base64 内联进 `.svg` 冒充矢量。若源是 SVG，静态校验（§5.2 第 1 条）会拒绝含 `<image>` 或 `base64` 的 SVG。

**顺带修掉一处历史遗留：** `docs/public/favicon.svg` 是旧章鱼标（Astro 脚手架遗物，从未换成产品标识），已删除并以 `docs/public/favicon.ico`（主图生成）替代 —— 2026-09-09 落地。`blog/public` 在本仓库已无目录，博客站后续若恢复按 §5.4 补同一 favicon。

### 5.6 托盘图标

macOS 菜单栏图标**只读 alpha 通道**（颜色全丢），所以"把彩色主图直接丢进去"这条路永远是错的。但**主图的 alpha 本身是合法剪影** —— 2026-09-09 起，无专门 `logo-mono.png` 时工具把它作为缺省派生成纯黑 + alpha 的模板图（§5.2 第 6 条），`logo-mono.png` 不再是必需交付物。

**自动派生的已知局限**：若 logo 内部细节（眼睛、嘴、高光）是"画在图案上的浅色"而非"真镂空的透明"，这些细节不在 alpha 通道里，派生后菜单栏上就是实心轮廓。设计若愿意多交一张真镂空的剪影版，托盘观感会更好 —— 此时工具优先使用专门源，并断言它只有 `#000000` 一种颜色。

现有代码走 Wails 的 `tray.SetTemplateIcon`（`cmd/octo-desktop/main.go`），即 macOS 的 template image 通道。该通道**只读 alpha 通道，颜色全部丢弃**，由系统按菜单栏明暗自行染色。所以把彩色图丢进去，得到的是它的实心剪影。

实测对比现有资产与 dev-zxy 的替换：

| 文件 | 尺寸 | 纯黑占比 | 有彩色占比 | 去重颜色数 | 非透明占画布 |
|---|---|---|---|---|---|
| `main` 的 `tray-icon.png` | 88×88 | **100.0%** | 0.0% | **1** | 28% |
| dev-zxy 换成的图 | 64×64 | 9.9% | **78.3%** | **1001** | 53% |

`main` 那个是正确的 template 图：纯黑 + 透明、单一颜色、非透明只占画布 28%（图形的主要笔画）。dev-zxy 换成了 1001 色的彩色立方体，送进 template 通道后颜色全丢，而立方体在整个六边形轮廓内都不透明 —— 三个面与所有明暗消失，菜单栏里只剩一个**实心六边形色块**。这是 dev-zxy 引入的功能回归，不是观感问题。

| 平台 | 做法 |
|---|---|
| macOS | 从 `logo-mono.png`（缺省由主图 alpha 派生）生成单张 `tray-icon.png`，纯黑 + alpha，尺寸沿用现有的 **88×88**（菜单栏实际约 22pt，88px 足够覆盖 Retina）。不需要 `@2x`：代码是 `go:embed` 单个文件后调 `SetTemplateIcon(bytes)`，没有 AppKit 那套按文件名找 `@2x` / `Template` 后缀的机制。专门源存在时生成工具**断言产物去重颜色数为 1**，把上面那个回归变成构建失败 |
| Windows / Linux | 彩色图标，复用 `logo-mark.png` 派生的 256×256 PNG（现有代码就是这么用的，一个文件两用） |
| 降级路径 | 无专门 `logo-mono.png` 时自动派生（见本节开头）。该路径产出纯黑单色模板，**不会**重演 dev-zxy 的彩色色块回归 —— 派生是把 alpha 抄到纯黑上，不是把彩色图直接丢进 template 通道。局限是内部浅色细节丢失，后续可用专门剪影替换 |

### 5.7 界面内 Logo 组件

`web/src/components/layout/OctoLogo.svelte` 更名为 `BrandMark.svelte`，三个使用点一起改：`Sidebar.svelte`、`FirstRunSetup.svelte`、`ChatView.svelte`。

组件从 `brand.visual.logo.mark` 取路径渲染 `<img>`，**与 favicon / exe 图标同源**。

dev-zxy 在这里踩了两个坑，都要避免：

1. **两套 Logo 并存。** 最后一个 commit 换了全部 PNG/ICO/ICNS 资产，但没同步 Svelte 组件，结果侧栏显示橙色布丁笑脸、任务栏显示蓝色立方体。根因是界面 Logo 与资产不同源 —— 本方案用同一份文件消除这个可能。§4.5 的资产漂移检查是第二道防线。
2. **SVG 渐变 id 冲突。** 组件内联 SVG 时 `<defs>` 用了硬编码 `id="pb-box"`。这个组件在同一页面渲染三次，产生重复 id（非法 HTML），且首个实例卸载后其余实例的 `url(#pb-box)` 引用会失效变透明。若确实需要内联 SVG，id 必须按实例唯一化；用 `<img>` 则天然没有这个问题。

**顺带收敛一处历史重复：** 同一份标识几何过去被手抄在约 10 个地方 —— 除了 Svelte 组件，还有 `landing/index.html` 的导航/主视觉/页脚三处内联、`shared/octo-nav.js` 的 `MARK()`（博客导航与页脚共用）、`docs/src/assets/octo-mark.svg`、`landing/og-image.svg`、`blog/public/og-default.svg`，并且用了**三种不同的蓝**（`#2F54EB` / `#1677FF` / `#4f46e5`）。这是「换 logo 很难」的真正原因。

> **2026-09-09 现状**：桌面图标与 `web/public/` 资产已由主图 PNG 一次生成；`OctoLogo.svelte`（章鱼内联 SVG）已改为渲染 `brandAsset('mark')` 的新主图 —— **web UI 内（Sidebar / ChatView / FirstRun / 登录页等）已全部显示布丁主图**。landing / 文档站点手工内联几何与 `og-card` 仍待站点类 PR（P6 范畴）跟进，统一从 `branding/source/logo-mark.png` 出图，不再手抄。

关于页与拦截页的主标题用「方形 Logo + `{brand}` 文字」的组合布局，不再要求设计单独交横版 Logo —— 文字由 §4 的模板变量插值提供，换名字时自动跟着变，比一张写死文字的图更符合本方案的取向。

### 5.8 工作流：设计换图后研发做什么

```bash
# 1. 把新的主图放到 branding/source/logo-mark.png（可选：logo-mono.png / og-card.png）
# 2. 一条命令
make brand

# make brand 展开为：
#   node scripts/sync-branding.mjs
#   go run ./cmd/generate-brand-assets --source branding/source

# 3. 自检
make brand-check   # = 两个 --check，与 CI 同一套判断
git status         # 应只看到 branding/assets/ 与各生成目标变动
```

改文案（改名、改口号、改版权方）只需编辑 `branding/brand.json` 后跑 `node scripts/sync-branding.mjs`，不碰图形。

### 5.9 已有资产的处置

dev-zxy 分支里的蓝色立体 BOX 立方体图标**不直接沿用**。对那张 `pudding-box-icon-1024.png` 的实测数据：

| 指标 | 实测值 | 问题 |
|---|---|---|
| alpha 包围盒 | x 78–943，y **0–1023** | 上边距 **0 像素**，图形顶到画布边缘；macOS 圆角遮罩与 Android 安全区会切到 |

| 去重颜色数 | 6,308 | 位图，且烙入字标，16px 下无法辨识 |

三条都踩在 §5.1 的验收线上。设计按[品牌资产交付说明](./品牌资产交付说明.md)重新提供三个矢量后，走 §5.8 的流程重新生成全套。若决定沿用这个立方体图形，需要重绘为矢量并去掉字标、补足安全边距、另出一版单色剪影。

## 7. 打包与系统元数据

### 7.1 Windows

- `generate-syso` 继续负责 icon + manifest + VERSIONINFO。dev-zxy 把 VERSIONINFO 拆成可单测的 `buildVersionInfo(appVersion)` 是好做法，保留；但按 §2.2.1 改成**单 translation block**。
- `OriginalFilename` 必须等于 `PuddingBox.exe`，与实际交付文件名一致。
- 构建产物改名为 `PuddingBox.exe`：影响 `.github/workflows/desktop.yml`、`release.yml`、`windows-installer-check.yml` 的 `-o` 参数与 `octo.iss` 的 `[Files]` / `[Icons]` 条目。CLI 仍是 `octo.exe`。
- `octo.iss`：`AppName` / `AppPublisher` / `AppPublisherURL` / `UninstallDisplayName` / `[Icons]` 从 `brand.iss` 的 `#define` 取；`AppId`、`DefaultDirName` 保持不变。
- dev-zxy 把 `FileCopy` 改成 `CopyFile` 本身是对的（Inno Setup **6.4.0** 把 `FileCopy` 更名为 `CopyFile`，旧名仍可用但编译会告警），但这把最低 ISCC 版本抬到 **6.4.0+**。要在 `packaging/README.md` 与 CI 的安装步骤里写明这个下限，否则本机装 6.2 的人会突然编不过。

### 7.2 macOS

`Info.plist` 改 `CFBundleName` / `CFBundleDisplayName`，`CFBundleIdentifier` 与 `CFBundleExecutable` 不动（§2.4）。`icon.icns` 与 `tray-icon.png` 由管线生成（§5.6）。`packaging/macos/distribution.xml` 的显示标题随品牌。

### 7.3 Linux

`octo-desktop.desktop` 的 `Name` / `Comment` 随品牌，`Exec` / `Icon` 保持 `octo-desktop`（文件名不改）。`AppRun` 里三处提示文案随品牌。

### 7.4 移动端

`capacitor.config.ts` 只改 `appName`。`mobile/src/boot.ts` 的引导层文案改成从 `brand.ts` 取值，**用 locale 规范化函数取**，不要直接 `brand.product.names["zh-CN"]` 硬取一种语言。`mobile/tsconfig.json` 需要 `resolveJsonModule` + `allowSyntheticDefaultImports` 才能 import JSON —— 这一项 dev-zxy 已经处理对了，直接沿用（但别顺手把整个文件重排格式，那是无谓的 diff）。

### 7.5 Web / 落地页 / 文档站 / 博客

四个站点各自有独立构建根，各分发一份 `brand.config.json` 与 favicon 系列。`web/index.html` 的静态 `<title>` 填**英文全称**（单语言），运行时由 `App.svelte` 的 `<svelte:head>` 覆盖成当前语言。dev-zxy 填的 `布丁盒子 · Pudding Box` 把两种语言写死在一个串里，正是需求 §5.2 要避免的形态。

### 7.6 Relay 推送

`cmd/octo-relay` 是嵌套 Go 模块，不能引用主模块的 `internal/brand`，所以它需要自己那份 `brand.json` + 独立 `go:embed`。dev-zxy 的做法正确，沿用。注意 `//go:embed` 指令前要有空行分隔文档注释，否则 `gofmt` 会挂（dev-zxy 正是栽在这里）。推送正文保持 content-free，只替换品牌词。
