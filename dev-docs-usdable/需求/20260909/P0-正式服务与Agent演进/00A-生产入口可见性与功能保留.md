# P0-00A：生产入口可见性与功能保留

| 项 | 内容 |
| --- | --- |
| 主责建议 | 桌面客户端 / 产品策略负责人 |
| 优先级 | P0-00 的纠偏与补充任务；在 P0-04 能力矩阵前完成基础规则 |
| 依赖 | [P0-00](00-Server最小改动与生产Profile前置.md)、[P0 正式上线需求基线](../P0-正式上线需求基线.md) R1、R6、R12 |
| 不做 | 不删除 `config.yml`、MCP、channel、后台任务、工具或第三方模型实现；不改 `internal/server` 的通用行为 |

## 1. 目标

当前阶段的产品要求是**隐藏首发不开放的入口，而不是移除已经存在的功能**。

1. `config.yml` 和第三方模型配置功能继续保留，供 developer 构建、自动化测试和本地维护使用。
2. standard production UI 暂不显示“添加第三方模型”等入口；正式模型调用链在 P0-05 接入中台网关后，以网关为正式会话的唯一模型出口。
3. MCP、channel、工具、后台任务及其既有路由/启动逻辑不删除、不因菜单隐藏而停用；P0-04 的能力矩阵只决定 `visible`、`entitled` 与 PEP 判定。
4. `production`/`developer` 仍是构建时选择，运行时配置不能把 production 二进制切换为 developer；这条规则不等于禁止 developer/test 使用 `config.yml`。

## 2. 实现范围

| 位置 | 要做 | 不做 |
| --- | --- | --- |
| `internal/productprofile` | Profile 明确“能力实现保留”；生产构建不以 Profile 关闭 tools/channel/MCP/background | 不将业务规则塞进 Profile |
| `cmd/octo-desktop` | 保持现有 server 功能启动；仅在产品 UI 层使用可见性配置隐藏首发入口 | 不在 `main.go` 写中台业务或删除 server 启动代码 |
| `internal/server` | 零改；保留 `server.New` 对 `config.yml`、MCP、channel、后台能力的既有处理 | 不增加 product-specific Config 字段，不删除配置/路由/功能 |
| `internal/productpolicy`（P0-04） | 消费能力矩阵，分别处理显示、资格与 PEP | 不把“隐藏”当作授权或功能删除 |

## 3. 明确行为矩阵

| 能力 | developer / 测试 | standard production 首发 | 后续灰度 |
| --- | --- | --- | --- |
| 第三方模型配置 | 保留并可用于本地测试 | UI 不展示；不得成为 P0-05 正式会话模型来源 | 由能力矩阵决定是否展示 |
| `config.yml` | 正常读取、保存、测试 | 保留读取/保存与既有兼容；不是正式网关的凭证来源 | 同左 |
| MCP / channel / 工具 / 后台任务 | 保持现有功能 | 实现和既有启动保持；菜单可 `visible=false`，执行仍受 PEP | 能力矩阵可逐项显示/授权 |
| `OCTO_DESKTOP_DEV_URL` | developer 构建允许 | production 忽略 | 不适用 |
| Profile 选择 | 构建标签选择 | 构建标签选择 | 不允许运行时切换 |

**作用域必须分清（避免误伤开发能力）**：本表限制的是 **production 正式会话的模型来源**，不是 `config.yml` 这个功能本身。

- **developer / 测试**：`config.yml` 里的供应商 endpoint、`base_url`、`api_key`、`headers` **完全允许**，这就是本地联调、第三方模型验证和离线开发的方式，不受本表限制。
- **production**：`config.yml` 仍可读取/保存/测试，UI 也可按能力矩阵决定是否显示；但**正式会话不得把它当模型来源或凭证来源** —— 正式模型只能来自签名目录、经中台网关。
- 因此正确的表述是「production 正式会话不得以 `config.yml` 作模型来源」，**不是**「`config.yml` 不得提供 URL/key」。后者会让开发环境失去联调手段。

## 4. 验收

- developer 构建可继续通过已有 `config.yml` 配置第三方模型并完成本地测试。
- production 构建不将 `OCTO_DESKTOP_DEV_URL` 用作 WebView 地址；但 tools、channel、MCP 和后台能力的代码与既有启动路径不因 Profile 被删除或关闭。
- 第三方模型配置入口在 standard production UI 不出现；P0-04 的 capability contract 能将其标记为 `visible=false`，而不删除实现。
- P0-05 完成后，正式桌面会话的模型请求只能经过中台网关；这不改变 developer/test 的本地配置能力。
- 不修改 `internal/server`。

## 5. 与后续任务的关系

- P0-04 负责能力矩阵、可见性与 PEP 的正式实现。**`capabilities[].id` 的唯一登记表是[中台交付包 §4.4](../产品客户端与中台对接/中台交付包.md)（能力 ID 注册表，初稿待 Q4 确认），本文件不复制 id 清单**；本任务交付的是「哪些入口首发隐藏、功能保留」的规则，Q4 只确认 §4.4 清单的增删与首发 `visible` 取值。
- P0-05 负责将正式会话的模型出口切换到网关；届时验证本地 `config.yml` 不会改变正式模型调用链。
- P1 只治理长期的账户、设备、扩展来源和后台任务生命周期，不负责把这些能力移除。
