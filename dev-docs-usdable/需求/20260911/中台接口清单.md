## 0. 怎么用这份文档

1. **中台需要实现的，是 §1 的 9 个接口 + §5 的 4 个非代码交付物。**
2. 每个接口给四样：**请求 / 响应 / 必须满足的约束 / 失败码**。约束那一栏是客户端**已经按它写了断言**的，不满足会在联调当场失败。
3. **§4 是签名方案**，两个被签名的接口（目录、词库）都按它做。签名不过 = 客户端拒绝使用（fail closed），没有降级路径。
4. **§6 是本轮明确不做的部分**，其中「能力矩阵」请**不要实现**（客户端永不消费）。
5. 联调前请过一遍 **§8 的检查清单**。

> **一句话摘要**：中台要提供 **1 个控制面主机 + 1 个网关主机 + 一把 ed25519 签名密钥**，实现 **8 个 JSON 接口（统一信封 + 统一错误码）** 和 **1 个 OpenAI 协议流式补全接口**。

## 2. 传输层约定（所有控制面接口共用）

### 2.1 请求头

| 头 | 何时带 | 值 |
| --- | --- | --- |
| `Accept` | 总是 | `application/json` |
| `Content-Type` | 有请求体时 | `application/json; charset=utf-8` |
| `X-Client-Version` | 总是（非空时） | 客户端版本号 |
| `X-Client-Platform` | 总是（非空时） | `darwin` / `windows` / `linux` |
| `X-Client-Arch` | 总是（非空时） | `amd64` / `arm64` |
| `X-Install-Id` | 总是（非空时） | **每次安装**随机生成的 UUID，非硬件序列号 |
| `Idempotency-Key` | 有值时才带 | 见 §6.3 —— **本轮客户端不发** |
| `Authorization` | 需要鉴权的接口 | `Bearer <accessToken>` |

**请求头与请求体都要容忍未知字段**：客户端会随版本新增头与字段，中台应忽略不认识的部分而不是拒绝。

### 2.2 成功信封（所有 2xx）

```json
{
  "data": { },
  "requestId": "req_...",
  "serverTime": "2026-09-16T01:23:45Z"
}
```

| 字段 | 必须 | 说明 |
| --- | --- | --- |
| `data` | 是 | 载荷。`GET /auth/logout` 的 `data` 是 `null`，无字段 |
| `requestId` | 是 | 关联一次调用；客户端出错时会带在错误里，便于对账 |
| `serverTime` | 否 | 客户端**不读**它，保留给人工排查 |

`data` 内**多余的字段一律忽略**（客户端用普通 JSON 解码，未知键不报错）。但**已声明的字段不能改名**。

### 2.3 失败信封（所有非 2xx）

**注意：失败体是平铺的，不包在 `data` 里。**

```json
{
  "code": "insufficient_credits",
  "message": "…",
  "field": "code",
  "retryAfterSec": 42,
  "requestId": "req_...",
  "phoneMasked": "138****0000"
}
```

| 字段 | 何时带 | 说明 |
| --- | --- | --- |
| `code` | **总是** | 见 §2.4。**没有 `code` 的失败体会被降级**：5xx → `upstream_unavailable`，4xx → `internal_error` |
| `message` | 可选 | **只给人看，客户端不上屏**（界面文案一律由 `code` 映射到本地 i18n）。不要往里放需要用户理解的信息 |
| `field` | 可选 | **客户端目前不读它** —— 见下面的「字段级还是业务级由 `code` 决定」。请照发作为排查信息，但**不要指望它改变呈现** |
| `retryAfterSec` | 可选 | 仅 `rate_limited` 用；界面据此倒计时。不带就等于「可以立刻重试」 |
| `requestId` | 可选 | 同上 |
| `phoneMasked` | **仅 `phone_mismatch`** | **必须带**：这个激活码当前绑定的脱敏手机号。客户端无从得知（换新机器时本地什么记录都没有），界面要能说出「这个码绑在哪个号上」 |

**不要发明 `messageKey` / `traceId` 等第二种命名。** 就这 6 个。

#### 字段级还是业务级，由 `code` 决定，不由 `field` 决定

这是最容易误解的一条，**请务必按它设计**：中台回什么 `code`，决定了错误显示在**输入框下面**还是顶部**横幅**里。归属由客户端**本地**的固定清单决定，而且**按路由各有一份，不是一张全局表** —— 两条路由今天一共只有**两个**平台码会落到输入框里：

| 路由 | 平台 `code` | 呈现位置 |
| --- | --- | --- |
| §3.1 发验证码 | `invalid_phone` | **手机号输入框下面** |
| §3.2 登录 / 激活 | `invalid_code` | 验证码输入框下面 |
| 两条路由 | **其余所有平台码**（含 `activation_invalid`、`activation_code_used`、`box_code_unknown`、`box_code_mismatch`、`phone_mismatch`…） | 顶部业务横幅 |

两份清单在代码里各有一个 owner（§3.8）：发验证码那条是 `web/src/lib/product.ts` 的 `PHONE_FIELD_CODES`（成员只有 `invalid_phone`，`V-94` 之后**按名字准入**），登录那条是 `internal/productruntime/envelope.go` 的 `fieldLevelCodes`（`invalid_code` → 验证码框；另两行是客户端自己的 `nickname_format` / `nickname_sensitive`，不在这张平台码表里）。

**不要从"码的名字"推断位置。** `invalid_phone` 最容易误判：它在**发验证码**那条落在手机号框下面（那正是这个码唯一有意义的呈现，也是客户端本地 handler 刻意把它写成业务级码、再由前端归档的原因），而在登录那条会变成横幅 —— 但登录那条的格式错在本地就被拦下（请求根本发不出去），**所以中台在那个路由上不该收到 `invalid_phone`**。

`activation_invalid` 在协议里带 `field`，**客户端刻意忽略它**并把这条显示为横幅（文案指向「去激活」按钮，而不是某个输入框）。`field` 只当排查信息发，不改变呈现。

> **实践结论**：平台侧只要把 `code` 送对，归属由客户端按路由决定；`field` 不影响呈现。若某个失败必须落在**某个输入框**里、而它不在上表那两行里，请先联系我们 —— 在客户端本地校验里拦比新开一个字段级码更稳。

### 2.4 错误码登记表

**这张表是超集**：中台按需要实现，但**取值必须从这张表里选**。最后一列说清客户端今天拿这个码做什么。**表内每一个码都有本地文案，表外的码没有** —— 但那句话在两条路径上的含义不同，见本表后的两条。

| HTTP | `code` | 含义 | 客户端今天怎么用它 |
| --- | --- | --- | --- |
| 400 | `invalid_phone` | 手机号形状不合法 | 专属文案，**落在手机号输入框下面**（仅 §3.1 发验证码那条；登录那条本地会先拦，正常不会来自中台） |
| 400 | `invalid_code` | 短信验证码错误 | 专属文案，**落在验证码输入框下面**（仅 §3.2 登录那条） |
| 400 | `code_not_sent` | 该手机号本次还没发过码 | 专属文案 |
| 400 | `activation_invalid` | 激活码不存在 | 专属文案（横幅） |
| 400 | `activation_code_used` | 激活码已被使用（一码一账号） | 专属文案 |
| 400 | `box_code_unknown` | 盒子编号不认识 | 专属文案 |
| 400 | `box_code_mismatch` | 盒子编号与激活码不配套 | 专属文案 |
| 400 | `invalid_request` | 请求本身畸形 | 专属文案 |
| 401 | `unauthorized` | 未带 / 无效 access token | 专属行为：清本地凭证、回拦截页，**不显示错误** |
| 401 | `token_expired` | access token 过期 | 同上（客户端还会先尝试刷新一次） |
| 402 | `insufficient_credits` | 余额不足 | 专属文案（回合错误位置：「余额不足」+ 充值入口） |
| 403 | `activation_required` | 该手机号没有可用授权（**业务级，不带 `field`**） | 专属文案 + 「去激活」按钮 |
| 403 | `phone_mismatch` | 激活码绑的是另一个手机号（**必须带 `phoneMasked`**） | 专属文案，会念出绑定的号码 |
| 403 | `account_restricted` | 账号被限制 | 专属文案；**不清凭证、不给重试** |
| 403 | `plan_expired` | 套餐到期 | 专属文案（「套餐已到期，请续费后继续使用」） |
| 403 | `feature_not_entitled` | 该功能未授权 | 专属文案 |
| 403 | `model_not_allowed` | 该模型不允许用 | 专属文案（「当前套餐不能使用该模型，请换一个模型」） |
| 403 | `safety_blocked` | 内容安全拦截 | 专属文案（「内容未通过安全校验，请修改后重试」；服务端撤回能力见 §6.2） |
| 403 | `content_restricted` | 内容受限 | **与 `safety_blocked` 同一句文案**（两个码、一件事、一个动作） |
| 404 | `model_not_found` | 模型不存在 | 专属文案 —— **复用选择器那句「该模型已下架，请重新选择」**（与本地 `model_withdrawn` 同一句） |
| 409 | `request_in_progress` | **同一请求正在处理中，不要开始第二次模型调用** | 专属文案（「上一次请求还在处理中，请稍候再试」） |
| 409 | `duplicate_request` | 重复请求 | 专属文案 |
| 429 | `rate_limited` | 限流 | **登录/激活页**靠 `retryAfterSec` 倒计时（该字段在整个客户端只有这一个消费点）；**回合路径**的文案只说"稍后再试"，**不承诺倒计时** —— `turn_error` 事件上没有 `retryAfterSec` |
| 503 | `maintenance` | 维护中 | 专属文案（「服务维护中，请稍后再试」） |
| 5xx | `upstream_unavailable` | 上游故障（平台自己返回的 5xx） | 专属文案（档位横幅，给重试）—— 与拦截页那一档**同一句** |
| 5xx | `internal_error` | 平台内部错误 | 专属文案（「服务出错了，请稍后重试」） |

**「客户端会说什么」按路径分工，本文不复述那张表。** 码 → 文案的 owner 是两个前端文件：回合路径 `web/src/lib/turnError.ts`、控制面 `web/src/views/BlockedView.svelte`。把它们抄进本文会在下一次改文案时静默过期（`开发规范` §3.8 禁止第二份）。可以依赖的是这两条**性质**：

1. **控制面（§3.1–§3.8）专属文案只覆盖登录族**：上表的 `invalid_phone` / `invalid_code` / `code_not_sent` / `activation_invalid` / `activation_code_used` / `box_code_unknown` / `box_code_mismatch` / `activation_required` / `phone_mismatch`，加上三个档位（`upstream_unavailable`、`account_restricted`，以及本地码 `network_unavailable`）。**上表其余码、以及所有表外的码，在控制面落到本地通用句**（`发送失败，请重试`），并在控制台记一行 `no copy for business code "<码>"`。
2. **回合路径（§3.9）表内十五个码各有本地文案；表外的码回落服务端句子** —— 而从网关来的那个句子就是供应商的原始英文 JSON（`openai: HTTP 4xx: {"code":…}`）。这一条今天是**可见的**，所以**表外的码在回合路径上仍然是缺陷**：中台若要用表外的码，请提前告诉我们加映射。

**`unauthorized` / `token_expired` 刻意没有文案，且两条路径上不同。** 它们的正确答案是行为而不是句子：控制面（§3.1–§3.8）会刷新并重放一次，被拒才清本地凭证、回拦截页，且**不显示错误**；**网关（§3.9）两件事都不做**，见 §2.5 与 §3.9 的说明。回合路径上这两个码在 `turnError.ts` 里是**显式缺席**的 —— 给它们一句文案等于叫用户重试一次注定失败的回合。

**没有 `code` 的失败体会被降级**：5xx → `upstream_unavailable`，4xx → `internal_error`。所以 `code` 不能省。

**客户端本地产生的码**（中台**不要下发**，列在这里只为说明客户端也会用同一个命名空间）：
`network_unavailable`、`catalog_signature_invalid`、`policy_expired`、`bootstrap_stale`、`usage_pending`、`model_withdrawn`、`input_sensitive`。

### 2.5 客户端对状态码的处理（决定了中台能依赖什么）

| 情形 | 客户端行为 | 中台要注意 |
| --- | --- | --- |
| 2xx | 解 `data` | — |
| **304** | 只对 §3.6 / §3.7 两个条件请求有意义，表示「你手上的副本还是最新的」 | **对非条件请求回 304 是协议违规**，客户端按错误处理 |
| 401 / `unauthorized` / `token_expired` —— **控制面** | **恰好一次**刷新 + **一次**重放；刷新再被拒 ⇒ 会话结束，清本地凭证回拦截页 | 不要指望客户端重试第三次 |
| 401 —— **网关** | **不刷新、不重放**（见 §3.9 的说明） | 请在 access token 有效期内接受它；过期之后客户端只能靠重启或重新登录恢复，而**它不会自己告诉你这件事** |
| 403 / 其余 4xx / 5xx | **不重试**。`account_restricted` 不清凭证，其余档位按 §2.4 各自呈现 | **重试策略完全在中台侧**（`429` 之外，客户端不自动重发） |
| 连接不通 / 超时 | 记为 `network_unavailable`（本地码） | 30 秒超时；响应体最多读 1 MB |

## 3. 逐接口

### 3.1 `POST /auth/sms/send` —— 发登录验证码

**请求**

```json
{
  "phone": "13800000000",
  "purpose": "login",
  "clientRequestId": ""
}
```

| 字段 | 必须 | 说明 |
| --- | --- | --- |
| `phone` | 是 | 11 位大陆手机号 |
| `purpose` | 是 | 本版本**只发 `"login"`** |
| `clientRequestId` | 否 | **本轮恒为空串**（见 §6.3）。中台要容忍空串与缺失 |

**响应 `data`**

```json
{ "cooldownSec": 60, "expiresInSec": 600 }
```

| 字段 | 必须 | 说明 |
| --- | --- | --- |
| `cooldownSec` | 是 | 该手机号多少秒内不能重发。**界面据此倒计时**；为 0 时客户端用本地默认 60 秒 |
| `expiresInSec` | 是 | 验证码有效期。客户端目前只解析不展示，但请照发 |

**失败码**：`invalid_phone`(400)、`rate_limited`(429, 带 `retryAfterSec`)、`upstream_unavailable`(5xx)、`internal_error`(5xx)。

> `PQ23`：P0 不加人机验证；若日后要加，请求体预留 `captchaToken?`。

### 3.2 `POST /auth/login` —— 首次激活 / 后续登录（同一个入口）

**首次激活与二次登录走同一个接口**，靠是否带 `activationCode` / `boxCode` 区分 —— 中台**不要**按「该手机号有没有账号」自行判定，客户端可能在全新机器上登录一个已激活的账号。

**请求**

```json
{
  "phone": "13800000000",
  "code": "123456",
  "nickname": "小明",
  "activationCode": "BUDING-DEMO-0001",
  "boxCode": "BOX-DEMO-0001",
  "installId": "0b0e…",
  "clientRequestId": ""
}
```

| 字段 | 必须 | 说明 |
| --- | --- | --- |
| `phone` / `code` | 是 | 手机号 + 短信验证码 |
| `nickname` | 是（两次登录都给） | 用户昵称；首次激活时用它建账号，二次登录时也照发 |
| `activationCode` | **仅首次激活** | 一次性激活码 |
| `boxCode` | **仅首次激活** | 盒子编号。**与激活码是两次独立校验**：码要存在且未用过，盒子编号要是这个码当初配套的那个 |
| `installId` | 是 | 与请求头 `X-Install-Id` 同值，重复给是为了落库 |
| `clientRequestId` | 否 | 本轮恒为空串 |

**必须满足的约束**

1. **三个激活失败码必须分得开**：`activation_invalid`（码不存在）/ `activation_code_used`（码已用）/ `box_code_unknown`（盒子编号不认识）/ `box_code_mismatch`（编号与码不配套）—— 用户填错一位要能被准确地指出来，否则永久卡住。
2. **一个盒子编号可以配多个激活码**（一对多）：同一个 `boxCode` + 两个不同的未用激活码，**两次都要成功**。
3. **`activationCode` + `boxCode` 要么都给、要么都不给** —— 只给一个由中台按 `invalid_request` 拒绝。
4. **没有激活记录、也没带激活凭证** ⇒ `403 activation_required`（业务级，**不带 `field`**）。不要用 `activation_invalid` 代替：前者对应「去激活」，后者对应「激活码不对」，界面出路完全不同。
5. **`phone_mismatch` 必须带 `phoneMasked`**，且 HTTP 用 403。

**响应 `data`**

```json
{
  "accessToken": "at_…",
  "refreshToken": "rt_…",
  "accessTokenExpiresInSec": 7200,
  "account": { "id": "acct_001", "phoneMasked": "138****0000", "nickname": "小明" },
  "activation": {
    "status": "active",
    "activatedAt": "2026-09-16T01:00:00Z",
    "expiresAt": "2027-09-16T01:00:00Z",
    "boxCode": "BOX-DEMO-0001"
  }
}
```

| 字段 | 必须 | 说明 |
| --- | --- | --- |
| `accessToken` | 是 | 内存持有，**从不落盘** |
| `refreshToken` | 是 | 客户端落盘到 `data/credential.json`，随 `data/` 可复制 |
| `accessTokenExpiresInSec` | 是 | 秒 |
| `account.id` | 是 | 账号 id |
| `account.phoneMasked` | 是 | **已脱敏的字符串，中台负责脱敏**，客户端原样渲染（不再二次打码） |
| `account.nickname` | 是 | 昵称 |
| `activation` | 首次激活必须；二次登录也要给 | 见下 |
| `activation.boxCode` | 可缺 | **不脱敏、原样渲染**。老记录可能没有 ⇒ 界面显示「—」，**不拦截** |
| `activation.activatedAt` / `expiresAt` | 是 | RFC3339。`expiresAt` 用于算「剩余 N 天」，**到期只提示不拦截** |
| `activation.status` | 是 | 原样保存 |

**失败码**：`invalid_phone`、`invalid_code`、`code_not_sent`、`activation_invalid`、`activation_code_used`、`box_code_unknown`、`box_code_mismatch`、`phone_mismatch`、`activation_required`、`rate_limited`。

### 3.3 `POST /auth/refresh` —— 轮换 token

**请求**

```json
{ "refreshToken": "rt_…" }
```

**响应 `data`**

```json
{ "accessToken": "at_…", "refreshToken": "rt_…", "accessTokenExpiresInSec": 7200 }
```

**必须满足的约束**

1. **必须轮换**：旧的 `refreshToken` 在本次应答后立即失效。**返回同一个 refresh token 是违约**（客户端按轮换写了对账与断言）。
2. 被拒时用 **401 `unauthorized`**（或 `token_expired`）—— 这是「会话结束」的唯一信号，客户端据此清本地凭证回拦截页。
3. **网络/5xx 失败 ≠ 会话结束**：请务必用 5xx（或干脆不回），**不要用 401 表达「暂时查不到」**。用 401 表达临时故障会把一次断网变成强制重新登录。

### 3.4 `POST /auth/logout` —— 撤销当前 session

**请求**：无体，带 `Authorization: Bearer <accessToken>`（**access token 过期也允许先刷新再调**，客户端会自动做）。

**响应 `data`**：`null`。**不要发明 `{"revoked": true}` 之类的字段** —— 客户端只读 HTTP 状态。

**必须满足的约束**

撤销的是**整个 session**，不是当前这一个 token：

1. 该账号**所有已签发的 access token** 都不再被接受；
2. 该账号**所有已签发的 refresh token** 都不再能换到新的 —— 这是本接口存在的**全部理由**：威胁模型是「`data/` 被整份拷走」，拷走的那份在登出后不能继续刷新；
3. **不动激活记录、不动绑定手机号、不动余额** —— 登出不是反激活（用户再次登录必须还能回到已激活态）。

### 3.5 `GET /client/bootstrap` —— 启动拉取

**请求**：无体，带 Bearer。

**响应 `data`**：账号摘要 + 签名策略信封**并排**在同一个对象里（不是嵌套）：

```json
{
  "account": { "id": "acct_001", "phoneMasked": "138****0000", "nickname": "小明" },
  "activation": { "status": "active", "activatedAt": "…", "expiresAt": "…", "boxCode": "BOX-DEMO-0001" },
  "credits": { "balanceMicroCredits": 12500 },
  "policy": { "policyVersion": "…", "issuedAt": "…", "expiresAt": "…", "audience": "puddingbox", "keyId": "…", "catalog": { } },
  "policySignature": { "keyId": "…", "sig": "…" }
}
```

**`policy` 是内嵌的 JSON 对象，不是字符串。** 客户端按 `json.RawMessage` 接收，以保住中台签名覆盖的那串原始字节（见 §4.2）—— 请**原样内嵌**，不要二次序列化。

| 字段 | 必须 | 说明 |
| --- | --- | --- |
| `account` / `activation` | 是 | 同 §3.2 |
| `credits.balanceMicroCredits` | 是 | 微积分单位。**客户端不从这里写余额**（余额唯一写入路径是 §3.8），但字段请照发 |
| `policy` / `policySignature` | **可以整块缺席** | 缺席 = 「这个构建没有目录」，是**合法状态**，客户端不会报错，模型选择器空着 |
| `capabilities` | **不要发** | 见 §6.4（这是策略顶层的 `capabilities[]`，与 §4.3 里 `models[].capabilities` 不是同一个字段） |

### 3.6 `GET /catalog/models?knownVersion=<版本>` —— 条件刷新目录

**请求**：带 Bearer。`knownVersion` 是客户端**当前缓存里目录的版本**；客户端没有缓存时**不带这个参数**（要求无条件全量）。

**响应：两种合法「没变」的写法，任选一种**

| 写法 | 说明 |
| --- | --- |
| HTTP **304**（无响应体） | 推荐 |
| HTTP **200** + `data.unchanged = true` | 也支持 |

**响应：有新目录时**，与 bootstrap 同样的平铺信封：

```json
{
  "policy": { },
  "policySignature": { "keyId": "…", "sig": "…" },
  "unchanged": false
}
```

**必须满足的约束**

1. **版本单调递增**，且形状为 `YYYY-MM-DD` 或 `YYYY-MM-DD.<计数器>`（例：`2026-09-10.1`）。客户端按**数值**比较各段（不是字符串比较），**派发一个比缓存旧的版本会被判为「回滚攻击」并拒绝刷新（且不覆盖缓存）**。
2. 形状不符合时客户端退回字符串比较 —— 不会崩，但防回滚的能力变弱，**请不要用别的形状**。
3. `policy` 里有一个 `catalog.ttlSec`：客户端取「策略有效期」与「目录 TTL」**两者中较早的那个**作为过期时间。

### 3.7 `GET /dictionaries/sensitive?version=<版本>` —— 条件拉取合规词库

**请求**：带 Bearer。`version` 是客户端已验证并接受的缓存版本；没有缓存时不带。

**响应 304** = 「你手上的还是最新的」。

**响应 200 `data`**

```json
{
  "dictionary": { },
  "dictionarySignature": { "keyId": "…", "sig": "…" }
}
```

`dictionary` 是一个**被签名的 JSON 对象**（与 `policy` 同一套签名方案，见 §4）：

| 字段 | 必须 | 说明 |
| --- | --- | --- |
| `version` | 是 | 本次快照的版本。也是客户端下一次条件请求带的 `version` |
| `mode` | 是 | `"full"` 或 `"delta"` |
| `words` | `full` 时是 | 完整词表 |
| `baseVersion` | `delta` 时是 | **必须等于客户端缓存里的版本**，否则整个应答被丢弃（fail closed） |
| `add` / `remove` | `delta` 时是 | 增量。客户端会归一化去重后应用 |
| `sha256` | 是 | **应用之后完整词表**的 SHA-256。算法：`encoding/json` 紧凑编码成 UTF-8 JSON **数组**后取 SHA-256 的十六进制小写。**全量应答也要带最终快照的校验和**，这样 delta 不会被错误地应用到错误的基线上 |
| `keyId` | 是 | 必须与 `dictionarySignature.keyId` 一致 |
| `audience` | 是 | 见 §4.3 |
| `issuedAt` / `expiresAt` | 是 | RFC3339，**在签名覆盖范围内** |

**注意**：词库是**只读下发**。客户端本地还有一张用户自编词表，两者合并生效，但用户**改不动**中台下发的这一层。

### 3.8 `GET /credits/ledger` —— 读余额

**这是余额的唯一来源**。客户端**不扣减、不估算、不推导**：所有「回合结束 / 窗口重获焦点 / 打开积分页 / 手动刷新」都只是**触发这次调用的理由**，而不是携带数字的通道。

**请求**：无体，带 Bearer。

**响应 `data`**

```json
{
  "balanceMicroCredits": 12500,
  "entries": [ ]
}
```

| 字段 | 必须 | 说明 |
| --- | --- | --- |
| `balanceMicroCredits` | **是** | 缺失时客户端**拒绝这次应答**并保留旧值 —— 这是刻意的：「中台没给数字」和「中台说余额是 0」必须分得开（0 是最可能的合法值） |
| `entries` | 否 | 逐笔记账。客户端**不解析**，原样丢弃；请照发以便日后上屏 |

**单位**：微积分（整数）。**计费换算规则只在 §6.5 那一族里，本轮不涉及**。

### 3.9 `POST {gatewayHost}/v1/chat/completions` —— 模型网关

**协议：标准 OpenAI Chat Completions。** 客户端复用现成的 `internal/provider/openai` 适配器，**不写第二个解析器**。

**请求头**：`Authorization: Bearer <accessToken>`、`Content-Type: application/json`、`Accept: text/event-stream`（流式）。
**token 无效时用 401 `unauthorized`**。

> **⚠️ 这条路径上客户端不会自己刷新 token（与 §2.5 的控制面那一行不同，请勿混淆）。**
> 控制面的每个调用都走一次「401 → 刷新 → 重放一次」的包装；网关这一条**没有** —— 它是按 OpenAI 协议直接发出的请求，bearer 在每回合开始时从内存里现读，而客户端**只在内存里完全没有 token 时才补一次**（那是重启后的场景），对「有 token 但已过期」不作判断、收到 401 也不重放。
> 后果（客户端侧缺口，已登记为 `V-92`，不在本轮修）：**`accessTokenExpiresInSec` 一到，之后每一回合都会被拒**，用户看到「发送失败」，且**不重启或手动登出就不会自愈**。
> 对中台的实际要求只有一条：**不要比客户端更早判定 token 失效**（即按自己签发的 `accessTokenExpiresInSec` 接受它，不要另设更短的窗口）；如果联调期发现网关 401 频繁，请先告诉我们，而不是自行放宽 —— 这一档的表现今天取决于客户端，不取决于你们。

**请求体（客户端实际会发的字段）**

```json
{
  "model": "buding-cloud-pro",
  "messages": [ { "role": "user", "content": "你好" } ],
  "stream": true,
  "stream_options": { "include_usage": true },
  "tools": [ { "type": "function", "function": { "name": "terminal", "description": "…", "parameters": { } } } ],
  "reasoning_effort": "medium",
  "max_tokens": 4096
}
```

| 字段 | 说明 |
| --- | --- |
| `model` | **目录里的 `id`**（ASCII），不是供应商模型名。网关负责映射到真实模型 |
| `messages` | 标准 `role`/`content`；助手带工具调用时是 `tool_calls`，工具结果回来时是 `role:"tool"` + `tool_call_id` |
| `stream` | 产品路径**恒为 `true`** |
| `stream_options.include_usage` | **恒为 `true`** —— 请务必在流末发 usage 帧（见下），否则该回合的 token 数只能显示 0 |
| `tools` | 客户端会把自己可用的工具 schema 发上来；**是否允许由中台决定**（见 §6.3 的 `toolPolicy`） |
| `reasoning_effort` | 扁平字符串（`low`/`medium`/`high`/`xhigh`/`max`）。**「关闭」时字段整个缺席**，请把缺失当合法输入 |
| `max_tokens` | 可为空 |

**未知请求字段：请忽略，不要拒绝。** 客户端的字段集合会随版本增删，而中台网关也不该被客户端发版卡住。

**必须满足的响应形状**

1. **SSE**，每帧 `data: <json>` + 空行，最后 `data: [DONE]`。
2. 分片字段：`id` / `object` / `created` / `model` / `choices[].index` / `choices[].delta` / `choices[].finish_reason` / `usage`。
   - 正文增量：`choices[].delta.content`
   - 思考增量：`choices[].delta.reasoning_content`（**必须与正文分开**，客户端把两者渲染成两个不同的块）
   - 工具调用：`choices[].delta.tool_calls[]`，**按 `index` 归并**；`id` 与 `function.name` **只在第一个分片出现**，`function.arguments` 是**跨多个分片的 JSON 片段**，客户端负责拼接后再解析
   - `finish_reason`：普通结束 `"stop"`；要调工具 `"tool_calls"`（客户端适配器会归一成内部的 `tool_use`，中台按 OpenAI 拼法发即可）
3. **usage 帧**：在 `finish_reason` 之后、`[DONE]` 之前，发一帧 **`choices` 为空数组** 的 chunk，携带 `{"prompt_tokens","completion_tokens","total_tokens"}`。客户端只在这个位置读 usage。
4. **流中出错**（已经返回 200 之后）用 `data: {"error": {"message": "…", "type": "…"}}`，不要靠断流表达。
5. **拒绝整次调用**（余额不足、模型不允许、内容拦截等）要在**开始输出之前**用平铺错误信封 + 相应状态码应答：`402 insufficient_credits`、`403 model_not_allowed`、`403 safety_blocked`、`429 rate_limited` 等。
6. **校验顺序**：先鉴权（401），再资格/余额/模型校验，最后才是生成 —— 这样「没额度」是一个干净的信封，而不是一个死在半路的流。

**本轮明确不做、请不要发的事件**：`retract`（撤回已渲染内容）、账本终态帧。客户端目前**收不到它们的语义**：未知的顶层字段既不会让流失败，也不会被处理 —— **已渲染的内容不会被撤回，也不会有任何用户可见提示**。形态建议见 §6.2。

## 4. 签名方案（目录与词库共用）

两个被签名的工件 —— **策略目录**（`policy`）与 **合规词库**（`dictionary`）—— 用同一套方案。

### 4.1 算法

| 项 | 取值 |
| --- | --- |
| 算法 | **Ed25519**，detached signature |
| 签名对象 | **即将发到线上的那串 JSON 字节本身** |
| 编码 | 签名与公钥都是 **base64（标准，带 padding）** |
| 信封形状 | `{"policy": <对象>, "policySignature": {"keyId": "...", "sig": "..."}}` |

### 4.2 序列化要求（最容易踩的一条）

> **序列化一次，签那串字节，发那串字节。**

- 客户端验的是**到达时的原始字节**，不做规范化（不用 JCS / RFC 8785）。因此中台**不得**在签名之后重新序列化（不同库的字段顺序、空格、数字格式都可能变）。
- **必须关闭 HTML 转义**：Go 的 `json.Encoder` 默认把 `&` `<` `>` 转成 `\u0026` 等，那会改写字节并让签名失效。一个叫 `Tools & Agents` 的模型名就足以触发。
- **不要让中间层重新序列化 JSON**（压缩、美化、代理改写都会破坏签名）。

### 4.3 策略（`policy`）载荷

```json
{
  "policyVersion": "2026-09-16.1",
  "issuedAt": "2026-09-16T01:00:00Z",
  "expiresAt": "2026-09-16T02:00:00Z",
  "minClientVersion": "0.1.0",
  "audience": "puddingbox",
  "keyId": "prod-policy-2026-a",
  "catalog": {
    "version": "2026-09-16.1",
    "ttlSec": 3600,
    "models": [
      {
        "id": "buding-cloud-pro",
        "displayName": { "zh": "布丁专业版", "en": "Pudding Pro" },
        "modeIds": ["smart", "default"],
        "transport": "gateway",
        "capabilities": { "stream": true, "tools": true, "vision": true },
        "maxContextTokens": 128000,
        "maxOutputTokens": 8192,
        "eligible": true,
        "pricingVersion": "2026-09-a"
      }
    ],
    "modes": [
      { "id": "privacy", "defaultModelId": "buding-privacy-1" },
      { "id": "smart", "defaultModelId": "buding-cloud-pro" },
      { "id": "default", "defaultModelId": "buding-cloud-fast" }
    ]
  }
}
```

| 字段 | 必须 | 约束 |
| --- | --- | --- |
| `audience` | 是 | **恒为 `puddingbox`**（产品标识）。不符 ⇒ 客户端拒收（防跨产品重放） |
| `keyId` | 是 | 必须与 `policySignature.keyId` 一致，且必须是客户端**内置信任锚里存在的**那把 |
| `issuedAt` / `expiresAt` | 是 | RFC3339。**必须在签名覆盖范围内**（在范围内才能防篡改与撤销）。建议窗口 1 小时；客户端额外允许 ±2 分钟时钟偏差 |
| `catalog.version` | 是 | 同 §3.6 的版本单调性规则 |
| `catalog.ttlSec` | 是 | 目录自身的新鲜度声明 |
| `catalog.models[].id` | 是 | **稳定技术键，英文 ASCII，不随语言变**。会话绑定、网关请求、账本都用它 |
| `catalog.models[].displayName` | 是 | `{zh, en}` 两语言。**中台是唯一来源** —— 客户端不保留 id→名称表，请让改名只改这里 |
| `catalog.models[].modeIds` | 是 | 该模型属于哪些模式。**分组只此一处**，`modes[]` 里不重复列成员 |
| `catalog.models[].transport` | 是 | **只有 `"gateway"` 的模型会被投影进选择器**（别的值等于不上架） |
| `catalog.models[].eligible` | 是 | `false` = 保留在目录里但不下发。**界面提示「该模型已下架，请重新选择」而不是静默换模型** |
| `catalog.models[].capabilities` | 否 | **发不发都一样**：字段在 DTO 里，但**没有任何消费方**（登记为 `V-93`）—— 客户端不据此判据，**请勿让它成为任何行为的前提** |
| `catalog.models[].maxContextTokens` / `maxOutputTokens` | 否 | 同上：已建模、**零消费方**（`V-93`）。上下文与输出上限今天不由目录决定 |
| `catalog.models[].pricingVersion` | 否 | 同上（`V-93`）。计费换算不在本轮（§6.5） |
| `catalog.modes[]` | 是 | **只给三个 id 与顺序相关元数据**：`privacy` / `smart` / `default`（产品常量）。成员关系从 `models[].modeIds` 读。**未知的 mode id 会被忽略且不新建模式** |
| `modes[].defaultModelId` | 是 | 必须是同组成员，否则该组无默认 |
| `minClientVersion` | 否 | 客户端目前**不消费**（是否用于强制升级尚未拍板） |

### 4.4 客户端验签的失败分支（都 fail closed）

| 失败 | 客户端行为 |
| --- | --- |
| 无签名 / 窗口不可解析 / 本地没配受众 | 拒绝（`catalog_signature_invalid`），**不上屏、不覆盖缓存** |
| `keyId` 不在信任锚 | 拒绝。重试无用 —— 锚是编译进客户端的 |
| 签名不匹配字节 | 拒绝（可能是中间人改写，也可能是上面 §4.2 的转义问题） |
| `audience` 不符 | 拒绝 |
| 超出有效期窗口（含 ±2 min 偏差） | 拒绝 |
| 版本比缓存旧 | 拒绝，**且缓存一个字节都不动** |
| 词库 `sha256` 与最终词表不符 | 丢弃整次应答，保留旧缓存 |

**验签失败没有任何降级路径** —— 不会回落到本地内置模型或 `config.yml`。
