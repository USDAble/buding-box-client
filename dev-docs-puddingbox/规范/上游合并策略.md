# 上游合并策略

> 将上游变更安全带入本 fork 的操作规则。功能不为兼容性让步，但实现必须把下一次合并成本降到最低。

## 当前边界

当前指定的上游基线是 `origin/main`，产品集成目标是 `v1`。本仓库目前没有 `upstream` remote；不要臆造 remote、修改 remote 或把本地 `main` 当作额外必经阶段。

更换上游来源、remote 或集成目标属于仓库级决策，必须由维护者确认后才修改本策略和实际 Git 配置。每个上游合并 PR 都应写明合入的完整 ref 与 commit SHA。

## 不可变规则

- 上游同步是独立变更，不与产品功能、重构或文档整理混在同一 PR。
- 将上游带入 fork 使用 `merge`，绝不对已存在的 fork 历史执行 `rebase`。功能分支仍按 `.octorules`、`CLAUDE.md` 的常规流程合入 `v1`。
- 从干净、最新的 `v1` 创建专用合并分支；不在产品功能分支上做上游合并。
- 冲突解决的目标是同时保留上游的新行为和 fork 的已确认行为，而不是机械地“选我方”或“选上游”。

## 合并流程

```bash
git fetch origin --prune
git switch v1
git pull --ff-only origin v1
git switch -c merge/upstream-YYYYMMDD
git merge origin/main
```

解决冲突后先检查变更，再运行：

```bash
make gate
```

若改动触及发包路径、嵌入资产、桌面构建或平台相关行为，再运行相应的构建/产物检查，例如 `make desktop-portable`、`make portable-check` 或 `make test-production`。命令因本机平台不可执行时，PR 必须说明未覆盖的范围和由何处补验。

通过后以独立 PR 合入 `v1`。PR 标题使用 `chore(upstream): merge origin/main @ <short-sha>`；描述中列出上游 ref/SHA、冲突文件、保留的 fork 行为和验证结果。

## 解决冲突的判断顺序

1. 先理解上游改动解决的用户问题或缺陷；不能说明时不要急着恢复 fork 旧代码。
2. 能把 fork 逻辑移入新增文件、适配器或独立区块的，就收口；上游文件只留下最薄的调用点。
3. 清单型文件的 fork 新增项集中在独立、带 `OCTO-FORK` 原因的区块，通常保留双方再放回文件末尾。
4. 上游重构了被 fork 包装的函数时，按新入口重建适配；不要把旧补丁原样贴回去。
5. 上游删除或替换了 fork 改过的文件时，暂停并确认功能是已被上游吸收、迁移还是仍需保留；不能默认复活旧文件。

每个保留下来的 fork 改动都遵守 `开发规范.md` 的标记规则。若必须删除上游文件（无法留下标记），PR 描述必须写明删除原因、替代物以及如何确认它不会再进入产物；不要在本策略维护删除清单或合并日志。

## 降低下一次合并成本

- 新逻辑优先放 fork 新文件；修改上游文件时只做必要接线。
- 需要停用上游能力时，优先让它不可达而非删除代码。确实要删除时，按上一节说明替代和产物影响。
- 不改变广泛调用的上游公开签名来实现 fork 行为；优先使用适配器、配置或稳定入口。
- 数据路径、品牌、用户状态和降级逻辑保持单一所有者，避免在多个上游文件复制 fork 判断。
- 上游变更被拒绝或延后时，保留一次清晰的 PR 决策即可；不要把已完成事件沉积成长期文档台账。

## 合并完成定义

一次上游同步完成，意味着：上游目标 ref 已被实际合入；冲突的产品行为有明确结论；受影响的 `OCTO-FORK` 标记和守卫仍有效；`make gate` 及必要的构建检查通过；PR 不混入无关改动；合并来源和验证证据留在 Git 提交与 PR 中。

## 非目标

- 不规定上游发布频率或强制固定节奏；安全修复和功能依赖由维护者决定优先级。
- 不替代 `开发规范.md` 的工程设计规则，也不记录历史合并日志、删除清单或待办表。
