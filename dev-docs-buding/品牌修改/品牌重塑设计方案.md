## 3. 背景与目标

这个仓库实际包含完整的 `octo-agent` 产品链路，而不只是一个客户端：Go CLI/Agent、Web UI、Wails 桌面端、Capacitor 移动端、Relay、安装包、官网、博客、文档、Release 和内置帮助都可能暴露旧身份。

目标不是简单替换一个 Logo，而是让新用户在以下接触点看到一致的新产品身份：

- 启动、登录、首次引导和主界面
- Web 浏览器标签页、favicon、Header、Sidebar、设置页和 About
- 桌面窗口、托盘、原生通知、安装器和系统应用列表
- Android/iOS 应用名、图标、启动画面、配对和设置页面
- CLI help、版本输出、错误提示、升级提示和默认帮助
- 官网、博客、README、下载页、安装脚本和 Release artifact
- 内置技能、产品帮助、默认提示词和对外说明

同时必须保证：

- 现有用户的数据、脚本、会话和配对能力不因品牌改造突然失效。
- 真实版权、许可证、第三方依赖归属和来源说明继续保留。
- 后续可以分阶段迁移 CLI、数据目录、环境变量、协议和系统包标识。

## 4. 明确采用的品牌架构

### 3.1 三层身份

| 层级 | 作用 | 当前处理 |
|---|---|---|
| 展示身份 | 用户直接看到的名称、Logo、文案、官网和安装包名称 | 采用新品牌 |
| 兼容身份 | 旧 CLI、目录、环境变量、协议、模块和跨端约定 | 暂时保留 |
| 法律与归属身份 | 版权、许可证、第三方声明、真实团队和来源 | 必须真实保留 |

当前阶段要让展示身份统一，但不把兼容身份误当成可随意删除的文案。代码中出现的 `octo` 需要先分类，不能全局替换。

### 3.2 当前阶段与未来阶段

#### 当前阶段：新品牌展示 + 兼容运行

可以改：

- 中文/英文产品显示名
- Logo、favicon、桌面和移动端图标
- Web、桌面、移动端的产品文案
- About、官网、博客、文档和下载页
- 安装包名称、系统显示名称、Release artifact 名称
- 用户可见的 CLI help、启动日志、升级提示和内置帮助
- 新官网、文档、下载和反馈入口

暂时保留：

- `octo` CLI 命令及其脚本兼容
- `~/.octo` 数据目录
- `OCTO_*` 环境变量
- `octo-ui` 内部协议标识
- `octo-pair` 配对协议标识
- 现有 API/WS 路由、帧格式和会话数据结构
- `github.com/open-octo/octo-agent` Go module 路径
- 已发布客户端能够识别的旧深链、配对码和升级通道

#### 未来阶段：完整身份迁移

未来可以按《完整身份迁移预留方案》逐项迁移：

- 新 CLI 命令和可执行文件
- 新 Go module/import 路径
- 新数据目录及旧目录迁移
- 新环境变量前缀
- 新 API/WS/配对协议标识
- Capacitor、Android、iOS 的 Bundle/Application ID
- URL Scheme、Universal Link 和 App Link
- macOS Bundle ID、LaunchAgent、pkg identifier
- Windows AppUserModelId、安装目录和卸载标识
- Release 仓库、下载域名、升级地址和镜像路径

## 5. 品牌资料在执行前必须确认

代码动手前，产品负责人需要提供一份最终品牌资料，至少包括：

1. 中文产品名和英文产品名。
2. 产品短描述、长描述和一句话定位。
3. 团队或公司真实名称、真实介绍和联系方式。
4. 官网、文档、下载、反馈、隐私和安全页面地址。
5. 版权主体、许可证策略和第三方归属说明。
6. Logo 源文件、浅色/深色版本、单色版本、favicon、桌面图标和移动端图标。
7. 是否保留 `octo` 作为隐藏兼容命令，是否增加新 CLI 别名。
8. 当前版本和未来版本的升级地址、Release 仓库及签名策略。
9. 是否在未来迁移数据目录、协议和系统包标识。

未确认的品牌资料不应被写成虚构的团队、邮箱、域名或版权信息。

## 6. 统一品牌配置建议

实施时不要把新名称散落在组件和脚本中，建议建立集中配置层，至少覆盖：

- 产品显示名：中文、英文、短名
- 产品一句话描述和 About 长描述
- 官网、文档、下载、反馈、隐私和安全链接
- 当前展示版本和兼容协议版本
- Logo、favicon、桌面图标、移动图标和启动画面资源路径
- 新品牌 ID 与旧兼容 ID 的映射
- 当前阶段是否展示原项目来源说明
- 版权、许可证和第三方归属入口

配置层只负责统一引用；旧 CLI、数据目录、协议等兼容常量必须单独命名，不能与展示名称共用一个变量。

推荐概念上区分：

- `display identity`：面向用户的展示身份
- `compatibility identity`：旧名称、旧路径和旧协议
- `legal identity`：真实的版权、许可证和归属

## 9. 文案与 About 原则

- 产品定位要描述真实能力，不夸大团队、技术或服务承诺。
- 团队名称、联系方式、官网和版权主体必须可验证。
- 许可证和第三方归属不能隐藏或删除。
- 可以使用新品牌作为产品名称，但不能把原项目来源伪装成虚构的原创经历。
- 中文和英文版本要同步维护，不允许只改其中一套。
- 所有用户可见旧名称都要进入扫描清单；代码内部兼容常量则单独登记并说明保留原因。

## 10. 当前阶段验收标准

当前阶段完成时，应满足：

- 新品牌在 Web、桌面、移动端、官网、安装包和下载页一致。
- 主界面、首次引导、设置页、About、通知、错误和升级提示无遗漏旧展示名。
- 系统应用列表、托盘、窗口、快捷方式和安装器显示新品牌。
- 新旧配对流程和已有用户数据仍可用。
- 旧 CLI、旧数据目录、旧环境变量和旧协议兼容性有自动化或手工验证记录。
- Release artifact、升级地址和安装脚本指向正确的新渠道。
- About、许可证、第三方声明、版权和来源信息真实完整。
- 全仓库旧名称扫描结果已经分类：展示残留必须清零；兼容残留必须有登记和测试。

## 11. 不在本轮执行的事项

本轮不修改以下内容，只做设计预留：

- Go module 路径和全部 import 迁移
- `~/.octo` 到新目录的真实搬迁
- `OCTO_*` 环境变量的真实废弃
- API/WS/配对协议重新命名
- Android/iOS/macOS/Windows 标识的破坏性切换
- Release 仓库和升级域名的强制切换

这些事项必须按《完整身份迁移预留方案》单独立项。
