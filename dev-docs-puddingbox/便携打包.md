# 便携打包与交付

写作参照：`dev-docs/relay-runbook.md`。沿用其“交付目标 → 生成路径 → 自检 → 现场验收”的结构；本文以 `Makefile`、`scripts/package-*`、`packaging/portable` 和 CI 工作流为事实源。

> 便携交付不是“有一个可执行文件”而已，而是一份可复制、可移动、可自检的运行单元。它必须带着正确目标平台的程序与资源，并把用户业务数据限定在同级 `data/`；不能借用构建机状态、本机用户目录或未知网络资源来显得可用。

## 范围与非目标

本文件说明 Windows 便携目录、macOS `.app`、Linux AppImage 的实际打包路径、预检、自检和现场验收。具体的测试/生产出包命令和 Profile 切换步骤见 [打包操作手册](打包操作手册.md)。数据根规则见 `便携数据根.md`，启动/冻结行为见 `启动与生命周期.md`，品牌事实源见 `品牌与标识.md`，生产 Profile 见 `运行时Profile配置.md`。

不包含安装器迁移、系统服务注册、用户 home 初始化、代码签名/公证的发布决策，也不把“在开发机运行过”写成便携验收。

## 交付矩阵与当前边界

| 平台             | 当前产物                                | 构建入口                                             | 主要特点                                             |
| ---------------- | --------------------------------------- | ---------------------------------------------------- | ---------------------------------------------------- |
| Windows amd64    | `dist/<portableDirName>/` 与同名 zip  | `make desktop-portable`                            | 主交付物；可从任意主机交叉编译。                     |
| macOS universal  | `Pudding Box.app`                     | `make desktop-app` / `make desktop-portable-all` | 原生 macOS 构建，合并 Intel 与 Apple Silicon slice。 |
| Linux            | 当前脚本输出`Octo-<arch>.AppImage`    | `make desktop-appimage`                            | 原生 Linux 构建；依赖宿主 GTK4/WebKitGTK。           |
| Android (移动端) | `app-debug.apk` / `app-release.apk` | `cd mobile/android && ./gradlew assemble*`         | 基于 Capacitor 封装的薄客户端，含 Noise 原生插件。   |
| iOS (移动端)     | `App.app` / Archive                   | `cd mobile && xcodebuild` / `npx cap open ios`   | 基于 Capacitor 封装的薄客户端，含 Swift 原生插件。   |

Windows 目录名、exe 名、使用说明中的产品名称取自 `branding/brand.json`。macOS `.app` 文件名也取英文产品名；测试 Profile 另输出 `Pudding Box-test.app`。安装器与 CI 均消费同一派生名称，包内 `CFBundleName` 和 `CFBundleDisplayName` 在打包时与品牌配置核对。历史 `Octo.app` 不自动删除，已有 Dock 固定项需由用户移除并重新固定新应用；Bundle ID、包内可执行文件及发布 ZIP `Octo-darwin-universal.zip` 暂时不变，以保留兼容路径。Linux 产物名仍含历史 `Octo` 字面量，跨平台统一留待单独确认。

所有正式交付路径必须带 `product_production`：它选择生产 Profile，并排除开发专用实现。漏掉该 tag 会得到一个可运行但信任边界错误的开发包；`release-profile-guard` 因此将其作为硬失败。

测试交付使用另一组明确入口：`make desktop-test-portable`、`make desktop-test-app` 和 `make desktop-test-appimage`。它们编译 `product_test`，产物名带 `-test`，不会覆盖生产产物。默认测试 Profile 由测试版程序在本机启动中台替身；测试中台就绪后，先更新 `internal/productprofile/profiles/testing.json` 为 HTTPS 测试地址、测试公钥和 `startLocalStandin: false`，再使用原命令重建。生产命令始终只读取 `production.json`，不包含也不启动替身。

## Windows 便携目录的组成

`scripts/package-portable.mjs` 默认目标为 `windows/amd64`，最终将下列内容放入 `dist/<portableDirName>/`，并生成 `dist/<portableDirName>-windows-amd64.zip`。zip 内仍保留最外层目录，解压即可整体复制。

| 内容                                                                   | 来源与规则                                                                                                              |
| ---------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `<exeName>`                                                          | 在`cmd/octo-desktop` 内以 `embedrg product_production`、`-trimpath`、GUI subsystem 和注入的 Version/Commit 构建。 |
| Web UI、ripgrep                                                        | 编译/嵌入到桌面二进制；先按 Windows 目标执行`rg-embed`，不能重用其他平台的 payload。                                  |
| `data/sensitive-words.txt`、`data/config.yml`、`data/workspace/` | 从`packaging/portable/data` 复制的出厂模板。`workspace/.gitkeep` 仅用于在版本库保留空目录。                         |
| `使用说明.txt`                                                       | 从模板渲染；名称和 exe 占位符由品牌配置替换。                                                                           |
| `bin/uv.exe`（可选）                                                 | 若已预置`dist/bundled-tools/windows-amd64/uv.exe` 则复制；缺失时构建给出警告，不伪造该工具。                          |

不预置 `chat-modes.json`：模型列表来自已签名的中台目录，重新把旧的固定模型写入数据模板会制造第二个事实源。WebView2 loader 已在桌面二进制构建时嵌入，不随目录另带 DLL；Windows 主机若缺少 WebView2 Runtime，首次启动仍会提示安装，这是平台运行时前提而非包内遗漏。

首次启动可以在同级 `data/` 创建状态、会话、凭证和其它子目录，但不得以 home、当前工作目录或构建机目录作为业务数据 fallback。拷贝、移动或在 U 盘上运行时，数据根随这个交付单元移动。

## macOS 与 Linux 的实际组装

macOS 打包脚本先分别为 `amd64`、`arm64` 获取对应 ripgrep 并构建带 `embedrg product_production` 的 slice，再以 `lipo` 合并为通用桌面二进制，写入 `.app/Contents/MacOS`。`Info.plist` 的版本字段和显示名都会被自检；图标可复制入 Resources；CLI 与 `uv` 仅在相应环境变量提供文件时作为可选资源加入。脚本使用 ad-hoc signing 使本地 bundle 可运行，Developer ID 签名与公证仍是独立发布步骤。

### macOS 桌面端打包操作步骤

#### 1. 前置依赖

- macOS 环境并安装 Xcode Command Line Tools（包含 `clang`、`lipo`、`plutil`、`codesign` 等）；
- Go 1.25+ 与 Node.js 22+（`make node-check` 校验通过）。

#### 2. 核心打包命令

在项目根目录下执行：

```sh
# 生产环境 Universal .app 包（选择 product_production，连接正式中台）
make desktop-app

# 测试环境 Universal .app 包（带 -test 后缀，连接测试中台或启动本地替身）
make desktop-test-app

# 仅编译本地单架构裸二进制（非 .app 包，输出到 ./octo-desktop 用于快速调试）
make desktop
```

#### 3. 产物路径与规格

- **产物位置**：项目根目录下的 `Pudding Box.app`（测试包为 `Pudding Box-test.app`）。
- **通用双架构 (Universal Binary)**：由 `scripts/package-desktop-macos.sh` 自动完成编译。脚本分别为 Intel (`x86_64`) 与 Apple Silicon (`arm64`) 构建 slice，并调用 `lipo -create` 压制合并，实现多架构 Mac 原生无损运行。
- **品牌元数据同步**：包内 `Info.plist` 的 `CFBundleName` 与 `CFBundleDisplayName` 在构建时直接根据 `branding/brand.json`（经 `packaging/macos/scripts/brand.sh`）派生更新并做一致性校验。
- **签名机制**：
  - **本地开发/测试**：脚本末尾自动执行 Ad-hoc 本地签名（`codesign --force --deep --sign - "Pudding Box.app"`），双击即可运行无需开发者证书。
  - **正式对外发布**：发布机通过 Developer ID Application 证书进行深层签名（`codesign --options runtime ...`），打成 ZIP 后提交苹果进行 Notary 公证（`xcrun notarytool submit`）。

Linux 脚本本地编译带 `embedrg product_production` 的二进制，组装 AppDir 后以 `appimagetool` 输出与主机架构匹配的 AppImage。GTK4/WebKitGTK 6.0 不被塞入 AppImage，AppRun 在目标机预检并提示缺失依赖；因此它是便携应用，而非对任意 Linux 系统的无条件静态包。

## 移动端 App 打包步骤 (Android / iOS)

移动端工程位于 `mobile/` 目录，采用 Capacitor 壳工程将 Web 前端打包，并通过原生插件 `OctoTunnel`（Kotlin / Swift）接入 Noise XX 加密隧道与配对协议。

### 1. 环境准备与前提

- **Node.js**：Node.js 22+（`make node-check` 验证通过）；
- **Android 环境**：
  - Android SDK、Build-Tools 与平台工具；
  - **Java 21**：Android Gradle 插件要求 JDK 21。如果构建报错 `错误: 无效的源发行版：21`，须通过环境变量指定（如 Android Studio 自带的 JBR）：

    ```sh
    export JAVA_HOME="/Applications/Android Studio.app/Contents/jbr/Contents/Home"
    ```

    或在 `mobile/android/gradle.properties` 中固定配置：
    ```properties
    org.gradle.java.home=/Applications/Android Studio.app/Contents/jbr/Contents/Home
    ```
- **iOS 环境**：
  - macOS 宿主系统与 Xcode（需已下载 iOS SDK 与 iOS 模拟器组件）。

### 2. 标准组装流程

在仓库根目录下执行前端构建，然后进入 `mobile/` 目录装配原生工程：

```sh
# 步骤 1：构建 Web 前端产物并注入移动端打包目录
make web-build
cd mobile
npm install
npm run bundle-web

# 步骤 2：生成原生工程目录（初次或重新生成时执行，android/ 与 ios/ 目录已 gitignore）
npx cap add android
npx cap add ios

# 步骤 3：注入原生插件与品牌图标 (wire-native)
# --local 用于开发/模拟器环境开启明文支持；生产发布时去除 --local
npm run wire-native -- --local

# 若仅刷新品牌生成的最新全套启动图标，可执行：
node scripts/wire-native.mjs --icons-only

# 步骤 4：同步 Web 资源到原生工程（后续每次修改 web/ 前端代码后必须执行）
npx cap copy
```

### 3. 原生平台编译与出包

#### Android (APK)

```sh
# 进入 android 目录并确保 JAVA_HOME 为 Java 21
cd android
./gradlew assembleDebug

# 生成的 Debug APK 产物路径：
# mobile/android/app/build/outputs/apk/debug/app-debug.apk

# （可选）直接安装到已连接的真机或启动的模拟器：
adb install -r app/build/outputs/apk/debug/app-debug.apk

# 若需打包正式 Release 包（需在 build.gradle 配置签名）：
./gradlew assembleRelease
```

#### iOS (App / Simulator / Archive)

```sh
# 方式 A：命令行编译 Simulator 调试版本
xcodebuild -project ios/App/App.xcodeproj -scheme App \
  -destination 'platform=iOS Simulator,name=iPhone 15 Pro' build

# 方式 B：通过 Xcode 打开项目进行设备调试、证书签名与 Archive 归档
npx cap open ios
```

### 4. 联调配对

在主机启动服务并开启隧道配对：

```sh
puddingbox serve --tunnel
```

手机端打开 App 扫描终端输出的二维码即可完成 Noise 密钥交换并建立端到端加密连接。

## 构建顺序与预检

Windows 的推荐入口：

```sh
make desktop-portable
```

本机中台替身的测试交付使用：

```sh
make desktop-test-portable
```

该目标先生成 Web UI、校验品牌、按 Windows 目标嵌入 ripgrep，再调用打包脚本。macOS/Linux 打包各自也先运行 `scripts/preflight.mjs`。预检有两层：

| 层级   | 作用                                                                      | 结果                                                   |
| ------ | ------------------------------------------------------------------------- | ------------------------------------------------------ |
| 硬失败 | 数据根规则、发布 Profile tag、复用边界、规范/AGENTS 同步、敏感词规范。    | 任一失败拒绝出包。                                     |
| 告警   | 生产 Profile 是否仍为`.invalid` 占位、与上游基线的差异、fork 标记巡检。 | 打印告警，不中断内部测试包或尚未配置真实控制面的构建。 |

因此 `release-config-guard` 的占位 host/空可信键告警不能被读成“发布已就绪”：当前生产 Profile 结构合法且故意不可连接。真正面向用户的发布必须先由发布负责人提供真实地址和可信公钥，再将该告警清零。

## Windows 产物自检

组装完成后，打包脚本不直接 zip，而是先对目录做产物级检查：

- 只有一个顶层 exe，且文件名、GUI subsystem、VERSIONINFO 产品名与描述均匹配品牌配置；
- 没有 `node_modules`、`.git`、source map、PDB 等开发残留；
- `data/`、两个模板文件和 `workspace/` 均存在；
- 二进制不含开发本地模型的固定回复或 PII 日志路径，证明生产 tag 实际生效；
- 不含构建仓库/用户 home 的绝对路径；`-trimpath` 是主防线，第三方随包 payload 按完整字节归属，不把供应商路径误报为本项目泄漏；
- 每个随包原件的文件头符合目标平台（Windows `MZ`、Linux ELF、macOS Mach-O），阻止把另一个平台缓存的 ripgrep/工具装入交付物；
- 记录总大小，超过基线 20% 发出告警而非静默变化。

`portable-check` 运行这条脚本及 PE 解析、Web 资源清理和预检的单元测试；它验证检查机制本身，不会生成发布包。

## CI 与现场验收

Portable 工作流在 Windows 上构建 Web UI、测试完整服务只写入隔离数据根、准备 `uv.exe` 和 Windows ripgrep、打包并上传 zip。macOS job 构建 `.app`；对应桌面工作流负责其它平台的原生构建验证。CI 证明构建与自检可重复，不能替代可移动介质上的用户路径。

交付验收至少覆盖：

1. 在一台无既有产品数据的机器/临时目录解压或复制产物并启动；确认没有借用主机用户目录。
2. 创建会话、完成允许的登录流程、正常退出并重开，确认数据从产物同级 `data/` 读取。
3. 关闭应用后整体移动目录或 U 盘路径，再启动并确认同一数据继续可用。
4. 运行中移除可移动介质，确认写入被冻结且有明确反馈；恢复到同一路径后才允许恢复，详见数据根文档。
5. 在目标平台确认 WebView2（Windows）或 GTK/WebKit（Linux）的外部运行时前提、图标、版本和启动体验。

## 失败处理与变更边界

资源缺失、目标平台不匹配、Production tag 未生效、品牌/版本元数据不符、数据根不可用或嵌入 payload 错平台时，构建或启动必须明确失败；不能从本机路径、用户目录、默认模型或网络下载悄悄补齐。

改变数据模板、交付目录布局、可选工具、平台依赖、产物名、签名或公证策略均会影响既有用户和发布通道。此类变更须先说明兼容性、迁移/回滚、目标平台验证和 CI artifact 影响，经确认后再实现。
