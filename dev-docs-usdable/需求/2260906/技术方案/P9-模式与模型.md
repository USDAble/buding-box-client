## 1. 目标与非目标

**目标**

1. 选择器改为「先模式、后模型」两级，选中值仍是具体模型。
2. 模式是**会话属性**，持久化在会话上。
3. 预置 §5.6.3 的四个本地确定性模型与三个分组。
4. 名单为空时给说明，**绝不弹配 Key 向导**。

**非目标**

- 不做隐私模式的提示与 PII（P10）。
- 不做本地确定性模型的实际回复（P11）。
- 不改上游的 endpoint / model 配置体系（§5.6 规则 1：名单由配置提供）。

## 3. 设计

### 3.1 模式是什么

模式（mode）= **模型的分组标签** + **会话上的一个属性**。三个值：`privacy` / `smart` / `default`。

需求 §5.6 表格里「智能」与「默认」的**发送策略完全相同**（都只过合规敏感词），差别仅在名单与对用户的含义。所以模式在代码里只有两个作用：

1. 决定选择器里能选哪些模型；
2. `privacy` 时额外触发 PII 脱敏与三处提示（P10）。

不要为「智能」写任何特殊分支 —— 它和「默认」在发送路径上是同一条代码。

### 3.2 配置来源

需求 §5.6 规则 1：「名单由配置提供，不写死在页面。三个名单允许重叠。」

新增 `data/chat-modes.json`（数据根内，用户可改）：

```json
{
  "schemaVersion": 1,
  "modes": [
    { "id": "privacy", "models": ["buding-local-general", "buding-local-fast"],
      "defaultModel": "buding-local-general" },
    { "id": "smart",   "models": ["buding-cloud-plus", "buding-cloud-pro"],
      "defaultModel": "buding-cloud-plus" },
    { "id": "default", "models": ["buding-local-general", "buding-local-fast",
                                  "buding-cloud-plus", "buding-cloud-pro"],
      "defaultModel": "buding-cloud-plus" }
  ]
}
```

- 模式 id 与展示名分离：id 固定 ASCII，展示名走 `i18n.ts`（`mode.privacy` / `mode.smart` / `mode.default`），随语言切换。
- 模型 id 固定（`buding-*`，需求 §5.2.4「标识符例外」，**不随品牌名改**）；展示名同样走文案层。
- 文件缺失 → 用内置默认（内容等同上表），与敏感词词库同样的兜底策略。
- 首次启动时把这份内置默认**写出到数据根**，这样用户能看到并编辑它（需求「用户可改配置」）。

模型本身仍走上游 `config.yml` 的 endpoint/model 体系 —— `chat-modes.json` 只是分组映射，不重新定义模型。四个本地确定性模型由 P11 注册进 endpoint 体系。

### 3.3 选择器交互

```
点模型芯片
  ┌─────────────────────────────┐
  │ 🛡 隐私        本地通用  ✓  │  ← 一级：模式；展开显示该模式下的模型
  │               本地极速      │
  │ ─────────────────────────── │
  │ ⚡ 智能        云端智能     │
  │               云端旗舰      │
  │ ─────────────────────────── │
  │ ○ 默认         本地通用     │
  │               本地极速      │
  │               云端智能      │
  │               云端旗舰      │
  └─────────────────────────────┘
```

采用**分组展开**而不是两次点击的级联菜单：级联需要用户点两次才看得到模型，而需求 §5.6 说「先模式后模型，选中值仍是具体模型」，分组展开一次就能看全，也更贴近上游现有的「按 endpoint 分组」结构 —— 改动最小。

- 当前模式的分组默认展开，其余折叠。
- 某模式下无模型：该分组展开处显示「该模式下暂无可用模型」（需求 §5.6 规则 2），**不显示「管理」跳转、不弹向导**。
- 底部保留上游的「管理」入口跳完整设置（这不是配 Key 向导，是已登录用户的正常设置入口）。

### 3.4 会话属性

模式存在会话上。`internal/agent/session.go` 已有 `SetModelConfig`（`:803`）、`SetWorkingDir`（`:852`）这类「追加一条 meta 记录」的模式，照抄新增 `SetChatMode`：

```go
func (s *Session) SetChatMode(mode string) error
```

追加 meta 记录而不是重写整个文件 —— 与上游既有做法一致，也符合 P1 的增量落盘要求。

规则映射：

| 需求 §5.6 规则 | 实现 |
|---|---|
| 4 每个模式可指定默认模型 | `chat-modes.json` 的 `defaultModel` |
| 5 新会话模式 = 个人中心「新会话默认模式」 | 建会话时读 `prefs.defaultChatMode`（P3 schema，P5 提供 UI），出厂 `default` |
| 6 仅改当前会话，不影响其它会话、不改默认值 | 选择器只调 `SetChatMode` + `SetModelConfig`，不碰 `prefs` |
| 7 中途改模式只作用于之后的消息 | 天然满足：模式在发送时读当前值，已有气泡不重算 |
| 8 智能是否允许云端体现在名单里 | 配置驱动，代码无分支 |

### 3.5 彻底关掉配 Key 向导

需求 §5.1.2-3「**禁止出现**（含名单被删空、开发调试）」，所以不能只是「有模型时不弹」，必须无条件关闭：

- `App.svelte:213` 的 `phase === 'key_setup'` 分支：桌面端永不进入。
- 判定放服务端：`GET /api/product/state` 返回 `"suppressOnboarding": true`，前端据此跳过。桌面服务恒为 true —— P1 统一数据根后不再有「模式」之分，`octo-desktop` 这个二进制就是便携产品本身。
- `FirstRunSetup.svelte` **不删除**（上游文件，删了会产生合并冲突），只是到不了。
- 名单空时的展示由 §3.3 覆盖，路径上不经过向导。

## 4. 接口与数据结构

```go
// internal/chatmode/chatmode.go
package chatmode

type Mode struct {
    ID           string   `json:"id"`           // privacy | smart | default
    Models       []string `json:"models"`       // 模型 id 列表
    DefaultModel string   `json:"defaultModel"`
}

type Config struct {
    SchemaVersion int    `json:"schemaVersion"`
    Modes         []Mode `json:"modes"`
}

// Load 读数据根内的 chat-modes.json；缺失则返回内置默认并写出一份。
func Load(path string) (Config, error)

func (c Config) ModeByID(id string) (Mode, bool)
// ModesForModel 反查一个模型属于哪些模式，供芯片展示当前分组用。
func (c Config) ModesForModel(modelID string) []string

const (
    ModePrivacy = "privacy"
    ModeSmart   = "smart"
    ModeDefault = "default"   // 分组名「默认」，不是「系统缺省值」的泛称
)
```

```
GET /api/product/chat-modes
    → { "modes": [ { "id": "privacy", "models": [
          { "id":"buding-local-general", "compositeId":"buding::buding-local-general" } ],
          "defaultModel": "buding-local-general" } ] }

PUT /api/sessions/{id}/chat-mode   { "mode": "privacy" }
```

前端：


## 6. 测试

**Go 单测**

- `Load` 缺文件 → 内置默认 + 文件被写出。
- `Load` 文件损坏 → 内置默认，不 panic，不覆盖用户文件（保留原文件并旁路，避免吞掉用户手改的内容）。
- `ModesForModel("buding-cloud-plus")` → `["smart","default"]`，不含 `privacy`。
- 出厂配置断言：**隐私列无云端项、智能列无本地项**（需求 §8 明确验收此条，写死断言）。
- `SetChatMode` 追加 meta 记录，重新加载会话后模式仍在。

**前端单测**

- 模式空列表 → 渲染「该模式下暂无可用模型」，且 DOM 中不存在配 Key 向导。
- 切模式后再建新会话 → 新会话用的是 `prefs.defaultChatMode` 而非上一个会话的模式（需求规则 6）。

**手工验收**

1. 选择器先模式后模型；出厂名单符合 §5.6.3。
2. 把 `chat-modes.json` 的 `privacy.models` 清空 → 该分组显示说明，不弹向导。
3. 删光 `config.yml` 的所有 endpoint → 仍不弹向导。
4. 个人中心改「新会话默认模式」为隐私 → 新建会话确实是隐私模式，旧会话不变。
5. 会话中途改模式 → 已有气泡不变。

第 3 条是需求「含名单被删空、开发调试」的直接验收，容易漏测。

## 7. 上游合并影响

**等级：中。**

- `Composer.svelte:746-1000` 这段模型菜单被整体替换，上游若改这段必冲突。缓解：新逻辑全在 `ModeMenu.svelte`，`Composer.svelte` 内只保留芯片按钮与一行 `<ModeMenu />`。冲突时的解法是「取上游的芯片实现 + 重新挂 ModeMenu」。

- `App.svelte` 的 `key_setup` 分支加短路：一行。
- `FirstRunSetup.svelte` 保留不删，避免删除类冲突。

## 9. 风险与决策

| 项 | 处理 |
|---|---|
| 模式与上游 endpoint 体系的耦合 | `chat-modes.json` 只存模型 id，不重新定义模型。上游改 endpoint 结构时只需改 id → composite id 的解析一处 |
| 用户手改 `chat-modes.json` 写坏 | 损坏时用内置默认并保留原文件，界面提示一次。不静默覆盖 |
| 「默认」这个词的歧义 | 需求 §3 已警告。代码里常量叫 `ModeDefault` 并注释说明它是分组名；文案键 `mode.default`，中文「默认」英文 "Default" |
| 分组展开 vs 级联菜单的取舍 | 已定（2026-09-07）：分组展开。见 §3.3 |
