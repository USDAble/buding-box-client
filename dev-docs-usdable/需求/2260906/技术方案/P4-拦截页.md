## 1. 目标与非目标

**目标**：一页即表单的拦截页，覆盖首次激活与二次登录两种形态，全部校验规则按需求逐条实现，中英可切且立即生效。

**非目标**

- 不做真实短信 / 真实激活（需求 §2.2）。
- 不做密码、第三方登录、换绑（需求 §7）。
- 不自绘 Logo 图形（需求 §5.2.4：研发不自拟图形）。

## 3. 设计

### 3.1 页面结构

严格按需求 §5.2.4「拦截页结构」，自上而下：

```
┌────────────────────────────────────────┐
│                          [中文 | EN]   │  ← 右上角语言切换
│                                        │
│              ▢ BrandMark               │  ← 方形 Logo，图形与语言无关
│              布丁盒子                   │  ← 全称，随语言
│   让本地工具、任务与智能代理，…          │  ← 口号，随语言
│                                        │
│   手机号  [                    ]       │
│   验证码  [        ] [发送验证码 60s]   │
│   昵称    [ 用户3271           ]       │
│   激活码  [                    ]       │  ← 仅首次激活
│           请输入随程序目录提供的激活码    │
│                                        │
│        [    激活并登录    ]            │  ← 二次登录时为「登录」
│                                        │
│        用户协议 · 隐私政策              │
└────────────────────────────────────────┘
```

无「跳过」「游客」入口（需求 §5.3.1 末句）。

### 3.2 两种形态的判定

由 `GET /api/product/state` 返回的 `activation.activated` 决定，前端不自行推断：

| 状态 | 表单 | 主按钮 |
|---|---|---|
| `activated == false` | 手机号 / 验证码 / 昵称 / **激活码** | 「激活并登录」 |
| `activated == true` | 手机号 / 验证码 / 昵称（预填上次） | 「登录」 |

二次登录时 `state` 里带 `account.phoneMasked`（如 `138****1234`），用于手机号不匹配时的错误提示。**不返回明文手机号** —— 比对在服务端做。

### 3.3 校验分层

需求 §5.3.3 有一条容易做错的规则：「**格式类错误全部同时标在对应字段旁**（不因前一个失败而隐藏后面的）。格式都过之后，再按『验证码是否已发送且正确 → 激活码是否正确』检查」。

所以是**两轮**：

```
第 1 轮（前端 + 服务端各做一次）：格式
  手机号格式 / 验证码 6 位数字 / 昵称 2-16 且字符集合法 / 激活码非空
  → 全部错误一次性返回，逐字段展示

第 2 轮（仅服务端）：业务，短路
  验证码是否已发送 → 验证码是否正确未过期 → 激活码是否正确
  → 第一个失败即返回，停留本页
```

前端做第 1 轮是为了响应速度，**服务端必须重做一遍** —— 前端校验是体验，服务端校验才是规则。

### 3.4 手机号规范化（§5.3.2）

单一实现放服务端，前端复用同一套逻辑的 TS 移植版（两边各有测试，用同一组 fixture）：

```
1. 删除所有空格（含全角）与短横线
2. 若结果以 "+86" 或 "86" 开头，且剩余部分为 11 位数字 → 去掉该前缀
3. 结果必须是 "1" 开头的 11 位数字，否则错误「请输入正确的手机号」
```

第 2 步的条件顺序要注意：`8613800001234` 去掉 `86` 剩 11 位 → 有效；而 `8613800001` 去掉后只有 8 位 → 不去前缀，整体按 10 位判定 → 无效。按需求字面实现，不做「尽量帮用户猜」的额外容错。

### 3.5 验证码（假）

服务端内存态，不落盘（进程重启需重发，可接受）：

```go
type codeSession struct {
    phone    string
    sentAt   time.Time      // +10min 过期
    cooldown time.Time      // +60s 之前不可重发
}
```

- `POST /api/product/send-code` — 规范化后手机号合法才受理；60 秒内重复请求返回剩余秒数。
- 校验：必须先发过（否则「请先获取验证码」）、码等于 `123456`、未超 10 分钟。
- 固定码 `123456` 定义在服务端常量，**不下发给前端**（需求：「界面不要把正确答案印在输入框里」）。

### 3.6 昵称

- 默认值：进页时按**当前界面语言**生成，中文 `用户` + 4 位随机数字，英文 `User` + 4 位。语言切换时，**若用户未编辑过**则重新生成；已编辑则保留（否则用户切个语言输入就没了）。
- 格式：长度 2–16，字符集 `[\p{Han}\p{L}\p{Nd}_]`。用 Unicode 属性而非 `[一-龥]`，避免漏掉扩展汉字区。长度按**字符数**（rune）不是字节数。
- 敏感词：调 P7 的引擎，命中直接拒绝保存，错误「昵称包含敏感内容」，**不打码后保存**（需求 §5.3.3 明确）。P7 未合入前，本 PR 先留接口 + 一份 stub 实现（恒不命中），P8 接上真引擎。

### 3.7 激活码

- 固定 `BUDING-DEMO-0001`。比对前 `strings.TrimSpace` + `strings.EqualFold`（大小写不敏感；首尾空格忽略；**中间空格不忽略** —— 直接用 `EqualFold` 即可满足，不要做去空格）。
- 这是 ASCII 标识符（需求 §5.2.4「标识符例外」），**不随品牌名改**，也不进 `brand.json`，就是一个 Go 常量。要在常量旁写注释说明它为什么不是品牌字面量，否则将来有人会「顺手」改成 `PUDDING-*`。

### 3.8 语言切换

- 未登录时可切（需求 §5.3 明确的唯一例外），`PUT /api/product/locale` 写 `prefs.locale`。
- 初始语言：`prefs.locale` 有值用它；否则跟系统 UI 语言 —— **简体中文用中文，其余一律英文（含繁体中文）**，需求 §5.3.1 / §10 T10。判定放服务端（Go 能拿到系统 locale，浏览器 `navigator.language` 在 webview 里不一定准）。
- 切换后立即刷新：产品名、口号、校验文案、按钮、页脚。图形不动。

### 3.9 协议与隐私占位页

- 内容取 `brand.json` 的 `about.termsTitle` / `about.privacyTitle` + `copy.termsBody` / `copy.privacyBody`（这些键在 `branding/brand.json` 里**已存在**）。
- 应用内 modal 渲染，不开外部浏览器、不依赖外网（需求 §6）。

## 4. 接口与数据结构

```
POST /api/product/send-code
  req  { "phone": "138 0000 1234" }
  resp 200 { "cooldownSec": 60 }
     | 400 { "field": "phone", "code": "invalid_phone" }
     | 429 { "retryAfterSec": 42 }

POST /api/product/login
  req  { "phone": "...", "code": "123456", "nickname": "用户3271",
         "activationCode": "BUDING-DEMO-0001" }   // 二次登录省略
  resp 200 { "state": <ProductStateDTO> }
     | 400 { "fieldErrors": { "phone": "invalid_phone", "nickname": "nickname_sensitive" } }
     | 400 { "code": "code_not_sent" | "code_invalid" | "activation_invalid"
             | "phone_mismatch", "phoneMasked": "138****1234" }

PUT /api/product/locale
  req  { "locale": "zh" | "en" }
```

错误用**机器码**不用文案 —— 文案在前端按当前语言渲染，服务端返回中文句子会导致切英文时露出中文。

```ts
// web/src/lib/phone.ts
export function normalizePhone(raw: string): { ok: boolean; value: string }
// web/src/lib/nickname.ts
export function randomNickname(locale: 'zh' | 'en'): string
export function validateNickname(v: string): 'ok' | 'format'
```

## 6. 测试

**Go 单测**

- `normalizePhone`：`"138 0000 1234"` / `"+8613800001234"` / `"86-138-0000-1234"` → 同一结果；`"8613800001"` → 无效；`"23800001234"` → 无效（非 1 开头）。
- 未发码直接登录 → `code_not_sent`。
- 发码后 61 秒内重发 → 429。
- 发码后 10 分 1 秒 → `code_invalid`。
- 激活码 `" buding-demo-0001 "` → 通过；`"BUDING DEMO 0001"` → 失败。
- 二次登录换号 → `phone_mismatch` 且带 `phoneMasked`。
- 昵称 `"a"` / 17 字 / 含 `-` → 格式错；含敏感词 → `nickname_sensitive`。

**前端单测**

- `randomNickname('zh')` 匹配 `^用户\d{4}$`；`'en'` 匹配 `^User\d{4}$`。
- 格式错误一次性全标（用一组四个字段全错的输入断言返回 4 个 fieldError）。

**手工验收**：按需求 §8「登录」段逐条走。
