## 1. 目标与非目标

**目标**

1. 面板里有一个词库管理页：看得到内置词，能增删改自己的词。
2. 支持导入 / 导出，方便批量维护和在多份程序目录之间搬。
3. 改完立即生效，不需要重启。

**非目标**

- **不做服务器同步**（2026-09-07 评审决定）。本期无中台（需求 §2.2），且需求 §6 要求不依赖外网。界面上**不出现**「同步」按钮 —— 做出一个点了没反应的入口比没有更糟。
- 不改匹配规则（P7 已定）。
- 不做词库分类、不做正则、不做词条备注。

---

## 2. 与需求原文的差异（已回写，留档）

**需求 §5.5 与 §8 已按下述结论改写（2026-09-07）。本节解释改了什么、为什么。**

原需求写的是：「……用户直接改词库文件即可更新，**无单独管理界面**。」

现结论：补一个管理界面。**文件仍然是唯一真相** —— 界面只是这个文件的编辑器，不引入第二份存储。手改文件和用界面改，效果完全一样。

这一点是本 PR 的设计底线：如果界面把词库搬进数据库或另一份 JSON，需求「替换该文件后下一次检测生效」这条就废了，用户也没法再靠拷文件来分发词库。

**需求 §5.5 已同步改写**（2026-09-07）：删掉「无单独管理界面」半句，补齐界面要求；§8 补了 5 条验收。本方案与需求正文一致。留档见 `../开发计划.md` §4.1 第 3 / 4 项。

## 4. 设计

### 4.1 两级词库

```
生效词表 = 内置词（只读）∪ 用户词（可编辑）

内置词    Go 常量里的 7 个（赌博/毒品/发票/gambling/drugs/invoice/fapiao）
          界面只读展示，不能删 —— 它们是「文件读不出来时也得拦住」的兜底
用户词    data/sensitive-words.txt，界面增删改的就是这个文件
```

**内置词不写进文件**。理由：写进去用户就能删，删完再遇到文件损坏就真的一个词都没有了。保持「内置是地板，文件是加法」的关系。

需求 §5.5 说文件缺失时「用内置示例词」—— 这里改成「内置词**总是**生效，文件是叠加」。语义更强，不违背需求意图（缺失时的行为完全一致）。

### 4.2 界面

`AccountPanel` 的一个二级页，走 P5 的 `accountPanelPage = 'sensitive'`：

```
┌─ 敏感词库 ───────────────┐
│  ← 返回                  │
│                          │
│  内置词  7 条    [展开]   │
│  ────────────────────    │
│  我的词库  3 条           │
│  ┌────────────────────┐  │
│  │ 赌博          ✕    │  │
│  │ 毒品          ✕    │  │
│  │ 测试词        ✕    │  │
│  └────────────────────┘  │
│  [ 输入新词        ] [+] │
│                          │
│  [导入文件] [导出文件]    │
│                          │
│  改动立即生效             │
└──────────────────────────┘
```

- 内置词默认折叠（用户平时不关心），展开为只读列表。
- 用户词列表可删；点词条可就地改。
- 新增：输入框 + 回车 / 点 `+`。
- 重复词（与内置或已有用户词**规范化后**相同）→ 提示「该词已在词库中」，不重复添加。用规范化后比较，否则「发 票」和「发票」会被当成两个词。
- 空词、纯符号词（规范化后为空）→ 拒绝，提示「该词无效」。这类词会命中一切文本。

### 4.3 导入 / 导出

- **导出**：把当前用户词写成同格式的 `.txt` 下载。桌面端走 Wails 的保存对话框，Web 端走 Blob 下载。
- **导入**：选一个 `.txt`，按同格式解析（一行一词、`#` 注释、空行忽略），与现有词**合并去重**，不是覆盖。
  - 覆盖 vs 合并：选合并。用户导入通常是「加一批词」，覆盖会静默丢掉他手工加的词。需要覆盖的话可以先清空再导入。
  - 导入前显示预览：「将新增 N 条，其中 M 条已存在会跳过」，确认后写入。

### 4.4 写入与并发

- 写文件用**原子写**（写 `.tmp` + `os.Rename`），与 `product-state.json` 一致。U 盘上尤其重要 —— 就地改写被拔盘打断会留下半个文件。
- 保留文件里用户手写的 `#` 注释：解析时记住每条注释挂在哪一行，回写时放回原位。做不到完美就至少**保留文件头部的连续注释块**（用户的说明多半在开头）。这条不做的话，用户在界面上加一个词，他辛苦写的注释就没了。
- 写完不需要通知引擎 —— P7 的 `ModTime` 热加载会在下一次检测时自动重读。

### 4.5 冻结状态

P2 的看门狗冻结期间（拔盘），词库写入直接返回错误并提示，不尝试落盘。

## 5. 接口与数据结构

```go
// internal/sensitive/dict.go （P7 已有文件，本 PR 扩展）

// BuiltinWords 返回只读的内置词表。
func BuiltinWords() []string

// UserWords 读用户词库文件，返回词条（已去掉注释与空行，保持文件顺序）。
func UserWords(path string) ([]string, error)

// WriteUserWords 原子写用户词库，保留文件头部的注释块。
func WriteUserWords(path string, words []string) error
```

```
GET    /api/product/sensitive/dict
       → { "builtin": ["赌博", …], "user": ["测试词", …] }

PUT    /api/product/sensitive/dict
       { "user": ["测试词", "另一个"] }
       → 200 { "user": [...] }
       | 400 { "code": "invalid_word", "word": "!!!" }

POST   /api/product/sensitive/dict/import
       { "words": ["a", "b"], "dryRun": true }
       → { "added": 5, "skipped": 2 }      // dryRun 用于导入前预览
```

全部走产品门保护（未登录不可用）。

整表 PUT 而不是逐条增删的 REST：词库最多几千条，整表传输开销可忽略，而整表写避免了并发下的部分更新问题。

## 7. 测试

**Go 单测**

- `WriteUserWords` 保留文件头部注释块；词条顺序与传入一致。
- 原子性：写入过程中进程被杀（模拟为写 `.tmp` 后不 rename）→ 原文件完好。
- 内置词总是生效：用户词库为空文件时，`Filter("赌博")` 仍命中。
- 用户词与内置词重复 → 不重复计入，`Filter` 行为不变。
- 规范化后为空的词（`"!!!"`、`"   "`）→ 400，且**不写入文件**。
- 写入后不重启，下一次 `Filter` 就用上新词（验证 P7 的热加载与本 PR 配合）。

**前端单测**

- 添加重复词（`发 票` vs `发票`）→ 提示已存在，列表不变。
- 导入预览的 added / skipped 计数正确。
- 导入是合并不是覆盖（导入后原有词仍在）。

**手工验收**

1. 面板 → 敏感词库 → 加一个词 → 直接在聊天里发这个词 → 被拦住（不重启）。
2. 删掉该词 → 再发 → 能发出去。
3. 内置词「赌博」删不掉（无删除按钮）。
4. 导出 → 用文本编辑器打开 → 格式与 `data/sensitive-words.txt` 一致。
5. 手工编辑 `data/sensitive-words.txt` 加一个词 → 界面重新打开能看到它（文件是唯一真相）。
6. 文件里写几行 `#` 注释 → 界面加词 → 注释还在。

第 5、6 条是本 PR 的设计底线（§2），必须验。

**需求 §8「敏感词」段已补入的 5 条验收**（2026-09-07 回写）：

- 界面加词后**不重启**即能拦住；删掉后不再拦。
- 内置词不可删。
- 手工编辑 `data/sensitive-words.txt` 后，界面重新打开能看到改动；界面加词后文件里原有的 `#` 注释仍在。
- 导入是合并不是覆盖：导入后原有的自定义词仍在。
- 词库为空文件时，内置词仍然生效。

## 10. 风险与决策

| 项 | 处理 |
|---|---|
| 用户加了一个太宽的词（如「的」）导致什么都发不出去 | 加一条软提示：单字词或极短词会大面积误伤，确认后仍允许添加。不硬性禁止 —— 这是用户自己的词库 |
| 注释保留做不完美 | 至少保住文件头部连续注释块；行内注释丢失可接受，在 UI 上提示一次 |
| 服务器同步以后要加 | 数据结构已按「内置 + 用户」两级设计，将来加「通用词库（服务器）」是第三级，不改现有两级的语义 |
| 词库很大时界面卡 | 超过 500 条时列表虚拟滚动。本期本地确定性数据量级不会触发，先记着 |
