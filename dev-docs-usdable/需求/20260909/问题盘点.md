## 0. 大类别总览

用户给的四个方向保留，另外补充七类（标 ★），它们是从“上线”角度审视时，原清单没有充分覆盖、但对一个要正式对外发布的便携产品**必不可少**的维度：


| #   | 大类别            | 一句话定义                      | 与用户的对应 |
| --- | -------------- | -------------------------- | ------ |
| A   | 功能逻辑不完整        | 逻辑存在但只做了一半 / 边界没闭环         | 方向 1   |
| B   | 交互问题           | 界面/流程行为与预期不符（需走查确认）        | 方向 2   |
| C   | 静态 / 旧本地实现   | 写死常量、旧本地数据、未批准文案、固定回复         | 方向 3   |
| D   | 真实接口对接         | C 中「将来要接中台/短信/计费/模型」的落地    | 方向 4   |
| E   | 品牌与视觉资产        | Logo 正式稿、主色、托盘/社交卡等设计资产    | 补充     |
| F   | 安全与技术合规        | PII 范围、敏感词误伤、鉴权语义、WebView2 | 补充     |
| G   | 工程与上游合并        | upstream、游离修复、防回潮、能力断言     | 补充     |
| H   | 质量 / 稳定性 / 跨平台 | 真模型验收、跨平台、拔盘边界、产物自检        | 补充     |
| I   | ★ 数据安全与灾备      | 备份/恢复、版本迁移、损坏自愈、U 盘磨损      | **新增** |
| J   | ★ 可观测性与诊断支持    | 崩溃上报、诊断包、日志脱敏、遥测           | **新增** |
| K   | ★ 发布、分发与签名     | 代码签名、版本号、渠道、便携更新           | **新增** |
| L   | ★ 法务与监管合规      | 协议/隐私真实文案、PIPL、内容安全监管、备案实名 | **新增** |
| M   | ★ 服务边界与凭证模型   | 模型流量、计费、密钥、设备身份由谁负责         | **新增** |
| N   | ★ 运营与用户服务闭环   | 账户生命周期、计费争议、客服、故障与运营责任     | **新增** |
| O   | ★ AI 能力安全与治理    | 工具权限、提示注入、数据外发、后台任务的产品边界 | **新增** |


**为什么补这七类**：A–H 覆盖的是“把产品做对”，但完整上线还必须回答七个问题——① U 盘丢了/坏了数据怎么办（I）；② 用户报“打不开/闪退”时拿什么定位（J）；③ 怎么把带签名、能更新的包发到用户手里（K）；④ 处理手机号、做内容过滤、写用户协议时，适用地区和渠道的法务门槛是什么（L）；⑤ 真实模型的调用、扣费、密钥和设备身份到底由客户端还是服务端负责（M）；⑥ 用户换号、丢盘、扣费争议、服务故障时由谁接住（N）；⑦ AI 能调用哪些本机能力、如何抵抗外部内容诱导（O）。M/N/O 是从“能研发验证”到“能长期运营”最容易漏掉的三段。

**C、D 与 M 的关系**：C 是「现状盘点」，D 是「接口和客户端替换动作」，M 是「真实服务的权威边界」。不是所有 C 项都要接真接口——例如 P11 本地确定性模型通道（C6）是长期保留的研发验证/离线/测试设施，永远不会「替换」成真接口。若 M 未先拍板，D 类即使逐个接通，也会留下“能调用模型但账不一致、或把供应商密钥放进 U 盘”的结构性风险。

## 2. 完整上线闭环（排期前先对齐）

“功能完成”不等于“产品可以上线”。任何 P0/P1 工作项必须同时回答下表四个问题：谁拥有规则、失败时用户看到什么、数据/钱/权限怎样保持一致、出了问题谁能恢复。只写接口或页面、没有反向路径的条目不算完成。

| 阶段 | 用户与系统必须闭合的事 | 对应大类 | 最小完成定义 |
| --- | --- | --- | --- |
| 获得与启动 | 下载的是哪个正式包、是否可验证、能否在目标 Windows 环境启动、数据是否只写 U 盘 | E / H / K | 渠道、版本、哈希/签名状态、支持矩阵和启动失败提示均有记录 |
| 身份与授权 | 验证码、激活、token、设备复制/丢失、过期与换号怎么办 | D / F / I / M / N | 服务端为身份权威；刷新、撤销、迁移和客服恢复有明确流程与机器码 |
| 对话与工具 | 模型请求、敏感词/PII、模型工具、外部网页/文件输入、用户授权如何处理 | A / B / F / M / O | 模型、工具和数据外发均有明确许可边界；拒绝、取消、超时和提示注入场景可复现 |
| 计费与交付 | 余额、用量、套餐、支付、退款/争议、模型失败时钱如何处理 | D / M / N | 同一个请求 ID 能追到模型网关、账本和用户可见记录；重复/失败不会多扣或无依据扣款 |
| 留存与自助 | 会话/词库/凭证怎么备份、导入、删除、导出；U 盘损坏如何恢复 | I / J / L / N | 数据分级、导入校验、删除/保留期限和诊断脱敏均已验收 |
| 运营与演进 | 服务故障、依赖漏洞、证书/密钥泄露、版本回退、客服升级由谁处理 | G / J / K / N / O | 有告警/工单关联、事件分级、回退/撤销路径和演练记录 |

**每个条目的完成模板**：`产品决策`（规则与 owner）→ `技术契约`（接口/状态机/数据归属）→ `正向与反向验收`（成功、拒绝、超时、重试、重复、断网、撤销）→ `运营证据`（日志/账本/诊断/客服或值班路径）。这四段中任一缺失，任务应保持“进行中”，不要标为已上线。

**P0 的建议顺序**：先完成 P0-00：确认 `buding` 已接收批准的 `main`、禁止扩大 `internal/server` 改动面，并把 production 的开发/本地旁路和运行时 profile 切换逐项封住；随后冻结 O1/O2 的能力与数据外发边界，并在 M1/M2 中决定模型网关、扣费权威和凭证生命周期；再签署 D1–D6/J5 的接口、账本和请求关联契约，由 `productclient`、`productpolicy` 和 `credentialstore` 并行实现；再由 L1/L2 将真实数据流反映到协议、同意与删除规则；最后以 H1 的真实账号、真实模型、失败与恢复全链路验收作为发布门。这个顺序不是瀑布式排斥并行，而是确保后续实现不会建立在“工具默认全开、计费两边各算、密钥随包走”的错误前提上。

## A. 功能逻辑不完整

**核心建议**：这一类的关键不是“补更多判断”，而是把产品概念和边界说准确。A1 已确认是当前范围；A2 要拆清激活、套餐和积分；A3 已确认客服处理；A4/A5/A9 则应先由中台契约锁定，再实现客户端替换。这样不会把本该由服务端权威的规则散落成前端或本地状态判断。


| #   | 问题           | 现状 / 根因                                              | 建议                                                                                                                                                                         | 优先级 |
| --- | ------------ | ---------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --- |
| A1  | PII 仅自动识别手机号（当前范围内正确） | `internal/pii` 当前只处理中国手机号；登录表单和本期产品只主动收集手机号 | **不是当前缺陷，不扩展身份证/银行卡正则。** 仅当产品新增采集这些字段的表单、将其写入日志/诊断包，或要求对云端发送前做自动脱敏时，才必须定义识别规则。用户自由输入的对话内容不宜靠不可靠正则“保证全识别”；本期以 L2 的告知、日志/诊断包白名单和隐私模式为边界。验收是手机号不进模型副本/日志/导出，而非声称识别全部个人信息 | — |
| A2  | “授权到期”与套餐、积分语义混淆 | 当前仅有 `Activation.ExpiresAt`（首次激活后 365 天）并在界面展示；`trial` 套餐没有到期字段；积分为本地余额且 0 分仍可发 | **这不是“积分用完”也不是当前套餐到期。** 建议 v1 明确三条独立规则：① 激活授权到期仅展示“已过期”与续期/客服入口，暂不拦截；② 套餐到期由 D5 未来单独返回 `planExpiresAt`、权益和降级规则；③ 积分不足按 A5/D4 的真实 token 账本决定是否拒绝模型请求。接口和文案不得把三者共用“授权到期”一词 | P1 |
| A3  | 换绑手机号只支持客服 | 现有帮助页为未批准；本期不做自助换绑 | **确认保持客服路径。** 正式帮助页提供真实联系方式、工作时段和需提交的最小信息；登录时中台返回 `phone_mismatch`，客户端说明“当前设备已绑定其他手机号，请联系客户服务”，但不显示旧号码全量、不允许本地改 JSON。客服后台状态迁移、审计与丢盘场景归 N1 | P1 |
| A4  | 通用敏感词库缺服务器词源 | 当前是内置词 ∪ 用户本地词；缺服务器通用词 | 保留**本地内置词 + 用户本地词 + 服务器通用词**三层并集，服务器词只读、用户不可删除。中台按 `version`/`ETag` 下发完整或增量词表；客户端校验后原子替换缓存，拉取失败继续使用“内置 + 最近有效服务器缓存 + 用户词”，不能清空词库或阻塞启动。词源接口和签名/缓存策略写入[中台交付包](产品客户端与中台对接/中台交付包.md) §6 | P1 |
| A5  | 积分扣减是旧规则 | 当前是“请求交给本地 agent 即扣 1 分”，与模型、输入/输出 token、套餐和失败无关 | **改为中台模型网关统一计费，不保留客户端 `amount` 扣费接口。** 客户端只传 `clientRequestId`、服务端目录中的 `modelId` 和消息；网关按模型定价版本、输入/缓存/输出/推理 token、套餐折扣和赠送额度预留并在流结束后结算，返回账本 ID、实际用量与余额。超时/取消/重试只按同一请求 ID 结算一次，未知用量进入待核对而非客户端猜扣；完整字段、状态机与错误码见[中台交付包](产品客户端与中台对接/中台交付包.md) §5 | P0 |

| A8  | 繁体中文未支持      | 繁体系统走英文                                              | i18n 层已支持多语言，加繁体就是补 `zh-TW` 文案行（`web/src/lib/i18n.ts` 的键表）。**建议作为 P2 一次性补全**，比逐个漏改强                                                                                        | P2  |

## K. ★ 发布、分发与签名（新增）

**核心建议**：这一类是“从研发验证包到正式包”的交付门槛。未签名 Windows 可执行文件可能触发 SmartScreen 警告，但不是所有机器上的绝对技术阻断；是否必须 EV/OV 证书、何种渠道必须签名，取决于发布渠道和企业策略。无论选择什么，都要有版本、哈希、签名状态和回退办法，不能让用户只看到“即将支持”。

## L. ★ 法务与监管合规（新增）

**核心建议**：一个处理手机号、向模型发送用户内容并做内容过滤的产品，需要正式的法务/合规评审；但本表不作法律结论，也不把“短信验证 = 实名”“所有软件都必须备案/软著”写成既定事实。应由法务/运营按目标地区、主体、分发渠道和实际数据流给出适用清单，再映射到技术验收。


| #   | 项           | 现状          | 建议                                                                                 | 优先级 |
| --- | ----------- | ----------- | ---------------------------------------------------------------------------------- | --- |
| L1  | 用户协议/隐私政策   | 「本页为开发未批准」   | **法务出正式文案**，走 `brand.config.json` 文案层替换，保留多语言键结构。未批准文案不能上线                          | P0  |
| L2  | 隐私与跨境数据评审 | 处理手机号；接真模型后还会传输对话、诊断与设备数据 | 按实际数据流画清收集、用途、保存地点/期限、接收方、删除与用户权利；由法务判断 PIPL、GDPR、数据出境等适用要求。隐私政策、产品同意和真实实现必须一致 | P0 |
| L3  | 内容安全与审计边界 | 敏感词过滤是核心能力 | 由合规 owner 评审目标地区/服务类型的要求，并明确过滤目标、人工处置、误报申诉、日志最小留存与访问权限；技术侧按批准的规则版本和审计范围实现，不能以一份静态词表自证合规 | P1 |
| L4  | 身份核验级别 | 当前只是手机号验证码研发验证 | 明确业务需要的是号码验证、实名核验、年龄/地区限制还是都不需要；若需要实名，选定受监管的服务与失败/申诉流程。不要把短信验证码本身描述为已完成实名 | P1 |
| L5  | 分发备案/知识产权 | 未形成按渠道和地区划分的清单 | 由法务/运营按官网、应用商店、企业内部分发、目标市场和主体确认可能需要的备案、软件著作权、开源许可证/notice、出口或内容要求；形成 release checklist 后再排期 | P2 |

## M. ★ 服务边界与凭证模型（新增）

**核心建议**：产品已确认正式模型由中台下发目录并经中台网关调用，本地 provider 配置仅保留给开发/维护 profile。当前缺口不再是“选择哪种架构”，而是让客户端抽象层、中台接口、账本、凭证缓存和发布 profile 全部按同一个边界实现；否则代码仍会从本地 `config.yml` 或固定扣分路径绕开正式规则。

| # | 问题 | 现状 / 风险 | 建议与完成定义 | 优先级 |
| --- | --- | --- | --- | --- |
| M1 | 模型调用与计费权威待落地 | 当前客户端可直连 provider，旧中台草案另有独立 `credits/consume` | **架构已确定：标准产品走中台模型网关。** 桌面仅持短期产品会话，调用经认证的模型网关；网关在同一请求链内校验授权、预留/结算 token 用量，并返回 `requestId`/账本/余额/可重试状态。模型目录只下发元数据，供应商 endpoint/key 不下发。验收覆盖超时、取消、重复请求、流式中断和余额不足，契约见[中台交付包](产品客户端与中台对接/中台交付包.md) §5 | P0 |
| M2 | 凭证生命周期待落实 | 远端链路需要 access/refresh token，通用配置又可存 API key；当前没有“存什么、存多久、何时轮换/撤销、备份是否带走”的统一规则 | 定义最小凭证集、存储位置、过期/刷新并发、登出/设备丢失后的远端撤销及客服恢复流程。标准便携版不持有供应商长期密钥；本地开发凭证与正式 profile 严格隔离。任何持久凭证均受 F6/I1/J4 的排除与脱敏规则约束 | P0 |
| M3 | 程序目录复制后的设备语义不清 | 当前“激活/登录绑定”在本地文件中；复制 `data/` 后会带走身份状态，接真后可能造成设备数、恢复、换盘和风控语义冲突 | 不用硬件序列号猜设备身份。创建可轮换的安装标识，并让中台定义绑定上限、转移、备份恢复、注销、丢失 U 盘后的撤销和隐私告知；这些规则是 D2、I1 的共同前置 | P0 |
| M4 | 开发输入与正式 Profile 切换缺少护栏 | 现有 local provider、固定验证码和旧积分属于开发支持路径；desktop 可接受开发 Web URL，且过去没有可信 Profile 来源 | 以 P0-00 固化全局嵌入式 `production`/`developer` Profile：构建标签选择 Profile，环境变量、配置、缓存、命令行和 WebView 输入均不能切换。production 忽略开发 Web URL、环境 provider/model/key 与 `OCTO_DATA_ROOT`；`config.yml`、MCP、channel、工具和后台能力保留（`config.yml` 的 URL/key 在 developer/test 完全允许），P0-00A/P0-04 以入口可见性、资格和 PEP 分别治理。为开发输入与 Profile 切换补黑盒测试和发布证据 | P0 |

## N. ★ 运营与用户服务闭环（新增）

**核心建议**：上线后用户遇到的问题不会按代码模块出现，而是“U 盘丢了”“手机号不用了”“扣了钱没回复”“我要删除数据”。这些事件若只留“联系客服”，最终会迫使客服手工改数据、研发翻日志，既不可扩展也不安全。正确做法是先定义状态机、责任边界与可审计的自助/人工路径，再让接口、页面、账本和工单共用同一个状态。

| # | 问题 | 现状 / 风险 | 建议与完成定义 | 优先级 |
| --- | --- | --- | --- | --- |
| N1 | 账号、换号、丢盘与设备找回无闭环 | 当前二次登录只能使用已绑定号码；本期换绑明确只支持客服；复制或丢失 `data/` 后的服务端语义尚未定义 | 建立账户状态机（正常、待验证、设备迁移、已撤销、待删除），但本期不做自助换号/解绑。用户通过真实客服入口提交申请；客服仅能通过受控后台发起状态迁移，不得要求用户提交 token 或直接修改 JSON。丢失设备撤销等高风险操作同样走人工复核；每次操作记录原因、操作者、时间和 request ID | P1 |
| N2 | 充值、账单、退款/争议未定义 | 当前积分和套餐为旧本地数据，充值/升级 disabled；若接支付，模型失败与扣费争议会直接落到客服 | 采用“支付服务商订单 → 服务端签名回调 → 不可变账本 → 账户余额”的唯一链路，客户端只展示服务端账本。明确订单超时、重复回调、退款、赠送积分、发票/收据、异常补偿与争议处理；用户能查看交易 ID 和用量明细，客服可按 J5 查询但不能无审计改账 | P1 |
| N3 | 账户注销、远端数据删除与保留期限没有产品流程 | 当前“退出登录”只清本地 token；真实服务后的对话、诊断、账单、备份和模型网关日志的删除边界未定义 | 把 L2 的数据主体权利落为产品流程：区分退出、本地清除、账户注销、远端删除请求和依法/合约必须保留的账本。给出影响说明、撤回窗口、完成通知、导出能力和后台执行证据；删除任务需覆盖索引、缓存、备份和供应商处理方，不能只删主表 | P1 |
| N4 | 客服与事件升级路径缺失 | 当前帮助/反馈为 cheat sheet，诊断包和中台 request ID 尚未接入工单 | 选定一个反馈/工单渠道，定义 P0/P1/P2 事件分级、首响/升级 owner、需要的最小信息、隐私同意和用户状态通知。工单关联 J5 request ID 与脱敏诊断包；服务端故障时能批量告知受影响用户，而不是逐条人工猜测 | P1 |
| N5 | 短信、激活、模型与积分滥用/成本控制不完整 | 接口草案只提到登录/验证码限流；模型网关、设备共享、批量注册和异常用量尚无统一规则 | 在服务端做分层限额：IP/号码/账号/设备/模型维度的速率、并发、日预算和风控信号；限制由网关强制而非前端计数。对误杀提供可解释的申诉路径，对异常扣费和服务商账单设置告警、冻结和人工复核 | P1 |
| N6 | 服务可用性与事故响应未落责 | 代码可写本地日志，但真实短信、账号、支付、模型会引入多方依赖 | 为每个外部依赖指定 owner、健康检查、SLO、降级策略和事故联系人；建立状态页/站内公告的触发标准。演练“短信服务不可用”“模型供应商大面积超时”“支付回调延迟”“凭证泄露”四类事件，验证技术回退与对用户的沟通同样闭合 | P1 |

## O. ★ AI 能力安全与治理（新增）

**核心建议**：敏感词过滤不是 AI 安全边界。当前桌面启动显式设置 `Tools: true`，仓库具备终端、文件、网络、浏览器、MCP、技能、后台任务等上游能力；把 IM/MCP/Light Apps 从首屏隐藏，并不等于模型无法触达这些能力。正式产品必须先决定“布丁盒子是只聊天，还是可操作本机的 agent”，并让默认权限、产品文案、服务端路由、审计和测试一致。

| # | 问题 | 现状 / 风险 | 建议与完成定义 | 优先级 |
| --- | --- | --- | --- | --- |
| O1 | 产品能力集合需支持分阶段露出 | 桌面以 `Tools: true` 启动；上游保留渠道、MCP、技能、任务等能力。产品已确认隐藏菜单只是暂不露出，功能不能删除 | **P0 建立服务端下发的“能力矩阵”，把“功能存在”与“是否显示/当前用户是否可用”分开。** 每项含 `available`、`visible`、`entitled`、`permissionPolicy` 和最小客户端版本：首发可令菜单 `visible=false`，但保留实现和后续灰度开关；启用时不必重发架构。工具执行仍按最小权限和确认策略约束，隐藏 UI 不等于放宽权限；无人值守/后台路径不得比前台更宽 | P0 |
| O2 | 提示注入与数据外发缺少端到端防线 | 外部网页、附件、仓库文件、导入的技能/工作流都可能含不可信指令；模型可据此请求读文件、联网或执行命令 | 将外部内容标为不可信上下文，不允许其指令改变权限或绕过用户目标。对读取敏感路径、向新域名发送内容、执行命令、安装/导入扩展显示“做什么、涉及哪些文件/域名、为什么”的确认；建立红队用例验证网页/附件中的诱导不能触发越权工具或秘密外发 | P0 |
| O3 | 长任务、后台进程和定时任务的可见性不足 | 仓库支持后台工具、任务与 cron；窗口关闭进托盘、U 盘拔出时这些能力可能仍在运行或失败 | 正式产品需有统一的“运行中任务”视图：启动者、权限、工作目录、网络目标、资源预算、取消/强杀和最终结果均可见。关闭窗口、退出登录、拔盘、token 撤销、余额不足时的中止语义必须明确且可测试；默认禁用用户未主动创建的后台/定时执行 | P1 |
| O4 | 模型输出安全与透明度只靠敏感词 | 当前输出过滤是敏感词子串替换，无法覆盖错误建议、危险操作、版权/隐私、模型幻觉或高风险场景 | 产品/合规共同定义适用场景、拒答/安全提示、人工升级和反馈分类；对会执行工具的建议，模型文本不能视为授权。界面应区分“模型建议”“待确认操作”“已执行结果”，并保留最小必要审计以支持纠错，不把静态词表当成完整治理 | P0 |
| O5 | 技能、MCP 与第三方扩展需保留但来源未治理 | 上游支持扩展/技能发现与导入；菜单可暂时隐藏，未来仍计划开放 | 不删除能力；首发以能力矩阵控制 `visible=false` 或按用户灰度开放，同时建立来源、签名/校验、权限声明、版本更新、撤销和隔离策略。真正露出前，导入页必须展示来源与权限，导入后可一键禁用/删除；供应链记录纳入 K5 | P1 |
