## 1. 目标与非目标

**目标**

1. 产品运行期间的全部业务数据只写可执行文件同级 `data/`。
    20|2. 进程 cwd = 程序目录，禁止切到用户 Home。
3. 会话默认工作区固定 `data/workspace/`。
4. 提供一条**唯一**的路径解析入口，让后续所有 PR 与所有上游合并都无法绕过它。

**非目标**

- 不做拔盘冻结与启动期错误提示（P2）。
- 不做便携目录的打包产出（P12）。
- 不区分「桌面 / CLI」两套数据根。本期**统一删除 `~/.octo` 这条路径**，CLI 与桌面都只认 `<可执行文件目录>/data`（需求 §2.1、§5.7.9、§9.14）。这是让 `datapath-guard` 对字面量 `".octo"` 做到**零例外**的前提——双模式必须给 guard 开例外，例外一开，上游合并带回的新写入点就能从口子溜进来。

## 3. 设计



### 3.1 收口层 `internal/datapath`

一个零依赖的新包，是本 PR 的核心，也是唯一允许调用 `os.UserHomeDir()` 决定业务路径的地方。

    70|```
             ┌─────────────────────────────┐
 任何进程 ──▶ │ datapath.Root()             │  = OCTO_DATA_ROOT 或 <exe>/data
             └──────────────┬──────────────┘
                            ▼
   所有包 ──▶ datapath.Sub("sessions") / Sub("bin") / Sub("skills") …
```

关键点：**没有降级路径**。`data/` 不可写就返回错误，由 P2 转成启动期提示后退出，绝不 fallback 到主机目录（需求 §2.1「禁止降级位置」是硬约束）。

    80|

### 3.2 数据根解析（唯一一条路径）

需求 §5.7.9 要求「数据根只有一条解析路径，代码里不保留任何降级分支（含 `~/.octo`），CLI 与桌面一致」。因此没有 portable / home 两种模式，只有一条规则，按优先级：

1. `OCTO_DATA_ROOT` 已设置 → 用它。这是**显式指定**而非降级位置，只用于三种场景：自动化测试、开发调试、CLI 被装到只读目录（需求 §9.14）。
2. 否则 → `filepath.Dir(os.Executable())/data`。

    90|桌面与 CLI 走同一套逻辑。`os.Executable()` 在 Windows 上返回真实 exe 路径；符号链接用 `filepath.EvalSymlinks` 解一次，避免 macOS 上 `.app` 内软链导致数据根飘走。

CLI 装在只读目录（如 `/usr/local/bin`）时 `<exe dir>/data` 不可写——这不是本 PR 要兼容的场景（需求 §9.14 明确主交付是便携目录），`Root()` 返回错误即可，由调用方决定是否提示用户设 `OCTO_DATA_ROOT`。

### 3.3 cwd 与工作区

- `ensureWorkingDir()` 改写：**无条件** `os.Chdir(ProgramDir())`，不再走上游 `homeIfRootLaunch`（`main.go:96` 从盘符根拉起时切 Home 的行为正是需求 §5.7.2 要改掉的）。桌面与 CLI 一致。
- 会话默认工作区：`internal/tools/workspacedir.go` 的默认值改为 `datapath.Sub("workspace")`，目录不存在则 `MkdirAll`。用户在对话里显式给的主机绝对路径不受限制（需求 §3 术语 + §5.7 白名单）。
   100|


### 3.4 防回潮：CI guard

这是「高」等级合并影响的必需配套。没有它，下一次上游合并会悄悄带回 `~/.octo` 写入，而验收 §8「主机不出现新 `.octo` 业务数据」是硬项，回归后很难被人眼发现。

新增 `scripts/datapath-guard.mjs`：

- 扫描 `internal/ cmd/ shared/` 下所有非 `_test.go` 文件。
   110|- 两类命中分开处理（与 `../../../开发规范.md` §3.1 一致）：
  - 字面量 `".octo"`：**零例外，直接失败**。产品里已经没有这条路径（含 CLI），任何一处出现都是回潮。
  - `os.UserHomeDir()`：失败，除非在 `scripts/homedir-allowlist.txt` 里。例外只给「真的要访问主机 home」的场景，**每条必须写理由**。已知合法例外：


| 文件                                   | 理由                          |
| ------------------------------------ | --------------------------- |
| `internal/datapath/*.go`             | 收口层自身                       |
| `internal/tools/read_file.go`        | 展开用户输入路径里的 `~/`，是用户意图不是产品数据 |
| `internal/browser/chrome.go`         | 定位主机真实 Chrome 用户配置，无法重定向    |
| `internal/sandbox/sandbox_darwin.go` | sandbox 规则需要主机 home 的字面路径   |
   120|| `internal/shellpath/*`               | 读用户 shell rc，属主机环境探测        |


挂进 `.github/workflows/go.yml`，与既有 `brand-guard` job（`:28`）并列，命名 `datapath-guard`。

**项目级 `.octo` 目录一并消除**：guard 的零例外不止约束数据根，也约束仓库内的项目级 hooks 文件 `<cwd>/.octo/hooks.yml`（那是上游约定，与主机 `~/.octo` 数据根无关，但字面量 `".octo"` 无法区分）。本 PR 把它平铺为 `<cwd>/.octo-hooks.yml`，与 `.octorules` 的「仓库根单点文件」约定一致。已有仓库里的 `.octo/hooks.yml` 需手动改名为 `.octo-hooks.yml` 才继续生效——本期不做自动迁移（与 §9「旧主机 `~/.octo` 不迁移」同一取舍）。

## 4. 接口与数据结构
   130|
```go
// internal/datapath/datapath.go
package datapath

// Root 返回当前数据根的绝对路径，必要时创建。解析规则见 §3.2：
// OCTO_DATA_ROOT 已设置则用它，否则 <可执行文件目录>/data。
// 不可写即返回错误，不做任何降级 —— 需求 §2.1。
func Root() (string, error)

// ProgramDir 返回可执行文件所在目录（= 数据根的父目录）。
   140|func ProgramDir() (string, error)

// Sub 返回 Root 下的子路径并确保其存在，等价于旧代码的
// filepath.Join(home, ".octo", parts...) + MkdirAll。
func Sub(parts ...string) (string, error)

// Join 只拼路径不创建目录，给「读」路径用。
func Join(parts ...string) (string, error)
```

> 没有 `Mode` 枚举：数据根统一后不再区分 portable / home（见 §3.2）。P2（隐藏自启动 / 关闭更新）与 P9（抑制配 Key 向导）原本想用 `CurrentMode()` 区分便携 / 安装形态，这两处改为「本期恒为便携交付」——见 P2 §3.5、P9 §3.5。

## 6. 测试

**单测**

- 默认 `Root()` 指向 `<可执行文件>/data`（用 `os.Executable()` 注入的临时 exe 目录测）。
- `OCTO_DATA_ROOT` 已设置 → `Root()` 用它。
- `data/` 只读 → `Root()` 返回错误，且错误里不含任何 home 路径（防止提示误导用户去主机找）。
- `Sub` 创建多级目录；`Join` 不创建。
   210|- 符号链接下的 exe 解析到真实目录。

**集成测试**（新增 `cmd/octo-desktop/portable_test.go`）

- 在 tmpdir 造一份假程序目录，跑桌面 bootstrap 到「服务已监听」为止，断言：tmpdir 之外**没有任何新文件**。这是验收 §8「主机不出现新 `.octo` 业务数据」的自动化版本，比手工抽查可靠。

**手工验收**

1. Windows 上把便携目录放到 U 盘，双击，全程操作一轮。

## 7. 上游合并影响

**等级：高。** 第 2 步替换会碰 50+ 个上游文件，几乎每次上游更新都会在这些文件上产生冲突。缓解：

   230|1. **替换必须机械、无逻辑改动**。冲突时的解法是「取上游版本，再重跑一次替换」，而不是逐行手工合并。为此第 2 步单独成 commit，且 PR 描述里写明这一点。
2. `datapath-guard` **是安全网**。合并完只要 CI 红，就说明上游带回了新的 home 写入点，定位成本从「全仓 review」降到「看 CI 输出」。
3. **不改上游函数签名**。`config.Path()`、`serveproc.PidPath()` 等对外签名保持不变，只换内部实现，这样上游对这些函数的新调用点合并进来即自动正确。
4. 详见 `../../../上游合并策略.md` §3「高冲突面清单」。
