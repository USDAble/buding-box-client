## 1. 相位与判定入口（已实现）

### 1.1 三个相位

`web/src/lib/product.ts` 的 `productPhase` 只有三个取值，**没有任何"半可用"的中间态**：

| 相位 | 含义 | 界面 |
| --- | --- | --- |
| `unknown` | 还没问过服务端 | 空白/加载（`App.svelte:607`） |
| `blocked` | 未登录，或产品路由不可达 | **拦截页**（`App.svelte:609` → `BlockedView`） |
| `ready` | 已登录 | 主界面 |

**为什么 `blocked` 同时承载"未登录"和"路由不可达"**：两者对用户是同一件事 —— **进不去**。分成两个相位会让主界面多一个"该不该显示"的分支，而那个分支的判断依据与 `blocked` 完全相同。**区分发生在拦截页内部（§2/§3），不发生在相位上。**

### 1.2 唯一的入口

`refreshProductState()` 是**唯一**决定相位的函数，前端启动时调用一次：

```
windowToken() 为空 ──▶ phase = "ready"（浏览器直连 `octo serve`，产品门形同不存在）
                    │
                    └─▶ GET /api/product/state（带 X-Octo-Window-Token）
                          ├─ 200 → state.loggedIn ? "ready" : "blocked"
                          └─ 非 200 / 抛错 → "blocked"
```

**两处容易被误改的点：**

1. **`windowToken()` 为空就直接 `ready`，这不是降级**。普通浏览器（`octo serve`、开发期）本来就没有窗口身份，产品门对它不存在（`本地API契约` §1.1）。把它当降级会让 `octo serve` 的界面永远停在登录页。
2. **`catch` 里的 `blocked` 是有界降级（§3.9）**：目标是"让用户能重试登录"，不是"假装没事继续用"。**它必须保持可见** —— 若改成静默继续渲染主界面，就变成了向未授权来源降级。

## 2. 两个「未配置」页（`L-B2` · ⚠️ 页面待实现）

### 2.1 它们是两件事，不是一件事

| 状态 | 判据（**唯一 owner** `internal/productprofile/profile.go`） | 含义 | 谁的错 |
| --- | --- | --- | --- |
| **未配置控制面** | `ControlPlaneConfigured() == false`（:90） | 这个构建**没写**中台地址 | **出包事故**（正式构建）／预期状态（developer 构建未填 Sandbox） |
| **无信任公钥** | `HasTrustedKeys() == false`（:97） | 有地址，但**没有任何公钥**，签名目录一律验不过 | **出包事故** —— 等价于永远拿不到目录（`A1` 规则 6） |

**为什么必须两页不同文案**：两者都是"出包事故"，但**用户能做的事不同**。前者用户无论怎么试都不通（要换包）；后者是"能登录但看不到模型"。把两句合成一句"未配置"会让前者看起来像网络问题、让用户反复重试。

**两页的共同硬约束（`A1` 规则 6）：不出现 URL、不出现技术名词。** 用户看不到 `apiHost`、看不到 "production.json"、看不到 "trustedKeyIDs"。**原因是这不是用户可以修的东西** —— 出现地址只会让人以为"是不是填错了"，而他们没有任何地方可填。

### 2.2 判据怎么到达界面

**现状的问题**：`ControlPlaneConfigured()` 只在装配期被用一次（`cmd/octo-desktop/product.go:98`），结果是 `Platform = nil`；用户要**点了登录**才会拿到 `control_plane_unconfigured`。`HasTrustedKeys()` **完全没有调用点**，所以"无公钥"这一页今天没有任何信号能触发它。

**方案（待确认）**：新增一个只读端点，把两个布尔值送到界面，使拦截页在用户输入前就能分页。

| 项 | 定 |
| --- | --- |
| 端点 | `GET /api/product/control-plane` |
| 应答 | `{"configured": <bool>, "hasTrustedKeys": <bool>}` |
| 判定位置 | **`internal/productprofile`**（两个判据的唯一 owner）；`productruntime` 只转发，不自己判断 |
| 是否需登录 | 否 —— 未登录时正是要显示它 |
| 为什么不用 `GET /api/product/state` | `ProductStateDTO` 是**状态文件 `product-state.json` 的投影**（`E6.1`），而这两个值是**编译期 Profile 的事实**，与用户数据无关。塞进 state 会让"state = 磁盘状态"这条映射失效，也把两个 owner 混进一个 DTO |

**前端分页规则（优先级从上到下）：**

```
control-plane 读取失败        → 保持 "blocked"，渲染未登录表单（保守：不因读不到而谎报"未配置"）
hasTrustedKeys == false       → 渲染「无公钥」页
configured == false           → 渲染「未配置」页
两者都正常                    → 渲染未登录表单（BlockedView）
```

**顺序不可交换**：`hasTrustedKeys` 更早判定，因为"有地址但没公钥"与"没地址"相比，前者已经越过了配置检查，是更靠后的失败。

### 2.3 有界降级（§3.9）

| 情形 | 降级到 | 用户被告知 | 何时恢复 |
| --- | --- | --- | --- |
| 新端点读取失败 | 未登录表单 | 否（用户只看到正常的登录页） | 下次启动；**不谎报"未配置"** |
| `ControlPlaneConfigured()==false` | 「未配置」页 | 是 | **不自行恢复** —— 要换构建 |
| `HasTrustedKeys()==false` | 「无公钥」页 | 是 | **不自行恢复** —— 要换构建 |

**绝不**因为这两个状态而"回落到本地模型源"（`A1`/`B1`）—— 那正是 `S-6` 明确否决的做法。

## 3. 控制面四档失败（`L-B3` · ⚠️ 四档 UI 待实现）

### 3.1 档位与判定位置

**判定只在 `internal/productclient` 一处实现（`需求基线` `C12`）**，`productruntime` 与前端都只**消费**档位，不重新判断。理由（§3.8）：四处各判一次，中台改一个状态码就要改四处，且四份必然漂移。

| 档 | 触发（`productclient`） | 本地 HTTP | 可重试性 | **凭证语义** |
| --- | --- | --- | --- | --- |
| `network_unavailable` | 请求**没到达**中台（`client.go:263/269`） | `503` | ✅ **可重试**，且**自动重试无意义** —— 是网络/拔盘，让用户手动重试 | **不动凭证** |
| `upstream_unavailable` | 中台 **5xx**（`client.go:308`） | `503` | ✅ 可重试（用户手动） | **不动凭证** |
| `unauthorized` | 401 且**刷新被拒** → `ErrSessionExpired`（`dto.go:55`） | `401` | ❌ **不可重试** —— 拒绝的 refresh token 不会自愈（`E12`） | **清凭证**（§4） |
| `account_restricted` | 403 + `account_restricted` 族 | `403` | ❌ 不可重试 | **不清凭证** —— 账号被限制不等于会话失效 |

**这两列的区分是本节的要点**："能不能重试"和"要不要清凭证"**不是同一个问题**。把 `account_restricted` 也清凭证，用户会连账号绑定一起丢掉，而限制解除后本该能直接恢复。

### 3.2 为什么 `network_unavailable` 必须与 `upstream_unavailable` 分开

两者的**可重试性相同**，但**归因不同**，而归因决定用户该做什么：

- `network_unavailable` = **本机到中台的链路断了**（没网 / 拔盘 / DNS）。用户能做的是**检查网络**。
- `upstream_unavailable` = **中台自己挂了**（5xx）。用户什么都做不了，只能等。

合成一句"服务不可用"会让前者的用户去等一个不会好的东西。这条区分已在 `中台交付包.md` §3.2 登记（`v0.9`），由 `productclient` 生产。

### 3.3 四档的 UI 要求

| 档 | 文案要求 | 必须提供的动作 |
| --- | --- | --- |
| `network_unavailable` | 说"连不上"，**不说**中台/服务器 | 「重试」按钮 |
| `upstream_unavailable` | 说"服务暂时不可用，请稍后再试" | 「重试」按钮 |
| `unauthorized` | **不显示错误**，直接回拦截页（见 §4） | 无（自动） |
| `account_restricted` | 说明账号当前不可用 | **客服入口**（`V-4`：渠道载体未定，本轮至少给一个确定动作） |

**`account_restricted` 的客服入口依赖 `V-4`。** `V-4` 未解决前，本节该档只能做到"文案 + 一个确定动作"，不能引用一个不存在的联系方式 —— 界面上出现"请联系客服"而没有任何联系方式，是本文件**明确要避免**的死路。

## 4. 会话失效 → 清凭证 → 回拦截页（`L-A6` · ✅ 已实现 2026-09-12，见 §4.5）

### 4.1 识别

**唯一判据是 `productclient.ErrSessionExpired`**，判断函数是 `productruntime.IsSessionExpired`（`runtime.go:333`）。它的含义被限定为**极窄的一句**：

> refresh token **没了**，或被中台**明确拒绝**了。刷新一次仍然失败。

**它不包含**：401 但刷新**成功**（那是正常轮换，用户无感）、网络不可达（那是 `network_unavailable`）、5xx（那是 `upstream_unavailable`）。**这三者都不得清凭证** —— 一次网络抖动就登出用户，等于把可用性问题放大成数据问题。

### 4.2 时序（顺序不可交换）

```
中台应答 401
  → productclient 单飞刷新一次（C2 规则 4）
      ├─ 刷新成功 → 重放原请求 → 正常返回（用户无感，**到此为止**）
      └─ 刷新被拒 → ErrSessionExpired
            → ① 清凭证：credentialstore.Delete()
            → ② 清登录态：productstate.Logout()（**保留激活记录与绑定手机号**，E7）
            → ③ 应答 unauthorized
            → ④ 前端 productPhase = "blocked" → 拦截页
```

**为什么必须先清凭证再应答**：反过来的话，前端一收到 `unauthorized` 就会去渲染拦截页，而此刻 `credential.json` 还在盘上。用户重开一次窗口，`refreshProductState()` 读到"仍有凭证"而走 `loggedIn` 分支 —— **界面与磁盘不一致**，且这个不一致会一直留到用户手动登出。

**为什么保留激活记录**：会话失效 ≠ 未激活。丢了 `data/` 才是丢激活。保留 `activated` 与绑定手机号，二次登录才能走"只填手机号 + 验证码"的短路径（`E2` / `E7`）。

### 4.3 与登出的区别（`E7`）

| | 会话失效（本节的自动路径） | 用户点登出（`POST /api/product/logout`） |
| --- | --- | --- |
| 凭证 | 删 | 删 |
| `loggedIn` | false | false |
| `activated` | **保留** | **保留** |
| 绑定手机号 / 昵称 | **保留** | **保留** |
| 用户被告知 | 是（回到拦截页，可重登） | 是（同上） |

两者**唯一相同的结果是"回到拦截页"**，实现可以是同一条路径。但**触发源不同**：一个是"中台拒绝了"，一个是"用户主动要求"。

### 4.4 有界降级（§3.9）

| 情形 | 降级到 | 用户被告知 | 何时恢复 |
| --- | --- | --- | --- |
| 清凭证失败（只读盘 / 拔盘） | **仍然回拦截页**（内存相位已 `blocked`），但**失败被记为 `slog.Error`**（含 cause） | 是 | 磁盘可写后，下次登出/失效会再试；**绝不"清不掉就假装还登录着"** |

**这一条是本节最容易做错的地方**：清盘失败时若"什么都不做、继续当已登录"，用户会停在一个所有请求都会 401 的界面上（每个请求都触发一次失败刷新），且无法自行脱困。**内存相位必须先把界面带回拦截页，磁盘是第二步。**

**已实测（`PR-2c`）**：`TestUnreadableCredentialStillReturnsToTheLoginPage` 把数据根 `chmod 0500`，`Creds.Delete()` 与 `State.Logout()` **双双失败**（日志可见两条 `permission denied`），而应答仍是 `401 unauthorized`、`loggedIn` 仍是 `false` —— 即"清不掉也必须回拦截页"这条真的成立，不是纸面约定。**注意它同时说明 `State.Logout()` 是"先改内存、后落盘"**：落盘失败不会把内存相位留在已登录。这是有序写入的刻意结果，改动写入顺序会同时破坏本节。

### 4.5 落地记录（2026-09-12，`PR-2c`）

| 环节 | 落点 | 说明 |
| --- | --- | --- |
| 唯一汇合处 | `productruntime.failPlatform`（`runtime.go:346`） | `send-code` / `login` 两个 handler 都改走它。**存在的理由是让规则无法被漏掉**：新加一个 handler 若不用它，就等于连错误映射一起没写 |
| 清凭证 | `forgetSession`（`runtime.go:369`） | `Creds.Delete()` → `State.Logout()`，**顺序即 §4.2 的时序**。清盘失败**不阻断**后续：只记 `slog.Error`，`Logout()` 仍执行（§4.4） |
| 映射 | `envelope.go:76` | `errors.Is(err, productclient.ErrSessionExpired)` → `401 unauthorized`。**这一行是 `V-21` 的修复点**：此前它落进"请求没到达中台"分支，被报成 `503 network_unavailable` |
| 契约登记 | `本地API契约.md` §3 新增 `unauthorized` 行（`v0.4`） | 该码此前**两端都没登记**，这是误分类长期无人发现的原因 |
| 前端规则 | `noteSessionLost`（`product.ts:103`） | 收到 401 ⇒ `phase=blocked` + 把 `productState.loggedIn` 置 `false`（**只改这一个字段**，§4.5.1） |
| 前端调用点 | `productFetch`（`product.ts:115`）与 `api.ts` 的 `request` | 两处覆盖了"走 product 模块的调用"与"走通用取数层的调用"两类 |

#### 4.5.1 一个实现取舍：为什么不重读 `/api/product/state`

本来更"正统"的做法是会话失效后重读状态（服务端是 state 的 owner）。**没有这么做，两个理由**：

1. **会递归**：重读走 `productFetch`，而 `productFetch` 正是调用 `noteSessionLost` 的地方 —— 一旦状态读取本身返回 401（中台不可达时完全可能），就是无限循环。
2. **不需要**：服务端保留了 `activated` 与绑定号码（`E7`），而拦截页只读这两个字段来决定表单形态与预填。失效后**这两个值恰好都没变**，重读拿到的是同一份；唯一变了的是 `loggedIn`，已经在本地改掉。多一次请求只是多一次失败机会。

**若将来拦截页开始依赖更多字段**，应当改成"重读 + 显式的重入保护"，而不是继续在本地拼状态 —— 本条记录是为了让那次改动知道边界在哪。
