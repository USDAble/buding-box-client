## 本批次特有的三个结论（读到这儿就够了）

1. **「真正和模型通信」的代码已经存在，不重写。** `config.Endpoint` → `app.SenderOptions` → `app.NewSender` → `internal/provider/openai`（SSE 聚合、tool call 分片拼接、usage 归一、限流、自定义 Headers）全部可用。**联调期按「零改动」路径即可跑通**：标准 `chat/completions` + 目录 `id`。协议里没有的产品事件/字段（`retract`、账本终态、`clientRequestId`、`toolPolicy`）统一登记在 [`待解决问题.md`](待解决问题.md) `D-002` / `D-003`，上线前一次补齐。
2. **`《中台交付包》§5.3` 的 `event: xxx` 写法与现有解析器不兼容。** `internal/provider/openai/stream.go:152` 会**静默丢弃**所有非 `data:` 开头的行 —— 若按 `event: retract` 发，安全撤回会在客户端静默失效。建议改为在 `data:` 行内扩字段（已迁出为 [`待解决问题.md`](待解决问题.md) `D-002`，联调期不收 `retract`，但**兜底必须留**：未知顶层字段要报错或打 error 日志）。
3. **模型列表只来自中台签名目录**，不内置名单；`data/chat-modes.json` 不再落盘；`data/config.yml` 的 endpoint **只在 `developer` Profile 生效**（中台真实地址与验签公钥是它的前置，见 [`待解决问题.md`](待解决问题.md) `D-001`）。

**联调期没有任何阻塞项。** 最省路径是**零改动**：标准 OpenAI 请求 + 目录 `id`，不加字段、不发 `clientRequestId` / `toolPolicy`、不收 `retract`，走 `developer` Profile。上线前再把 `D-002` + `D-003`（都在同一个改动位置）一次补齐。已决定暂不解决的是 `D-001`（中台地址与验签公钥）、`D-002`（`retract` 与账本终态）、`D-003`（`clientRequestId` / `toolPolicy` / `model` 语义）。

**但"走 `developer` Profile"能真跑起来，有两个前提（`V-8` / `V-9`，2026-09-11 补）：**

1. **`developer.json` 里已填 Sandbox 的地址与签名公钥。** 未填则 `ControlPlaneConfigured()` 为 `false`，界面停在「未配置」页（`A1` 规则 6/7）。取值 owner = 中台（`S-8`）。
2. **已删掉 `web/src/dev/devBackend.ts`。** 它无条件替换 `globalThis.fetch` 接管全部 `/api*`，不满足时联调**不是"有阻碍"，而是"看起来通过"** —— 假数据形状合法、界面完全正常（`G5`）。

**但「开工」已经没有任何阻塞项。** 原唯一阻塞项 `PQ17`（登录凭证放 `data/` 还是 OS 凭证库）已于 2026-09-11 拍板：**明文存 `data/credential.json`、随 `data/` 复制**；复制后的安全性明确暂后，登记为 [`待解决问题.md`](待解决问题.md) `D-004`（其中「中台可撤销单个 refresh token」与「客户端 401/403 清凭证回拦截页」仍为上线前必须）。其余决策点（`PQ18`–`PQ24`）都已给最简取法。

**最高优先级的对外索取：中台的 OpenAPI 3.1 + Sandbox + 测试激活码 + contract test**（[`需求基线.md`](需求基线.md) §5.3 `S-8`）—— 没有这四样，`internal/productclient` 的字段名只能靠猜，之后必然返工。

**当前阶段原则（[`需求基线.md`](需求基线.md) §0）：先把流程走通，再解决其他问题 —— 实现一律选不增加复杂度的那条路。** 未定项都已按此给出「最简取法」（见 [`待确认问题清单.md`](待确认问题清单.md) §1），可直接照做；`v1` 已从最新 `base` 切出并推送，本批次即其需求基线。
