## 0. 文档范围（开发规范 §3.10）

**这份文档写的是 P3 的前端半：静态 UI 与交互。** 具体是——登录态在界面上的三态呈现、窗口令牌在前端的全生命周期、登录 / 激活表单本身，以及每个字段与按钮做什么。

**不在本文档内**：`internal/productstate`、`internal/productgate`、`/api/product/*` 路由的实现与校验规则。那部分不在本分支上，登记在 20260909 线。本文档只说明这些页面**期望**后端给出什么形状的应答（§4.2），形状的唯一来源是[《中台交付包》](../../20260911/中台交付包.md) §3.2（错误码）与 §4.2（账号接口），本文档不复制它们。

**原 P4（拦截页 = 登录表单）的 UI 部分并入本文档。** 理由：拦截页就是登录表单（需求 §5.3.1 明写「不要先做一页只有『登录』按钮再跳转」），在静态 UI 这一层它与产品门是**同一个页面、同一份状态机、同一组 store**。拆成两份文档会让状态机在第 3 节、表单在第 4 节、错误码映射在两处各写一半，正是开发规范 §3.8 要禁止的「同一件事两个定义」。P4 的**后端**（`/login` `/send-code` 的校验顺序与假码规则）仍归 P4。

## 1. 目标与非目标

**目标**

1. 定义产品门在前端的**三态状态机**（`unknown` / `blocked` / `ready`），并让 `App.svelte` 顶层按它分支——未登录只渲染登录页，没有任何「跳过 / 游客」出口。
2. 落地**窗口令牌**的前端生命周期：接入 → 存放 → 每个出网点带回去 → 从地址栏抹掉。这是前端半唯一「漏一处就等于没做」的地方（§3.3）。
3. 落地登录 / 激活表单的全部静态 UI 与交互：两种形态、两轮校验、60 秒倒计时、昵称默认值与语言联动、语言切换、协议/隐私弹层。
4. 把服务端返回的**机器码**映射成当前语言的文案——只做映射，不自己发明码值。

**非目标**

- 不做后端（`productstate` / `productgate` / `/api/product/*`），见 §0。
- 不做真实鉴权、不做 token 过期（需求 §5.3.5 明确本期不做过期）。
- 不做「退出登录」按钮的位置与确认框——按钮在 P5 的账户面板；本方案只提供 `logout()` 与状态回退。
- 不做主界面入口隐藏（P6）、不做昵称的服务端敏感词判定（P8）。
- 不做「前端门」的安全兜底。**前端门拦不住 F12 与 `curl`**，这是设计而非疏漏，见 §9.3 与需求 §9.8。

## 2. 现状（代码事实）

**上游已有的两道东西，都不解决本需求**

- 机器门：`internal/server/auth.go:28` 的 cookie `octo_access_key` + `requireAuth`，对 loopback 豁免（`internal/server/auth.go:98 isLoopbackRemote`）。前端对应 `web/src/lib/auth.ts` 与 `web/src/components/overlays/AuthGate.svelte`。
- 工具权限门：`internal/app/gate.go`。这是**工具调用**的权限引擎，作用面与本需求无关，不要混。

**上游没有的**

- 没有「用户身份」概念。`internal/server` 里没有 session / user 中间件可复用——上游是单机单用户。
- `App.svelte` 顶层只有 `authDenied` → `onboardPhase` → `mobileShell` 三个分支（`web/src/App.svelte:605-620`），没有「未登录」这一态。
- `web/src/lib/api.ts:43` 的 `request()` 不携带任何「窗口身份」凭证；`web/src/lib/ws.ts:48` 的 `/ws` 连接同样没有。
- 拦截页 / 登录表单 / 激活表单：上游不存在，本批全部新增。

**本分支缺的东西（决定了 §9.1）**

本分支**没有**这些页面所调用的后端。`/api/product/state`、`/send-code`、`/login`、`/logout`、`/locale`、`/nickname`、`/prefs` 全部 404。因此本分支带一份 **dev-only 假后端**（`web/src/dev/devBackend.ts`），只为让这套 UI 在浏览器里点得通；它与真实现的对应关系、以及删除步骤，登记在[《开发期假后端说明》](开发期假后端说明.md)。**假后端里的任何校验细节都不是设计，不要照抄进真实现。**

## 3. 设计

### 3.1 三态状态机

前端只有三个状态，`App.svelte` 顶层按它选渲染什么：

```
窗口打开
  │
  ├─ 没有窗口令牌（普通浏览器 / octo serve）──────────▶ ready
  │     门不生效：后端认不出「窗口」，本机没有产品登录这回事
  │
  └─ 有窗口令牌 → GET /api/product/state
        ├─ 成功且 loggedIn ─────────────────────────▶ ready
        ├─ 成功且未登录 ───────────────────────────▶ blocked
        └─ 请求失败 ───────────────────────────────▶ blocked
```

| 状态 | 渲染 | 代码 |
| --- | --- | --- |
| `unknown` | 全屏 spinner | `web/src/App.svelte:607-608` |
| `blocked` | `<BlockedView />`（登录 / 激活表单） | `web/src/App.svelte:609-612` |
| `ready` | 继续走 `onboardPhase` → 主界面 | `web/src/App.svelte:613-617` |

两处「状态漂移」也收敛到 `blocked`：

- 任何一个请求返回 `403` 且 `error === "product_gate"`（例如另一个窗口退了登录）——`web/src/lib/api.ts:56-58`。
- `/api/product/state` 本身读失败——`web/src/lib/product.ts:98-102`。

**为什么读失败落 `blocked` 而不是 `ready`**：这是有界降级（开发规范 §3.9）。降级目标 = 登录页；用户看得到（不是白屏或死 spinner）；恢复方式 = 重新登录一次。反过来选 `ready` 会让未登录的人直接进主界面，属于「降级即授权」，不允许。

### 3.2 窗口令牌的前端生命周期

```
桌面壳启动 ── 生成 32 字节随机（仅内存）──▶ 注入 webview URL ?window_token=…
                                                │
                     adoptWindowToken() ←───────┘   （web/src/App.svelte:51，模块初始化期，早于任何 fetch）
                                │
                                ├─ 存 sessionStorage
                                └─ history.replaceState 抹掉地址栏参数
                                │
                后续每个出网点把令牌带回去（§3.3）
```

三个取舍写清楚：

- **为什么 `sessionStorage` 而不是 `localStorage`**：令牌是进程内内存态，一个窗口一份、重启即换（`web/src/lib/product.ts:25-28`）。`localStorage` 会把 A 标签页的令牌留给 B 标签页，而 B 可能是另一个壳实例。
- **为什么要抹地址栏**（`web/src/lib/product.ts:69-76`）：令牌留在 webview 历史里就等于留在磁盘上，与它「仅内存」的前提冲突。做法与上游 `?access_key=` 一致（`web/src/lib/auth.ts` 头注释）。
- **为什么不需要吊销**：重启即换新值，旧值随进程消失。

### 3.3 三个出网点必须全覆盖

**这是前端半唯一的系统性风险。** 门只拦「带了令牌的请求」；窗口内的请求**漏带**令牌，会被后端当成 loopback 同伴（CLI）而放行——也就是说，漏带不是报错，是**静默地让门对该请求失效**。

| 出网点 | 覆盖了什么 | 落点 |
| --- | --- | --- |
| `request()` | 绝大多数 API | `web/src/lib/api.ts:43-48` |
| `withWindowToken()` | 不能走 `request()` 的调用（409 冲突、multipart 上传、blob 下载） | `web/src/lib/api.ts:69-81` |
| `/ws` 握手 | WebSocket 不能自定义 header，令牌走查询参数 | `web/src/lib/ws.ts:48` + `web/src/lib/product.ts:80-83` |

`web/src/lib/api.ts:69-75` 的注释写明了这条约束，就是为了让后来加 fetch 的人知道：新开一个绕过 `request()` 的出口时，必须自己调 `withWindowToken()`。

### 3.4 登录表单：两种形态共用一个组件

形态由**服务端的激活标志**决定，不由前端猜（需求 §5.3.4；`web/src/views/BlockedView.svelte:33` 的 `activated` 派生自 `$productState`）。

| | 首次激活（数据根内无绑定） | 二次登录（已有绑定） |
| --- | --- | --- |
| 字段 | 手机号、验证码、昵称、**激活码** | 手机号、验证码、昵称（**无激活码**） |
| 昵称初值 | 按当前语言随机生成 `用户1234` / `User1234` | **预填上次昵称** |
| 主按钮 | 「激活并登录」 | 「登录」 |
| 代码 | `web/src/views/BlockedView.svelte:188-195` 的 `{#if !activated}` | 同处的取反分支 |

昵称初值的三条规则（`web/src/views/BlockedView.svelte:35-44` 的 `onMount` 与 `:46-53` 的 `pickLang`）：

1. 有绑定账号 → 用账号里的昵称，切语言**不覆盖**。
2. 无绑定 → 按当前界面语言生成随机昵称。
3. 用户手动改过（`nicknameEdited`）→ 切语言不覆盖。**语言切换永远不抹掉用户正在输入的内容。**

### 3.5 两轮校验

需求 §5.3.3 要求「格式类错误全部同时标在对应字段旁，不因前一个失败而隐藏后面的」。

- **第一轮 · 格式**（`web/src/views/BlockedView.svelte:92-96`）：手机号规范化、验证码 6 位、昵称 2–16 字、激活码非空。用 `errs` 对象一次收齐**全部**失败项，再一次性挂到 `fieldErrors`，所以四个字段的错误同时亮。
- **第二轮 · 业务**：交服务端按「验证码是否已发送且正确 → 激活码是否正确」顺序判（需求 §5.3.3）。前端**不**判这两件事，也不预判顺序；服务端失败就留在本页，把返回的机器码渲染成文案。

客户端只做格式校验，是为了避免同一个规则在前后端各写一份（§3.8）——格式规则同一份在 `web/src/lib/phone.ts` / `web/src/lib/nickname.ts`，业务规则只有后端一份。

### 3.6 未登录时允许的两件事

需求 §5.3 前言 + §5.3.1 末段：未登录**可以**切界面语言、**可以**打开用户协议 / 隐私政策，除此之外不得改配置。

- 语言：`pickLang()`（`web/src/views/BlockedView.svelte:46-53`）调 `setLocale()`（立即重渲染）**并** `setProductLocale()` PUT 写数据根。写入失败被吞掉是有意的——UI 语言已经切了，不该因为落盘失败弹错。
- 协议：`LegalModal`（`web/src/views/BlockedView.svelte:212-217`），入口在页脚（`:204-208`），文案取自 `branding`，不在此处硬编。

### 3.7 错误码 → 文案：两层，不混用

前端有**两套**错误码，来源不同，必须分开看：

| 层 | 谁产生 | 取值 |
| --- | --- | --- |
| 格式码（第一轮） | 前端自己 | `invalid_phone`、`invalid_code`、`nickname_format`、`nickname_sensitive`、`invalid_activation` |
| 业务码（第二轮） | 服务端 | `code_not_sent`、`invalid_code`、`activation_invalid`、`phone_mismatch` |

映射分两个函数：格式码在 `web/src/views/BlockedView.svelte:119-128`，业务码在 `:130-139`。

**服务端码的取值唯一登记在[《中台交付包》](../../20260911/中台交付包.md) §3.2**，前端只做 `code → i18n key` 的映射，不自己发明取值、不解析 `message`。渲染走 `$t(key)`（`web/src/views/BlockedView.svelte:156-160`）而不是把文案存进 state，这样切语言会跟着重渲染。

已知的一处不齐见 §9.2。

### 3.8 退出登录

`logout()`（`web/src/lib/product.ts:109-117`）清服务端登录态、清 `productState`、把 phase 落回 `blocked`。服务端保留 `activation` 与 `credits`（需求 §5.3.5：退出登录不删积分、不删激活绑定）。**按钮不在本方案**——它落在 P5 的账户面板。

- `web/src/lib/nickname.test.ts`：中英两语言的随机格式、2–16 字边界、非法字符。

**手工验收**（走一遍，就是需求的 §5.3 全流程）

1. 未登录打开 → 只有登录页，无「跳过 / 游客」；右上角能切中 / 英，Logo 字随之变（布 / B）。
2. 不点「发送验证码」直接提交 → 「请先获取验证码」。
3. 点发送 → 按钮进入 60 秒倒计时且不可再点；重发刷新。
4. **先点发送、再输错验证码 → 红条显示「验证码不正确或已过期」且确有文字。** 这条专门钉住 §9.2 修掉的空白横幅，因为映射表的 `default` 分支就是返回空串，错了不会报错、只会静默变空。
5. 首轮：把手机号、验证码、昵称、激活码**同时**填错 → 四条错误**同时**显示（不是只显示第一条）。
6. 首次激活填对 → 进主界面；重启进程 → 直达主界面（token 无过期）。
7. 二次登录：改昵称输入框 → 提交不匹配的手机号 → 「此程序目录已绑定 138****1234」且不回显完整旧号。
8. 已登录状态下用 `curl`（不带令牌）打 `/api/sessions` → 放行（这是有意的，见需求 §9.8）。
9. 已登录状态下 F12 里 `fetch('/api/sessions')`（带令牌）→ 后端半就绪时应 403 并落回登录页。

第 4 条目前**只有手工验收、没有单测**：`businessErrorKey()` / `fieldErrorKey()` 是组件内私有函数，vitest 覆盖不到。要自动化需要先把它抽出成可导出的纯函数（映射表 → i18n 键），顺带就能加一条「§3.2 登记表里的每个码都有映射」的断言——那正是防住 §9.2 复发的手段。留待后端半接入时一并做。

## 7. 上游合并影响

**等级：低。** 除了 §5 表里那 7 行接线，其余全是新增文件。

风险点两个：

1. **`api.ts` 的 `request()` 是上游高频改动点。** 合并冲突时取上游版本，再把 `withWindowToken(init?.headers)` 这一处重新包上——改动只有一行，重做成本低。若上游新增了绕过 `request()` 的 fetch 出口，需要人工判断是否补 `withWindowToken()`；§3.3 的注释就是为了让人合并时能看见这条约束。
2. **`App.svelte` 顶层的分支链。** 上游若在 `authDenied` 与 `onboardPhase` 之间插入新分支，需要确认 `productPhase` 的 `blocked` 仍在最外层之一——未登录优先于一切，顺序不能反。

两处都不是「高」等级：没有散布在几十个文件里的机械替换，也不需要新的 CI guard。

## 9. 风险与决策

### 9.1 本分支没有这些页面的后端

页面调用的 `/api/product/*` 在本分支全部 404，离开假后端就登不进去。处理：`web/src/dev/devBackend.ts`，**临时件**，只提供走通流程所必需的应答；安装点门在 `import.meta.env.DEV` 后（`web/src/main.ts:18`，块起始于 `:9`），生产构建把调用消除、模块被 tree-shake。真实现落地后整体删除。对应关系与删除步骤见[《开发期假后端说明》](开发期假后端说明.md)。

**假后端刻意不做的事**：字段校验、手机号绑定与脱敏、词库去重、真实持久化、WebSocket 事件流。在假后端里复现这些会造出契约的第二个定义（开发规范 §3.8），以后必然与真实现漂移。

### 9.2 ✅ 已收敛：`code_invalid` → `invalid_code`

**已解决，2026-09-11。** 保留记录是因为它会复发：任何人在前端新增一个业务码映射时，都可能再写一个 §3.2 之外的名字。

原问题：`web/src/views/BlockedView.svelte:133` 映射业务码 `code_invalid`，`web/src/dev/devBackend.ts:227` 也返回 `code_invalid`。但[《中台交付包》](../../20260911/中台交付包.md) §3.2 的登记值是 **`invalid_code`**——同一份文档 §4.2 还专门留了一条更正记录，说明 `code_invalid` 是旧命名、已按 §3.2 收敛。这也是[《需求基线》](../../20260911/需求基线.md) §1.3 登记的待修项。

后果：`businessErrorKey()` 的 `switch` 认不出 `invalid_code`，落 `default: return ''`，**用户看到一条没有文字的红色横幅**。假后端一直在返回旧码，把这个 bug 完美遮住——假后端与前端"各自都能跑"，接真后端才露馅。

处理：按开发规范 §3.8 取值以 §3.2 为唯一来源，改前端与假后端、不改登记表。三处：

| 位置 | 改动 |
| --- | --- |
| `web/src/views/BlockedView.svelte:133` | `case 'code_invalid'` → `case 'invalid_code'` |
| `web/src/dev/devBackend.ts:227` | 应答值 `code_invalid` → `invalid_code` |
| `web/src/lib/i18n.ts:986, 2059` | 键名 `product.err_code_invalid` → `product.err_invalid_code` |

第三项是顺手做的：i18n 键名只是内部标签，但留着 `code_invalid` 子串会让以后 grep 这个废弃码时误命中（§3.8 的同一个考虑）。改名后全仓代码里再无该字面量。

**验证方式**：改之前先说清它会怎么坏、改完怎么证明——故意输错验证码，红条应显示「验证码不正确或已过期」（英文界面为 "Verification code is incorrect or expired"）而非空白。改后实测通过，0 运行时错误。

**仍未收敛的同类风险**：`businessErrorKey()` 与 `fieldErrorKey()` 的 `default` 分支都返回空串——认不出的码会静默变成空文案。真后端落地后应改为「至少回落到一句通用错误」，或加一条断言把「登记表里的码都有映射」固定住。这条留待后端半接入时处理。


### 9.3 前端门拦不住 F12 与 `curl`

只在前端判断登录态的写法是可绕过的。本方案的定位是「让令牌在窗口内每个出网点都带上」，真正的拦截判定在后端半；需求 §9.8 也已把「本机其它进程仍可能访问 loopback API」列为已知限制。**不要把这条当 bug 上报**——它是写明的边界，且已在 §6 的手工验收第 7、8 条固定住行为。

### 9.4 `productState` 读失败落 `blocked`

见 §3.1 的有界降级说明：降级目标明确（登录页）、用户可见（不是白屏）、可恢复（重新登录）。不选 `ready`，因为那等于把降权当授权。

### 9.5 令牌经 URL 传递

会进 webview 历史，因此接入后立刻 `history.replaceState` 抹掉（§3.2），与上游 `?access_key=` 的既有做法一致。
