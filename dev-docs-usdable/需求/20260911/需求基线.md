## 0. 本文档怎么读

> ### 当前阶段原则（2026-09-11，人工决定）：**先把流程走通，再解决其他问题**
>
> 实现一律选「**不增加复杂度**」的那条路。具体判据：
>
> 1. **能复用现成能力，就不新写。** 例：模型通信直接用 `internal/provider/openai`，联调期零改动（见 `D-003`）。
> 2. **能由中台下发/判定，就不在本地判。** 例：额度、免费与否、到期与否，客户端只渲染（见 `PQ7` / `PQ8`）。
> 3. **能先占位，就不做半成品。** 例：更新渠道与支付先挂占位（见 `PQ12`）。
> 4. **未定项取最简口径，把复杂度留在中台侧。** 见 `PQ7`–`PQ12` 每条的「当前阶段最简取法」。
> 5. **不得为「更完整」引入第二套**解析器 / 映射表 / 存储（§3.8、§3.5）。
>
> **不适用面（作用域，§3.10）：** 这条原则**只简化功能面，不放松安全面**。以下两条底线不因简化而让步：
> - **失败关闭**：签名 / 版本 / audience / 时钟校验失败一律不用、不放行（`C9`、§3.9）；
> - **不静默降级**：任何降级都必须说明落到哪、用户是否被告知、何时恢复；未知顶层字段必须报错或打 error 日志（`C6` `D-002`）。
>
> 另外：**联调期先跑通 ≠ 上线前可以缺项**。`D-002` / `D-003` 登记的就是「当前故意不做、上线前必须补」的两块，别把「先走通」误读成「不做也行」。

- **§1 现状基线**：当前工区代码到底有什么、缺什么。后面所有「新增」都以这里为基准，不重复实现已存在的部分。
- **§2 功能点总表**：只有名字，供对齐粒度与排期。
- **§3 逐功能点说明**：每条给「要求 / 规则 / 现状 / 验收」。
- **§4 待确认与阻塞项**：只给结论与链接；完整清单见 §4 指向的两份文件。
- **§5 落地缺口**：写代码前还要补的 —— 规格缺口、新决策点（`PQ17`–`PQ24`）、外部依赖、文档冲突。
- **本文档不重复中台合同的字段定义。** 出现字段名、错误码、SSE 事件时只给结论 + 指向《中台交付包》§号（开发规范 §3.8）。

## 3. 逐功能点说明

### A 运行环境与 Profile

#### A1 环境内置配置（编译期 Profile 二分）

**要求.** 「不同环境一份内置配置」这件事**已经存在**，不新造。它必须是**编译期嵌入、运行时不可切**，而不是环境变量或 `data/config.yml` 选出来的「正式/开发环境」。

**规则.**

1. 唯一事实来源是 `internal/productprofile/profiles/{production,developer}.json`，由构建标签 `product_production` 二选一。完整 schema、校验规则、装配顺序见 [`../../运行时Profile配置.md`](../../运行时Profile配置.md)。
2. `production` 的三个 `allow*` 必须全 `false`；`apiHost` / `gatewayHost` 必须是非空、绝对、`https` 的 URL；`trustedKeyIDs` 的每个值是 base64 的 32 字节 ed25519 公钥（**可以为空**，空 = 任何签名都无法验证 = 等同无目录）。
3. **`AllowEnvironmentModelSource` 的作用域必须写进文档并实现**：
   - `production`：正式会话的模型来源**只能是**签名目录 + 中台网关。`data/config.yml` 的 endpoints **不参与**正式会话选模型。
   - `developer`：`data/config.yml` 的 endpoints/URL/key 正常可用，这是本地开发与自动化测试的闭环。
   - 判据用 `Profile.RequiresControlPlane()`（`profile.go:108`），**不要在业务代码里比较 `Profile.Name == "production"`** —— 两个 Profile 不能各自漂移。
4. `apiHost` / `gatewayHost` 不得来自 `config.yml`、环境变量、`product-state.json`、缓存或 WebView 输入。地址是 bootstrap 自身的前提，不可能由远端下发。
   - **作用域（§3.10）：本条约束的是「正式会话」** —— 即 `RequiresControlPlane()` 为真（`profile.go:108`）的生产构建。它**不**禁止 developer 构建把地址写在 `developer.json` 的字面值里 —— 那也是**编译期内置**，同样不是运行时切换。规则的**目的**是「不许运行时选环境」，不是「不许 dev 构建有地址」；把作用域读成后者会直接挡死联调（见规则 7）。
5. 未配置的发布包保留 `.invalid` 占位（RFC 6761 保留 TLD，DNS 永不解析），并由 `Profile.ControlPlaneConfigured()`（`profile.go:90`）与 `HasTrustedKeys()`（`profile.go:97`）把状态暴露给调用方。**`false` 的语义是「拒绝启动控制面」，不是「回退到默认地址」。**
6. **`ControlPlaneConfigured() == false` 时用户看到什么（`S-6`，2026-09-11 定）：专用的「未配置」页，且不给本地可用。**
   - 文案（`i18n.ts` 新增 key，中英两版）：「此安装包未配置服务地址，请联系客服」。**不出现任何 URL、不出现技术名词**（用户无法据此自救，只会增加客服沟通成本）。
   - **不给"进入本地可用模式"的按钮。** 正式包出现这个状态 = **出包事故**（`release-config-guard` 本该在 preflight 拦住它）。让用户"先用本地"等于把一个可发现的构建错误变成静默降级，且这份包永远拿不到模型列表与授权 —— 违背 §3.9「有界降级」：没有可回退的合法来源时应当 fail-closed。
   - **页面要能进诊断包**（`F4`）：把 `profile.name`、`ControlPlaneConfigured()`、`HasTrustedKeys()` 三个值放进诊断信息，客服据此判断是"包发错了"还是"公钥漏了"。
   - 与 `HasTrustedKeys() == false` **文案不同**：有地址但无公钥 = 目录无法验签，提示「服务配置不完整，请联系客服」。两者都拒绝启动控制面，但**客服看到的线索不同**，所以不能合并成一条。
   - **developer 构建出现这一页是预期状态，不是事故**（`V-8`）：`developer.json` 在拿到 Sandbox 地址前就是空的，联调前按规则 7 填上即可。**同一个界面在两种构建下的含义相反**，所以诊断包里必须带 `profile.name`，否则排障时无法区分。
7. **Sandbox 接入方式（`V-8`，2026-09-11 定，人工确认）：developer 构建指向 Sandbox、正式构建指向正式，二者都靠编译期 Profile 二分。**
   - `developer.json` 的 `apiHost` / `gatewayHost` 填 **Sandbox 地址**；`production.json` 填**正式地址**。**不新增第三份 Profile、不加运行时开关、不读环境变量**（这是规则 4 的目的所在）。developer 允许 `http`，Sandbox 无需为此上 TLS。
   - `developer.json` 的 **`trustedKeyIDs` 同样要填 Sandbox 的签名公钥**，否则 `HasTrustedKeys()` 为 `false` = 目录等同不存在，模型列表拿不到，联调只能走到登录为止。
   - **取值 owner = 中台**（§5.3 `S-8` / `D-001`）。**拿到之前 `developer.json` 保持为空**，此时 developer 构建停在规则 6 的「未配置」页 —— 见规则 6 最后一条。
   - **联调自检：** 打 developer 构建 → 不应出现「未配置」页；出现即说明 `apiHost` / `gatewayHost` 还没填。

**现状.** `internal/productprofile` 已落地；`production.json` 目前是 `https://api.invalid/v1` / `https://gateway.invalid/v1`、`trustedKeyIDs` 为空。`ControlPlaneConfigured()` / `HasTrustedKeys()` **在本分支还没有调用方** —— 没有调用方，fail-closed 就只是文档里的一句话。

**验收.**

- 打一个 `production` 包：预设所有开发环境变量 + 写一份含第三方 endpoint 的 `data/config.yml`，正式会话仍不从中取模型。
- `ControlPlaneConfigured()` 为 `false` 时，控制面启动被拒绝，且提示可诊断。

**阻塞.** 真实 `apiHost` / `gatewayHost` / `trustedKeyIDs` 的取值 —— **owner：中台**。客户端不能自己填。

#### A2 生产包拒绝开发旁路

**要求.** `production` 忽略开发 WebView URL、provider/model/key 环境变量、`serve.env` 与 `OCTO_DATA_ROOT`。

**规则.** 逐条对应 `Profile.AllowDevWebview` / `AllowEnvironmentModelSource` / `AllowDataRootOverride`。三个开关都只在 `developer` 允许为 `true`。`Profile.Validate()` 在 `production` 下任一为 `true` 即 `panic`（`profile.go:127` 起）。

**现状.** 机制已在；需要的是 C9（不回落）接上同一个判据。

**验收.** 预设 `OCTO_DATA_ROOT` / `OCTO_DESKTOP_DEV_URL` / `DEEPSEEK_API_KEY` 后，`production` 桌面仍不加载开发 WebView、不切数据根、不用环境 key。

#### A3 数据根与便携工作区（已实现，纳入基线）

**要求.** 数据根 = 可执行文件同级 `data/`，只此一种；进程 cwd = 程序目录；默认会话工作区 = `data/workspace/`。

**规则.** 全部路径走 `internal/datapath`（`Root` / `Sub` / `Join`）。禁止 `os.UserHomeDir()`、禁止 `".octo"` 字面量。主机家目录访问例外只允许进 `scripts/homedir-allowlist.txt`。

**现状.** 已实现，`datapath-guard` 守。本次只做回归，不改。

**验收.** 使用过程中主机用户目录不新增 `.octo` 业务数据；cwd 不是用户家目录（从资源管理器双击亦然）。

#### A4 生产包不出现「配 API Key」向导

**要求.** `production` 包**任何情况**都不出现上游首次运行向导（含名单被删空、开发调试）。名单为空时在选择器内提示「该模式下暂无可用模型」。

**规则.**

1. 上游判定在 `detectOnboardPhase()`（`internal/server/onboard_config_handlers.go:126`）：无 key 时返回 `key_setup`，前端 `FirstRunSetup` 全屏阻塞。
2. 前端已有抑制位 `ProductStateDTO.suppressOnboarding`（`web/src/App.svelte:95` 用它把 `key_setup` 折叠掉）。**后端必须真的把这一位置为 `true`**，且内置网关在「无用户配置 key」时也计入「已配置」。
3. 该判定只作用于 `production`；`developer` 保留原生向导，本地开发链路不变（`A1` 规则 3）。

**现状.** 前端抑制位已在；后端 `detectOnboardPhase()` 仍是上游逻辑，不认内置网关。

**验收.** `production` 包删空所有用户 endpoint 后启动，不进 `key_setup`，直接进主界面并在选择器提示无可用模型。

#### A5 `product_production` 出包门禁

### B 模型目录（聊天框模型列表）

#### B1 目录唯一来源＝中台签名目录

**要求.** 聊天框可选模型**只能**来自中台签名目录。**不内置名单**；`data/config.yml` 的名字、`data/chat-modes.json` 一律不参与。

**规则.**

1. 选择器的全部数据 = 签名目录投影的结果。目录不可得 ⇒ 选择器为空 + 明确提示，**不是**回落到内置名单或本地/环境 endpoint。
2. `data/chat-modes.json` **彻底删除，不再落此文件**。分组成员 = 目录投影，不读任何用户文件；模式 id 三组是产品常量。理由：它当初的用途是「让用户往分组里加模型」，现在用户没有任何可编辑内容，留着只留下「空文件把选择器清空」的陷阱。将来若要做用户自定义分组，走独立 UI + 独立文件，不靠手改 JSON。
3. `developer` 下允许 `config.yml` 的 endpoint 参与选模型（A1 规则 3），但**这条路径必须在代码上与正式路径分开**，不能靠"目录为空时自然落到 config"来实现 —— 那就是静默降级。
4. **`/api/product/chat-modes` 的应答形状（`S-4`，2026-09-11 定）：改为目录投影，唯一登记处是 [`本地API契约.md`](本地API契约.md) §2.8，本节不复述字段。** 三件必须一起改的事：① **删掉 `fallback: boolean`** —— 现有前端类型（`web/src/lib/api.ts:330`）的注释还写着「`chat-modes.json` 不可读时用内置默认」，那是 B1 已作废的行为，**顺着旧形状实现会把内置名单带回来**；② 加双语 `displayName`（B6）；③ 目录不可用时返回**空列表 + 可重试**，**不是** `fallback: true` 加一份内置表。

**现状.** `chatMode.ts:64` 的 `modelDisplayName()` 目前查本地 i18n `model.<id>` 表（见 B6），`devBackend.ts` 提供假名单。

**验收.** 断网 + 无缓存启动：选择器为空，显示不可用提示，不出现任何内置模型名；`data/` 下不产生 `chat-modes.json`。

#### B2 目录验签与本地缓存

**要求.** 目录是**签名信封**：签名覆盖 `data.policy` 值的**原始 JSON 字节**，客户端对**收到的字节**验签、**不做任何规范化**（2026-09-11 拍板，取代早前的 JCS 方案，契约见 `中台交付包` §4.3），验签通过后才使用，并把**原始信封**缓存到数据根。

**唯一 owner：`internal/catalogstore`。** 与 `internal/productstate`（`product-state.json`）、`internal/credentialstore`（`credential.json`）同构，三者各管一个文件、互不兼任 —— 一个包管两个文件会让"包 = 磁盘上那个文件"这条映射失效。

**规则.**

1. 缓存 `data/catalog.json` 保存原始签名信封 + `catalogVersion` / `fetchedAt` / `expiresAt` / `keyId` / `audience`，**原子替换**写入（复用 `internal/atomicfile`）。**`expiresAt` 取两个时间轴的较早者**：policy 的签名窗口与目录自身的新鲜度（`issuedAt + ttlSec`）—— 两条都成立目录才可用（详见 `开发计划` `PR-4b` 第 2 步补充 ②）。
2. 签名 / 版本 / audience / 时钟窗口任一校验失败 ⇒ **fail-closed**：不使用、不覆盖已有缓存、不回落本地 provider。契约见《中台交付包》§4.3 与 §3.1。
3. 版本单调：验签通过后只接受不低于当前的 `catalogVersion`；版本回退视为拒绝。
4. 缓存文件不得是启动期写入的用户可编辑文件（开发规范 §3.9.1）——只有校验通过且版本前进时才写。

**验收.** 篡改缓存里的目录内容 → 下次读取拒绝使用并走 B4；`keyId` 不在 `trustedKeyIDs` → 拒绝，不请求网络重试成功。

#### B3 目录刷新时机

**要求.** 启动异步刷新、按 TTL 周期刷新、陈旧时按需刷新、换账号强制刷新；服务端返回 304 时不重写缓存。

**规则.** 刷新是**后台**动作，不得阻塞主界面渲染，也不得阻塞第一条消息之外的东西 —— 但发消息前若目录已过期，走 B4。

**验收.** 启动瞬间界面可用；TTL 到期后下一次开选择器触发刷新；同一份缓存收到 304 后文件 mtime 不变。

#### B4 目录过期与不可用语义

**要求.** 三种「不可用」必须区分（见《中台交付包》§1.2），每种的用户可见行为不同，且都要写清「回落到什么 / 用户是否被知会 / 何时恢复」（开发规范 §3.9）。

**规则.**

| 情形 | 行为 | 恢复 |
| --- | --- | --- |
| 目录过期且刷新失败 | **不得开启新回合**；老会话可读、可改标题；提示「模型列表需要联网更新」 | 下次刷新成功即自动恢复 |
| 验签失败 | fail-closed，不上屏、不覆盖缓存；终态提示，不自动重试同一份响应 | 服务端换签名/密钥后，下一次刷新 |
| 无缓存 | 选择器空 + 不可用提示，**不弹配 Key 向导** | 首次成功刷新 |

**禁止.** 任何一条都不得回落到 `config.yml`、本地 provider 或内置名单。

**验收.** 三条各造一次；确认无一条会落到本地模型，且用户都能看到原因。

#### B5 选择器结构与模式分组

**要求.** 两级：先模式、后该模式下的模型。选中值仍是某个具体模型；模式同时是**该会话上的属性**。

**规则.**

1. 三个模式 id 为产品常量（隐私 / 智能 / 默认）。**展示名**是界面文案；**分组归属**来自目录。两者不得互相推导。
2. 某模式下列表为空 → 「该模式下暂无可用模型」，禁止空白无说明。
3. 新会话模式取个人中心「新会话默认模式」（出厂「默认」）。
4. 仅改当前会话的选择器，不影响其它会话，不改个人中心默认值。
5. 会话中途改模式只作用于**之后**发出的消息。
6. 会话级「模式」与「模型」是**两个独立属性**，分别持久化。

**现状.** 前端两级的 UI 与 `chatMode.ts` 的 store 接线已在（P9 前端半）。

**验收.** 交互规则回归 [`../2260906/需求20260906.md`](../2260906/需求20260906.md) §5.6 规则 1–8，数据来源改为目录。

#### B6 模型展示名

**要求.** **原样渲染目录里的 `displayName`**。前端**不保留** id→名表。

**规则.**

1. `web/src/lib/chatMode.ts:64` 的 `modelDisplayName(id)` 当前查 `i18n` 的 `model.<id>` 并回落原 id —— 这正是 §3.8 说的「本地表遮蔽服务端」：平台改名后界面会一直显示旧名。**改为渲染目录 `displayName`。**
2. **`displayName` 由目录返回中、英两版（已拍板 2026-09-11）：** 形状 `"displayName": {"zh": "云端旗舰", "en": "Cloud Pro"}`。客户端按当前界面语言取；缺当前语言键时回落 `en`，再缺则回落 `id`。**客户端不做 id→多语言的映射表。**
3. **模型 `id` 一律英文 ASCII（已拍板 2026-09-11）**，如 `buding-cloud-pro`。`id` 是稳定的技术键（网关请求、账本、日志、策略都用它），**不随语言变化，也不做本地化替换** —— 见 §3.3 对 ASCII 数据键的规定。
4. 回落只允许出现在 debug/test 路径；正式渲染路径不得回落。

**验收.** 把目录里某个 `displayName.zh` 改成别的值，刷新后中文界面即变；**同一个模型在英文界面显示 `displayName.en`**；代码里搜不到该模型 `id` 的文案键。

#### B7 模型可选资格与能力矩阵

**要求.** 只有 `eligible = true` 且 `transport = gateway` 的模型可选。首发入口可见性由能力矩阵决定。

**规则.**

1. `visible = false` 的入口**从界面移除**，不是「隐藏但可绕过」；`entitled = false` 的入口展示为不可用并给出原因。
2. `permissionPolicy` 默认列是 `ask`，**不是 `allow`**；`allow` 只用于用户当场可见、无外部副作用的读动作。
3. 能力 ID 取值唯一登记在《中台交付包》§4.4，客户端先落一张常量表，**只增删、不改名**（改名会让已下发的策略失配）。
4. 隐藏 ≠ 删除：上游能力保留，入口默认隐藏（P6 前端半已在）。

**验收.** 下发一份把某入口 `visible=false` 的策略，该入口从侧栏与空状态消失；`curl` 直连该路径不返回功能。

#### B8 会话模型绑定与模型下架

**要求.** 会话记录绑定的是**目录里的模型 id**；模型被下架后，老会话的行为必须明确。

**规则.**

1. 上游会话存的是 `<endpoint>::<model>` 复合 id（`PATCH /api/sessions/{id}/model`）。正式会话的 endpoint 前缀固定为内置网关，可变部分只剩目录 id。
2. 模型在新目录里消失时：老会话**可继续读**；下一条消息前提示「该模型已下架，请重新选择」，**不静默换模型**。
3. 会话级模型与模式（B5 规则 6）持久化在会话上，换机器随 `data/` 走。

**验收.** 发一次消息 → 下架该模型 → 新目录刷新 → 再发：提示重选，不换模型、不报硬错。

#### B9 空名单与不可用提示

**要求.** 是 B1/B4/B5 的**统一出口**：任何一个「没有可用模型」的状态都必须有文案，且都不得弹配 Key 向导。

**规则.** 文案分两种：目录不可用（联网/验签问题，可重试）与目录可用但该分组为空（无该模式模型）。两者不得共用一句话。

**验收.** 四种输入各造一次：无缓存 / 过期 / 验签失败 / 分组空 —— 四条文案互不相同且都出现。

### C 模型通信（走中台网关）

> **本节先给一个结论，避免重复劳动。** 「真正和模型通信」的代码在本分支**已经完整存在**：`config.Endpoint` → `app.SenderOptions` → `app.NewSender` → `internal/provider/openai`（SSE 聚合、`[DONE]` 容错、tool call 分片按 `index` 拼接、usage 归一、限流、自定义 Headers 覆盖内置头）。**本次不新写 HTTP 客户端，也不新写 SSE 解析器。** 需要改的只有 7 处「OpenAI 协议里没有的产品字段/事件」，逐条列在 C5–C7。

#### C1 内置网关端点

**要求.** 正式会话唯一出口是**内置**网关端点：**不可编辑、不可删除、不可被 `config.yml` 覆盖**。

**规则.**

1. 端点形状：`provider = custom`、`protocol = openai`、`base_url = Profile.GatewayHost`。用 `Endpoint` 表达而非新造类型 —— 这正是「复用既有能力」。
2. 它**不出现**在 `GET /api/config/endpoints`（`internal/server/onboard_config_handlers.go:300`）的应答里，也不出现在 Settings → Endpoints（`web/src/components/settings/EndpointsSection.svelte`）。用户看不到它，也改不了它。
3. 它**不写入** `data/config.yml`。`config.yml` 里同名 id 不得覆盖它。
4. `Profile.GatewayHost` 为 `.invalid`/空时（`ControlPlaneConfigured() == false`）拒绝启动控制面 —— 不回落 `localhost`、不回落 `config.yml`。
5. 内置端点默认 `headers` 里带 `Accept: text/event-stream`；`Authorization` 由 C2 注入，不进配置。

**现状.** 机制齐备（`Endpoint` 支持任意 `BaseURL` + `Headers`，且 `Headers` 会覆盖内置头）；缺的是「内置 + 隐藏 + 不可覆盖」这条接线。

**验收.** 在 `config.yml` 里手写一个 id 相同的 endpoint：正式会话仍用 `Profile.GatewayHost`；Settings → Endpoints 里看不到它。

#### C2 动态凭证注入与 401 刷新

**要求.** 中台 access token **只驻内存、不落盘**；过期时单飞刷新一次，不并发风暴。

**规则.**

1. `config.Endpoint.APIKey` 与 `Headers` 都是**构造期静态明文**（`internal/app/sender.go:152` 把 `entry.Headers` 直传，`buildClient` 里 `client.Headers = headers`）。access token 短期且不许落 `config.yml` ⇒ **不能放在那里**。
2. 采用「**用当前内存 token 装配 sender**」：`NewSender` 很轻，而限流器按 `limiterKey(provider, baseURL)` 复用（`internal/app/sender.go:91`），所以同一网关端点跨回合仍共享同一个限流预算。
3. 必须**先查内存里的凭证**再构造；构造阶段不得读盘、不得发起刷新。
4. `401`：单飞刷新（同一时刻只允许一个刷新在飞，其余等待结果），刷新成功后**重放一次**原请求。重放只允许一次。
5. `401` 且刷新失败 ⇒ 清内存 token、落 `blocked`（E8），不做无限重试。
6. 刷新令牌本身不进 `product-state.json`，进 `data/credential.json`（E6 规则 1）。

**现状.** 完全缺失。这是本次**最实的一处新增**。若给 `internal/provider` 加口子，改动须带 `// OCTO-FORK:` 标记并说明理由；**优先选择不改上游**（规则 2 的方案不需要改）。

**验收.** 用过期 token 发一次消息 → 只发生一次刷新、原请求重放一次、用户无感；把刷新接口打断 → 落 `blocked`，不循环重试，token 不落盘（检查 `data/` 全目录无明文 token）。

#### C3 复用既有 provider 栈

**要求.** 内容、工具调用、思考过程、usage 的**流式解析一律复用** `internal/provider/openai`，不新写解析器。

**规则.** 不得为「中台专属」新建一套 SSE 聚合。若确实需要新代码，只能在**产品扩展字段**层面加（C5–C7），且必须复用同一个 `streamChunk` 解析循环 —— 不许并行开第二条解析路径。

**验收.** 全局搜不到第二个解析 `choices[].delta` 或拼接 `tool_calls[].index` 的实现。

#### C4 每次网关调用一个 `clientRequestId`

> **⏸ 本条联调期不实现，见 [`待解决问题.md`](待解决问题.md) `D-003`。** 联调期按「零改动」路径：不发 `clientRequestId`。**缺失面**：没有幂等键 ⇒ 重复计费防护与 `GET /v1/ai/requests/{clientRequestId}` 对账入口不可用。**上线前必须补。**

**要求.** 粒度是**每次网关调用**（一个用户回合内的多轮工具调用各自独立），它贯穿流式调用、账本与客服定位。

**规则.**

1. 生成：客户端生成 UUID（`crypto.randomUUID()` 等价物），**每次调用新生成**，不复用一个回合的 id。
2. 传法：请求体字段（契约见《中台交付包》§5.2）。**不依赖请求头** —— `Client.Headers` 是静态的，无法表达每调用一值。
3. 同 id 重发的语义（`409 request_in_progress`、已结算返回终态）按《中台交付包》§5.4 表，客户端**不生成新 key 硬重试**。
4. 客户端主动取消一个回合，需撤销该回合内**所有**未结算预留（同一回合有多个 `clientRequestId`）。
5. 日志与工单展示里，`clientRequestId` 与网关侧 `requestId` 都要能拿到（E14）。

**验收.** 一个触发两轮工具调用的回合，抓包可见两个不同的 `clientRequestId`；断网重连后不盲重发（改为查状态）。

#### C5 网关扩展字段的载体

> **⏸ 本条联调期不实现，见 [`待解决问题.md`](待解决问题.md) `D-003`。** 联调期按「零改动」路径：标准 OpenAI `chat/completions`，`model` 填目录 `id`，**不新增任何字段**。**缺失面**：`toolPolicy`（工具白名单，权限）未下发、`model` 语义未固化。**上线前必须补**，与 `D-002` 同一处改动。

**要求.** 明确 4 个**非 OpenAI 字段**挂在哪，并落成实现。这是「复用既有能力」唯一的代价。

| 字段 | 现状 | 载体 |
| --- | --- | --- |
| `clientRequestId` | 请求体已列（§5.2） | 请求体新增顶层字段 |
| `toolPolicy` | 请求体已列（§5.2） | 请求体新增顶层字段 |
| 模型标识命名 | 目录里叫 `id`，网关请求体叫 `modelId`，OpenAI 叫 `model` | **统一成一个线上的字段名**，见 [`待解决问题.md`](待解决问题.md) `D-003`（联调期不阻塞） |
| 模型 id 的语言 | — | **`id` 一律英文 ASCII，不做本地化替换**（已拍板 2026-09-11） |
| 模型展示名语言 | — | **目录返回中、英两版**（已拍板 2026-09-11），见 `B6` |
| 账本终态（`settled`/`reversed`/`reconciliation_pending`） | 无 OpenAI 对应 | SSE 扩展字段（C7） |

**技术事实（决定代价）.**
`internal/provider/openai` 的请求体是**固定结构体**，在 `stream.go:52` 组装、`stream.go:66` 直接 `json.Marshal(body)`；客户端**没有** `ExtraBody` / 任意字段逃生口（`Client` 只有 `BaseURL` / `Headers` / `Limiter` 等字段，`client.go:123`）。因此要让请求体带上 `clientRequestId` / `toolPolicy`，只有两条路：

1. 给 `internal/provider/openai` 的 `apiRequest` 加一个透传字段 —— 这是改**上游文件**，必须 `// OCTO-FORK: <原因> — see 需求基线 C5`。
2. 网关接受这两个字段作为**请求头**（静态不可行，见 C2/C4）或在网关侧由别的头推导 —— 与 §5.2 的契约不符。

**结论.** 走第 1 条，且**只加一个字段**（一个 `map[string]any` 或一个具名字段），不复制整个请求结构体。

**验收.** 抓包确认网关请求体含 `clientRequestId` 与 `toolPolicy`，且 OpenAI 标准字段（`tools` / `tool_choice` / `role:"tool"` + `tool_call_id`）逐字未变。

#### C6 流中安全终止 `retract` 的载体

> **⚠️ 本条当前「暂不解决」，见 [`待解决问题.md`](待解决问题.md) `D-002`。** 联调期只跑内容 / 工具 / usage；`retract` 不在联调验收内。下面保留完整设计，供重新评估时使用。**必须保留的兜底**：解析到「既非已知标准字段、也非 `[DONE]`」的顶层字段时要**报错或打 error 日志**，不得静默 `continue` —— 这是「静默失效」与「明确失败」的分界。

**要求.** `retract` 必须被**真正执行**（原子撤掉已渲染的 delta），且账务终态同时给出。

**现状（重要，别踩）.**
`internal/provider/openai/stream.go:152-154` 的解析循环里：

```go
if !strings.HasPrefix(line, "data:") {
    continue
}
```

**任何非 `data:` 行被直接丢弃。** 所以如果网关按《中台交付包》§5.3 发 `event: retract`，这一整帧会被静默吞掉，用户看到的是**未被撤回的原文** —— 一个安全需求静默失效，而不是报错。这属于「静默降级」，不允许。

**规则.**

1. `retract` 与被撤回的内容必须落在**同一套 `data:` 帧**里（网关在 `data:` 的 JSON 对象上多加一个顶层字段，如 `{"retract": {...}}`），从而复用既有的扫描循环。
2. 客户端在 `streamChunk` 上新增该字段 + 一个新的回调（与 `OnText` / `OnToolDelta` / `OnThinking` 同级），由 agent 层执行「按 `scope.fromDeltaIndex` 原子移除已渲染 delta」。
3. `retract` 之后必须收到终态（`settled` / `reversed` / `reconciliation_pending`）；该终态由 `event: usage`/`error` 的等价 `data:` 帧给出。**被撤回的内容不得计费。**
4. 收到安全终态后，尚未执行的 streaming tool call **必须丢弃**；已批准且已开始的高风险动作仍走本地取消语义（C10）。
5. 「只追加一句『已拦截』」不算实现。
6. 这处对 `internal/provider/openai` 的改动要带 `// OCTO-FORK:` 标记。

**验收.** 造一次流中拦截：已上屏的 N 个 delta 被原地移除，随后显示终态文案，界面与**落盘历史**都不含被撤回文本。

#### C7 用量与账本终态上屏

> **⚠️ 本条部分「暂不解决」，见 [`待解决问题.md`](待解决问题.md) `D-002`。** 账本**终态帧**收不到 ⇒ 「只有 `settled` 才更新余额」这条链路不通。联调期兜底：余额走 `GET /v1/credits/ledger` **主动查询**（拉模式）。token 数本身仍由 `provider/openai` 正常归一（规则 1 不受影响）。

**要求.** 余额与用量的权威是网关账本；客户端只做**只读投影**，不本地扣费。

**规则.**

1. `provider/openai` 已能把 token 数归一进 `Response`（`InputTokens` / `OutputTokens` / `CacheReadTokens`，注意 openai 协议要 `prompt - cached`，见 `stream.go:188-201`）。**这套不动。**
2. 网关的**账务字段**（`ledgerId` / `state` / `chargeMicroCredits` / `balanceMicroCredits` / `usageSource`）没有 OpenAI 对应 ⇒ 走 C6 同一套 `data:` 扩展字段。
3. 界面更新余额的**唯一时机**是收到终态帧。流中不预扣、不回滚。
4. 供应商没给 usage 时，`usageSource = estimated` 或 `reconciliation_pending` 要能显示成「用量核对中」，**客户端不补扣**。
5. 免费额度、套餐包含额度、赠送额度必须在目录/权益里显式表达；「余额为 0 仍发送」不得成为付费模型的隐式规则。

**验收.** 断流场景 → 显示「用量核对中」，重启后查 `GET /v1/ai/requests/{clientRequestId}` 收敛；余额变化只发生在终态帧之后。

#### C8 错误信封 → UI 状态

**要求.** 错误码取值唯一登记在《中台交付包》§3.2；客户端只做 `code → i18n key` 的映射，不解析 `message`、不自己发明码值。

**规则.**

1. 字段名固定 `code` / `message` / `field` / `retryAfterSec` / `requestId`；不存在第二套命名（无 `messageKey` / `traceId`）。
2. `402 insufficient_credits` / `409 request_in_progress` / `429` / `5xx` / SSE 中断 / `safety_blocked` 每个都要有明确 UI 状态与恢复动作（契约 §5.4 表）。
3. 修掉 §1.3 的 `code_invalid` → `invalid_code`。
4. `retryAfterSec` 必须驱动冷却，不用固定秒数硬编。

**验收.** 逐个错误码造一次，确认都有文案、都不是白屏/空横幅、`429` 有倒计时。

#### C9 不回落本地 provider / `config.yml`

**要求.** 正式会话在任何失败路径上都**不得**回落到本地 provider、环境变量模型来源或 `config.yml` 的 endpoint。

**规则.**

1. 判据统一用 `Profile.RequiresControlPlane()`（A1 规则 3），不逐处比较 Profile 名。
2. 失败面枚举（逐个覆盖并加黑盒回归）：目录不可用、网关 5xx、401 刷新失败、`Profile` 未配置、`config.yml` 里有可用 endpoint、环境变量里有 key。**六条都必须失败关闭。**
3. 「降级即授权」禁止：降级到本地模型等于绕过计费与内容安全，不允许。

**验收.** 六条各造一次，无一条能把请求发到网关以外的地方。

#### C10 工具调用仍过本地权限门

**要求.** 网关返回的工具调用只表示**模型请求工具**，不表示用户已授权执行。执行前仍过本地权限门（`internal/app/gate.go`）与 `permissionPolicy`。

**规则.** 流中安全终止（C6 规则 4）与用户取消都要能中断未执行的工具调用链路；已启动的高风险动作按既有取消语义处理，不静默完成。

**验收.** 一个高危工具调用在确认框停留时收到 `retract` → 该调用不执行。

#### C11 取消与限流

**要求.** 取消与限流**复用既有实现**，不新造。

**规则.**

1. 取消：`context` 取消已能关闭 `ChatStream`（`internal/provider/openai` 的 `cancelStream` + idle watchdog）。客户端取消要同时调 `context cancel` **和**告知网关（C4 规则 4），两者不可互相替代。
2. 限流：内置端点沿用 `Endpoint.RPM` / `MaxConcurrency` + `endpointLimiters`。取值与是否开启由 `PQ5` 定。
3. 客户端不得用固定 sleep 做退避 —— 退避读 `retryAfterSec`。

**验收.** 取消一次流式回复：连接立即关闭，网关侧收到取消，余额按已产生用量结算。

#### C12 控制面失败 vs 网关失败：两套口径（`S-7`）

**要求.** C8 的表是**网关**的（一条对话请求在路上失败）。登录 / 激活 / 目录 / 词库走的是**控制面**，多一类「网络根本不可达」，且**可重试性完全不同**。两者必须**文案不同、行为不同**，不能共用一套。

**规则.** 控制面失败按四档处理，**逐档定文案与是否可重试**：

| 档 | 判据 | UI | 可重试 | 是否清凭证 |
| --- | --- | --- | --- | --- |
| `network_unavailable` | DNS / 连接失败 / 超时，**本机侧** | 「网络不可用，请检查网络后重试」+ 手动重试按钮 | 是（仅手动） | 否 |
| `upstream_unavailable` | 中台 `5xx` | 「服务暂时不可用，请稍后重试」 | 是（**有界退避**，读 `retryAfterSec`；无该字段则固定上限次数） | 否 |
| `unauthorized` / `token_expired` | `401`，或 `403` 且非账号受限 | 「登录已失效，请重新登录」→ 回拦截页 | **否**（重试无意义） | **是**（清 `data/credential.json`，`E6` 规则 6） |
| `account_restricted` | `403` 且语义为封禁/受限 | 「账号受限，请联系客服」 | 否 | 否（保留凭证，便于客服核对） |

**三条硬约束.**

1. **`network_unavailable` 绝不回落本地模型**（与 `C9` 同一条判据）。「网断了所以先用本地」是最容易顺手写出的静默降级 —— 它绕过计费与内容安全（`C9` 规则 3）。
2. **`unauthorized` 必须清凭证且不重试。** 401 循环重试是这类产品的典型事故：凭证已被中台撤销，客户端却一直重试，既刷日志又让用户以为"在加载"。
3. **档位判定只在一处实现**（控制面客户端，`internal/productclient`），UI 只消费已判定的档位。**不得**让每个页面各自 `if (status === 401)` —— 那就是把同一份判定写 N 遍（§3.8）。

**验收.** 四档各造一次（断网 / mock 5xx / 用已撤销的 refresh token / mock 403 受限）：文案互不相同、重试行为符合上表、只有 `unauthorized` 会清掉 `data/credential.json`；断网时没有任何请求落到本地 provider。

### D 敏感词

> **现状提醒.** 本分支**只有前端半**：`web/src/lib/sensitive.ts` 调 `POST /api/product/sensitive/check`（现由假后端应答），`sensitiveDict.ts` 是词库管理页。**词库引擎、三层合并、服务端词库同步全部缺失。** 交互规则见 [`../2260906/需求20260906.md`](../2260906/需求20260906.md) §5.5，本节只写与中台对接相关的增量与「唯一实现」要求。

#### D1 输入检测（可关，关前确认）

**要求.** 默认开启；点发送、请求未交给模型时检测；命中则本轮不发、框内打码、下方提示，再次发送按**当前框内文本**重新检测。

**规则.**

1. 开关状态写入数据根，重启保持；关闭前需确认，文案明确「输入将按原文发送，模型回复仍会过滤」。
2. 关输入检测**不影响**输出过滤，也**不影响**隐私模式 PII（两者独立）。
3. 检测的**权威在后端**：前端调用只为即时上屏，前端可绕过。后端在聊天路径上必须再检一次。

**验收.** 关掉输入检测后，隐私模式 PII 仍生效；用 `curl` 绕过前端直接发命中词，后端仍拦。

#### D2 输出检测（不可关，只打码不截断）

**要求.** 命中片段一律打码 `***`（连续命中合并），**不截断整段回复**；用户不可关闭。

**规则.**

1. **落盘即打码**：写入 `data/` 的历史必须是打码后文本，与最终界面一致（流式可先短暂显示再打码，以落盘为准）。
2. 作用范围：模型可见正文、可见思考过程、界面**展示**的工具结果文本。不展示的工具原始 JSON / 附件二进制 / 图片 OCR 不做。
3. 客户端打码 + 服务端 `retract`（C6）是两层不同机制，不能互相替代：客户端打码管「本地不出现原文」，`retract` 管「服务端已判定违禁并撤回」。
4. 用户已发出的那一条：若发送前被替换，历史存替换后文本。

**验收.** 输出命中 → 最终界面与历史都是 `***`，不是整段消失；**重启后重读历史仍是打码后文本**。

#### D3 昵称检测

**要求.** 昵称命中合规敏感词则**拒绝保存**（「昵称包含敏感内容」），不把敏感词写成昵称、也不改成 `***` 保存。检测**始终开启**，不受输入框开关影响。

**现状.** `web/src/lib/nickname.ts` 只有格式校验；敏感词判定归后端（P3 §8 已标为范围边界）。

**验收.** 用命中词改昵称 → 拒绝且提示；改输入检测开关后行为不变。

#### D4 三层词库

**要求.** 有效词库 = **内置 ∪ 本地用户 ∪ 服务器下发的只读词库**。R7 明确是并集，任一层不能覆盖另一层。

**规则.**

1. 三层各自独立加载、失败互不连坐；合并后才做匹配。
2. 服务器词库**只读**，用户不能编辑；它不能删掉内置词或用户词。
3. 用户词的载体是数据根内 UTF-8 文本文件（一行一词，`#` 注释），`sensitiveDict.ts` 的注释已声明它「是唯一真相，只通过 Go 侧 API 编辑」—— 保持这条。
4. **路径写死（`S-3`，2026-09-11 定）：三层各自的落点如下，实现不得自行发明路径。**

   | 层 | 落点 | 形态 | 可写 | 缺失时 |
   | --- | --- | --- | --- | --- |
   | 内置 | **`go:embed` 进二进制**（`internal/sensitive/default-words.txt`） | 编译期嵌入 | 否 | 不存在缺失场景 |
   | 用户 | `data/sensitive-words.txt`（`datapath.Join`，**扁平落在数据根下**，与 `config.yml` / `mcp.json` 同级） | UTF-8 文本，一行一词，`#` 注释 | **是**（唯一可写层） | **当作空词表，不是错误** |
   | 服务器 | `data/sensitive-dict-server.json` | JSON：`{version, keyId, signature, words[], fetchedAt}` | 否（只由同步写） | 仅用内置 + 用户，可提示一次 |

   理由（§3.9.1）：**内置词必须是 `go:embed`，不能是随包文件**。随包文件放在数据根里会被用户删掉/改掉，而「文件缺失 = 用默认」要求默认值不在用户可触碰的位置。用户词文件名取 `sensitive-words.txt` 是因为**前端注释与导出文件名已经这么写了**（`sensitiveDict.ts` 的 `serializeDict` / `exportDict`），改名会同时打破导出文件与导入路径。
5. **量级与算法（`S-3`）：内置词 ≤ 2 000 条，本期用现有的子串匹配**（与 D6 的唯一实现一致）。**不做** AC 自动机 / Trie —— 三层合并后总量过万再评估，届时以 D2 的匹配规则为准、不改变本表路径。
6. 文件缺失/不可读：用内置词，可提示一次「词库读取失败，已用内置词」，不反复弹。三层各自降级到「该层为空」，**不整体 fail-open**（D5 规则 3）。

**验收.** 三层各放一个独有的词，三个都能拦；删掉用户文件后内置与服务器词仍生效。

#### D5 服务器词库同步

**要求.** 按版本/签名同步，原子写入缓存，失败保留旧版。

**规则.**

1. 契约见《中台交付包》§6.1：`keyId` + `signature` 必须真实验签；只有 `sha256` 无法防投毒。
2. 原子替换写入；验签失败/版本回退 ⇒ 保留旧版继续用，**并知会**用户（有界降级：说清回落到哪个版本、何时恢复）。
3. 同步失败不得导致敏感词检测整体失效（回落旧版），也**不得**fail-open 到「不检测」。

**验收.** 篡改下发的词库签名 → 保留旧版且提示；断网 → 旧版继续生效。

#### D6 匹配与替换规则的唯一实现

**要求.** 规范化 + 子串匹配 + 合并打码的规则**只有一处实现**。

**规则.**

1. 现在有两份：`web/src/lib/sensitiveDict.ts` 的 `normalizeWord()`（注释自称「mirrors internal/sensitive/normalize.go」）与 Go 侧（尚不存在）。**Go 侧一旦落地，前端那份降级为「仅用于客户端重复/空值预检」，且必须加测试断言两者一致**；权威判定只在 Go。
2. 规则（大小写折叠、去空白、去固定符号表、子串匹配、连续命中合并）见 §5.5，符号表原文照抄到唯一实现处，不得只写「同上游」。
3. 打码在**原文**上按命中片段替换，不是对规范化文本替换。

**验收.** 一份词表跑前端预检与 Go 判定，结论一致（含大小写、含符号插入、含全角）；符号表只有一处定义。

#### D7 用户词库管理

**要求.** 一个页面即可完成查/增/删/导入；导入是**合并**不是覆盖。

**规则.** 文件为唯一真相（D4 规则 3）；热加载（下次检测生效，无需发版、无需重启）；导入返回「新增 N / 跳过 M」；用户词不得写入服务器词库或内置词。

**现状.** `sensitiveDict.ts`（P13 前端半）已在，等后端。

**验收.** 页面上新增一个词 → 下一次发送即生效；导入一份含重复词的列表 → 报告 added/skipped。

#### D8 与服务端内容安全的边界

**要求.** 客户端敏感词与服务端内容安全是**两层**，职责不重叠，UI 上用户看到的结果必须自洽。

**规则.**

1. 客户端 D1–D7 管「本地不发送/不显示违禁内容」；服务端管最终判决，通过 `safety_blocked` + `retract`（C6）表达。
2. 用户看到的是两者的合并结果：客户端已打码的内容不会再被 `retract`；`retract` 撤回的内容也不由客户端补打码。
3. 界面上不出现「客户端拦了一次」和「服务端拦了一次」两条互相矛盾的提示。
4. 不得把用户原文送第三方审核（§5.5 已定）。

**验收.** 同一段内容分别触发客户端拦截与服务端 `retract`，两种提示互不重叠、不重复。

### E 用户体系

> **现状提醒.** 本分支有**完整的前端半**（P3）：三态状态机、窗口令牌、登录/激活表单、两轮校验、`phone.ts` / `nickname.ts`。缺的是 `/api/product/*` 后端与中台对接。交互细节回归 [`../2260906/需求20260906.md`](../2260906/需求20260906.md) §5.3–§5.4 与 [`../2260906/技术方案/P3-登录态与产品门.md`](../2260906/技术方案/P3-登录态与产品门.md)。

#### E1 首次激活

**要求.** 数据根内无绑定记录时，拦截页＝激活表单，**五个字段按此顺序**：手机号、验证码、**U 盘激活码、盒子编号**（两者相邻）、昵称。主按钮「激活并登录」。全部必填，格式错误**全部同时**显示。

**规则.**

1. 校验顺序：先格式（客户端），后业务（服务端：验证码是否已发送且正确 → U 盘激活码与盒子编号是否有效）。客户端**不预判**业务顺序，也不自己判「激活码 / 盒子编号合法」。
2. **U 盘激活码与盒子编号是两个独立字段，各提交一次、各自独立校验，两者都必须有效。** 语义区别：激活码回答「这份授权有没有买」；盒子编号回答「这份授权对应哪个盒子」。字段名固定为 `activationCode` / `boxCode`。
   - **两者的绑定关系是一对多：一个盒子编号可以搭配多个 U 盘激活码（已拍板 2026-09-11）。** 一个盒子可附多张 U 盘，每张各有自己的激活码。因此**盒子编号不是激活的唯一键**，也不存在「一个盒子只能激活一次」这种限制。
   - **中台会校验，可以不通过**，所以「盒子编号不存在」「激活码与盒子编号对不上」都是**合法的激活失败**，客户端必须能把这几种失败**分别**渲染成不同文案（不能都显示「激活失败」）。
   - **不得把「盒子编号已被使用」当成错误。** 一对多意味着同一盒子编号下的多个激活码可以分别激活（可落在同一账号，也可能是不同账号）。限制只存在于**激活码**维度，不在盒子编号维度。
   - **一个 U 盘激活码只能用一次（已拍板 2026-09-11）。** 激活成功后该码即作废，无第二次使用机会。中台对同一码的第二次提交返回 `activation_code_used`；客户端只渲染文案，不做任何本地判断。
     > **这条的后果要提前想清楚：** 因为「一次性」，所以**用户若丢失 `data/`（重装系统、换机但没拷 `data/`、U 盘损坏），无法用同一个激活码重新激活** —— 只能走客服。这与「激活绑用户、`data/` 换机可用」（规则 7）**不矛盾但边界很窄**：能用同一份 `data/` 就没事，`data/` 没了就要客服。**因此 `PQ9` 的「客服纠错通道」不是可选项，而是这条规则的必然搭配。**
     > 注：规则 7 说的是**同一份 `data/` 换机器**（激活记录跟着走，不需要重新提交激活码），与「同一激活码只能用一次」**不冲突** —— 前者不产生第二次激活提交。
   - **必须同时存在客服纠错通道**（否则用户抄错一位、买到对不上的组合、或丢了 `data/` 就永久卡死、客户端自己无解）。错误文案里必须给出「联系客服」的入口或联系方式，见 [`待确认问题清单.md`](待确认问题清单.md) `PQ9`。
   - 客户端仍然**不做**任何盒子编号合法性判断，只提交 + 渲染中台返回的错误码。
3. **客户端不关心两者的来源，也不校验来源。** 激活码随 U 盘包装内附；盒子编号可能来自包装内附、客服提供、他人转赠等 —— 这些都属于业务渠道，**产品实现只做「收集 → 规范化 → 提交 → 按中台判定渲染」**，不内置任何合法取值，不做本地白名单，不做渠道判断。
4. **规范化与校验口径（两者相同）：** 去首尾空格、大小写不敏感；空值按「未填」处理并提示「请填写…」。长度与字符集**以中台判定为准**，客户端只做非空校验 —— 若中台后续给出明确格式，再补客户端格式校验。
5. **不读任何硬件标识。** 盒子编号是**业务提供的一个字符串**，不是从 U 盘序列号、主板、网卡或任何硬件派生。本产品**不存在**读取硬件序列号的逻辑。旧需求「不读 U 盘硬件序列号」（[`../2260906/需求20260906.md`](../2260906/需求20260906.md) §2 第 4 条）**继续有效，不需修订**。
6. 激活成功后**分别**记录（`V-3`，2026-09-11 澄清 —— 原文把两者混成一句，与 `E6.1` 冲突）：
   - **中台侧（权威记录，字段名以《中台交付包》为准）**：绑定手机号、`U 盘激活码`（一次性凭证的使用留痕，用于审计与客服核对）、盒子编号、激活时间、授权到期日。
   - **本地 `product-state.json`（只有一个是业务属性）**：绑定手机号（**脱敏**）、盒子编号（**明文不脱敏**，`E6.1`）、激活状态、激活时间、授权到期日、昵称、登录态引用、积分初始值。**本地不存 `U 盘激活码`** —— 它是一次性凭证，激活成功后再无提交机会，留着只增加泄露面；界面也不展示它（`E6.1` 表下注）。
   - 因此「不脱敏」这条只适用于**盒子编号**（以及对中台的记录），不适用于本地手机号：本地手机号仍是 `138****1234`。
   - 凭证本身另存 `data/credential.json`（`E6.3`），**不在** `product-state.json` 里。
7. **激活绑定的是用户账号，不绑定设备、也不锁定盒子。** 同一份 `data/` 换到另一台电脑：因为其中**同时持有登录态（`data/credential.json`）与激活记录**，**直接正常使用，不要求重新激活、也不需要重新登录**。盒子编号只是**登记属性**，不参与设备锁定，也不因换机而改变。（凭证为何跟盘走、复制后的安全取舍见 `E6` 规则 1 / 3 与 `D-004`。）
8. 盒子编号与激活码**不进诊断包**（业务标识，不用于排障）。
9. `BUDING-DEMO-0001` / `123456` 自本基线起降级为假后端演示数据（见 §1 与 [`../2260906/技术方案/开发期假后端说明.md`](../2260906/技术方案/开发期假后端说明.md)），正式取值由中台签发。**假后端需补一个演示盒子编号**，建议 `BOX-DEMO-0001`（固定 ASCII 数据键，不是品牌文案）。

**验收.** 五个字段同时填错 → 五条错误同时显示；U 盘激活码或盒子编号留空 → 不提交；激活后重启进程直达主界面；把同一份 `data/` 拷到另一台电脑 → 直接可用，不出现重新激活。

**仍未定.** 中台侧只剩**客服纠错通道**。**错误码已按 §3.8 收敛到《中台交付包》§3.2 的命名**：激活码无效沿用已登记的 `activation_invalid`（不再另造 `activation_code_invalid`），并新增登记 `activation_code_used` / `box_code_unknown` / `box_code_mismatch`（三个新码由本次 boxCode 需求引入，2026-09-11 登记）。客户端侧**无阻塞**：字段、顺序、口径都已定；盒子编号由中台校验、它与激活码是**一对多**、**激活码只能用一次**这三点都已拍板。

**验收补充.** 盒子编号不存在 / 激活码与盒子编号对不上 → 显示**专属**文案 + 客服入口，且不写激活记录。**同一个盒子编号 + 两个不同激活码**分别激活 → **两次都成功**（可落在同一账号或不同账号），这是「一对多」关系的回归用例，防止被实现成一对一。

#### E2 二次登录

**要求.** 已有绑定记录时**不出现 U 盘激活码，也不出现盒子编号**（两者在首次激活已完成绑定），主按钮「登录」，昵称预填上次值（可改）。

**规则.**

1. 手机号规范化后必须与绑定号一致，不一致返回脱敏绑定号 `138****1234`（前 3 后 4）。
2. 二次登录不重置激活信息与积分。
3. 昵称初值三条：有绑定用绑定昵称（切语言不覆盖）；无绑定按当前语言随机生成；用户手改过则切语言不覆盖 —— **语言切换永远不抹掉用户正在输入的内容**。

**验收.** 换号被拒且提示含脱敏号；切语言不丢正在输入的昵称。

#### E3 手机号规范化

**要求.** 提交与「发送验证码」前先规范化：去空格与短横线 → 剥离 `+86` / `86` 前缀 → 必须为 `1` 开头 11 位数字。

**规则.** 二次登录比绑定号时用**规范化后**的值比较。错误文案「请输入正确的手机号」。实现只有 `web/src/lib/phone.ts` 一处（客户端格式校验）+ 服务端权威校验一处，不重复第三份。

**验收.** `+86 138-0000-0000` 与 `13800000000` 判定为同一号码。

#### E4 验证码

**要求.** 由中台签发与校验；客户端只有倒计时与冷却。

**规则.**

1. 未点发送就提交 → 「请先获取验证码」；错误或过期 → 「验证码不正确或已过期」（`invalid_code`）。
2. 规范化后手机号合法才可点发送；点击后进冷却，冷却内不可重发；重发刷新有效期。
3. 冷却秒数与有效期**取服务端返回值**（`cooldownSec` / `retryAfterSec`），不硬编 60。
4. 界面不得把正确验证码印在输入框里。

**验收.** 不点发送直接提交 → 正确提示；冷却内连点 → 按钮不可用且显示剩余秒数。

#### E5 激活状态与授权到期

**要求.** 能进主界面即说明这份数据根已完成激活 —— 授权页**不出现「未激活」空态**，只有「已激活」或「已过期」。

**规则.**

1. 展示剩余天数 = `max(0, 到期日 − 今天)`（本机本地日历）+ 绑定脱敏手机号 + **盒子编号**（不脱敏）。
   - **不再显示「绑定于当前程序目录」这类字样（`N-3`，2026-09-11 更正）。** 原条文要求渲染它，但 `LicensePage.svelte` 从未实现、`i18n.ts` 也没有对应 key；而且凭证改为随 `data/` 复制之后，这句话的语义已经错了 —— 授权/登录态**不绑目录**，换个目录、换台机器照样可用（`E1` 规则 7）。**这条要求作废**，不是"待实现"。
   - 盒子编号读 `productState.activation.boxCode`（`E6.1` 字段表），**渲染原文、不做任何脱敏或打码**。
   - **为什么客户端自己存一份：** 授权页要离线可读（目录/网络不可用时也要能看），所以缓存进本地状态；但**真值来自服务端响应**（激活或 bootstrap 带回），不是「用户输入过的那个字符串」。**全新 `data/` 上二次登录也必须能看到盒子编号** —— 二次登录表单不出现 boxCode（`E2`），所以它只能来自服务端。
   - **老数据缺 `boxCode` 时该行显示「—」**，不拦截、不要求补填、不影响产品门（`PQ19`）。
   - **不展示 U 盘激活码**：一次性凭证，本地状态里也没有它（`E6.1`）。
2. **到期是否拦截是一个必须拍死的策略**：本期（P0）按 §5.4.2 只展示「已过期」、仍可对话；接入中台后若改为拦截，须在《中台交付包》里有一条驱动它的能力/状态位，不能靠客户端改判断。← 见 `PQ7`
3. 换绑/解绑本期不做；帮助页留「如需更换手机号，请联系客服」（占位）。

**验收.** 把到期日改到昨天 → 显示「已过期 / 剩余 0 天」，行为与本节拍死的策略一致。

#### E6 登录态与凭证存储

**要求.** access token **只驻内存**（永不落盘）；refresh token **存数据根、可随 `data/` 复制**；`product-state.json` 仍不含任何令牌（令牌单独一个文件）。

**规则.**

1. **凭证介质（已拍板 2026-09-11）：refresh token 明文存数据根内的 `data/credential.json`，随 `data/` 一起复制、迁移。** 判据：本产品是便携 U 盘版，「插上就能用」是核心价值；把凭证放进 OS 凭证库会让每换一台电脑都要重新短信登录，等于把便携体验砍掉一半。
   - **`internal/credentialstore` 的职责因此改为「读写数据根内的那个凭证文件」**，不再对接 Windows Credential Manager / macOS Keychain。包名保留（`credentialstore` 仍然准确），实现是文件存储。
   - `product-state.json` 仍然**不含令牌**：非敏感状态与凭证分文件。这样「凭证明文」集中在一个文件里，将来要整体加密或整体清空，只动一个点。
2. access token 仍只驻内存，进程退出即失效，不写任何文件。
3. **「复制 `data/` 就复制了登录态」是明文写下的已知取舍，不是缺陷。** 用户把 `data/` 拷给别人、或 U 盘丢失，等同交出账号。止损手段是**中台侧撤销 refresh token**（E12），不是本地加密（见规则 4）。帮助页写一句即可。
4. **不得用「机器相关密钥」加密凭证来防复制。** 那会重新引入硬件标识判定，违反 E1 规则 5（不读任何硬件标识）；而且换机后解不开，体验等同把凭证放进 OS 凭证库 —— 两头都不占。
5. `Profile.RequiresControlPlane()` 为真时，登录态必须来自中台；`developer` 可用假 token 走通链路，但**假 token 不得被当成正式凭证接受**。
6. **撤销路径是安全底线的一部分**（见 [`待解决问题.md`](待解决问题.md) `D-004`）：令牌可复制 ⇒ 中台必须能撤销单个 refresh token；客户端收到 401/403 后清本地凭证并回拦截页，不静默继续。

##### E6.2 状态文件的升级与缺字段（`S-5`）

**要求.** 已经有**不含 `boxCode`** 的 `data/` 在用户手上，升级必须**只加字段、不迁移、不清空**。

**规则.**

1. `schemaVersion` **单调递增**，只在**新增/改变字段语义**时 +1；纯新增可选字段也要 +1（让诊断包能判断"这份数据有多老"）。
2. **缺字段 = 未登记，不是损坏。** 读取时缺 `boxCode` ⇒ 该字段为 `nil` ⇒ 授权页显示「—」，**不拦截、不要求补填、不影响产品门**（`PQ19`）。
3. **不存在"写入式迁移"。** 启动**不重写** `product-state.json`（§3.9.1：启动不得写用户可编辑文件）。新字段在**下次因用户操作而保存状态时**自然带上。首次激活的种子是唯一例外，且必须幂等、不阻塞启动、不与用户编辑竞争。
4. **`schemaVersion` 比当前程序新 ⇒ fail-closed。** 说明用户用旧程序打开了新数据（降级场景，如把新版 `data/` 拷回旧 U 盘）。此时**拒绝启动并提示「数据来自更新版本」**，**不得**按旧结构解析后再写回 —— 那会把新字段悄悄抹掉。
5. **JSON 损坏 / 校验失败 ⇒ 降级为「未登录」并保留原文件**，回拦截页让用户重新登录；**不得**静默清空或覆盖（否则一个解析 bug 就永久毁掉用户数据）。
6. 本期**没有真正的迁移**（字段只加不减）。规则 4 / 5 是**上线前必须**的护栏，现在写下来是为了让第一版实现就带上，而不是等出事故再补。

**验收.** 拿一份不含 `boxCode` 的旧 `data/` → 正常进主界面、授权页显示「—」、`product-state.json` 未被改写；手写一个 `schemaVersion` 高于当前的 `product-state.json` → 拒绝启动并给出可读提示；把 `product-state.json` 改成非法 JSON → 回拦截页且原文件仍在。

##### E6.3 `data/credential.json` 字段表（`N-2`）

**唯一 owner：`internal/credentialstore`。** 与 `E6.1` 分文件：非敏感状态一个、凭证一个（`E6` 规则 1）。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `schemaVersion` | int | 同 `E6.1` 规则 1；凭证文件形态变化时 +1 |
| `refreshToken` | string | **明文**（已拍板 2026-09-11）。唯一长期凭证 |
| `obtainedAt` | RFC3339 | 取得时间。仅用于展示/诊断，**不用于本地过期判断**（到期由中台说了算） |
| `accountPhoneMasked` | string | 便于"未联网时也知道上次登录的是谁"；**脱敏**，不存明文 |

**写盘要求.**
1. access token **不落盘**（`E6` 规则 2），本文件里没有它的位置。
2. **原子写**：写临时文件 → `rename` 覆盖。断电/拔出 U 盘不得留下半截 JSON。

##### E6.4 首启初始化时序（`V-7`，2026-09-11 定）

**要求.** `E6.1` 说 `installId`「首次启动生成一次」、`E6.2` 规则 3 说「首次激活的种子是唯一例外」—— 但**谁在什么时刻创建**、**写哪些初值**、**`installId` 由壳还是 Go 生成**、**只读盘上失败怎么办**，此前四处都没写。本节把它定死。

**规则.**

1. **责任人：Go 本地服务**，不是桌面壳。`installId` 是**「这台安装」的属性**，而「安装」的边界是数据根（`data/`），数据根由 Go 侧的 `internal/datapath` 唯一拥有 —— 让壳去生成会造出第二个路径与生命周期的 owner（§3.8）。壳只负责把**系统语言**带进来一次（`PQ18`）。
2. **时刻：`Open` 时惰性创建（2026-09-11 修正，`V-12`）。** 文件**不存在** ⇒ 就地播种并写盘；文件**已存在** ⇒ **只读，绝不重写**。因此「写」在整份安装的生命周期里**最多发生一次**，且只可能发生在文件尚不存在的时刻。
   - **为什么不是原条文那种更严格的「推迟到首次读才写」**：那条路要么让 `Open` 变成半只读的半成品，要么让 `handleState` 从只读变成可能写盘、还要接住写失败（规则 5 要求上抛）—— 把一次写盘的**时序**问题变成读路径的**错误分支**，而两者对用户可见的行为**完全相同**：前端启动的第一个调用本就是 `GET /api/product/state`，本条自己也写着"实际效果是那一次读"。按 §0「先走通流程，不增加复杂度」取了这条。
   - **保护不来自"什么时候写"，而来自"已存在就不写"**。后者才是用户不被覆盖、编辑不被竞争的原因，所以它必须被测试钉住而不只是写在纸上：`TestExistingStateIsReadNotRewritten` 用 `os.SameFile` 判定（写是 temp+rename，重写必然换 inode——**即使内容一模一样**），并在**只读目录**下断言 `Open` 仍成功（即不需要写权限）。注：只比较字节是**不够**的（重写同样内容会得到相同字节），只等报错也**不够**（写失败可能被调用方吞掉）。
3. **初值**：`schemaVersion = 当前版本`、`installId = UUIDv4`、`prefs.locale = 壳带入的系统语言`（**非中文落 `en`**）、`loggedIn = false`、`activated = false`、其余为空。**不写**任何 token、手机号明文、激活码。
4. **只生成一次。** `installId` 在登录、登出、换账号、切语言、升级之后**都不变**。文件已存在时**只读不写**（`E6.2` 规则 3），所以「生成一次」是靠"文件在，就不生成"保证的，不是靠额外的标记位。
5. **只读盘 / 写失败 ⇒ 有界降级，不是崩溃，也不是静默。** 内存里仍持有一份默认状态让界面能渲染（**不阻塞启动**）；写失败的错误**向上返回**，由调用方决定是否告知用户。**禁止**在写失败后假装已持久化 —— 那会让用户以为激活成功、重启后却回到登录页。
   - 已知会走到这条的场景：U 盘写保护、盘已拔出（`F2` / `L-E3`）。
6. **与 `E6.2` 规则 4/5 的关系**（三者共同构成首启的完整护栏，顺序固定）：
   - 文件**不存在** → 规则 2/3 播种；
   - 文件**存在但版本更新** → **fail-closed 拒绝启动**（`E6.2` 规则 4），**不播种、不覆盖**；
   - 文件**存在但损坏** → 降级为未登录 + **保留原文件**（`E6.2` 规则 5），**不播种、不覆盖**。
   - 注意后两者**都不得**走播种路径 —— 否则一个新版本数据或一份损坏数据会被悄悄替换成空白状态，正是 `E6.2` 规则 5 要防的事。

**验收.** ① 全新 `data/` 上 `Open` → 生成文件且含合法 UUIDv4；② 同一根目录**再次** `Open` → **文件未被替换**（`os.SameFile` 为真，字节也不变），且**在只读目录下 `Open` 仍成功**（证明它不需要写权限）；③ `installId` 在登录→登出→再登录后不变；④ 把 `data/` 目录设为只读 → **启动不报错、界面可渲染**，写失败被返回；⑤ `schemaVersion` 更高的文件与损坏的文件 → **都不进入播种路径**（前者拒启动，后者保留原文件）。

#### E7 退出登录

**要求.** 退出登录 ≠ 退出进程。清登录态、回拦截页、**进程保持、托盘仍在**；积分、会话、激活绑定均保留。

**规则.** 确认框标题「退出登录」，正文说明需重新验证手机号；按钮是「取消」「退出登录」（不得写成和托盘「退出」混用的「退出」）。退出时同时清服务端登录态与内存 token。

**验收.** 退出登录后任务栏/托盘仍有图标；重启进程直达拦截页；积分与历史仍在。

#### E8 产品门（界面门 + 请求门）

**要求.** 拦的是**桌面窗口里的界面**与**该窗口发起的聊天相关请求**；不拦 CLI；不替代上游机器门（`internal/server/auth.go` 的 `octo_access_key`）。

**规则.**

1. 三态：`unknown`（全屏 spinner）/ `blocked`（拦截页）/ `ready`。无窗口令牌（普通浏览器 / `octo serve`）⇒ `ready`（门不生效）。
2. **窗口令牌必须覆盖三个出网点**：`request()`、`withWindowToken()`（409 / multipart / blob）、`/ws` 握手（查询参数）。漏带令牌不是报错，而是**静默让门失效** —— 这是本模块唯一的系统性风险。
3. 降级方向：`/api/product/state` 读失败 ⇒ `blocked`，**不得** ⇒ `ready`（降级即授权，不允许）。
4. `403 product_gate` ⇒ 落 `blocked`。
5. 未登录**允许**：切界面语言（写数据根）、打开协议/隐私页。其余不得改配置。
6. 前端门拦不住 F12 与 `curl` —— 这是**写明的边界**，判定在后端；不要把这条当 bug 上报。

**验收.** 三条：不带令牌 `curl` 放行（有意）；F12 带令牌访问受保护接口被 403 并落回登录页；WS 握手带令牌。

#### E9 积分与用量

**要求.** 积分的**权威在中台**（网关账本）；客户端做只读投影，**不本地扣费**。

**规则.**

1. `data/chat-modes.json` 时代的「每条消息 +1 / 扣 1」本地规则（§5.4.4）自本基线起**作废**，只在假后端里保留。
2. 余额更新有**两条并列的合法来源**（`V-11`，2026-09-11 修正 —— 原条文只说终态帧，与 `C7` 的兜底冲突）：
   - **有终态帧时（`D-002` 交付后）：只有 `settled` 才更新余额**，流中不预扣、不回滚（`C7` 规则 3）。
   - **无终态帧时（本轮）：走 `GET /v1/credits/ledger` 拉模式**（`C7` 抬头已写明这条兜底），只在**回合结束 / 界面重获焦点 / 用户手动刷新**时拉，**不得流中轮询**。
   - **判据据此分两版**：本轮按拉模式判（回合结束后或手动刷新能刷到中台的值、流中无余额跳变）；`D-002` 交付后改按终态帧判。**本条此前只写终态帧，会让 `L-C4` 在本轮必挂。**
3. 0 余额时的行为由中台判定：付费模型返回 `402 insufficient_credits`（不得创建供应商请求）；免费/套餐内额度必须在目录/权益里显式表达。
4. 客户端可展示预估，但**预估不作为扣费依据**。
5. 跨月 `/ 月初重置`、赠送额度、套餐包含额度的展示规则：**客户端不实现**（见 `PQ8`）。中台给什么分项就显示什么分项；没有分项就只显示一个「余额」总数。旧文档的「本月消耗按月归零」是基于本地假数据的规则，作废。
6. **充值入口常驻显示（已拍板 2026-09-11）**，不依赖余额是否为 0、也不依赖是否 402。理由：用户想充值的时候不该先把自己耗到 0；把入口藏起来只会增加客服量。

**验收.** 余额变化与选定的来源一致（本轮：拉模式；`D-002` 后：终态帧）；0 余额发付费模型 → 402 且有明确文案；**空账号（余额充足、从未用过）也能一眼看到充值入口**；扣费金额与账本一致。

**要求.** 一个事实只有一个 owner：provider 装配 → `internal/app`；数据路径 → `internal/datapath`；品牌 → `branding/brand.json`；合约签名字段名/错误码 → 《中台交付包》§3.2/§4.3/§4.4；模式分组 → 目录投影；权限 → `internal/permission`；模型展示名 → 目录 `displayName`。

**要求.** `web/src/dev/devBackend.ts` 是**临时替身**，它的接管**无条件、无 passthrough**，所以**必须先拆除再联调** —— 否则联调结论是假的。

#### 5.2.1 `PQ17` 凭证介质：已拍板（2026-09-11）

**决定：方案 A —— refresh token 明文存 `data/credential.json`，随 `data/` 复制。复制之后的安全性（防拷贝、泄露止损）明确「以后再说」。**

**拍板时的三个候选（留档，供重新评估时对照）：**

| 方案 | U 盘插到另一台电脑 | 安全性 | 与 E2E-11（改前） |
| --- | --- | --- | --- |
| **A. 令牌存 `data/`（选定）** | **即插即用** | U 盘被复制 = 账号泄露；靠中台撤销兜底 | 需改合同验收用例 |
| B. 令牌存 OS 凭证库（原 `E6`） | 每次换机都要重新短信登录 | 好，复制 `data/` 拿不到令牌 | 一致 |

**为什么不选 C.** 它既不解决换机体验（解不开），又必须引入硬件标识，直接与 `E1` 规则 5 冲突 —— 两头都不占。

1. ✅ `E6` 规则 1 / 3 已改写：明确「`data/` 即凭证介质，丢失等同账号泄露」，并禁止用机器相关密钥加密。

4. ⏳ 撤销路径（`E12`）从「可选 UI」升级为**必须有的后端动作**。原样登记为 [`待解决问题.md`](待解决问题.md) `D-004`：**
   - 中台必须能**撤销单个 refresh token**（客服后台 + `DELETE /v1/account/sessions/{sessionId}`）；

   - **防拷贝（如 U 盘被复制后如何提前止损）不在本期解决** —— 用户明确接受这个代价。
