# 桌面设置直接管理手机连接

写作参照：dev-docs/mobile-managed-tunnel-design.md

桌面应用的“设置 → 手机”可以直接启动当前桌面 Hub 内的托管隧道；不再要求用户另外运行一个占用同一端口的 `serve` 进程。连接中显示状态，连上中继后通过既有 `/api/tunnel/pairing` 数据展示二维码；用户可手动关闭，退出桌面应用时也会停止。浏览器中的设置页仍只读取由 CLI `serve --tunnel` 发布的配对信息。

## 一个 Hub 拥有隧道与配对状态

`cmd/octo-desktop` 的 `desktopTunnel` 拥有启动、重连状态和停止动作，复用 `internal/tunnel.NewHost` 构建的 Host 隧道。CLI `serve --tunnel` 也使用同一构建入口，因此身份文件、配对 URL 与本地回连地址不会出现两套解释。身份仍由 `internal/datapath` 定位并持久化；每次启动生成新的配对 token。二维码中的 `octo-pair` 是既有手机配对协议，不随 CLI 的品牌命令名改变。

桌面隧道默认使用上游预置的 `wss://relay.octo.dev`；本功能没有新增用户可配置的中继地址。目前尚无经产品确认并部署的可用中继地址，本地开发环境对预置地址的 TLS 握手会直接断开，因此按钮只能进入重试状态，不能完成手机配对。不能把“已发起启动”当作“已连接”，也不能将这一故障直接归因于用户网络。上线前需确定中继地址及运营责任、部署并从桌面与手机两端完成联调；更换地址时同步调整共同的 Host 配置。

## 状态和接口

桌面本地 API 在原有窗口令牌门禁下提供：

- `GET /api/product/tunnel`：返回 `state` 与可选错误码；
- `POST /api/product/tunnel/start`：幂等启动，初始状态为 `connecting`；
- `POST /api/product/tunnel/stop`：等待隧道停止并清除配对信息。

状态为 `off`、`connecting`、`connected`、`retrying`、`stopping`。拨号失败或连接中断进入 `retrying`，显示 `relay_unavailable`，隧道自行退避重连；本地身份创建等启动失败保持 `off`，显示 `start_failed`。只有 Host WebSocket 连上中继时才向原有 `/api/tunnel/pairing` 发布二维码；断开、手动停止和桌面退出时清除它。前端只在“设置 → 手机”打开期间轮询状态，不另建一套连接推断。

桌面版的配对接口仅允许持有窗口令牌的本机窗口读取，避免配对 token 被其他本机浏览器或经中继转发的手机读出；CLI 的既有接口行为不变。配对 URL 及 token 不写入日志或状态接口。当前隧道转发沿用现有服务端访问密钥和 Noise 加密机制，不让中继解密会话内容。

## 非目标

- 不启动第二个 HTTP 服务或 CLI 子进程，不自动随桌面启动建立外网连接。
- 不改变手机 App 的配对协议、现有二维码组件、上游 CLI 命令或浏览器入口。
- 不在此功能中提供更换中继、账号绑定、多设备管理或配对 token 轮换界面。

## 验证

自动测试覆盖共享 Host 的身份和 token、桌面配对接口的本机窗口限制，以及设置页启动、展示二维码和关闭的用户路径。人工联调应在真实桌面包与手机 App 上确认：中继不可用时显示错误并重试；恢复后才出现可扫描二维码；手动关闭与退出桌面应用后手机连接断开。与上游移动端协议的关系以 `dev-docs/mobile-managed-tunnel-design.md` 为参照，实际行为以 `internal/tunnel`、`cmd/octo-desktop/mobile_tunnel.go` 与上述接口测试为准。
