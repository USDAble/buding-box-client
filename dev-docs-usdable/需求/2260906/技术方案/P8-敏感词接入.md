## 1. 目标与非目标

**目标**：把 P7 的引擎接到三个位置 —— 用户输入（可关）、模型输出（不可关）、昵称（始终开）。

**非目标**

- 不做附件二进制、图片 OCR、界面不展示的工具原始 JSON（需求 §5.5「不做」）。
- 不做 PII（P10）。
- 不改引擎规则（P7 已定）。

## 2. 现状（代码事实）

**输入侧**：`web/src/components/chat/Composer.svelte` 的发送函数。P6 已在此处建立 `ComposerNotices.svelte` 容器。

**输出侧**（这是本 PR 的难点，需要精确定位三个收口点）：

## 3. 设计

### 3.1 三个接入点各自的位置

```
┌─ 输入 ───────────────────────────────────────────────┐
│ Composer 点发送                                      │
│   → POST /api/product/sensitive/check（P7 提供）      │
│   → 命中：框内替换 + 下方提示 + 不发送 + 不扣分        │
│   → 未命中：正常发送                                  │
│   （开关关闭时整段跳过）                               │
└──────────────────────────────────────────────────────┘

┌─ 输出 ───────────────────────────────────────────────┐
│ agent 产出 text delta                                │
│   → 【收口点 A】流式过滤 → 推给前端上屏               │
│ agent 完成一条 assistant message                      │
│   → 【收口点 B】整段过滤 → 写进 Message.Blocks        │
│   → session.Save() 落盘的就已经是打码后文本            │
└──────────────────────────────────────────────────────┘

┌─ 昵称 ───────────────────────────────────────────────┐
│ login / nickname handler → Engine.Filter → 命中即拒   │
└──────────────────────────────────────────────────────┘
```

### 3.2 输出过滤：为什么是两个收口点

需求 §5.5.2 要的是两件事：「聊天区最终状态不得停留原文」+「写入数据根的历史必须是打码后文本，**与最终界面一致**」。

只在 A 过滤不够 —— 流式缓冲边界可能让某次 delta 漏过，且历史是从 message 落盘的不是从 delta 拼的。
只在 B 过滤也不够 —— 用户在流式过程中会看到原文，且如果连接断了、消息没走完 B，界面上就留着原文。

所以**两处都做**，B 是权威：

- **A（上屏）**：用 P7 的 `StreamFilter`，尽量在 delta 层面就打码。允许「先闪后改」（需求 §9.5 已列为已知限制）。
- **B（落盘 + 最终态）**：对完整 assistant 文本做一次 `Filter`，结果写进 `Message.Blocks`。完成时向前端推一个 `message:final` 事件，前端**用它替换**流式拼出来的文本 —— 这样界面最终态与历史严格一致，不依赖 A 的完美。

前端替换而不是追加，是「聊天区最终状态不得停留原文」的实际保证。

### 3.3 收口点 B 的具体位置

**放 `internal/agent` 还是 `internal/app`？**

选 `internal/app`。理由：

- `internal/agent` 是上游核心循环，改它 = 每次上游更新都冲突（合并影响从中变高）。
- `.octorules` 的分层约束是 `provider → agent`，`internal/app` 在 agent 之上，是本项目「唯一构造 Sender 并做适配」的层 —— 在这里包一层过滤 Sender 是符合既有架构的做法，不是硬塞。

具体做法：在 `internal/app` 里新增一个 **装饰器 Sender**：

```go
// internal/app/sensitive_sender.go
// filteringSender 包住任意 agent.Sender，对模型返回的可见文本做合规过滤。
// 装饰而非改 agent 循环：agent 包是上游核心，改它会让每次上游合并都冲突。
type filteringSender struct {
    inner  agent.Sender      // 或 ToolStreamingSender，按能力逐层实现
    engine *sensitive.Engine
}
```

`Sender` 接口栈是 `Sender → StreamingSender → ToolSender → ToolStreamingSender`，调用方用类型断言挑最高能力。装饰器**必须逐层实现**，否则包一层就把流式能力降级了。这是本 PR 最容易出错的地方，要有专门测试断言「包装后仍满足 `ToolStreamingSender`」。

### 3.4 过滤哪些内容块

需求 §5.5 作用范围：「模型正文；若展示思考过程，则一并过滤。界面若展示工具结果文本，同样过滤；不展示的原始 JSON / 附件二进制 / 图片 OCR 本期不做」。

| ContentBlock 类型 | 过滤 | 理由 |
|---|---|---|
| `text` | ✅ | 模型正文 |
| 思考 / reasoning 文本 | ✅ | 需求明确「若展示则一并过滤」 |
| `tool_result` 的**可见文本** | ✅ | 需求明确 |
| `tool_use` 的 input JSON | ❌ | 界面不展示原始 JSON；且打码会破坏 JSON 结构导致工具调用失败 |
| 附件 / 二进制 | ❌ | 需求明确不做 |

`tool_use` 不过滤这条要写进代码注释——否则将来有人会觉得是遗漏而「补上」，结果打坏工具参数。

### 3.5 输入侧：开关与再次发送

需求 §5.5.1 的循环规则：

```
点发送
  ├─ 开关关闭 → 直接发送（原文）
  └─ 开关开启 → 检测
       ├─ 未命中 → 发送
       └─ 命中 → ① 不发送
                  ② 输入框内容替换为打码后文本
                  ③ 下方提示「包含敏感内容，已替换敏感词，确认后可再次发送。」
                  ④ 用户再点发送 → 对【当前输入框文本】重新检测
```

第 ④ 条是关键：**每次都对当前框内文本重新检测**，不记「用户已确认过」的状态。所以「用户把 `***` 改回原词再发送」自然会被再次拦住（需求 §5.5.1 第 5 条），不需要额外逻辑。这一点要写测试固定住，避免有人为了「改善体验」加一个「已确认」标志把这条规则破坏掉。

**开关**：

- 存 `product-state.json` 的 `prefs.inputSensitiveCheck`（P3 已定 schema）。
- 位置：输入框下方（需求 §5.5.1），走 P6 的 `ComposerNotices` 的 `slot: 'below'`（下方第一条）。
- 关闭前确认框：「关闭后，输入将按原文发送。模型回复仍会过滤。」重新打开无需确认。
- **只影响输入**。输出过滤与昵称检测不受它影响 —— 这三处共用引擎但各自独立判断是否启用。

### 3.6 与积分、PII 的顺序

需求 §5.5 末段 + §5.4.4，合起来是一条固定流水线：

```
点发送
 1. 输入合规检测（可关）      ── 命中 → 停，不扣分不计消耗（P6）
 2. 扣减积分（P6）
 3. 交给模型 ── 构造 provider 请求时做 PII 脱敏（不可关，仅隐私模式，P10）
```

第 1 步在前端触发（为了即时打码回填输入框），但**服务端在第 2 步之前必须再做一次**——前端可绕过。服务端命中时返回 400 而非静默过滤，前端按同样的规则展示提示。

PII 脱敏只作用于「发给模型的副本」，用户气泡与历史存原文（需求 §5.6.2 表格）。第 1 步的替换则是三处都替换（气泡、模型、历史一致）。这两条规则相反，实现时容易搞混，在 `Composer.svelte` 和服务端 handler 各写一段注释对照需求 §5.6.2 的表。

> PII 物理上位于「交给模型」一步内部（agent 构造 provider 请求时，P10 §3.3 的装饰器），因此排在扣减之后。它不影响计费，先后顺序无业务影响；画在第 3 步内部是为了与 P10 的实现位置一致，也与 P6 §3.5 的链路对齐。

## 6. 测试

**Go 单测**

- `WrapSensitive` 后仍满足 `ToolStreamingSender`（类型断言测试）。
- 流式：模型吐 `发` / `票` 两个 delta → 上屏最终为 `***`，落盘为 `***`。
- 落盘：`Message.Blocks` 里的 text 已打码；`tool_use` 的 input **未被改动**。
- 思考文本被过滤；工具结果可见文本被过滤。
- 昵称命中 → 400 且状态文件未变。
- 输入检测开关关闭时，输入原文发出，但**输出仍被过滤**。

**前端单测**

- 命中 → 输入框文本被替换、提示出现、未调发送接口。
- 用户把 `***` 改回原词 → 再次点发送仍被拦（这条显式测）。
- 开关关闭需确认；重新打开不需确认。

**手工验收**：按需求 §8「敏感词」段全条。特别是「关输入检测后隐私模式 PII 仍在」——跨 P8/P10 联调项。

## 7. 上游合并影响

**等级：高。** 这是本期第二个高等级项。

冲突面与缓解：

| 位置 | 风险 | 缓解 |
|---|---|---|
| `internal/app` 构造 Sender 处 | 上游重构 Sender 装配 | 装饰器本身是独立文件；接入只有一行 `WrapSensitive(...)`。冲突时重新包一次即可 |
| `internal/server` chat handler | 上游高频改动 | 输入检测抽成一个函数，handler 里只有一行调用 |
| `Composer.svelte` | 上游高频改动，且本 PR 与 P6/P10 都改它 | 三个 PR 的改动全部走 `ComposerNotices`（P6 建立）与独立的 `sensitive.ts`，`Composer.svelte` 内只留调用 |
| **Sender 接口栈变化** | 上游若增删 Sender 层级，装饰器会静默降级能力 | 类型断言测试是主要防线；接口变化时测试会红 |

最后一条是最阴险的：装饰器少实现一层接口不会编译失败，只会让运行时能力降级（比如流式退化成非流式）。**必须有测试断言包装后的能力集合**。

## 9. 风险与决策

| 项 | 处理 |
|---|---|
| 流式「先闪后改」 | 需求 §9.5 已接受。`StreamFilter` 把窗口压到最小；`message:final` 保证最终态正确 |
| 装饰器降级能力 | 类型断言测试 + PR 检查表里列为必查项 |
| 前端检测被绕过 | 服务端重做一次，前端只是体验 |
| 打码破坏 Markdown / 代码块 | `***` 在 Markdown 里是强调语法，可能让渲染变形。本期接受（需求只要求打码），若验收时明显难看，改用 `***` 的转义形式并记入下期 |
| 输入检测的 HTTP 往返延迟 | loopback，实测应在 1ms 内。若输入框逐字检测则加 150ms 防抖；**发送时必检**不防抖 |
