## 二、建议先区分两种改造范围

### 方案 A：白标品牌重塑，保留兼容性 — 推荐

只改变用户看到的产品身份：

- 新软件名称
- 新 Logo
- 新 About
- 新官网和文档品牌
- 新桌面安装包名称
- 新移动 App 名称
- 新图标和系统显示信息
- 新团队介绍
- 新下载页和更新地址

但暂时保留：

- `octo` CLI 命令
- `~/.octo` 数据目录
- `OCTO_*` 环境变量
- `octo-ui` 内部协议
- `octo-pair` 配对协议
- 旧 API/WS 行为
- 旧 Go module 路径

这样风险最低，不会导致用户已有配置、会话、技能、脚本和移动端协议全部失效。

### 方案 B：完整 fork 身份迁移

除了界面，还彻底改成另一个产品：

- CLI 可执行文件从 `octo` 改成新名字
- Go module 改成新仓库路径
- 所有 import 路径迁移
- `~/.octo` 改成新数据目录
- `OCTO_*` 改成新的环境变量前缀
- `octo-ui`、`octo-pair` 改成新协议名
- Capacitor Bundle ID、Android Application ID、iOS URL Scheme 全部改
- macOS Bundle ID、LaunchAgent、pkg identifier 改
- Windows AppUserModelId、安装目录、卸载信息改
- Release 仓库、下载域名、升级地址全部改
- 所有文档、内置技能和源码注释重新命名

这个方案更像独立产品，但会涉及较大的兼容和迁移工作，不能简单全局替换。

**我的建议是先做方案 A，再预留方案 B 的命名层。**
也就是说，先把展示层和发布层白标化，同时把内部标识集中管理，后续再决定是否迁移数据和协议。

- 原始版权和许可证

- 实际贡献者归属
- 真实团队信息
- 第三方项目的明确来源
- 不能声称原作者是新团队，除非确实获得授权并且事实如此

也就是说，**可以让产品拥有新的视觉品牌和团队信息，但 About、许可证和归属信息必须真实**。原来的“Prior Art & Acknowledgements”也不能为了让它看起来像完全原创而删除。

## 八、当前建议

我建议默认采用：

> **新品牌展示 + 新官网/安装包/系统元数据 + 保留旧 CLI、数据目录和协议兼容 + 真实 About 和许可证归属**

这样能达到用户看到的是一个新团队、新产品的效果，同时不破坏已有用户数据和系统集成。

下一步需要你先确定上面“阶段 0”的品牌资料，以及选择：

- **只做白标重塑，保留内部兼容**
- **完整迁移成全新产品身份**
