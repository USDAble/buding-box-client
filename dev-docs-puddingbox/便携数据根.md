# 便携数据根

> 本文记录当前实现的持久化边界：产品自己的状态随程序目录携带，默认位于 `data/`；不可用时停止需要写入的功能，不把数据悄悄写回主机目录。它不是每个数据文件格式的说明，具体格式仍由各自模块拥有。

## 写作参照与结构取法

参照 `dev-docs/desktop-update-notice.md` 的“目标与非目标 → 运行时路径 → 失败/恢复状态 → 验证”结构。本文将其用于跨桌面壳、持久化包和前端事件的便携数据链路；不照搬更新产物、发布流程等无关章节。路径 API、目录归属、启动检查和拔盘状态机分别对应其中的运行时接线、边界条件与验证部分。

## 目标、边界与非目标

便携交付要求桌面端和 CLI 对“产品数据放在哪里”给出同一个答案。配置、会话、日志、随包工具、产品状态和服务协调文件不能因为启动方式不同而落到两套目录，更不能在数据盘不可用时改写到主机 home。

本设计还约束两类很容易遗漏的路径：进程 cwd 固定为程序目录，会话未显式配置工作区时使用 `data/workspace/`。这避免出现“持久化数据是便携的，默认工作区却留在启动机器”的半便携状态。

以下内容不属于本机制：

- 不迁移、不发现、也不提示旧的 `~/.octo` 数据；新产品不以它作为兼容数据源。
- 不支持“桌面用便携目录、CLI 用主机目录”的双模式。
- 不重写用户明确给出的绝对工作路径或用户输入的 `~/…`；它们是用户指定的工作对象，不是产品自行决定的持久化位置。
- 不承诺可识别“另一块磁盘恰好挂回同一路径”的情况；当前监测的是固定路径是否是目录，并没有介质所有权标记。

## 术语与不变量

| 名称 | 含义 | 代码所有者 |
| --- | --- | --- |
| 程序目录 | 解析并跟随符号链接后的可执行文件父目录 | `internal/datapath.ProgramDir` |
| 数据根 | `OCTO_DATA_ROOT`，或默认的 `<程序目录>/data` | `internal/datapath.Root` |
| 写路径 | 会创建目录或写入文件的路径；必须从 `Root` 或 `Sub` 开始 | 具体写入模块 |
| 读路径 | 只定位、不创建文件或目录的路径；使用 `Join` | 具体读取模块 |
| 冻结 | 数据根在桌面运行期间丢失时，拒绝新的目录创建和写入准备 | `internal/datapath` + 桌面 watchdog |

需要长期保持的约束如下：

1. 产品持久化路径的解析由 `internal/datapath` 集中完成；调用方不能自行把 home、cwd 或可执行文件目录拼成产品数据位置。
2. 数据根不可写是错误，不存在静默 fallback。显式的 `OCTO_DATA_ROOT` 是覆盖配置，不是 fallback。
3. 只读代码不得因为“看看文件是否存在”而创建 `data/`。读写边界由 `Join` 与 `Root`/`Sub` 区分。
4. 冻结必须在文件系统入口生效，不能只显示一个 UI 状态；否则后台写入仍可能重建一个空的 `data/`。
5. `Sub` 和 `Join` 的 `parts` 是内部受信的相对路径片段，不是用于处理外部不可信路径的沙箱 API。当前实现只做 `filepath.Join`，调用方不得传入可能逃出数据根的 `..` 或绝对路径片段。

## 路径解析与公共接口

`internal/datapath` 是零业务依赖的路径收口层。其解析顺序固定：

1. 若 `OCTO_DATA_ROOT` 去掉空白后非空，转成绝对路径后使用；空字符串与纯空白等同于未设置。
2. 否则读取 `os.Executable()`，尽力解析符号链接，再使用其父目录下的 `data/`。

符号链接解析的目的不是改变用户选择，而是避免 macOS 应用包或链接启动时数据根随链接位置漂移。无法解析符号链接时仍使用可执行文件返回的路径；无法定位或绝对化程序目录时返回错误。

| API | 副作用与失败语义 | 适用场景 |
| --- | --- | --- |
| `ProgramDir()` | 只解析程序目录，不创建目录 | 固定 cwd、区分不同便携副本 |
| `Root()` | 冻结时返回 `ErrFrozen`；否则创建根目录并通过临时文件探测真实可写性 | 写入根目录文件，或启动期可用性检查 |
| `Sub(parts...)` | 先调用 `Root()`，创建指定的子目录 | 会话、日志、临时文件等写入目录 |
| `Join(parts...)` | 只解析并拼接，不创建目录，也不受冻结 gate 阻拦 | 读取、`Stat`、轮询和延迟写入前的路径定位 |
| `FreeSpace(path)` | 不创建任何内容；无法统计时返回错误 | 桌面启动期磁盘空间检查 |

`Root()` 创建目录的权限是 `0755`。它不能只依赖 `MkdirAll` 成功：已存在的只读目录也会让 `MkdirAll` 成功，因此实现会在根目录创建临时探针文件；探针失败即返回带上下文的错误。调用方必须把这个错误当成“本次操作不能安全落盘”，而不是自己寻找其他目录。

## 当前目录与默认工作区

桌面启动会在服务初始化之前执行 `ensureWorkingDir()`，把进程 cwd 固定为 `ProgramDir()`。因此从 Finder、桌面快捷方式或文件系统根目录启动，不会使技能发现、项目记忆等相对路径行为从 `/` 或用户 home 开始。若程序目录无法解析，函数保持原 cwd；它不以 home 作为替代目的地。

`internal/tools.ResolveWorkspaceDir` 负责会话默认工作区：

| `workspace_dir` 配置值 | 结果 |
| --- | --- |
| 未设置、空白或历史值 `auto` | `datapath.Sub("workspace")`，即 `data/workspace/`，必要时创建 |
| 其他非空值 | 作为显式工作区；其中前导 `~` 按用户意图展开 |

这里保留 `auto` 是配置兼容，不代表存在第二种自动选址策略。`ConfiguredWorkspaceDir()` 读取配置后复用同一个解析函数；解析失败时返回空字符串，让无运行中服务的调用者按“无可用工作区”处理。

## 目录归属

数据根不是一个要求预先创建全部内容的目录清单。各模块按需创建自己的文件或目录；下表列出当前实现中稳定、可观察的归属，未列出的同级文件不应自动被视为无效。

| 路径 | 主要拥有者 | 用途 |
| --- | --- | --- |
| `data/workspace/` | `internal/tools/workspacedir.go` | 未显式配置时的会话工作区 |
| `data/sessions/` | `internal/agent/session.go` | 会话 JSONL 与会话相关目录 |
| `data/logs/serve.log` | `internal/serveproc`、桌面壳 | 后端滚动日志 |
| `data/logs/cli.log` | `internal/serveproc` | 交互式 CLI 日志，与服务日志分开 |
| `data/logs/crash.log` | `internal/serveproc`、桌面壳 | 非终端启动时的崩溃 stderr |
| `data/serve.pid` | `internal/serveproc` | 后端端口占用与接管协调 |
| `data/config.yml` | `internal/config` | 产品配置 |
| `data/desktop.json` | `cmd/octo-desktop` | 桌面壳设置 |
| `data/bin/` | 工具安装与运行时模块 | 随包工具或可执行依赖 |
| `data/tmp/` | 工具与临时处理模块 | 产品临时文件 |

读取会话目录是读写分离的代表：`agent.SessionsDir()` 会创建 `data/sessions/`，而 `agent.SessionsDirPath()` 用 `Join("sessions")`，供周期性 store watcher 查询。后者不能改回创建型接口，否则每次轮询都要执行目录创建和可写性探针。

## 启动期检查与运行中冻结

桌面端的 `startHub()` 在接管已有后端或进入主界面之前调用 `datapath.Root()`：

```text
Root() 失败 ──> 显示启动错误 ──> 退出
Root() 成功 ──> 读取同一卷剩余空间
                    ├─ 可读取且低于阈值 ──> 显示可用/所需空间 ──> 退出
                    └─ 足够或无法读取 ──> 继续启动
```

空间阈值不是任意常量，而是 `internal/logfile` 当前滚动日志容量：`DefaultMaxBytes × (DefaultBackups + 1)`。目录已通过写探针但剩余空间低于该值时，启动会失败并向用户同时说明可用与所需空间。反过来，`FreeSpace` 本身读取失败不会阻止启动：这是一项预检查，不能因为统计接口不可用而推翻刚刚确认过的可写目录。

服务启动并显示窗口后，桌面壳为这一条已解析的根路径启动 watchdog。生产参数为每 2 秒检查一次，连续 2 次 `Stat` 失败才冻结；一次短暂失败不触发。它的状态机是：

```text
正常
  └─ 连续两次根路径不是可用目录 ──> Freeze + 一次 datastore:lost
冻结
  ├─ 根路径仍不可用 ──> 保持冻结，不重复通知
  └─ 同一绝对路径重新成为目录 ──> Thaw + 一次 datastore:restored
```

`Freeze()` 设置的是 `internal/datapath` 的进程级 gate。被冻结后，`Root()` 与 `Sub()` 在接触文件系统前返回 `ErrFrozen`；`Join()` 和 `ProgramDir()` 仍可读，因为它们不会重建根目录。桌面壳在状态转移时同时记录日志并经产品事件通道广播 `datastore:lost` / `datastore:restored`，界面层据此显示或撤销冻结状态。

当前恢复条件是“原先固定的路径重新是目录”，而不是“发现任何看起来像数据根的路径”。因此移动介质换了盘符或挂载点不会解冻；相反，不同介质若恰好挂载在同一路径会被当成恢复。这一限制需要介质/实例所有权记录才能消除，不能通过猜测 inode 或设备号替代。

## 防回归机制

路径规则仅靠 review 不够，因为上游同步很容易重新引入旧的 home 数据路径。`scripts/datapath-guard.mjs` 与 `internal/datapath/guard_test.go` 提供两层检查：

- 扫描 `internal/`、`cmd/`、`shared/` 中的非测试 Go 文件；裸 `".octo"` 字面量必须在同一行有 `octo-literal-allow: <原因>` 标记。
- `os.UserHomeDir()` 必须列在 `scripts/homedir-allowlist.txt`，每条有针对真实主机环境访问的理由。
- 运行时 prompt 与 skill 文本不得出现明确的 `~/.octo`，避免模型按指令把产品文件写到主机 home。
- Node guard 由 `make datapath-check` 和 Go CI 运行；Go 单测在不依赖 Node 的情况下镜像 `.octo` 标记规则。

项目仓库自己的 `<cwd>/.octo/` 与主机的 `~/.octo` 不是同一件事。前者可能是上游兼容的项目 hooks 或 worktree 目录，才允许逐行标记；标记不放宽同一文件的其他行，也不能作为产品持久化例外。允许访问 home 的条目同样不授予“在 home 写产品状态”的权限。

## 验证清单

改动涉及路径、启动、会话或持久化时，至少覆盖以下事实：

| 场景 | 现有自动化证据 | 预期 |
| --- | --- | --- |
| 默认解析、环境覆盖、空白覆盖值与符号链接 | `internal/datapath/datapath_test.go` | 根路径唯一且可预测 |
| 只读根、创建型与只读型 API | `internal/datapath/datapath_test.go` | 不可写明确失败；`Join` 无副作用 |
| 冻结、解冻和不创建空目录 | `internal/datapath/frozen_test.go` | `Root`/`Sub` 拒绝，读路径可继续定位 |
| 拔盘、短暂失败、同路径恢复、异路径不恢复 | `cmd/octo-desktop/watchdog_test.go` | 一次状态转移一次通知，写 gate 与监测一致 |
| 启动期低空间文案与阈值来源 | `cmd/octo-desktop/boot_failure_test.go` | 阈值跟随日志容量，错误可行动 |
| 完整服务启动的写入边界 | `cmd/octo-desktop/portable_test.go` | 主机 home 不产生 `.octo`，数据根确有运行时产物 |
| 静态防回潮 | `make datapath-check` | 未标注的旧路径或 home 访问使检查失败 |

手工验收仍需要在目标平台的可移动介质上完成：从便携目录启动、创建会话并重启，再确认目录移动后同一份数据被读取；运行中移除介质，确认界面冻结且没有新的空 `data/`；恢复到同一路径后再确认写入恢复。测试环境的 `OCTO_DATA_ROOT` 只用于隔离，不应掩盖真实打包产物的该项验收。

## 变更与上游同步

这是高冲突面：上游可能在任意业务包中新加路径、日志、配置或启动逻辑。同步时应先采用上游的结构和修复，再把产品持久化调用接回 `datapath`；不要在冲突解决中复制一个私有的 `octoDir` 或 home fallback。对确有分叉理由的接线保留 `OCTO-FORK` 注释，并按 [上游合并策略](规范/上游合并策略.md) 完成 guard 与相关测试。

新增数据文件时，变更同时需要回答四个问题：它的唯一所有者是谁、读路径是否无副作用、写入在冻结时如何失败、以及是否应加入本节的稳定目录归属表。文件格式、迁移和兼容行为则写入对应功能主题，不堆回本篇。
