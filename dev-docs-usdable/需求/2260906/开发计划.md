## 3. 分阶段实施计划

### 里程碑 0：便携数据根 + 启动行为（§5.7 + §5.1）

改动面最大、最该先做。目标是把上游写主机 `~/.octo` 的所有行为收敛到 `data/`。

**P1 数据根与工作区** — 方案见 `技术方案/P1-便携数据根.md`

- `data/`（可执行文件同级）作为唯一数据根；各模块只认当前数据根。
- 进程 cwd = 程序目录，禁止切到用户 Home。
- 会话工作区 `data/workspace/`（不存在则创建）。
- `uv.exe` → 数据根（不再写 `~/.octo/bin`）；`serve.pid` / 崩溃日志 / 登录态 / 词库 → 数据根。
- **先建收口层 `internal/datapath`，再机械替换全部调用点**，最后加 `datapath-guard` CI 防回潮。

> **评审修正（工作量被严重低估）**：初稿说「梳理 `internal/config`、`internal/serveproc`、`cmd/octo-desktop/uv.go`、`internal/crashlog` 等」——实际 `os.UserHomeDir()` 在**非测试代码里出现 71 次、横跨 57 个文件**，还涉及 `internal/tools`（15 处）、`internal/server`（9 处）、`internal/memory`、`internal/skills`、`internal/hooks`、`internal/mcp`、`internal/channel`、`internal/trash`、`internal/audit`、`internal/prompt`、`internal/agentprofile`、`internal/workflow`、`cmd/octo`。仓库里已经存在**两份**私有 `octoDir()`（`internal/serveproc/serveproc.go:18`、`internal/server/profile_handler.go:218`），本身就说明缺一层抽象。逐处改必漏，且每次上游合并都会带回新的写入点，因此收口层 + CI guard 是必需项而非可选优化。

> **评审修正（这项已经做了）**：「会话增量落盘」上游已实现——`internal/agent/session.go:654 Save()` 已是 append-delta（`appendDelta()` 在 `:720`），只有首次保存、compaction、repair 才 `rewriteAll()`。本 PR 的责任改为「**不破坏**既有增量语义 + 收敛真正高频整文件重写的几处（`config.yml`、桌面 settings、敏感词开关）」。

**P2 启动与生命周期** — 方案见 `技术方案/P2-启动与生命周期.md`

- 单实例（ID 已为 `app.puddingbox.desktop`）；第二次双击激活已有窗口并提示。
- 端口 8088 被占（含 Octo / `octo serve`）→ 明确提示后退出，不换端口、不改数据根。
- WebView2 缺失 → 本机可理解的错误说明，不闪退。
- 托盘「退出」先落盘再结束进程；拦截页关窗口同样进托盘；帮助写「先退出再拔 U 盘」。
- 运行中拔盘 / 目录消失 → 冻结界面，禁止改写主机；同路径恢复可继续。
- 隐藏开机自启动开关；关闭自动更新与托盘更新入口（个人中心「检查更新」待接入）。

> **评审补充**：初稿说「单实例 ID 已改」——已核实为真（`cmd/octo-desktop/main.go:226` 走 `brand.Identifier`）。但同一条需求还要求「若第二次点的不是正在运行的那份目录，须提示先退出」，上游 `OnSecondInstanceLaunch` 只调 `bridge.showWindow()`，**不区分是否同一份目录、也不提示**，这部分是全新工作。另：端口占用检测目前完全没有实现（`main.go:61` 的 `hubAddr` 是常量，监听失败即崩），需求 §5.1.2-6 的可读提示是新增项。这两条在方案里拆成了独立的可验收子项。

### 里程碑 1：登录与产品门（§5.3）

**P3 登录态与产品门** — 方案见 `技术方案/P3-登录态与产品门.md`

- 数据根登录态：本地 token（无过期）、昵称、脱敏手机号、激活信息、最近登录时间。
- 产品门 = 新增一层「拦桌面窗口 + 该窗口发起的聊天相关请求」，与现有 access key 机器门（`internal/app/gate.go`）并存、不替代、不拆除。
- 退出登录：确认后清登录态、回拦截页，进程保持、托盘仍在；积分/会话/激活绑定保留。

**P4 拦截页 = 登录表单** — 方案见 `技术方案/P4-拦截页.md`

- 首次激活（含激活码，主按钮「激活并登录」）/ 二次登录（无激活码，主按钮「登录」），无单独空门面。
- 手机号规范化：去空格短横线、`+86`/`86` 前缀、`1` 开头 11 位；二次登录与绑定号用规范化后比较。
- 验证码：固定 `123456`，先点发送（60s 倒计时），10 分钟有效。
- 激活码：固定 `固定本地激活码`（大小写不敏感）。
- 昵称：按当前界面语言随机默认（中文「用户」+ 4 位 / 英文 `User` + 4 位），长度 2–16，允许中文字母数字下划线，命中敏感词拒绝保存。
- 拦截页可切中/英（写入数据根），产品名与文案立即刷新（走 `{brand}` / `{brandShort}` 插值）；Logo 图形与语言无关，用品牌 PR4 的 `BrandMark.svelte` 渲染资产管线产物，不在拦截页自绘图形或文字标。
- 依赖：拦截页 Logo 依赖品牌 PR2（资产管线，⏳ 阻塞于设计交付矢量源）与 PR4（`BrandMark.svelte`，依赖 PR2）。PR2 未完成前拦截页先用待接入标志文件接口跑通，布局与键名按最终形态做，正式源到位后只重跑 `make brand`，不返工页面。

### 里程碑 3：敏感词（§5.5）

**P7 敏感词引擎** — 方案见 `技术方案/P7-敏感词引擎.md`

- 词库：数据根内 UTF-8 文本，一行一词、`#` 注释。**生效词表 = 内置词 ∪ 文件词**（内置词总是叠加，不只是缺失时的兜底 —— 这是 P13 界面能安全清空用户词的前提）。内置含 `赌博`/`毒品`/`发票`/`gambling`/`drugs`/`invoice`/`fapiao`。
- 匹配：Unicode 大小写折叠 + 去空白/符号 + 子串匹配；命中后在原文对应片段替换 `***`，连续命中合并。
- 词库文件替换后下一次检测生效，无需发版。

**P8 接入** — 方案见 `技术方案/P8-敏感词接入.md`

- 输入：默认开启，命中不发送、框内打码、可关（关前确认）、只影响输入、状态写数据根。
- 输出：必过、不可关；上屏与落盘历史都是打码后文本；流式允许先闪后改，以落盘为准。
- 昵称：登录页与账户面板改昵称始终检测，命中拒绝保存。

**P13 词库管理界面** — 方案见 `技术方案/P13-词库管理界面.md`

- 账户面板里一个二级页：内置词只读展示、用户词增删改、导入 / 导出（导入为合并不是覆盖）。
- **文件仍是唯一真相**：界面只是 `data/sensitive-words.txt` 的编辑器，手改文件与用界面改效果一致；保留文件头部注释块；原子写。
- 改完不重启即生效（复用 P7 的 `ModTime` 热加载）。
- **本期不做服务器同步**（无中台，需求 §2.2 / §6「不依赖外网」），界面上不出现同步按钮。数据结构按「内置 / 用户」两级设计，将来加「服务器通用词库」是第三级，不改现有语义。

> **评审补入（2026-09-07，需求已回写）**：需求 §5.5 原写「用户直接改词库文件即可更新，**无单独管理界面**」，现已删掉该半句并补齐界面要求与 5 条验收。见 §4.1 第 3 / 4 项。

## 5. 主要风险

- **便携数据根改动面大**：71 处调用点、57 个文件。靠人工梳理必漏，且每次上游合并会带回新的写入点。缓解：收口层 + `datapath-guard` CI，见 P1。
- **流式输出打码**：词语被拆开时允许「先闪后改」，但必须保证落盘文本一定是打码后（§5.5.2）。缓解：`StreamFilter` + `message:final` 双保险，见 P8 §3.2。
- **Sender 装饰器静默降级**：P8 / P10 都要包 `agent.Sender`。少实现一层接口不会编译失败，只会让流式能力悄悄退化成非流式，验收时表现为「过滤没生效」却查不出原因。缓解：包装后的能力集合断言测试，列入 PR 检查表。
- **跨平台行为**：需求只验收 Windows，但代码跨平台；单实例 / 拔盘 / 托盘在 macOS / Linux 上不能写坏，避免为 Windows 验收引入 macOS 回归。
- **上游合并尚未建立**：仓库当前**没有 upstream remote**，不知道落后多少。若已落后较多，建议在里程碑 0 开工**之前**先合一次——P1 会碰 50+ 文件，在落后基线上做完再合，等于两个大冲突叠加。见 `../../上游合并策略.md` §7 待办 C。
- **设计资源延期**：品牌 PR2（资产管线）与 PR4（`BrandMark`）阻塞在设计交付 3 个矢量源与主色值，而 P4 / P5 / P12 都是它的软依赖。缓解已定（临时文件 + 最终形态键名 + 到位后重跑 `make brand`），但**缺一个 owner 跟踪「设计交付」这件事本身**——它不在任何 PR 的 DoD 里。待办：指定负责人 + 兜底日期，写进里程碑 0 开工清单，避免它静默拖垮 P4 的视觉验收。
