## 生产控制面需要交付真实配置

生产构建选用 `internal/productprofile` 的 production Profile；当前其中的控制面与网关主机仍为 `.invalid` 占位值，可信签名公钥为空。因此构建和结构校验可以通过，但产品门会把该包呈现为未配置，不能完成真实中台登录或取得可信目录。开发 Profile 与 `productstub` 不能替代生产交付。

需要确认：真实的控制面和网关地址、签名 key ID/公钥及其交付渠道是否已具备；若尚未具备，发布流程应明确限制为内部验证，而非对外生产包。结论应回写 [运行时 Profile 配置](运行时Profile配置.md)、[中台接口契约](中台接口契约.md) 与 [便携打包](便携打包.md)。

## Profile 声明与运行时边界尚未对齐

Profile 有 `allowDataRootOverride` 与 `startup` 字段，但前者尚无运行时代码读取，`internal/datapath` 当前仍直接接受 `OCTO_DATA_ROOT`；后者目前只受 schema/测试约束，并不实际控制启动项或用户可见入口。不能把字段存在误读成生产限制已经生效。

需要确认：生产版是否必须禁止数据根环境覆盖，以及 `startup` 是应成为真实开关、从 Profile 删除，还是明确保留为未来兼容声明。若选择实现开关，需先定义对便携使用、已有脚本和用户数据的兼容性，再改代码和测试。详见 [运行时 Profile 配置](运行时Profile配置.md) 与 [便携数据根](便携数据根.md)。

## 跨平台产物命名要确定品牌迁移策略

Windows 便携目录和可执行文件由品牌配置派生；macOS 打包脚本仍输出 `Octo.app`，Linux 输出 `Octo-<arch>.AppImage`。这不是文档命名问题，而是不同平台已经对文件名作出了不同承诺。

需要确认：是否统一到品牌名；若统一，旧下载链接、更新识别、签名/安装说明与用户脚本如何兼容。确认前保持现状并在发布说明中使用实际名称，详见 [便携打包](便携打包.md) 与 [品牌与标识](品牌与标识.md)。

## 本地 Node 版本要与打包脚本前提一致

CI 已固定 Node 22；`scripts/package-portable.mjs` 的递归目录检查依赖 Node 22 提供的目录项路径属性。本机 Node 20 会在该检查中失败，而 Node 22 下相关 47 项脚本测试通过。

需要确认：开发环境的最低版本是否正式定为 Node 22，还是让打包脚本兼容 Node 20。前者需要把前提写入开发/预检入口；后者是工具脚本兼容性改动，应连同两种版本的测试一起实施。详见 [开发与联调](开发与联调.md) 与 [便携打包](便携打包.md)。

## 账户默认模式的事实源需要统一

聊天选择器由已验证目录投影模型和默认模型；但个人中心的默认模式控件目前把 `privacy`、`smart`、`default` 三个 ID 写在前端，后端也只按固定产品模式集合校验偏好。当前目录同样固定为这三组，所以没有立即可见的错误；不过若以后调整模式集合、顺序或可用性，两个消费面会发生漂移。

需要确认：模式集合是否是长期固定产品常量。若是，应在模式契约中明确“目录只提供模型归属，不能扩展模式”；若否，个人中心默认模式控件和偏好校验应改为消费同一个目录投影，并定义目录不可用时的编辑行为。详见 [模式与模型](模式与模型.md) 与 [个人中心](个人中心.md)。
