## 1. 执行原则

- 本计划已用于执行本轮品牌改造；后续品牌资料变更仍按同一阶段顺序复用。
- 不做全局字符串替换；每个旧身份先分类为展示、兼容、法律归属或第三方内容。
- 先集中品牌配置和资源，再修改各端引用，最后处理发布渠道。
- 每个阶段都要能独立构建、验证和回滚。
- 任何破坏已有数据、配对、升级或脚本的变更，必须转入《完整身份迁移预留方案》评审。

## 3. 阶段 1：建立品牌与兼容配置层

### 工作

1. 建立统一的展示身份配置：产品名、描述、链接、Logo 和 About 信息。
2. 建立兼容身份配置：旧 CLI、旧目录、环境变量、协议、模块和深链。
3. 建立法律身份入口：版权、许可证、第三方声明和来源说明。
4. 让 Web、桌面、移动端和发布脚本引用统一配置或生成文件。
5. 给每个不改的旧标识添加注释或文档登记，说明其兼容用途。

### 检查重点

- 展示名不能被兼容常量覆盖。
- 兼容常量不能被错误重命名。
- 同一名称不能在中英文、桌面和移动端出现不同拼写。

## 9. 阶段 7：扫描、回归和发布门禁

### 扫描分类

全仓库搜索下列旧身份及其大小写变体：

- `octo`
- `Octo`
- `octo-agent`
- `open-octo/octo-agent`
- `octo-agent.dev`
- `~/.octo`
- `OCTO_`
- `octo-ui`
- `octo-pair`
- `dev.octo.`

每条命中必须标记为：

1. 展示残留：必须修改。
2. 兼容残留：必须保留并登记。
3. 法律/归属内容：必须真实保留。
4. 第三方内容：按许可证和上游要求处理。
5. 测试夹具或历史迁移数据：保留并注明用途。

### 测试门禁

- `go test ./...`
- `go test ./cmd/octo-desktop/...`
- `go test ./cmd/octo-relay/...`
- Web typecheck、test、build
- Mobile test、typecheck、bundle、native wiring
- 各平台安装、升级、卸载和首次启动
- 旧目录、旧环境变量、旧配对码和旧客户端互操作
- About、许可证、第三方声明、隐私和反馈链接可访问
- 新品牌资源在亮色、暗色、高 DPI 和小尺寸下可读

### 发布顺序

1. 先发布兼容的新品牌版本，旧入口仍可工作。
2. 观察安装、升级、配对和错误反馈。
3. 再逐步替换官网和下载入口。
4. 最后才考虑完整身份迁移。

## 10. 回滚方案

每次发布前保留：

- 旧版本安装包和校验值
- 旧下载地址和升级 API 配置
- 旧 Logo 与文案资源
- 旧协议、旧数据目录和旧配置的读取能力
- 可恢复的 Git tag/branch
- 数据迁移前的备份和迁移日志

展示层出现问题时可回滚资源和文案；兼容层出现问题时必须允许旧路径、旧协议和旧数据继续读取，不能依赖用户手工恢复。

## 11. 完成判定

只有在所有平台通过构建和回归、旧兼容项有测试证据、法律归属完整、发布和升级链路验证通过后，才可以宣称品牌重塑完成。没有证据时只能标记为“方案完成”或“阶段完成”。
