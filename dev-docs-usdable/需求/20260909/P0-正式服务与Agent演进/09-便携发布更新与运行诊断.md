# P0-09：便携发布完整性、更新恢复与运行诊断

| 项 | 内容 |
| --- | --- |
| 当前仓库主责 | 客户端桌面/发布/QA 组 |
| 外部协作 | 发布/中台运维提供签名清单、渠道状态、下载托管和支持请求关联；本仓库不实现发布平台 |
| 可并行 | P0-01 的 profile 约束冻结后即可与 P0-07/P0-08 并行 |
| 依赖 | P0-01；P0-07 将消费本任务的 mock/真机验收结果，P0-08 的凭证迁移可并行接入 |
| 需求基线 | [P0 正式上线需求基线](../P0-正式上线需求基线.md) R1、R8、R9；更新必须由用户确认并可回退 |

## 目标

把“能下载新包”变成可恢复、可定位、可撤销的正式发布能力。当前代码已有更新检查、包校验和 crash log 基础，但正式上线还缺少发布信任根、状态迁移、失败恢复和面向用户支持的闭环。便携版允许更新，但绝不允许静默替换或损坏同级 `data/`。

## 当前仓库开发任务

1. 将 release manifest 的签名验签做成独立 `internal/releasepolicy`：公钥/允许 `keyId` 随 production 包发布，更新清单、包大小、SHA-256、版本/channel/minimum version 均须在签名 payload 内。仅 HTTPS 或单独 checksum 文件不能替代签名。
2. 固化更新状态机：`available -> user_confirmed -> downloading -> verified -> staged -> switched -> health_checked -> committed | rolled_back`。下载、解压和替换只在临时目录发生；`data/` 永不被更新器覆盖。
3. 在新版本首次成功启动后写健康确认；未确认、崩溃循环、签名错误、磁盘空间不足、拔盘/下载中断或替换失败必须回到已知可启动版本，并展示可诊断的机器码。
4. 为 `product-state`、凭证元数据、目录/策略缓存和会话索引建立独立 schema version 与单向迁移器。迁移前做可校验 preimage 备份，迁移失败只读恢复，不得静默初始化成空数据。
5. 建立最小安全启动模式：数据根不可用、策略签名失败或连续启动失败时，不加载远端模型和高风险工具；用户仍可查看错误、导出脱敏诊断、选择恢复/回退。
6. 将现有 crash log 收口为可轮换的本地诊断：记录 build/version/platform、data-root 状态、policy/catalog version、request ID 和机器码；不记录 token、供应商 key、完整对话或附件。上传必须由用户确认。
7. 发布产物 CI 输出版本、签名验证结果、SBOM/依赖清单、哈希和可复现构建元数据；Windows 真机验证签名、更新、回退、拔盘和磁盘不足。

## 发给中台/发布运维的交付要求（本仓库不实现）

1. 《发布与密钥轮换规范》：manifest 签名算法、root/next key 轮换、密钥泄露撤销、渠道/灰度、最小支持版本、强制更新、暂停/撤回与公告流程。
2. 稳定的 release manifest API、下载 CDN/对象存储约束、历史构件/哈希留存和 sandbox 渠道；更新服务变更必须遵守语义版本和弃用窗口。
3. 《故障支持与关联规范》：客户端 `requestId`、release version、diagnostic bundle ID 如何关联到网关/控制面日志；客服/值班的响应 owner、事件分级和升级路径。
4. 公开或受控的服务状态/维护信号、限流/故障机器码、预计恢复/重试语义；客户端不从 HTML 或临时公告文本解析状态。
5. 发布前提供经签名的测试构件：正常更新、撤回版本、签名错误、hash 错误、最低版本拒绝和回退版本均可在 Windows 真机复现。

## 验收

- 用无效 manifest、未受信任 `keyId`、篡改包、版本回退攻击和错误 channel 测试，客户端均拒绝安装。
- 更新中断、拔盘、磁盘不足、替换失败和新版本崩溃不会破坏旧程序或 `data/`；可恢复到已知版本。
- 任意 schema 迁移均有前置备份、幂等测试、损坏输入测试和人工恢复说明。
- 用户在不上传原始对话/凭证的前提下，可生成可供客服定位的脱敏诊断包。

## 不做

不把更新服务器私钥、发布后台、告警平台或远端崩溃收集服务放进当前仓库；不以“能检查 GitHub 最新版本”替代产品自己的受签名发布策略。
