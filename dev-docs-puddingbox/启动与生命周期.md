# 启动与生命周期

写作参照：`dev-docs/desktop-update-notice.md`。沿用其“启动条件 → 状态转换 → 失败与恢复 → 验证”结构；本文以 `cmd/octo-desktop`、`internal/datapath` 和 `internal/serveproc` 的实现为事实源。

> 桌面壳是同一后端的原生宿主：固定绑定回环 `127.0.0.1:8088`，在进程内运行 Web 服务，再将窗口连接到它。启动、隐藏到托盘、显式退出和数据根失联是不同状态，不能用“窗口还在/不在”混为一谈。

## 范围与非目标

本文定义桌面启动、单实例、端口接管、托盘驻留、退出和可移动数据根失联/恢复。数据根解析见 `便携数据根.md`；窗口身份与登录拦截见 `登录、访问控制与拦截页.md`；交付物内容见 `便携打包.md`。

不定义页面业务内容、Profile/中台协议或品牌资产；也不在启动失败后切换到主机 home、另一个数据目录或静默的内存模式。

## 启动闭环

```text
清理无效 TMPDIR，退出更新助手路径
  → Windows/macOS 在主线程显示原生启动提示
  → 设置 crash log、固定工作目录，读取桌面设置，准备原生托盘
  → 应用事件循环启动
  → 验证数据根与可用空间
  → 协调已有 serve 进程，绑定 127.0.0.1:8088
  → 创建隐藏窗口，加载随壳启动页；并行准备随包工具与本地服务
  → 启动页导航完成后显示 loading，后端 HTTP 就绪后导航到应用
  → 开始数据根 watchdog
```

进程工作目录固定为程序目录，避免图形启动从 `/` 或磁盘根目录开始发现工作区、技能或项目记忆。无效的 `TMPDIR` 会先清除，避免安装器遗留的临时路径在后续运行失效；崩溃日志尽早尝试落到数据根，开发者从终端启动时则保留终端 stderr。

`datapath.Root()` 是启动前第一道业务门：路径不存在、不可写或无法确定时显示本地错误并退出，尚未接管端口或停止其他进程。随后读取剩余空间；阈值为日志最坏轮转容量（10 MiB × 4），低于阈值明确展示实际/所需空间并退出。空间统计本身读不到时不把它误判为“磁盘已满”，前提是数据根刚刚已验证可用。

## 后端、窗口与启动失败

桌面后端固定使用 `127.0.0.1:8088`，复用上游 Web、`/api` 和 `/ws` 服务；LAN 暴露仍属于 CLI 行为。Windows/macOS 在 `main` 的早期阶段显示小型原生启动窗口，早于数据根写入探测、桌面设置读取、Wails 创建、通知服务启动与事件循环启动，标题及启动文案来自既有品牌和桌面本地化表。最早提示沿用默认英文，读取语言配置后在同一个原生窗口更新文字，不为显示提示而提前读取数据文件。macOS 使用 AppKit 的旋转进度指示器，Windows 使用 Win32 的不定进度条；它们不创建 WebView，不等待 HTTP 或应用脚本。Wails 在包初始化时锁定主线程，因此初次创建直接使用平台 API；清理在主线程直接执行，其他线程通过 Wails 调度回 UI 线程；因此框架启动前的失败收尾也不会调用尚未建立的调度器。macOS 先取得共享 AppKit application，Wails 随后复用它并设置自己的 delegate；Windows 先创建并同步绘制原生控件，随后的 Wails 消息循环负责持续动画。提示归桌面 bridge 管理；网页启动页显示后、启动错误对话框出现前或应用退出时只销毁一次。原生窗口创建失败时记录警告，沿用网页 loading；其他平台仍使用网页 loading。

窗口地址的唯一入口 `nativeBridge.showWindowAt` 在构建应用 URL 前调用既有 `windowToken()`，使提前保留的启动目标与后续 `server.Config.WindowToken` 使用同一凭据；不能等后端组装时才生成，否则应用导航会携带缺失或旧身份，产品接口被本地窗口门拒绝。该调整不放宽窗口验证。

托盘路由在冷启动等待后端和后端已就绪但窗口重新创建时都保留最新目标；普通“显示窗口”不覆盖“设置／新对话”等明确请求。首次导航交接后消费目标，相同 URL 不重复导航，也不把已消费的旧路由带到后续窗口。

端口成功绑定后才写入 `serve.pid`、打开共享日志并创建主窗口。主窗口起初隐藏，由 Wails 自身的资源处理器提供不依赖后端、外部 CSS 或应用脚本的 `/startup` 页面；原生导航完成后显示网页 loading，再关闭原生启动提示，避免直接显示尚无文档的 WebView。这里不能仅提前调用 WebView 的 Show：没有文档时网页无法绘制 loading，Windows 框架也会等待首次导航才显示窗口。

创建窗口后再同步登录 shell 的 PATH、准备随包工具、清理旧上传文件并组装产品路由，使 WebView 初始化和首次文件准备并行。服务在 goroutine 中运行，桌面壳等待 `/api/health` 返回 `200 {"status":"ok"}`，且启动页完成导航后，才在同一窗口导航到带 window token 的应用 URL；启动期间收到的托盘路由意图保留到此时。探测只走本机，忽略代理环境设置，最多等待 10 秒。超时沿用启动错误对话框并退出，不导航到尚未就绪的服务。产品状态再决定登录拦截页还是主界面。WebView 本身尚未初始化完成时，主窗口保持隐藏，由原生提示提供反馈。原生提示无需等待 Wails 建立事件循环；操作系统装载、签名检查以及 Go 依赖包在 `main` 前的初始化仍发生在提示出现前。不能用应用代码覆盖进程尚未执行的时间。第二实例由既有 Wails 单实例机制处理并退出，早期提示随该进程释放，不另建锁或实例判断。更新助手在任何 UI 初始化前完成，继续使用更新助手自身的交换日志。

应用 HTML 自带轻量启动占位和内联样式，不依赖应用脚本；入口先让启动占位获得一次绘制机会，再动态加载 `bootstrap.ts` 的应用依赖和 CSS。Svelte 产生初始 DOM 后移除占位。脚本加载或执行失败时显示错误及重试按钮；等待超过 15 秒时提示启动较慢并允许重试，不将慢启动判为失败。启动文案在构建时来自前端本地化表，应用加载前沿用页面默认语言。Word、Excel 预览解析库按文件类型动态加载，不进入首屏入口依赖。

`desktop startup` 记录 `main_entered`、`native_loading_visible`、`crash_log_ready`、`framework_init_started`、`framework_init_finished` 和 `event_loop_started`。入口和原生窗口时间在发生时保存，打开 crash log 后再写入，避免图形启动丢失早期日志；其他早期阶段也按既有 stderr 路径进入 `crash.log`，终端启动时则写入终端。累计时间从桌面包初始化起算，不包含依赖包初始化和操作系统装载时间。Windows/macOS 另记录 `desktop process timing`：通过系统的进程创建时间计算 `process_to_main_ms` 和 `process_to_native_ms`，把 `main` 前的依赖加载也纳入诊断；获取失败仅记录计时不可用警告，不影响启动。这些值仍不包含点击后、系统创建进程前的启动器等待。若入口至原生显示很短，但点击至提示仍明显停顿，应按这组计时区分进程内加载与进程创建前的等待，不能将其直接归因于 WebView。`serve.log` 的 `desktop startup` 分别记录窗口创建、网页 loading 显示、shell PATH 就绪、随包工具就绪、后端组装完成、HTTP 就绪、应用导航及首个前端心跳的累计毫秒数。相邻阶段的差值用于定位串行准备工作；窗口与后端初始化有重叠，不能把各阶段累计值相加。WebView 控制台的 `app startup` 记录导航至主模块就绪、初始 DOM 挂载及挂载后的帧回调耗时。导航完成和帧回调代表页面加载/渲染调度机会，不宣称物理屏幕已显示；真实冷启动时间仍需在 Windows/macOS 正式包上测量。首次释放内置技能等文件继续保持现有版本标记及写入边界。

产品组装未能安全打开状态/凭证等关键存储时，不挂载产品路由，窗口获得明确的不可用结果；不能制造空状态继续运行。桌面壳在本次启动开始时生成 window token，写入服务配置并放入首个 webview URL；详情见登录与访问控制文档。

## 单实例、跨副本与端口接管

窗口单实例、数据根 `serve.pid` 协调和端口监听是三个不同所有者：

| 问题 | 所有者 | 结果 |
| --- | --- | --- |
| 同一程序目录再次启动 | Wails 单实例 ID | 提升现有窗口。 |
| 不同程序目录在运行 | 第二实例回调携带的 `programDir` | 显示“另一副本正在运行”说明，不假装第二个副本已启动。 |
| 已有 `octo serve -d` 持有同一后端 | `serveproc` 与 `serve.pid` | 先询问，用户确认后停止旧 daemon，再等待最多 8 秒释放端口。 |
| 未识别的程序占用 8088 | 监听器 | 显示点名端口的错误并退出；不终止未知程序。 |

跨副本比较先规范化路径，再尝试解析符号链接；任一侧未知时按“同一副本”处理，只可能漏掉提示、不会向用户捏造冲突。接管成功后才重开共享日志，避免对仍活着的旧后端进行日志轮转。

## 窗口、托盘与退出

关闭窗口并不等于退出。Windows/Linux 是否在最后窗口关闭时保留后端由“保持后台运行”设置决定；macOS 通过自身的最后窗口策略实现同一选择。后台驻留时托盘仍提供显示窗口与明确的“退出”动作；显式退出还会考虑其他已连接客户端，不能把停止共享后端伪装成无影响操作。

真正退出时按以下顺序收尾：停止 watchdog；仅删除当前进程仍拥有的 pid 记录；以最多 5 秒的 context shutdown 本地 server；关闭日志。更新重启是唯一允许绕过后台驻留 veto 的退出路径，否则更新助手会等待永远不会结束的进程。

便携产品当前关闭自动更新检查和原地自替换路径；保留的相关 UI 不应发起出站版本检查或暗示“已检查最新”。这不等同于移除更新能力的未来决定，而是当前交付边界。

## 数据根 watchdog：冻结不是只遮住 UI

服务和首个窗口就绪后，watchdog 固定观察启动时解析出的**同一绝对数据根路径**。每 2 秒检查一次目录；连续两次失败才进入冻结，避免一次短暂 stat 故障打断用户。冻结/恢复各只广播一次：

| 状态变化 | 运行时行为 | 用户侧行为 |
| --- | --- | --- |
| 连续失败，根丢失 | `datapath.Freeze()` 关闭所有经 datapath 的写入/目录创建。 | 广播 `datastore:lost`，全局冻结层阻止继续操作。 |
| 同一路径重新成为目录 | `datapath.Thaw()` 重新允许写入。 | 广播 `datastore:restored`，解除冻结。 |
| 数据在其他路径出现 | 保持冻结。 | 不把陌生目录当作原数据，避免创建一份空数据。 |

冻结门由 `internal/datapath` 唯一拥有，watchdog 只决定何时翻转；这样不会出现“页面冻结但写入仍在继续”。冻结状态也会向之后连接的窗口重放。当前恢复判断只验证固定路径可用，无法区分“原介质重新挂载”和“另一块盘恰好挂到同一路径”；解决后者需要引入产品所有权标记，属于需要先设计的变更，不能用不可靠的文件系统身份判断替代。

## 验证

- 用数据根缺失、不可写和低空间分别验证启动前错误；确认未接管已有 daemon、未启动服务和未创建替代数据根。
- 用同目录二次启动、符号链接路径和不同便携目录验证窗口单实例提示；用已有 daemon、未知端口占用验证接管和拒绝路径。
- 验证关闭窗口、托盘显示、显式退出、更新重启的后端与 pid/log 生命周期不同。
- 在运行中移除数据根，确认两次检查后写入收到 `datapath.ErrFrozen`、只广播一次失联；原路径恢复后只广播一次恢复并重新允许写入，其他路径不解冻。
- 运行桌面壳嵌套模块的启动、单实例、watchdog 与便携数据根测试；目标平台再做真实可移动介质手工验收。
- 在 Windows/macOS 验证首次启动先显示原生提示；用仅存在于开发验证 overlay 的框架初始化延迟，确认等待期间提示已经可见。网页 loading 就绪后原生提示消失，再进入登录/主界面；启动失败、启动中退出时原生提示也应关闭；慢脚本加载期间占位保留，脚本失败可重试。记录正式包首次及再次启动的阶段日志，分别排查文件准备、WebView 初始化、主脚本解析与挂载。
