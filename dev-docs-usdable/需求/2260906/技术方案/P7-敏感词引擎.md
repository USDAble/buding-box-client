## 1. 目标与非目标

**目标**：一个独立的 Go 包，提供「规范化 → 子串匹配 → 在**原文**上打码」的完整能力，加词库热加载。这是本期唯一的敏感词实现，输入检测、输出过滤、昵称校验三处共用。

**非目标**

- 不做接入（P8）。
- 不做 PII 脱敏（P10 —— 那是另一套规则，需求 §5.5 末段明确「两套独立」）。
- 不做词库管理界面 —— 2026-09-07 评审决定**要做**，但拆到 P13；本 PR 只提供它需要的读写能力。
- 不做第三方审核（需求 §5.5 匹配规则第 4 条明确禁止）。

---

## 2. 现状（代码事实）

上游没有任何内容过滤能力。`internal/` 下无相关包。全新。

> **计划拍板**：开发计划 §4 第 1 条把「输出过滤放 Go 侧还是 Web 侧」列为待定。**本方案拍板为：唯一实现放 Go 侧 `internal/sensitive`，Web 侧不做第二套匹配逻辑，输入框的实时打码通过一个专用 API 调 Go 侧。** 理由：
>
> - 需求 §5.5.2 要求「写入数据根的历史必须是打码后文本」——落盘在 Go 侧，过滤必须在 Go 侧。
> - 若 Web 再实现一套，词库解析、Unicode 折叠、符号表三处规则必然漂移，而验收要求两边表现一致（§8「输入命中不发送，框内已替换」+「输出命中后界面与历史均打码」）。
> - 代价是输入框检测多一次本地 HTTP 往返（loopback，亚毫秒级），可接受。

## 3. 设计

### 3.1 三步流水线

需求 §5.5「匹配（已定）」四条规则，直译成三步：

```
原文:  "增值税 发 票管理"
                │
        ① 规范化（同时记录映射）
                │  折叠大小写 → 去空白 → 去符号
                ▼
规范文: "增值税发票管理"
索引映射: [0→0, 1→1, 2→2, 3→4, 4→6, 5→7, 6→8, 7→9]   ← 规范位 → 原文位
                │
        ② 规范文上做子串匹配
                ▼
命中: [3,5) = "发票"
                │
        ③ 映射回原文区间并合并相邻，替换 ***
                ▼
输出:  "增值税***管理"
```

**索引映射是这个设计的关键**。需求要求「命中后在**原文**对应片段替换为 `***`」——如果只在规范文上替换，返回的就不是用户写的那句话了（空格和符号都没了）。所以规范化时必须同步产出「规范文每个 rune 来自原文的哪个字节位置」。

### 3.2 规范化规则（需求 §5.5 逐条）

| 步骤 | 实现 |
|---|---|
| Unicode 大小写折叠 | `strings.ToLower` 不够（土耳其语 I、德语 ß）。用 `golang.org/x/text/cases` ？—— **不引入新依赖**（`.octorules`：无正当理由不加三方依赖）。本期用 `unicode.ToLower` 逐 rune 处理，覆盖需求要求的「英文不区分大小写」即可，在注释里写明局限 |
| 去空白 | `unicode.IsSpace` 覆盖普通空格、制表符、换行；再显式加全角空格 `U+3000`（`IsSpace` 包含它，但显式列出便于 review） |
| 去符号 | 需求给了确切符号表，**照抄成常量**，不用 `unicode.IsPunct`（后者范围更大，会误伤） |

符号表（需求 §5.5 原文）：

```go
// ASCII 标点 + 全角对应 + 中文标点。表来自需求 §5.5 匹配规则第 1 条，
// 逐字照抄 —— 用 unicode.IsPunct 会连带去掉需求没列的符号，改变匹配行为。
const stripSymbols = "!\"#$%&'()*+,-./:;<=>?@[\\]^_`{|}~" +
    "！＂＃＄％＆＇（）＊＋，－．／：；＜＝＞？＠［＼］＾＿｀｛｜｝～" +
    "、。「」『』《》—…·"
```

### 3.3 匹配

词条数量级：内置 7 个，用户词库预期几十到几千。用**朴素 `strings.Index` 逐词扫描**即可 —— 千级词库 × 千字文本约几百万次字符比较，微秒级，没有必要引入 Aho-Corasick 增加复杂度和依赖。若将来词库上万再换，接口不变。

留一个 `matcher` 接口以便替换实现，但本期只有一个朴素实现，不做过度设计。

### 3.4 区间合并

需求：「连续或**相邻**命中合并为一段 `***`」。

在**原文**坐标系上合并：两个命中区间若 `end1 >= start2`（重叠）或它们之间只隔被规范化去掉的字符（空白/符号），则合并。后一条是「相邻」的准确含义 —— `"发 票 赌 博"` 应该产出一段 `***` 而不是两段。

实现：把规范文上的命中区间先合并（规范文上相邻 = 索引连续），再整体映射回原文，天然满足。这也是选择「在规范文匹配、映射回原文」的第二个理由。

### 3.5 词库

```
# data/sensitive-words.txt
# 一行一词，# 开头为注释，空行忽略
赌博
毒品
发票
gambling
drugs
invoice
fapiao
```

- 位置：`datapath.Join("sensitive-words.txt")`（P1）。
- **热加载**：需求「替换该文件后**下一次检测**生效，无需发版」。实现为每次检测前 `os.Stat` 比对 `ModTime` + `Size`，变了才重新解析。stat 一个小文件的开销远低于每次解析，也避免了文件监听在 U 盘上的可靠性问题。
- **生效词表 = 内置词 ∪ 文件词**。内置词**总是**叠加，不只是缺失时的兜底。
- 文件缺失或读取失败 → 只有内置词，**并只提示一次**（需求：「可提示一次…不反复弹」）。用一个 `sync.Once` 语义的 `warnedOnce` 标志，进程内只报一次。
- 内置词表至少含需求列出的 7 个（`赌博` `毒品` `发票` `gambling` `drugs` `invoice` `fapiao`）。

> **相对需求的调整**：需求 §5.5 写的是「文件缺失或无法读取：用内置示例词」，即内置是**替代品**。本方案改为内置**总是**生效、文件是加法。理由：P13 要做词库管理界面，如果内置词只是兜底，用户在界面上清空词库就会连内置词一起没掉；改成叠加后，内置词是删不掉的地板。文件缺失时的行为与需求完全一致，不违背原意。见 `P13-词库管理界面.md` §4.1。

内置词表放 Go 常量而不是 `go:embed` 一个文件 —— 它只有 7 行，且必须在文件系统完全不可用时也能工作。

### 3.6 流式支持

需求 §5.5.2：流式时词可能被拆开，「允许先短暂显示再打码」，但**落盘必须是打码后**。

引擎提供两种入口：

```go
// Filter 一次性过滤完整文本。用于输入检测、昵称、落盘前的最终过滤。
func (e *Engine) Filter(s string) Result

// StreamFilter 增量过滤。内部保留一个不超过 maxWordLen-1 的尾部缓冲，
// 保证跨 chunk 的词也能被命中；Flush 吐出剩余部分。
type StreamFilter struct{ /* ... */ }
func (e *Engine) NewStream() *StreamFilter
func (sf *StreamFilter) Write(chunk string) (emit string)
func (sf *StreamFilter) Flush() string
```

`StreamFilter` 的尾部缓冲长度 = 当前词库中最长词的规范化长度 - 1。这样「先闪后改」的窗口被压到最小；P8 决定是否用它，还是简单地「先原样上屏、落盘前整段过滤」。

## 4. 接口与数据结构

```go
// internal/sensitive/sensitive.go
package sensitive

type Hit struct {
    Start, End int    // 原文字节区间（已合并）
    Word       string // 命中的词条（规范化形式），仅用于日志/测试
}

type Result struct {
    Text string // 打码后的原文；无命中时与输入完全相同（同一个 string）
    Hits []Hit
}

func (r Result) Matched() bool { return len(r.Hits) > 0 }

type Engine struct{ /* ... */ }

// New 用给定词库路径构造引擎。生效词表 = 内置词 ∪ 文件词；路径为空或
// 文件不可读时只剩内置词。词库变化在下一次 Filter 调用时生效。
func New(dictPath string) *Engine

func (e *Engine) Filter(s string) Result
func (e *Engine) NewStream() *StreamFilter

// FileUnreadable 报告词库文件是否缺失/不可读（此时只剩内置词生效），
// 供上层决定是否提示一次「词库读取失败，已用内置词」。
func (e *Engine) FileUnreadable() bool

// 打码串。需求固定为三个星号，不可配置。
const Mask = "***"
```

**HTTP**（供 Web 输入框实时检测，P8 挂路由）：

```
POST /api/product/sensitive/check
  req  { "text": "…" }
  resp { "matched": true, "text": "增值税***管理" }
```

## 6. 测试

需求给了可直接转成用例的例子，全部覆盖：

| 用例 | 输入 | 期望 |
|---|---|---|
| 子串命中 | `增值税发票管理` | `增值税***管理` |
| 英文大小写 | `INVOICE` / `Invoice` | `***` |
| 拼音词 | `fapiao` | `***` |
| 符号穿插 | `发-票` | `***`（原文两个字符 + 短横线整体打码） |
| 全角空格穿插 | `发　票` | `***` |
| 相邻合并 | `赌博 毒品` | 一段 `***`，不是两段 |
| 重叠合并 | 词库含 `发票` 与 `票管`，文本 `发票管理` | 一段 `***` + `理` |
| 无命中 | `你好` | 原样返回，`Hits` 为空 |
| 空文本 | `""` | 原样，不 panic |
| 纯符号 | `!!!` | 原样（规范化后为空，不匹配） |
| 词库缺失 | 路径不存在 | 内置词仍命中 `赌博`，`FileUnreadable()` 为 true |
| 词库为空文件 | 0 字节 | 内置词**仍然生效**（叠加语义，P13 的前提） |
| 文件词与内置词重复 | 文件里写 `发票` | 不影响匹配结果，不重复计数 |
| 热更新 | 写新词 → 再 Filter | 新词生效 |
| 注释与空行 | 含 `#` 行 | 不被当作词条 |

**流式专项**

- `Write("发")` + `Write("票")` → 合起来命中，且最终 `Flush` 后的完整输出是 `***`。
- 缓冲长度不超过最长词 - 1（用一个长词库断言内存不失控）。

**模糊测试**：`FuzzFilter` — 断言两条不变式：① 输出永远是合法 UTF-8；② 无命中时输出与输入逐字节相等。

**性能基准**：`BenchmarkFilter` 用 1000 词 × 10KB 文本，记录基线，防止后续改动引入退化。

## 9. 风险与决策

| 项 | 处理 |
|---|---|
| 子串匹配误伤（需求 §9.11 已列为已知限制） | 不做规避。输入侧用户可关（P8），输出侧不可关，这是需求定的 |
| Unicode 折叠不完整（土耳其语 I 等） | 需求只要求「英文不区分大小写」，`unicode.ToLower` 满足。局限写进代码注释，不引依赖 |
| 词库很大时的性能 | 朴素扫描，千级词库微秒级。留 `matcher` 接口，超出再换算法 |
| 热更新的 stat 开销在 U 盘上 | 单文件 stat，每次检测一次。若实测慢，加 200ms 内不重复 stat 的节流 |
| 索引映射的正确性 | 这是最容易写错的部分，模糊测试 + 上表逐例覆盖是主要保障 |
