```bash

# 2) 中台替身（另开一个终端）
go run ./cmd/productstub
```

**替身的固定夹具**（`internal/productclient/clienttest/server.go` 是 owner，此处只抄值）：

| 项 | 值 |
| --- | --- |
| 手机号 | 任意 11 位 |
| 短信验证码 | `123456`（`FixtureSMSCode`） |
| 激活码 | `BUDING-DEMO-0001`（`FixtureActivationCode`） |
| 盒子编号 | `BOX-DEMO-0001`（`FixtureBoxCode`） |

| 初始余额 | `12500`（`fixtureBalanceMicroCredits`） |

**替身的故障注入面**：`cmd/productstub` 的 flag（2026-09-15 起，见下），底层是 `clienttest.Server` 的同名 setter。

> **✅ 2026-09-15 起能在命令行触发了 —— 本表此前那个 ⚠️ 已消。** 此前 `cmd/productstub` 只暴露 4 个 flag（`-tool` / `-upstream` / `-key` / `-model`），**没有一个对状态面**，所以凡是"换余额"或"下架模型"的步骤都得改 Go 源码 + 重启替身，我在每一处标了 `✎ 需改源码`。现在这些 setter 全部接线成 flag，下表原有的 `✎ 需改源码` 已逐处替换成对应命令。**替身启动时会把已武装的开关打进横幅** —— 先看那一行再判断屏幕，否则"注入生效"与"流程坏了"长得一样。

| flag | 起什么作用 | 走查用在哪 |
| --- | --- | --- |
| `-balance=<微积分>` | 改 ledger 报的数（`-balance=0` 是"零余额"那一档） | `L-C4a` ②、`L-C4b` ② |
| `-model-ineligible=<模型 id>` | 把某个模型标成 `eligible=false`（**仍在目录里**，只是不再可选） | `L-C7` ② |
| `-fail-ledger=<status>[:<code>]` | 每次 ledger 读都失败 | `L-C4a` ④ |
| `-fail-bootstrap=<status>[:<code>]` | 每次 bootstrap 都失败 | 控制面四档（`L-B3`） |
| `-fail-completions=<status>[:<code>]` | 每次网关回合都失败 | `L-C4c`（`402`） |
| `-fail-logout=<status>[:<code>]` | 每次登出都失败（平台会话没撤销） | `PQ29` |
| `-omit-ledger-balance` | ledger 里**不给** `balanceMicroCredits`（"缺字段"而不是 0） | `E9` 规则 2 |
| `-catalog-version=<版本>` / `-catalog-ttl=<秒>` / `-policy-audience=<受众>` | 回退攻击 / 荒谬 TTL / 发给别的产品 | `L-C6` 已不做，降级面仍可用 |
| `-expire-access-tokens` / `-omit-policy` / `-tamper-policy` | 访问令牌失效 / 信封缺失 / 载荷被改一个字节 | `L-A6` / `L-C1` / `L-C2` |

**示例**（零余额 + ledger 读失败 + 下架一个模型，一次全武装）：

```bash
go run ./cmd/productstub -balance=0 -fail-ledger=502 -model-ineligible=buding-cloud-fast
```

**`-fail-*` 的两种写法**：`502` 是"**没有业务码**的拒绝"（代理层），`402:insufficient_credits` 是带业务码的。**两者是不同的场景**，不是详略之分 —— 前者落到客户端的传输层文案，后者落到那个码专属的文案。

## 3. 走查的可复跑性（2026-09-15 已解决）

**六条里有两条（`L-C7` ②、`L-C4b` ②）曾必须改 Go 源码 + 重启替身才能造出故障。** 后果不是"麻烦"，是：

- **不可复跑**：走查结论无法让别人重放，只能信记录；
- **容易改错东西**：为造故障去动 `clienttest/sign.go` 的夹具，是**动了契约替身**，而那份夹具同时是别的测试的输入；
- **与 `cmd/productstub` 的设计意图相抵**：`开发规范` 写明这个工具是"让**人**能手工走查"，且**明列"故障注入开关"是它该做的事**。`clienttest.Server` 上那些 `SetBalance` / `TamperPolicy` / … **已经全部存在**，只是没接线。

**处置（2026-09-15 落地）**：13 个 flag 落在 `cmd/productstub`（fork 自有文件，不动上游），§0 有对照表，§1 四处 `✎ 需改源码` 已逐处换成命令。取 flag 而非 loopback 注入端点的理由：走查是靠翻 shell 历史重跑的，开关必须在命令里，且**横幅要能读到它** —— 一个横幅读不到的注入面，等于把"注入生效"和"流程坏了"重新混在一起。

**顺带修掉一处替身自身的缺陷**：四个 `Fail*` 开关的门控不一致 —— `FailBootstrap` / `FailLogout` / `FailLedger` 看 **`code != ""`**，`FailCompletions` 看 **`status != 0`**。于是同一个家族里 `FailCompletions(502, "")` 会拒绝，而 `FailBootstrap(502, "")` **静默什么都不做**。统一为"看 status"（理由与历史写在 `FailBootstrap` 的注释上），钉子 `gate_test.go::TestABareStatusArmsEveryFailureSwitch` 逐成员锁死。统一后**额外买到一个此前表达不出的场景**：没有业务码的 502（代理层），客户端为它专门有一档文案（`catalogTransport`）。

**范围**（§3.10）：**仅限开发工具**，prod 路径不读它 —— 打包目标只构建 `cmd/octo-desktop`，本二进制不被任何打包目标引用。
