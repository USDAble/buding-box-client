## 0. 大类别总览

用户给的四个方向保留，另外补充四类（标 ★），它们是从「上线」角度审视时，原清单完全没覆盖、但对一个要正式对外发布的便携产品**必不可少**的维度：

| # | 大类别 | 一句话定义 | 与用户的对应 |
|---|---|---|---|
| A | 功能逻辑不完整 | 逻辑存在但只做了一半 / 边界没闭环 | 方向 1 |
| B | 交互问题 | 界面/流程行为与预期不符（需走查确认） | 方向 2 |
| C | 静态 / Mock 实现 | 写死常量、假数据、占位文案、固定回复 | 方向 3 |
| D | 真实接口对接 | C 中「将来要接中台/短信/计费/模型」的落地 | 方向 4 |
| E | 品牌与视觉资产 | Logo 正式稿、主色、托盘/社交卡等设计资产 | 补充 |
| F | 安全与技术合规 | PII 范围、敏感词误伤、鉴权语义、WebView2 | 补充 |
| G | 工程与上游合并 | upstream、游离修复、防回潮、能力断言 | 补充 |
| H | 质量 / 稳定性 / 跨平台 | 真模型验收、跨平台、拔盘边界、产物自检 | 补充 |
| I | ★ 数据安全与灾备 | 备份/恢复、版本迁移、损坏自愈、U 盘磨损 | **新增** |
| J | ★ 可观测性与诊断支持 | 崩溃上报、诊断包、日志脱敏、遥测 | **新增** |
| K | ★ 发布、分发与签名 | 代码签名、版本号、渠道、便携更新 | **新增** |

**为什么补这四类**：A–H 覆盖的是「把产品做对」，但一个便携单二进制产品要真正上线，还必须回答四个没人问过的问题——① U 盘丢了/坏了数据怎么办（I）；② 用户报「打不开/闪退」时你拿什么定位（J）；③ 怎么把带签名、能更新的包发到用户手里（K）；④ 处理手机号、做内容过滤、写用户协议，在中国/海外的法务门槛是什么（L）。这四类在需求正文里最多是「已知限制」一笔带过，没有一条落成待办。

**C 与 D 的关系**（沿用上版）：C 是「现状盘点」，D 是「动作清单」。不是所有 C 项都要接真接口——例如 P11 假模型通道（C6）是长期保留的演示/离线/测试设施，永远不会「替换」成真接口。交叉处互相引用。

## A. 功能逻辑不完整

**核心建议**：这一类「缺的不是代码量，是产品决策」。A2/A7/A8/A9 每一条都卡在「产品/业务没拍板」而非「没人力实现」，所以正确动作是**把待决策项集中拉到一次评审里拍掉**，而不是让研发各自猜。技术实现上，A1/A4 用「抽一层抽象、先做通用框架」的方式做，避免下次再为单个类型补洞。

| # | 问题 | 现状 / 根因 | 建议 | 优先级 |
|---|---|---|---|---|
| A1 | PII 只认手机号 | 仅 `MaskPhones`，身份证/银行卡/邮箱/姓名未做 | 把 `internal/pii` 的 `normalize + mask` 框架抽成「规则表」：每种标识符一个 `(识别正则/函数, 打码范围)` 条目，新增类型只加一条规则不写新函数。**顺序建议**：身份证（18 位，中间打码）→ 银行卡（中间打码）→ 邮箱（@ 前打码）→ 姓名（难识别，放最后）。别一次性全做，先等 T12 拍板范围 | P1 |
| A2 | 授权到期不拦截 | 只渲染「已过期」，仍可对话 | 到期拦截是产品策略（T11）。若决定拦，`internal/productgate/gate.go` 的 `Allow` 里加一个 `expired` 分支即可，字段（`Activation.ExpiresAt`）现成。**建议先做「登录后弹一次软提醒」**，硬拦截放最后——拦截会瞬间把一个「还能用的工具」变成「打不开的黑盒」，风险大 | P3 |
| A3 | 换绑手机号未提供 | 帮助页只有「联系客服」占位 | 接真中台后才有意义（换绑 = 中台短信验证新号）。本期保持占位即可，不要本地做一套假换绑——本地换绑会绕过真实身份绑定，纯属自欺 | P2 |
| A4 | 敏感词库只有两级 | 内置 ∪ 用户，无「服务器通用词库」 | 数据结构已按「内置/用户」两级设计，接中台时在 `sensitive.Engine` 加一个「远程词源」只读通道即可，**不改现有两级语义**（需求已明确）。建议先把 Engine 的词源抽象成接口，为第三级留位 | P2 |
| A5 | 积分扣减是假规则 | 成功发送 +1 消耗 / −1 分，与真实计费无关 | 见 D4。**建议先在 `productstate` 抽一个 `Creditor` 接口**（`Consume(msg) (Credits, error)`），本地实现保留现有假规则，接中台后替换实现，调用点不动 | P1 |
| A6 | 验证码会话在进程内存 | `loginCodeSession` 不落盘，重启即失效 | 接真短信（D1）后由中台管理验证码会话，本地假验证码保持内存即可（重启重发可接受，不算缺陷）。**不要为假验证码加持久化**——那是为即将删除的代码写功能 | P3 |
| A7 | 隐私模式是否允许云端模型 | 出厂名单硬编码隐私列无云端，但改配置则放行 | 纯产品策略（T6），配置已支持「改配置则按配置」。**建议保留现状**：出厂隐私列不含云端，不额外做「隐私列禁止云端」的硬校验——硬校验会和「用户可改配置」这条需求打架 | P3 |
| A8 | 繁体中文未支持 | 繁体系统走英文 | i18n 层已支持多语言，加繁体就是补 `zh-TW` 文案行（`web/src/lib/i18n.ts` 的键表）。**建议作为 P2 一次性补全**，比逐个漏改强 | P2 |
| A9 | 便携更新策略缺失 | 关闭自动更新，托盘「检查更新」移除，无「如何安全写回程序目录」方案 | 见 K4（归拢到发布分发类） | P2 |
| A10 | 单实例跨目录提示 | `OnSecondInstanceLaunch` + `checkSingleInstance` 已实现 | 已实现，**复核项**：走查「同一目录二次双击=激活窗口」「不同目录二次双击=提示先退出」两条分支都正确即可，非缺陷 | — |

## D. 真实接口对接

**核心建议（最重要的架构决策）**：当前**没有任何真实后端**，整条链路从登录到模型全是本地假数据。接真之前，**先立一个「产品服务抽象层」**——例如 `internal/backend`，定义 `Account / Activation / Credits / Plan / ModelCatalog / SensitiveSource` 几个接口，当前用 `productstate` 等本地实现，将来用中台实现替换。**UI 和 agent 层只依赖接口，不感知背后是本地还是中台。** 这比「每接一个中台就散落一堆 HTTP 调用」能省下后面成倍的返工，也和本仓库「provider→agent 单向依赖、每层收口」的既有风格一致。

| # | 对接项 | 现状 | 建议 | 优先级 |
|---|---|---|---|---|
| D1 | 短信验证码 | 本地假码 | 接短信服务商；验证码会话迁到中台/服务端。**注意实名制关联**：手机号验证码登录即完成实名，这是 L4 的前置 | P1 |
| D2 | 激活码校验 | 本地字符串比较 | 接激活服务；是否读 U 盘硬件标识（T8）需产品定。**建议先做「激活码 + 设备指纹（软）」，硬件序列号防拷是伪需求，可后置** | P1 |
| D3 | 登录/鉴权 | 假 token | 接真实账号系统（签发/过期/刷新/登出）。**建议保留 window-token 产品门不变**——它是「拦窗口」的进程内机制，与「账号鉴权」是两层，接中台只替换 token 的来源 | P1 |

| D5 | 套餐/订阅 | 固定 trial | 接套餐与支付。**支付在便携单二进制里是坑**（无内购、无常规收银台），建议先只读展示中台下发的套餐，支付走外链/H5 | P2 |

## F. 安全与技术合规

**核心建议**：技术安全层面大部分是「已知限制」而非「缺陷」（loopback 旁路、持有目录即登录、子串误伤都是需求白纸黑字接受的）。真正要在意的是**两处「失败开」**：`productstate.Sensitive` 默认放行（C13）、以及假 token 无任何鉴权语义（F4）。**建议把「失败开 → 失败关」作为上线前的安全加固原则**：凡是安全相关的默认行为，要么显式注入、要么默认拒绝，不允许「忘了接就静默放行」。

| # | 问题 | 现状 | 建议 | 优先级 |
|---|---|---|---|---|
| F1 | PII 范围 | 仅手机号 | 同 A1 | P1 |
| F2 | 敏感词子串误伤 | 子串匹配，如「发票」命中长业务句 | 需求已知限制，用户可关输入检测。**建议上线前做一轮内置词库评审**：内置词要「宁缺毋滥」，误伤率高的话合规效果反被用户关掉。可考虑对内置词加「边界判断」（如「发票」前后非字母数字才算命中）——但注意这是行为变更，要过需求 | P2 |
| F3 | loopback API 旁路 | 产品门只拦窗口请求 | 需求已知限制（§9.8），与「不拦 CLI」同类。接真 token 后，**建议把机器门（access key）与账号鉴权串起来**，否则中台 token 形同虚设 | P2 |
| F4 | 假 token 无鉴权语义 | `local-` 前缀，持 `data/` 即视为已登录 | 接 D3 后自然解决。在此之前，「持有目录即登录」是明示的演示约定，不算漏洞 | P1 |
| F5 | WebView2 检测误判 | 读注册表，边界误判（U-001） | 沿用 `未解决问题登记.md` 的「宁可信可用」兜底；真机复现「误拦可用机」或「放行后闪退」时再改 SDK 方案 | P3 |

## H. 质量 / 稳定性 / 跨平台

**核心建议**：质量类最大的缺口是 **H1（真模型验收）和 H3（拔盘边界未真机测全）**。前者是 P0 硬阻塞（见 D6），后者要靠「真机专项测试」——拔盘、换盘符、目录消失这几条**规格写得很细，但没有一条在真 Windows 上系统跑过**，建议把「便携边界专项」立为一个独立的测试里程碑。

| # | 项 | 现状 | 建议 | 优先级 |
|---|---|---|---|---|
| H1 | 真模型完整链路验收缺失 | 无真实 endpoint，敏感词/PII 只在假通道验证 | 见 D6。**敏感词/PII 的流式断言必须上真模型重跑一遍**——假通道是确定性测试设施，不能替代验收 | P0 |
| H2 | macOS/Linux 跨平台未验收 | 需求只验收 Windows，代码跨平台 | 单实例/托盘/拔盘在 macOS/Linux **不写坏**即可，不必功能齐。建议至少 mac 上冒烟一遍 | P2 |
| H3 | 拔盘/冻结边界 | watchdog+冻结已实现，边界只按规格写未测全 | 立「便携边界专项测试」：拔盘冻结、同路径恢复、换盘符不可续跑、退出后再拔盘抽测会话未写坏 | P1 |
| H4 | U 盘 IO 性能 | serve.log 10MiB、会话增量写、config 写 | 需求 §6「U 盘上发一条消息可完成」。**建议加一个冷启动 + 发送首条的耗时基准**，避免日志/同步写拖慢首屏。高频日志可评估延迟写/降级 | P2 |
| H5 | WebView2 检测 | 同 F5/U-001 | 复用登记 | P3 |

## I. ★ 数据安全与灾备（新增）

**核心建议**：这是便携产品上线的**最大盲区**。需求通篇在讲「数据只进 `data/`」，但从没回答「`data/` 丢了怎么办」。U 盘是易失介质，**「丢一次 U 盘 = 丢账号、丢会话、丢配置」在正式产品里是不可接受的**，而当前没有任何备份/恢复能力。最低限度要做「一键导出/导入」，云端备份等接中台后再补。

| # | 问题 | 现状 | 建议 | 优先级 |
|---|---|---|---|---|
| I1 | 无数据备份/恢复 | U 盘丢失/损坏 = 数据全丢 | **做「数据导出/导入」**：把 `product-state.json` + `sessions/` + `sensitive-words.txt` + `chat-modes.json` + 关键配置打包成单个 zip，界面一个「备份」一个「恢复」入口。这是便携产品的最低自保手段。云端备份（接中台后）作为第二步 | P1 |
| I2 | 状态文件无 schema 迁移 | `productstate` 有 `SchemaVersion` 字段但**没写迁移逻辑**；`agent/session.go` 靠 `omitempty` 兼容旧字段，无正式迁移 | 上线后每次发版都可能改结构。**建议给 `productstate` 补 `SchemaVersion` 检查 + `migrate(from int)` 函数**，读旧版本时走迁移；会话文件继续用「字段级向后兼容」策略，但要在每次发版时审查新字段是否有旧数据兜底 | P1 |
| I3 | 明文敏感数据落盘 | `product-state.json` 存明文手机号（`Account.Phone`） | 接中台（D3）后**只存脱敏手机号**，明文仅在登录瞬间用；正式版可评估数据根加密。本地假数据阶段明文可接受 | P2 |
| I4 | 损坏检测与自愈不统一 | `productstate` 解析失败返回错误，但会话/词库/配置损坏处理各异 | **统一「损坏→保留原文件 + 用内置/重建 + 提示一次」策略**（chatmode 已这么做，sensitive 已这么做，`productstate` 要复核对齐） | P2 |
| I5 | U 盘频繁写入磨损 | 日志 + 会话 + 配置持续写 U 盘 | 会话已是增量写；**评估日志量级**（serve.log 10MiB 上限是否过重）、config 类写入是否可用「脏标记 + 定时落盘」降频。这是长期项，先量测再优化 | P3 |

## J. ★ 可观测性与诊断支持（新增）

**核心建议**：上线后最真实的场景是「用户说打不开/闪退/卡住」，而**你手里只有一个本地 crashlog**，用户不会贴给你。所以必须有一条「用户自助把诊断信息送到研发」的通路。最低成本方案不是做遥测平台，而是**「诊断包导出」**——一键打包日志 + 版本 + 状态文件（脱敏后），随反馈提交。

| # | 问题 | 现状 | 建议 | 优先级 |
|---|---|---|---|---|
| J1 | 崩溃无上报/可读路径 | `crashlog` 只落本地 `data/logs` | **先做「诊断包导出」**：一键把 crashlog/serve.log/版本/状态（脱敏）打包成 zip 让用户提交。远程崩溃上报（Sentry 类）作为第二步，且**必须默认关闭、征得同意**——这是本地产品，不能默认传数据 | P0 |
| J2 | 反馈缺诊断信息 | 帮助与反馈是 cheat sheet，无真实渠道 | 反馈入口 + 自动附带诊断包（D10 的落地形态），否则客服拿到「打不开」三个字无法定位 | P1 |
| J3 | 无遥测/使用统计 | 无 | 产品决策需要数据，但本地便携产品**默认关闭、匿名、可关**。可选，非阻塞 | P3 |
| J4 | 日志可能含敏感信息 | serve.log 汇聚各子系统 stderr，可能含 token/key/PII | **上线前做日志脱敏审查**：确认 token、API key、明文手机号不进日志。`internal/audit` 已做 `maxFieldLen` 截断，serve.log 的敏感点要专门 review | P1 |

## K. ★ 发布、分发与签名（新增）

**核心建议**：这一类是「从演示包到正式包」的物理门槛。**代码签名是 P0**——未签名 exe 在 Windows 上会被 SmartScreen 拦，而需求里最核心的体验就是「双击打开」，签名不过这一步在大量用户机器上直接失败。签名之外，发布前必须定版本号与分发渠道，否则「上线」无从谈起。

| # | 项 | 现状 | 建议 | 优先级 |
|---|---|---|---|---|
| K1 | 代码签名 | 未签名，SmartScreen 拦截，帮助页写「仍要运行」 | **上线必须做代码签名**（EV/OV 证书 + 时间戳），这是「双击打开」的门槛。演示包可继续无签名，但正式发布通道必须签名 | P0 |
| K2 | 版本号管理 | `brand.json` + VERSION，无正式发布流程 | 采用语义化版本，发布时打 tag + 变更说明；`make desktop-portable VERSION=x.y.z` 已有入口，补发布检查单 | P1 |
| K3 | 分发渠道 | 无明确渠道（落地页/网盘/官网待定） | 定渠道 + 提供校验和/签名校验，下载页写明版本与哈希。落地页（`landing/`）已存在，需要对齐品牌与下载链接 | P2 |
| K4 | 便携更新策略 | 关闭自动更新，无「安全写回程序目录」方案 | 便携更新是硬骨头：**先做「检查更新→提示手动下载」**（最安全），自动替换放二期（需辅助进程/重启替换，Windows 下可延迟替换）。正式版前至少保证「能告知有新版」 | P2 |

## L. ★ 法务与监管合规（新增）

**核心建议**：一个处理手机号、做内容过滤、让用户登录的产品，在中国（以及出海）上线**绕不开法务门槛**，而这些在需求里全被「本地占位」掩盖了。**L1 是 P0**（占位协议不能对外发布），L4/L5 是发布前置项，L2/L3 需要法务/合规评审。建议**尽早拉法务介入**，不要等代码做完才发现协议文案、备案、实名这些事没排期。

| # | 项 | 现状 | 建议 | 优先级 |
|---|---|---|---|---|
| L1 | 用户协议/隐私政策 | 「本页为开发占位」 | **法务出正式文案**，走 `brand.config.json` 文案层替换，保留多语言键结构。占位文案不能上线 | P0 |
| L2 | PIPL/GDPR | 处理手机号（个人信息） | 本地存储降低了风险，但**接中台后（D1/D3）个人信息出境/存储要过合规评审**。隐私政策需写明收集范围与用途 | P0 |
| L3 | 内容安全监管 | 敏感词过滤是核心功能 | 内容过滤产品在中国有监管要求：内置词库需满足最低合规标准、需评估日志留存。**建议做一次合规评审**，确认敏感词覆盖与日志审计（`audit.log`）是否满足要求 | P1 |
| L4 | 实名制 | 手机号验证码登录即实名 | 接真短信（D1）后满足实名；在此之前是演示约定。**发布前确认实名链路真实可用** | P1 |
| L5 | ICP 备案 / 软著 | 无 | 在中国发布软件需备案+软著，属法务/运营项，**发布前排期** | P2 |
