# 开发规范

| 项 | 内容 |
|---|---|
| 文档状态 | 草案，供评审 |
| 日期 | 2026-09-07 |
| 适用 | `buding-box-client` 本期及以后所有开发 |
| 关联 | 上游通用规则见 `.octorules` / `CLAUDE.md`；合并见 `上游合并策略.md` |

本文档只写**本项目额外的**约束。`.octorules` 已有的（gofmt、分层、测试就近、英文注释、无新依赖、一个 PR 一个概念）继续有效，不重复。

---

## 1. 为什么要额外一份

这个项目有三个别的项目没有的性质，每一个都能在没有约束时安静地毁掉一整轮验收：

1. **它是 fork。** 随手改上游文件，代价在三个月后的合并里才显现。
2. **它是便携产品。** 「不写主机」是硬验收项，而任何一次 `os.UserHomeDir()` 都能破坏它，且破坏后在开发机上完全看不出来（开发机本来就有 `~/.octo`）。
3. **它是白牌产品。** 任何一句写死的 "Octo" 都是可见缺陷，而上游代码里到处都是。

下面的规则基本都是在防这三件事。

## 2. 分支与提交

### 2.1 分支

```
main                      上游跟踪分支：只接受 `chore(upstream): merge upstream/main`，与 upstream/main 保持一致
buding                    产品集成分支（受保护）：所有功能 / 修复 / 文档 PR 的合并目标，squash merge
├── feat/<pr编号>-<简述>   功能，如 feat/p1-portable-data-root
├── fix/<简述>            修复
└── docs/<简述>           纯文档
```

- 从**最新 `buding`** 切分支，不从别人的功能分支切。`main` 是上游跟踪分支，**功能 / 修复 / 文档 PR 一律合入 `buding`，不直接合 `main`**。
- **一个 feature / 特性 = 一个 PR = 一个 commit（squash）**。一个 PR 对应技术方案里的一个 P 编号：方案说这是一个 PR，就不要拆成三个，也不要合并两个；反之，也不要一个 PR 里夹带多个无关特性。
- 分支存活不超过 5 个工作日。超了说明 PR 太大，拆。

### 2.2 提交信息

沿用 Conventional Commits，**英文**（`.octorules` 已定）：

```
<type>(<scope>): <祈使句，小写开头，不加句号>

<为什么这么做。不是「做了什么」——diff 已经写了。>

Refs: dev-docs-usdable/需求/2260906/技术方案/P1-便携数据根.md
```

`type`：`feat` / `fix` / `refactor` / `chore` / `docs` / `test` / `ci`。
`scope`：包名或模块，如 `datapath`、`productgate`、`desktop`、`web`。

**机械改动单独成 commit**，且在信息里写明「纯机械，无逻辑改动」。这不是形式主义 —— 合并冲突时，reviewer 靠这句话决定是逐行看还是整块重做（上游合并策略 §3.4）。

## 3. 三条本项目专有的硬规则

违反这三条的 PR 不予合并，CI 也会直接拦。

### 3.1 不许自己解析数据路径

```go
// ❌ 禁止
home, _ := os.UserHomeDir()
p := filepath.Join(home, ".octo", "sessions")

// ✅
p, err := datapath.Sub("sessions")
```

`datapath-guard` 扫 `internal/` `cmd/` `shared/`，两类命中分开处理：

| 命中 | 处理 |
|---|---|
| 字面量 `".octo"` | **零例外，直接失败**。产品里已经没有这条路径了（CLI 也一样），任何一处出现都是回潮 |
| `os.UserHomeDir()` | 失败，除非在 `scripts/homedir-allowlist.txt` 里。例外只给「真的要访问主机 home」的场景（展开用户输入的 `~/`、定位主机 Chrome 配置、sandbox 规则），**每条必须写理由**且要过一次 review |

理由：见 §1 第 2 点。这是本期唯一一条「在开发机上完全测不出来」的硬验收项 —— 开发机本来就有 `~/.octo`，写进去看不出任何异常。

顺带一提：`OCTO_DATA_ROOT` 是**显式指定**不是降级位置。测试、开发调试、CLI 装在只读目录这三种场景用它，别的地方不要碰。

### 3.2 不许写死品牌字面量

```svelte
<!-- ❌ -->
<h1>布丁盒子</h1>
<h1>Pudding Box</h1>

<!-- ✅ -->
<h1>{$t('product.name')}</h1>       <!-- 文案表里是 "{brand}" -->
```

所有品牌文字走 `{brand}` / `{brandShort}` 插值，取值只从 `branding/brand.json` 来（需求 §2.5「产品名已定」；品牌取值细则见 §5.2）。`brand-guard` 已在 CI 上。

两个**例外**要显式标注，否则会被 guard 误判：

| 例外 | 处理 |
|---|---|
| 端口占用提示里的 "Octo"（指上游那个产品，不是我们的品牌） | 该行加 `// upstream product name, not our brand` |
| ASCII 标识符 `BUDING-DEMO-0001`、模型 id `buding-*` | 常量旁注释说明它属于需求 §5.2.4「标识符例外」，**不随品牌名改** |

第二条尤其重要：已经有人想把它们改成 `PUDDING-*`。注释是唯一的防线。

### 3.3 改上游文件要打标记

```go
// OCTO-FORK: 输出必须先过合规过滤再落盘（需求 §5.5.2）
// see dev-docs-usdable/需求/2260906/技术方案/P8-敏感词接入.md
sender = WrapSensitive(sender, engine)
```

`grep -rn "OCTO-FORK" .` 就是本 fork 相对上游的完整改动清单。合并时靠它区分「这是上游的」和「这是我们的」。

判断「是不是上游文件」：`git log --follow <file> | tail -1` 看首次提交是不是在 merge-base 之前。不确定就打标记，多打不扣分。

## 4. 技术方案先行

### 4.1 什么情况必须先写方案

- 开发计划里列出的每个 P 编号 —— 都已有方案，直接用。
- 计划外的新工作，只要满足以下任一条：改 3 个以上上游文件 / 新增一个包 / 改数据 schema / 影响验收条目。

方案写进 `dev-docs-usdable/需求/<批次>/技术方案/`，结构按该目录 `README.md` §2 的七节。**缺「上游合并影响」一节视为未完成**。

### 4.2 方案变了要回写

实现过程中发现方案不可行，改实现的同时改方案，同一个 PR 里。不允许出现「文档说 A、代码是 B」——那比没有文档更糟。

## 5. 代码评审

下面两张表就是 `.github/pull_request_template.md` 里 Self-review 各节的展开说明；提 PR 时勾模板即可，这里是「为什么要勾」。

### 5.1 通用检查表

- [ ] 有对应的技术方案，且实现与方案一致（不一致的地方方案已回写）
- [ ] `make fmt-check` / `make vet` / `make test` 全绿
- [ ] `make brand-check` 绿
- [ ] `node scripts/datapath-guard.mjs` 绿
- [ ] 新增/改动有测试；测试覆盖需求里的**边界值**而不只是happy path
- [ ] 无新增三方依赖（或 PR 描述里有正当理由）
- [ ] 改上游文件处有 `OCTO-FORK:` 标记
- [ ] 注释写「为什么」不写「做了什么」

### 5.2 本项目专项检查

| 场景 | 必查 |
|---|---|
| 任何落盘 | 路径来自 `datapath`；冻结状态下不写（P2） |
| 任何用户可见文字 | 走文案表；中英两份都加了；产品名是插值 |
| 改 `Composer.svelte` / `Sidebar.svelte` | 逻辑在新组件里，上游文件里只有一行挂载 |
| 包装 `agent.Sender` | 有「包装后仍满足 `ToolStreamingSender`」的类型断言测试 |
| 改 `product-state.json` schema | schema 是 P3 一次定完的，改它要说明为什么 |
| 新增 HTTP 路由 | 明确它在产品门的白名单里还是被保护（默认保护） |
| 涉及敏感词 / PII | 确认没有写第二套匹配逻辑（引擎只有 `internal/sensitive` 一份） |
| 改敏感词库 | `data/sensitive-words.txt` 是唯一真相，界面只是它的编辑器；没有引入第二份存储 |
| 删上游代码 | 先问「能不能改成让它到不了」。见 `上游合并策略.md` §4.4 |

### 5.3 评审规矩

- 至少一人 approve 才能合。
- Reviewer 只对**看懂了的**部分负责；看不懂就问，不要「看起来没问题」地 approve。
- 「这样写更好」属于建议，可以不采纳；「这样写是错的」属于阻塞，必须解决。评论里把两者说清楚。
- 作者不要在 review 中途 force push（除非 reviewer 同意），否则评论会丢上下文。

## 6. 测试要求

### 6.1 底线

- `make test`（`go test -race ./...`）必须绿。
- 前端 `npm test` 必须绿。
- **不许注释掉测试来让 CI 变绿**。环境问题导致失败就明说（`.octorules` 已有此条）。

### 6.2 本项目额外要求

**把验收项固化成测试。** 需求 §8 里凡是能写成断言的，都写成断言。本期至少这几条：

| 需求验收项 | 固化为 |
|---|---|
| 主机不出现新 `.octo` 业务数据 | `cmd/octo-desktop/portable_test.go` 的 tmpdir 隔离测试 |
| 代码里不存在 `".octo"` 字面量 | Go 测试里的全仓 grep 断言（本地 `make test` 就能发现，不用等 CI） |
| 隐私列无云端、智能列无本地 | `internal/chatmode` 的出厂配置断言 |
| 细条文案只提手机号，不提证件号/银行卡 | 前端字符串断言 |
| 假回复能被输出过滤命中 | `internal/provider/local` 的断言 |
| 用户把 `***` 改回原词仍不能发 | 前端行为测试 |
| 词库为空文件时内置词仍生效 | `internal/sensitive` 断言（P13 界面清空用户词的安全前提） |
| 未登录 + 无 window token 的请求放行（CLI 场景） | `internal/productgate` 测试 |

最后一条是个特例：它测的是一个**看起来像 bug 的有意行为**（需求 §9.8）。没有测试固定住，早晚有人「顺手修好」它。凡是这类反直觉的设计，都要有测试 + 注释双重固定。

### 6.3 手工验收

Windows 是唯一验收平台（需求 §6），但代码跨平台。所以：

- 每个 PR 的方案里都有手工验收步骤，合并前跑一遍并在 PR 里贴结果。
- **macOS / Linux 不能写坏**。任何 `runtime.GOOS` 分支都要有对应测试。为 Windows 验收引入 macOS 回归是开发计划 §5 明列的风险。

## 7. 需求与文档

### 7.1 需求有矛盾、或评审推翻了需求时

不要自己猜，也不要闷头按其中一种实现。流程：

1. 在技术方案里写一节说明矛盾或调整，引用需求的**章节号**（不要引行号 —— 需求一改行号就失效）。
2. 给出取舍与理由 —— 尤其是「为什么这样更好」，将来会有人问。
3. 记入 `开发计划.md` §4.1 表。
4. 评审拍板后**改需求正文**，并在需求的修订表里记一行。
5. 回头把技术方案里那一节改成「已回写，留档」，别让它读起来像还没解决。

**第 4 步最容易被跳过**，代价是几个月后验收时有人拿一条已作废的条款卡你，而当时在场的人都记不清了。本期 6 项已于 2026-09-07 一次性回写（Logo 字随语言变、账户面板形态、词库管理界面、内置词叠加语义、真模型验收、CLI 数据根），留档见 `开发计划.md` §4.1。

**跨文档取值改动**照 `开发计划.md` §4.2 的一致性矩阵同步——那张表列出了每个取值散落在哪几处。

### 7.2 已识别但暂不解决的问题

评审或真机测试中发现「有根因、有兜底、但决定先不做」的问题，**登记到
`未解决问题登记.md`**，别让它只存在于聊天记录里。登记格式与生命周期约定见该文件
文件头的「登记约定」。已立项进某个 PR 的功能不属于此类，那是 `开发计划.md` 的职责。

### 7.3 文档在哪

| 内容 | 位置 |
|---|---|
| 需求、开发计划、技术方案 | `dev-docs-usdable/需求/<批次>/`（当前 `2260906/`，方案在 `技术方案/`） |
| 本地开发 / 运行 / 端口分工 | `dev-docs-usdable/本地开发与运行.md` |
| 已识别但暂不解决（deferred）的问题 | `dev-docs-usdable/未解决问题登记.md` |
| 工程规范、合并策略 | `dev-docs-usdable/` |
| 上游架构设计 | `dev-docs/`（上游的，不要往里塞我们的东西） |
| 项目指引 | `.octorules` / `CLAUDE.md`（两份要同步改） |
| 品牌取值 | `branding/brand.json` —— **唯一来源**，文档里的表格都只是摘录 |

**不要把下游文档塞进 `dev-docs/`** —— 那是上游目录，塞进去每次合并都冲突。

**文档之间用相对路径 + 章节号互链，不要用行号。** 行号在下一次编辑就失效，而失效的引用比没有引用更误导人。

## 8. 定义完成（DoD）

一个 PR 算做完，要同时满足：

- [ ] 方案里的「改动清单」逐项做完，或方案已回写说明为什么不做
- [ ] 方案里的「测试」逐项通过（单测 + 手工）
- [ ] 方案里的「验收对照」中标记为「主责」的条目，能在 Windows 上演示
- [ ] CI 全绿（含四道 guard）
- [ ] Review 通过
- [ ] 若改了行为，`.octorules` / `CLAUDE.md` / 需求文档同步更新

一个**里程碑**算做完，额外要求：

- [ ] 需求 §8 中属于该里程碑的验收条目全部走过一遍
- [ ] 跑一次上游合并（上游合并策略 §3.2）
- [ ] `make desktop-portable` 产物在真机 U 盘上验一遍
