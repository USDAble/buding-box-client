## 0. 这个 PR 是干什么的（评审补充说明）

标题里塞了两件看起来不相干的事，容易看不出用途。分别说：

**第一件：把上游那三个功能入口藏起来。**

上游 octo-agent 的侧栏里有 IM 渠道、MCP 服务器、Light Apps 三个导航项。布丁盒子本期不做这些，但用户能在侧栏点进去 —— 点进去看到一堆配置界面，会以为是产品功能却完全用不了。所以要让这三个入口从界面上消失。

需求两处明写：§5.4.3「主界面**要做隐藏**（不是删除代码）」，§8 验收「主界面默认看不到 IM / MCP / Light Apps 入口」。同时 §7 明写「**不做**：删除这些上游能力」。所以是「藏起来但留着代码」，不是删。

**第二件：积分数字要会动。**

需求 §5.4.4 规定了积分这套假数据的行为：首次激活给 1280，每发一条成功的消息扣 1 分、本月消耗 +1，扣到 0 之后还能继续发（消耗继续涨、余额停在 0），跨月时消耗归零但余额不恢复，被敏感词拦住没发出去的不扣分。

P5 只是把这个数字**显示**在左下角和面板里，数字怎么变是这个 PR 的事。不做的话左下角永远是 1280，验收 §8「积分随成功发送减少；为 0 时有提示仍能发」直接过不了。

**为什么放在一个 PR？** 两件事都只改主界面这一层，都不涉及后端新模块，量都不大，改的文件还有重叠（`Sidebar.svelte`、`App.svelte`）。硬拆成两个 PR 会让这几个文件被改两遍，冲突反而更多。

若评审仍希望拆开，按 `P6a 入口隐藏` / `P6b 积分` 拆，两者无依赖，可并行。

## 1. 目标与非目标

**目标**

1. 主界面默认看不到 IM / MCP / Light Apps 的导航与入口，**代码保留**。
2. 积分假数据：初始 1280、按条扣减、跨月归零消耗、0 分仍可发。

**非目标**

- 不删除任何上游能力代码（需求 §7 明确「不做：删除 IM / MCP / Light Apps 等上游能力」）。
- 不接真实积分（需求 §10 T5）。
- 不做「积分不足禁止发送」（需求 §10 T7 本期仍允许发送）。

## 3. 设计

### 3.1 入口隐藏：单一开关，不是散点删除

新增一个前端能力开关模块，所有隐藏判断只读它一处：

```ts
// web/src/lib/features.ts
// 本期便携形态默认关闭的上游能力。代码全部保留（需求 §7），
// 这里只控制「能不能从界面到达」。
export const HIDDEN_VIEWS = ['channels', 'mcp', 'lightapps'] as const

export function viewHidden(v: string): boolean
export function visibleNav<T extends { view: string }>(items: T[]): T[]
```

三个消费点：

1. `Sidebar.svelte` — `topNav` / `railNav` 各套一层 `visibleNav(...)`。**不改数组本身**，这样上游往数组里加项时不会冲突。
2. `hashRouting.ts` — `normalizeHash` 遇到隐藏视图时返回主聊天的 hash。
3. `App.svelte` — 渲染分支前先判 `viewHidden`，命中则 `view.set('chat')` 并 `showToast($t('feature.not_available'))`。

需求 §5.4.3 给了两种处理：「回到主聊天」**或**「提示『本期不提供此入口』」。这里两样都做：跳转 + toast，用户才知道发生了什么，而不是莫名其妙被弹回去。

### 3.2 为什么用开关而不是删代码

- 需求 §7 明确要求代码保留。
- 上游会持续改这三个视图；删掉会让每次合并都产生「删除 vs 修改」冲突（git 最难自动解的一类）。留着则冲突为零。
- 将来要放开，改一个数组。

### 3.3 后端

需求 §5.4.3 末条：「服务端能力可保留；产品门未登录时这些聊天相关能力同样不可从窗口调用」——这条已由 P3 的白名单式产品门覆盖（`/api/channels*`、`/api/mcp*`、`/api/lightapps*` 默认被保护）。本 PR **后端零改动**。

登录后这些 API 仍可从窗口调用（只是界面没入口）。这是有意的：需求只要求隐藏入口，没要求禁用能力，而禁用会破坏上游代码路径。

### 3.4 积分模型

存 `data/product-state.json` 的 `credits`（P3 已定 schema）：

```json
"credits": { "balance": 1280, "monthUsed": 0, "monthKey": "2026-09" }
```

`monthKey` 是**本地日历月**的 `YYYY-MM`。跨月判定在每次读取时惰性执行，不用定时器：

```go
func (c *Credits) rollMonth(now time.Time) {
    key := now.Format("2006-01")
    if c.MonthKey != key {
        c.MonthKey = key
        c.MonthUsed = 0     // 消耗归 0
        // balance 不动 —— 需求 §5.4.4「积分余额不因跨月恢复」
    }
}
```

惰性而非定时：进程可能在跨月那一刻根本没运行（U 盘拔着），定时器不可靠。

### 3.5 扣减时机

需求 §5.4.4：「每条**成功交给模型**的用户消息：本月消耗 +1；积分 > 0 时再扣 1 分」，且「被敏感词拦住未发出的，不扣分、不计入消耗」。

因此扣减点必须在**敏感词检查之后、真正发出之前**：

```
用户点发送
  → P8 输入敏感词检查   ── 命中 → 不发送、不扣分、不计消耗  ✋
  → 扣减：monthUsed++；if balance > 0 { balance-- }   ← 本 PR
  → 交给模型（构造 provider 请求时做 PII 脱敏，P10，不影响计费）
```

放服务端，在 chat 请求的 handler 里、调用 agent 之前。理由：前端扣减会在刷新/多窗口时错乱，而且「成功交给模型」这个判定服务端才知道。

「成功交给模型」的定义取**请求已构造并送入 agent 循环**，不等模型返回 —— 否则网络失败时用户会觉得「没回复还扣了分」很怪，但等返回又会让流式场景的扣减时机难以确定。本期是假数据 + 假模型（P11），实际不会失败，取前者实现简单且可解释。这个取舍写进代码注释。

> PII 脱敏物理上发生在「交给模型」一步内部（agent 构造 provider 请求时，P10 §3.3 的装饰器），故排在扣减之后；它不影响计费，先后顺序无业务影响。与 P8 §3.6 的流水线一致。

### 3.6 0 分提示与提示排序

需求 §5.4.4 规定了输入框附近三条提示的固定顺序：

```
┌────────────────────────────────────┐
│ 🛡 隐私模式：发送前会处理手机号…    │ ← ① 输入框上方（P10）
├────────────────────────────────────┤
│ [ 输入框                        ]  │
├────────────────────────────────────┤
│ ⚠ 包含敏感内容，已替换敏感词…      │ ← ② 下方第一条（P8，会拦截）
│ ⓘ 积分不足                        │ ← ③ 下方第二条（本 PR，不拦截）
└────────────────────────────────────┘
```

三个 PR 各写各的会打架。**本 PR 先建立容器**：在 `Composer.svelte` 里加一个 `ComposerNotices.svelte`，接受一个有序的通知数组，顺序由数组顺序决定，P8 / P10 只往里塞条目。这样顺序规则只有一处实现。

`积分不足` 提示条件：`balance === 0`，发送前展示，**不阻止发送**。

## 6. 测试

**Go 单测**

- `ConsumeCredit`：1280 → 1279，`monthUsed` 0 → 1。
- balance 为 0：balance 保持 0，`monthUsed` 继续 +1。
- 跨月：`monthKey` 从 `2026-09` 到 `2026-10` → `monthUsed` 归 0，`balance` **不变**。
- 跨年：`2026-12` → `2027-01` 同样归 0。

**前端单测**

- `viewHidden('mcp')` true、`viewHidden('chat')` false。
- `visibleNav` 过滤后保持原顺序，且对上游新增的未知项默认放行（**不是**默认隐藏 —— 上游加了新功能应该可见，除非我们显式列入 `HIDDEN_VIEWS`）。
- `normalizeHash('#/mcp')` → chat hash。
- 通知顺序：三条同时存在时，DOM 顺序为 隐私条 → 输入框 → 敏感词 → 积分。

**手工验收**

1. 侧栏、rail、设置首页、空状态均看不到 IM / MCP / Light Apps。
2. 手输 `#/mcp` → 回到主聊天并 toast。
3. 连发几条消息，积分递减、消耗递增，个人中心与左下角同步。
4. 改 `data/product-state.json` 的 `balance` 为 0 → 重启 → 输入框下方有提示，**仍能发送**，消耗继续增加。
5. 敏感词拦住的那条：积分与消耗都不变（依赖 P8，联调时验）。

## 7. 上游合并影响

**等级：中。**

- `Sidebar.svelte` 的两个导航数组：只在**外层包一层函数调用**，不动数组内容。上游往数组加项时是纯追加，无冲突。
- `App.svelte` 渲染分支：加一个前置 if，冲突面小。
- chat handler 加一行 `ConsumeCredit`：上游若重构该 handler 会冲突，加 `// OCTO-FORK:` 注记。
- **零删除**，所以不会产生「上游改了我们删掉的文件」这类冲突。

## 9. 风险与决策

| 项 | 处理 |
|---|---|
| 隐藏后仍能通过 API 调用这些能力 | 有意为之（需求只要求隐藏入口）。写进代码注释与已知限制 |
| 扣减时机取「送入 agent」而非「模型返回成功」 | 已在 §3.5 说明取舍；本期假模型不会失败，接真实中台时（§10 T5）重新评估 |
| 多窗口/多进程同时扣减 | 本期整机单实例（需求 §5.1.2-5），不存在并发。`Store.Mutate` 仍加锁兜底 |
| 上游新增视图被误隐藏 | `visibleNav` 采用**黑名单**语义，未知项放行 |
