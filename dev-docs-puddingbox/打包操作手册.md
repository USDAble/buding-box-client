# 桌面包构建操作手册

写作参照：`dev-docs/relay-runbook.md`。本文以 `Makefile`、`scripts/package-*` 和 `internal/productprofile` 为事实源，说明如何构建可交付的测试包与生产包。

> 测试包和生产包是两种明确的编译产物，不通过安装者的环境变量、配置文件或界面在运行时切换服务地址。选择哪一种包，发生在构建时。

## 先选交付目标

| 目标 | 构建 Profile | 中台来源 | 适用情况 |
| --- | --- | --- | --- |
| 本机替身测试包 | `product_test` | 测试程序进程内启动的中台契约替身 | 测试中台尚未就绪，需要测试人员完整走通登录、目录和模型流程。 |
| 远程测试中台包 | `product_test` | 编译进包内的 HTTPS 测试中台地址 | 测试中台已部署，需要测试真实服务。 |
| 生产包 | `product_production` | 编译进包内的 HTTPS 生产中台地址 | 面向正式用户的交付。 |

开发构建不是上述任一种交付物。它允许本地开发 WebView 与环境模型来源，只用于开发人员本机调试，不能发给测试人员或用户。

## 构建前准备

- 使用项目要求的 Go 工具链，以及 Node.js 22.22.2 或更新版本；`make node-check` 是前端构建的前置检查。
- 从干净或已确认的工作区构建。打包前会运行数据路径、Profile、品牌和规范守卫；硬失败时不得通过手工跳过守卫继续出包。
- macOS 包需 Xcode Command Line Tools；Linux 包需 GTK4/WebKitGTK 6.0 开发依赖；Windows 便携包可按现有脚本交叉编译。
- 测试和生产包都需要在目标平台进行首次启动验收。编译成功不代表服务地址、签名公钥或外部运行时已经正确。

## 测试中台尚未就绪时构建测试包

仓库中的 [testing.json](运行时Profile配置.md) 默认开启 `startLocalStandin: true`，并固定到 `127.0.0.1:8788`。测试版桌面程序启动时会先启动与 `productstub` 相同的中台契约替身，再打开窗口；替身不监听局域网，也不连接构建机。

按目标平台执行：

```sh
# Windows 便携目录和 zip
make desktop-test-portable

# macOS universal .app
make desktop-test-app

# Linux AppImage
make desktop-test-appimage
```

测试产物带 `-test` 后缀，避免覆盖同目录中的生产产物。启动后使用替身横幅/夹具规定的测试输入完成登录、激活和模型回合走查；不要把替身的固定成功结果当作真实中台验收。

## 切换为远程测试中台包

测试中台部署完成后，测试包仍使用同一套 `make desktop-test-*` 命令。构建负责人只需在 `internal/productprofile/profiles/testing.json` 中完成以下变更后重新打包：

```json
{
  "startLocalStandin": false,
  "apiHost": "https://<测试中台 API>/v1",
  "gatewayHost": "https://<测试模型网关>",
  "trustedKeyIDs": {
    "<测试签名密钥 ID>": "<测试中台 Ed25519 公钥的 Base64 编码>"
  }
}
```

地址必须是 HTTPS；`apiHost` 必须带 `/v1`，网关地址不要求带 `/v1`。`trustedKeyIDs` 必须来自测试中台签名配置，不能沿用本机替身密钥或填写占位值。Profile 校验会拒绝缺少公钥、开发能力开启、HTTP 远程地址或本机替身地址不匹配的测试包。

远程测试包启动时不会启动替身。验收时应确认测试中台的请求日志确实收到登录、目录和模型网关请求，并覆盖中台返回的真实失败路径。

## 构建生产包

生产构建命令与测试构建命令分离：

```sh
# Windows 便携目录和 zip
make desktop-portable

# macOS universal .app
make desktop-app

# Linux AppImage
make desktop-appimage
```

生产命令只选择 `product_production`，既不带也不启动测试替身。构建前必须在 `internal/productprofile/profiles/production.json` 填入真实生产控制面、生产模型网关和生产签名公钥。`release-config-guard` 报告 `.invalid` 地址或空信任表时，说明该包不可交付给正式用户。

## 交付前检查的结果应当可解释

| 检查结果 | 处理方式 |
| --- | --- |
| Node 版本不足 | 先切换到项目要求的 Node 版本，再重新运行完整 `make desktop-*` 命令；不得跳过前端构建。 |
| 测试 Profile 校验失败 | 检查 `testing.json` 的模式、地址和测试签名公钥；不要让安装者自行填写服务地址。 |
| 生产 Profile 提示 `.invalid` 或无可信密钥 | 停止生产交付，等待生产中台地址与公钥。该提示不是网络问题。 |
| 测试包无法绑定 `127.0.0.1:8788` | 停止占用该端口的旧测试程序或替身后重试；测试包不会接管未知进程提供的服务。 |
| 测试包已改为远程中台却仍收到替身响应 | 检查是否重新构建并确认 `startLocalStandin` 为 `false`；Profile 在编译后不可修改。 |

## 每次交付都验证真实用户路径

1. 在没有既有产品数据的目标机器或临时目录中安装/解压并启动。
2. 确认测试包走预期的本机替身或远程测试中台；生产包只能走生产中台。
3. 完成登录、激活、目录获取和至少一个模型回合；重启后验证状态是否按设计保留。
4. 对便携目录执行移动后重启，确认业务数据仍只使用同级 `data/`。
5. 记录包版本、Git 提交、Profile 模式和被验证的中台环境，便于定位后续反馈；不要记录密钥、token 或用户数据。

## 非目标

- 本手册不提供让测试人员在本地输入任意服务地址的开关；这会绕过编译期信任边界。
- 本机替身不是生产中台的高可用、性能或安全验证工具。
- 代码签名、公证、安装器迁移和 CI 发布渠道属于独立发布决策，不因能生成测试包而自动完成。
