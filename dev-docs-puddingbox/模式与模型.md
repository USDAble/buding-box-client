# 模型列表与私密模型选择

写作参照：`dev-docs/endpoint-pr5-impl.md`

> 聊天框只保留一套上游风格的模型选择器。本地配置模型和中台目录模型投影成相同的可选行；私密属性影响排序、标识和私密会话路由，不再生成第二套“模式 → 模型”选择界面。

## 范围

本文件定义聊天模型的来源合并、身份、排序、私密标识和会话级选择行为。中台目录的签名与传输由 [中台接口契约](中台接口契约.md) 定义，私密会话的数据边界由 [个人信息保护与私密会话](个人信息保护与私密会话.md) 定义。

本文描述已确认的目标设计，同时列出当前实现差距；在代码完成前，不能把目标行为写成已经可用的产品能力。

## 非目标

- 不重新设计上游模型选择器的基本布局、交互和本地 endpoint 配置。
- 不把中台模型保存进用户的 `config.yml`，也不允许设置页编辑中台托管模型。
- 不按模型名称猜测它是否私密、本地或可信。
- 不在私密模型不可用时自动回退到公共模型。
- 不让中台目录成为第四套 provider 协议实现；网关继续复用既有 OpenAI 适配器。

## 一个选择器承载两个模型来源

上游模型选择器已经把本地配置的 endpoint 和模型展平为 `endpoint::model` 行，并处理会话绑定、默认模型、设置页变更后刷新和同名模型去歧义。中台模型应投影为同一种行结构，合并到这个选择器，而不是另建 `ModeMenu` 或“先选模式、再选模型”的树形界面。

模型有两个来源：

- 本地配置来源：用户通过上游 endpoint 设置添加的模型，事实源仍是 `config.yml`；
- 中台目录来源：登录后取得、验签并缓存的可用模型，事实源是已验证目录，不写入 `config.yml`。

两类模型使用同一复合身份 `endpoint::model`。同名模型位于不同 endpoint 时仍是不同选择；展示名称可以来自中台目录，但绑定和路由不能只依赖展示名称。

合并发生在只读的“可选择模型”投影中，不改变本地 endpoint 的增删改契约。设置页继续只管理用户模型；聊天框消费合并后的列表。这样既保留上游模型管理方式，也不会让托管模型伪装成可编辑配置。

## 排序只提升私密模型，不打乱其余顺序

中台目录明确标记为私密可用的模型排在列表最前面；其余模型保持各自来源的稳定顺序，避免每次刷新都重新排列用户熟悉的列表。排序不能代替标识：私密模型行在模型名前显示盾牌或“私密”标签，当前模型 chip 也显示同一标识。

首版的私密资格只接受已验证中台目录的声明；用户本地添加的模型继续参与普通列表，但在本地模型验证机制另行确定前不能仅凭 endpoint 名称获得私密资格。目录需要提供机器可读的私密资格和首选次序。字段名称与具体枚举尚需和中台确定，但客户端至少要能回答：

- 该模型能否用于私密会话；
- 多个私密模型中哪个是自动切换的首选；
- 该属性来自哪份已验证目录，而不是本地字符串推断。

## 私密会话自动选择合格模型

开启私密会话时：

1. 当前模型已经具备私密资格时保持不变；
2. 否则切换到中台目录指定的首选私密模型；
3. 明确提示“已切换到私密模型：<模型名>”，并说明不会自动使用公共模型；
4. 没有合格模型时不进入可发送状态，不能保持私密标识却继续使用原公共模型。

自动切换写入当前会话，不修改其他会话，也不把中台模型改成本地默认 endpoint。用户主动选择非私密模型时，是确认退出私密会话还是在该状态下禁止选择，仍需产品确认；无论选择哪一种，都不能静默退出私密保护。

还需要区分新会话和已有历史的会话：普通会话已经调用过公共模型后，再打开私密标识不能撤回已经外发的历史；私密会话若中途改用公共模型，下一次完整上下文可能把此前机密内容一并发送。建议把私密属性在首条消息后锁定：已有普通会话只能新建私密会话，已有私密会话只能选择私密模型。该交互在产品确认前不写成已实现行为。

## 目录失败不删除本地模型

中台目录缺失、过期或验签失败时，中台模型不能继续作为可信条目展示或用于新回合；本地配置模型仍按上游行为存在于列表中。是否允许普通会话继续使用本地模型由运行 Profile 决定，不能由前端列表自行推断。

私密会话的失败策略更严格：目录无法证明模型的私密资格时，私密会话停止发送。已有对话仍可阅读，恢复可信目录后再继续。

## 当前实现为什么显得复杂

当前聊天框实际仍使用上游 `Composer.svelte` 中基于 `/api/config/endpoints` 的模型选择器。与此同时，fork 又增加了：

- `ModeMenu.svelte` 的两级模式菜单；
- `chatMode.ts` 的三组模式状态和切换逻辑；
- `internal/chatmode` 的 `privacy`、`smart`、`default` 固定集合；
- `/api/product/chat-modes` 的目录分组投影。

`ModeMenu` 当前没有挂到实际聊天框，导致真实选择器看不到中台目录模型，而模式投影又维护了一套独立数据形状。后续实现应保留上游选择器及会话模型绑定，把中台目录投影接入统一可选列表；确认没有其他消费方后，再删除悬空的分组 UI 和重复状态。删除范围必须通过引用搜索、前端测试和会话兼容测试确认，不能只因组件当前未挂载就直接移除后端字段。

## 验证

- 本地配置模型和中台模型出现在同一个选择器，交互和视觉结构一致；设置页只管理本地模型。
- 私密模型稳定排在前面并具有明确标签；同名不同 endpoint 的模型仍能正确高亮和路由。
- 开启私密会话会保持或自动选择合格模型，并给出可见提示；没有合格模型时不发送。
- 中台目录异常不会删除、覆盖或写回用户本地模型，也不会让私密会话使用无法证明的模型。
- 普通模型选择、默认模型、会话绑定、设置页刷新和上游移动端入口保持既有行为。
