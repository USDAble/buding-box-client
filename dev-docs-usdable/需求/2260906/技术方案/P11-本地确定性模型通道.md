## 0. 定位（2026-09-07 评审调整）

初稿把本地确定性模型当成验收主路径。评审调整为：

| | 用什么 |
|---|---|
| **功能验收、日常开发** | **真模型**。配一个真实 endpoint（DeepSeek / DashScope 等已支持的 OpenAI 协议后端），走完整链路 |
| **开发验证、离线环境、自动化测试** | 本 PR 的本地确定性 provider |

也就是说这个 provider **保留但降级**：它不再是「不做就验收不了」的阻塞项，而是开发验证包和测试的便利设施。

为什么仍然要做：

- **开发验证场景**没有网络或不方便配 key 时得能跑（需求 §9.10 明说本期是开发验证包）。
- **自动化测试**需要一个确定性的模型输出。P8 的「跨 chunk 命中」、P11 的「回复必含敏感词」这类断言，用真模型没法稳定复现。
- 需求 §5.6.3 末段把本地确定性通道定位为「用于开发验证、离线环境与确定性自动化测试」「**不替代**真模型验收」—— 与本表定位一致。

排期上因此可以往后放 —— 不再需要「P9 一合入就立刻跟上」。

## 1. 目标与非目标

**目标**

1. 一个本地确定性 provider，在没有真实 endpoint 时也能让选择器、模式切换、敏感词、PII 全链路跑通。
2. 本地确定性回复正文**必须能被输出敏感词过滤命中**（需求 §5.6.3 末句，便于开发验证打码效果）。
3. 走真实的流式路径，让 P8 的 `StreamFilter` 与 P10 的装饰器都被真正执行。
4. 记录实际发给「模型」的请求，作为 PII 的观测手段。

**非目标**

- **不替代真模型验收**。功能验收用真 endpoint 走一遍，见 §0。
- 不做智能回复 —— 是固定模板，不是本地小模型。
- 不改上游 provider 接口。

## 2. 现状（代码事实）

- `internal/provider/provider.go` 定义接口栈：`Provider` / `StreamingProvider` / `ToolProvider` / `ToolStreamingProvider`。

## 3. 设计

### 3.1 作为一个正常的 provider 实现

按 `.octorules`「新 provider」的既定路径做：`internal/provider/local/`，实现 `ToolStreamingProvider`（最高能力层，这样类型断言选中它，走的是与真实 provider 完全相同的代码路径）。

**为什么要实现到最高层**：如果只实现 `Provider`，agent 会走非流式分支，P8 的流式过滤器就永远不被执行，等于验收时测的是一条生产环境不会走的路径。

### 3.2 预置 endpoint

首次启动时，若 `config.yml` 里没有 `buding` endpoint，写入一份：

```yaml
endpoints:
  - id: buding
    provider: local          # 新的 provider 类型
    baseUrl: ""              # 本地，不需要
    apiKey: ""               # 不需要 —— 这也是「不弹配 Key 向导」的前提
    models:
      - id: buding-local-general
      - id: buding-local-fast
      - id: buding-cloud-plus
      - id: buding-cloud-pro
```

- 模型展示名**不写在配置里**，走 `i18n.ts` 的 `model.buding-local-general` 等键（需求 §5.6.3「展示名随语言；id 固定」）。
- `apiKey` 为空是有意的：需求 §5.1.2-3 要求任何情况都不出现配 Key 向导，而这个 endpoint 天然不需要 key。P9 已在前端彻底关掉向导，这里是配置侧的呼应。

### 3.3 本地确定性回复内容

需求：「本地确定性回复正文须能被输出敏感词过滤命中（便于验收打码）」。

设计一组模板，按输入内容选择，**保证其中至少一条命中内置词表**：

| 触发 | 回复 |
|---|---|
| 输入含「发票」「invoice」等 | 一段包含 `发票` 与 `gambling` 的说明文本 → 上屏后应显示 `***` |
| 输入含手机号 | 回显「我看到你提供的号码是 …」→ 用于肉眼确认 PII 是否生效 |
| 其它 | 通用模板，末尾固定附一句含敏感词的句子 |

关键：**通用模板也要含敏感词**，否则验收人员随便发一句「你好」看不到打码效果，会误判功能没做。这句附加文本用一个显眼的固定句式，比如「（开发验证：本条包含示例敏感词 发票 / invoice，用于验证输出过滤。）」

回复按模式略有差异（隐私模式回复里提一句「当前为隐私模式」），让验收能直观看出模式确实传下去了。

### 3.4 流式行为

按 **rune** 切分，每 20–40ms 吐一小段，模拟真实流式。切分点要**有意落在敏感词中间** —— 比如把「发票」拆成两个 chunk 分别发出。这是 P8 `StreamFilter` 跨 chunk 命中的唯一真实测试场景，用固定的真实 provider 测不到。

切分带一点确定性的伪随机（种子固定），保证可复现。

### 3.5 请求日志（PII 验收手段）

把每次收到的**完整请求**（system + messages）写进 `data/logs/local-provider.jsonl`：

```json
{"at":"2026-09-07T10:00:00+08:00","model":"buding-local-general","messages":[{"role":"user","content":"我的电话 138****1234"}]}
```

这是 P10 验收「实际请求里是中间四位 `****`」的**可选可视化辅助**——P10 的权威断言在装饰器单测里（见 P10 §6），**不依赖本 PR 的这份日志**。

**这份日志只在本地确定性 provider 里存在**，接真实中台时随本 PR 一起下线 —— 在文件头注释里写明这一点，避免它被当成通用能力保留下来。

## 4. 接口与数据结构

```go
// internal/provider/local/local.go
package local

// Client 是本期开发验证用的本地确定性模型通道。它实现到 ToolStreamingProvider，
// 让 agent 走与真实 provider 完全相同的流式路径 —— 否则输出过滤与 PII
// 装饰器在验收时根本不会被执行。
type Client struct {
    logPath string
}

func New(logPath string) *Client

func (c *Client) Send(ctx context.Context, req provider.Request) (provider.Response, error)
func (c *Client) SendStream(ctx context.Context, req provider.Request, fn provider.StreamFunc) error
// ToolProvider / ToolStreamingProvider 的方法同样实现 —— 工具调用返回「本期不支持工具」的文本，
// 不真的发起工具调用（本地确定性模型没有工具能力，但接口要齐）。
```

（具体签名以 `internal/provider/provider.go` 的实际定义为准，实现时对齐。）

## 6. 测试

**Go 单测**

- 实现了 `ToolStreamingProvider`（类型断言）。
- 通用回复模板**必定含内置敏感词**（断言 `sensitive.New("").Filter(reply).Matched()` 为 true）—— 把「验收能看到打码」这件事固化成测试。
- 流式切分确实把某个敏感词拆到两个 chunk（断言至少存在一次跨 chunk 命中）。
- 请求日志写入格式正确，且路径在数据根内（配合 P1 的 guard）。
- 无 API key 也能正常工作。

**联调（本地确定性 provider 上跑，确定性高）**

- 与 P8：发一条触发敏感词的消息 → 上屏最终态与 `data/sessions/*.jsonl` 里都是 `***`。
- 与 P10：隐私模式发手机号 → `local-provider.jsonl` 里是 `138****1234`，会话历史里是原文。
- 与 P6：发一条 → 积分 -1。

**真模型回归（验收主路径，见 §0）**

同样三条，换成配好的真实 endpoint 再走一遍。本地确定性 provider 通过而真模型不通过，通常意味着装饰器只在某条能力路径上生效 —— 这正是 P8 §7 提到的「Sender 静默降级」，必须查清。

## 7. 上游合并影响

**等级：低。** 新增 provider 子包，走的是上游明确支持的扩展路径（`.octorules`「新 provider」）。唯一碰上游的是 `internal/app` 里 provider 类型的分发，加一个 case。

风险：上游若改 `provider` 接口定义，本包需跟着改 —— 但真实 provider 也一样要改，不是本 fork 特有的负担。

### 7.1 production 构建排除（2026-09-11）

**本包整体不进入 production 二进制。** 它不是"配了才生效的可选功能"，而是**编译期就不存在**：确定性回复引擎、含敏感词的演示文案、`data/logs/local-provider.jsonl` 的 PII 写入器都排在 `product_production` 之外。

| 文件 | 构建约束 |
|---|---|
| `local.go`（engine）、`reply.go`、`stream.go` | `//go:build !product_production` |
| `local_test.go` | `//go:build !product_production`（引擎不存在则其单测也不存在） |
| `local_production.go`（**新增**） | `//go:build product_production`；同样的 `Name` / `Client` / `New`，`Send`/`SendStream` 恒返回硬错误、不吐任何 token |

**为什么保留导出面而不是让 `internal/app/sender.go` 也带标签**：`sender.go` 是上游文件，它已有的 OCTO-FORK hunk 需要分发 `provider: local`。若在那里加构建标签，就要给上游文件引入两个变体，冲突面变大。改成 `buildClient` 只调用 `newLocalProvider()`（见下），标签收在两个 fork 自有文件里，**上游文件反而少了一行 hunk 和两个 import**：

| 文件 | 构建约束 | 职责 |
|---|---|---|
| `internal/app/localsender.go` | `//go:build !product_production` | 解析 `data/logs/local-provider.jsonl`（`datapath` 只在这里出现）并构造真 engine |
| `internal/app/localsender_production.go` | `//go:build product_production` | 返回桩；**刻意不引 `datapath`** —— PII 日志的路径不应出现在交付物里 |

净效果：`sender.go` 的 hunk 从 11 行缩到 3 行，且不再 import `datapath` 与 `provider/local`。

**两层防回潮**：

1. `make test-production` 与 `.github/workflows/go.yml` 的 `-tags product_production` 步骤（build + vet + test）。被 tag 排除的代码在默认构建里不参与编译，**不测就会烂**；`internal/app/local_sender_production_test.go` 的 `TestProductionLocal*` 三条断言只在生产模式跑。
2. `scripts/package-portable.mjs` 的 `checkProductionBinary()` 对**已构建的 exe** 断言 `本地演示模型的固定回复` 与 `local-provider.jsonl` 不存在，命中即拒绝出包。

> 这两层与 `release-profile-guard` 的分工：那个守卫看**源码**、证明标签被写进构建命令；`checkProductionBinary` 看**产物**、证明标签到达了编译器并改变了输出。`-tags` 被 `GOFLAGS` 遮蔽、或 `reply.go` 掉了标签，都只能被后者抓到。

**实测（真实二进制，非推断）**：删除标签前的 dev 二进制含演示文案与 `local-provider.jsonl`；`product_production` 二进制两者皆无。

**这不替代 P0-05**：P0-05 仍须拒绝为 production session 选中本地模型。差别是这里的失效是**结构化**的（生产二进制物理上发不出假回复），而选择判断是运行期条件、将来重构可能丢掉。

## 9. 风险与决策

| 项 | 处理 |
|---|---|
| 本地确定性回复被误认为产品缺陷 | 回复里带「（开发验证）」字样，帮助页写明本期是开发验证包（需求 §9.10） |
| 请求日志泄露用户输入 | 日志在用户自己的数据根内，与会话历史同级别。文件头注释写明「接真实中台时删除」 |
| **本地确定性 provider 掩盖真实集成问题** | 这正是 §0 调整定位的原因：功能验收一律用真模型走一遍，本地确定性 provider 只用于开发验证与确定性测试 |
| 开发验证时误连了真 endpoint 产生费用 | 便携包出厂 `config.yml` 只预置 `buding` 这个本地 endpoint，不含任何真实 key |
| 工具调用路径未被验证 | 本地确定性模型不发起工具调用，工具链路本期不在验收范围。上游能力保留，不受影响 |
