# 配置治理

写作参照：`dev-docs/endpoint-custom-headers-design.md`。本文以 `branding/brand.json`、`internal/productprofile` 与当前桌面组装为事实源，规定各类配置的所有者、信任边界和发布检查。

> 配置不是一个大 JSON 文件。公开品牌信息、编译期信任边界、用户数据、服务端动态事实与秘密必须由不同所有者管理；任何消费者不得从另一个域补造同一事实。

## 范围与非目标

本文覆盖品牌链接、开发/Sandbox 与生产 Profile、发布/更新配置以及用户运行时数据的边界。Profile 的字段语义、构建选择和验证细节仍由 [运行时 Profile 配置](运行时Profile配置.md) 完整定义；品牌资产和生成流程仍由 [品牌与标识](品牌与标识.md) 定义。

本文不定义中台运维配置、数据库、密钥轮换日程或用户偏好字段；它们分别属于服务端、密钥系统和产品状态所有者。

## 每类事实只有一个所有者

| 配置域 | 事实源 | 可以放什么 | 明确不能放什么 |
| --- | --- | --- | --- |
| 品牌与公开链接 | `branding/brand.json` | 名称、标识、官网、帮助中心、版本说明页 | API host、更新 manifest、签名 key、token、环境开关 |
| 构建 Profile | `internal/productprofile/profiles/*.json` | 可信公钥、开发能力开关；地址统一来自 `internal/productprofile/endpoints.json` | 用户偏好、账号、服务端动态目录、秘密 |
| 发布信任 | Profile 或由其可信 key 验证的发布清单 | 渠道、manifest 地址、版本/包签名 | 品牌文案、用户选择、未签名任意 URL |
| 用户设备状态 | `internal/datapath` 所属数据根与凭证存储 | 登录态、刷新凭证、偏好、缓存 | 编译期 host、品牌、开发 Mock |
| 中台动态事实 | 中台受保护接口及已验证目录 | 帐号授权、模型目录、词库、盒子能力、余额 | 浏览器 bearer、客户端私钥 |
| 秘密 | 运行环境或专用凭证系统 | 私钥、provider key、平台 token | 任意仓库 JSON、Web 配置或日志 |

## Profile 是发布信任边界

当前只保留两个嵌入 Profile：默认 `developer` 同时承担本地开发和 Sandbox 联调；`product_production` 选择 `production`。不新增运行时可选的“测试 host”或第三个 Profile，因为用户输入、环境变量和数据根都不能改变生产控制面。

`allowDevWebview`、`allowEnvironmentModelSource` 是已经有运行时消费者的开发能力；`allowDataRootOverride` 当前仅是 schema 字段、没有控制运行时路径，不能据此宣称覆盖已受生产保护。任何要把它变为实际开关的变更都必须先说明数据迁移、产品模式行为与验证。

## 链接与更新不能混淆

官网 `website`、帮助 `helpCenter` 和版本说明 `releaseNotes` 是给用户打开的公开 HTTPS 页面，放在品牌配置。缺失的可选链接应让 UI 隐藏对应动作；绝不以 `octo-agent.dev`、`.invalid` 或猜测域名作为回退。

“检查更新”所请求的版本服务、发布渠道和包签名决定代码信任谁，不是品牌信息。它必须由 Profile 或签名发布清单拥有，且继续遵守用户主动查询、查询不下载不安装的规则。品牌页只能提供发布说明链接，不能改变更新服务地址。

## 修改与验证

1. 先确定变更属于上表哪一域；跨域需求先拆出每个事实的唯一所有者。
2. 改品牌源后运行 `make brand-sync` 和 `make brand-check`，提交所有生成副本；不手改生成配置。
3. 改 Profile 后运行它规定的默认/生产 tag 测试、`make release-profile-check release-config-check`；真实 host 和公钥须由受权发布者提供。
4. 改本地或中台契约时同步更新对应契约、替身和测试；开发 Mock 只留在 `productstub`，不进入生产降级。
5. 涉及 URL、密钥、发布或数据路径时运行相关守卫并完成目标环境手工验证。
