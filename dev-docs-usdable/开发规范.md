| 文档状态 | 草案，供评审 |

本文档只写**本项目额外的**约束。`.octorules` 已有的（gofmt、分层、测试就近、英文注释、无新依赖、一个 PR 一个概念）继续有效，不重复。

> 有约束冲突或"这条约束挡路"的争议，先看 **§3.4 裁决原则**（A 正常开发本该如此 / B 无其他方案），不要各自凭感觉决定。

## 1. 为什么要额外一份

这个项目有三个别的项目没有的性质，每一个都能在没有约束时安静地毁掉一整轮验收：

1. **它是 fork。** 随手改上游文件，代价在三个月后的合并里才显现。
2. **它是便携产品。** 「不写主机」是硬验收项，而任何一次 `os.UserHomeDir()` 都能破坏它，且破坏后在开发机上完全看不出来（开发机本来就有 `~/.octo`）。
3. **它是白牌产品。** 任何一句写死的 "Octo" 都是可见缺陷，而上游代码里到处都是。

下面的规则基本都是在防这三件事。

## 2. 分支与提交

### 2.1 分支

```
main                      上游跟踪分支：只接受 `chore(upstream): merge upstream/main`，与 upstream/main 保持一致
v1                        产品集成分支（受保护）：所有功能 / 修复 / 文档 PR 的合并目标，squash merge
├── feat/<pr编号>-<简述>   功能，如 feat/p1-portable-data-root
├── fix/<简述>            修复
└── docs/<简述>           纯文档
```

- 从**最新 `v1`** 切分支，不从别人的功能分支切。`main` 是上游跟踪分支，**功能 / 修复 / 文档 PR 一律合入 `v1`，不直接合 `main`**。
- **一个 feature / 特性 = 一个 PR = 一个 commit（squash）**。一个 PR 对应技术方案里的一个 P 编号：方案说这是一个 PR，就不要拆成三个，也不要合并两个；反之，也不要一个 PR 里夹带多个无关特性。
- 分支存活不超过 5 个工作日。超了说明 PR 太大，拆。

**三条操作纪律（2026-09-11，人工明确要求，AI 助手同样适用）：**

1. **每次要改东西都新建分支。** 不论改动多小（一行文案、一个链接），都不以「改动很小」为理由直接改 `main` / `v1`。改完走 PR 合回 `v1`（squash）。
2. **合并动作必须经人确认后才执行。** AI 助手**不得自行**把任何分支合进 `v1` —— 它可以切分支、改内容、推分支、开 PR，但**合并那一步要人等一句"合"**。理由：合并是不可逆的集成决定，而"顺手合了"最容易把没审阅的内容带进主干。
3. **只合并「本地新建的特定分支」，绝不合并远程分支。** `origin/*` 上他人的分支（如 `origin/qingfeng`、`origin/dev-zxy`）是**并行实现**，不是合并来源 —— 它们与 `v1` 无共同祖先假设，整体 merge 会带进一整套冲突的技术选型（§3.5 复用优先要求的是**按能力拣选**，不是把别人的分支搬过来）。确需复用其中的代码时，**逐文件搬运并在 PR 里写明理由**（<人确认>），而不是 `git merge`。

**删除分支前先归档（2026-09-11 补）。** 删除远程分支**不可逆**：ref 消失后其独有提交成为悬挂对象，`gc` 之后无法恢复。因此删除前必须先打 tag 并推送：

```bash
git tag -a archive/<branch>-<YYYYMMDD> <branch> -m "archive: <why>"
git push origin archive/<branch>-<YYYYMMDD>
# 确认 tag 已在远端后，再删分支
```

> **产品集成分支变更（2026-09-11，人工决定）。** 全部产品代码与文档的合并目标由 `buding` 改为 **`v1`**：`v1` 从当时最新的 `base` 切出并推送，`base` 只作为它的切出基线，**同样不是 PR 目标**。**`buding` 停止接收 PR，保留只读以追溯历史**（它上面的 `需求/20260909/` 批次不会进入 `v1`，见 `需求/20260911/` 的说明）。
>
> **已登记的例外（2026-09-11，保留为历史记录，已被上面的变更加取代）。** P0-01 B0 + B1 的 8 个 commit 直接落在了本地 `buding` 上（`4e1e524d`…`1b0b20a1`），未推。原因是当时把这里当成"先落地、后补分支"的临时工作区，而 `norms-guard` 只断言 AI 工具入口文件存在且指向本文件，**不检查分支纪律** —— 所以没有任何自动化会发现。决定是**照常推送到 `buding`**（推之前已确认这批提交内部一致、未推、且工作区里另一位开发者的改动不受影响），不回溯改历史。
>
> 例外只此一次，规则本身不变：**后续任何改动仍从最新 `v1` 切 `feat/`・`fix/`・`docs/` 分支，走 PR。** 若再次出现直接落在 `main`/`v1` 上的提交，应视为流程失效而不是默认可行。补一个"HEAD 在 `main`/`v1` 且有未推送提交即失败"的检查是可以做的，但它必须由人确认后单独提 PR —— 不要顺手加进 `preflight`，出包不该因为分支名而失败。

### 2.2 提交信息

沿用 Conventional Commits，**英文**（`.octorules` 已定）：

```
<type>(<scope>): <祈使句，小写开头，不加句号>

<为什么这么做。不是「做了什么」——diff 已经写了。>

Refs: dev-docs-usdable/需求/2260906/技术方案/P1-便携数据根.md
```

`type`：`feat` / `fix` / `refactor` / `chore` / `docs` / `test` / `ci`。
`scope`：包名或模块，如 `datapath`、`productgate`、`desktop`、`web`。

**机械改动单独成 commit**，且在信息里写明「纯机械，无逻辑改动」。这不是形式主义 —— 合并冲突时，reviewer 靠这句话决定是逐行看还是整块重做（上游合并策略 §3.4）。

## 3. 本项目专有的硬规则与设计与裁决原则

违反下面 §3.1–§3.3 三条的 PR 不予合并，CI 也会直接拦。

§3.4–§3.11 是**设计与裁决原则**，适用于每一次写方案、评审和决定"能不能破例"。它们的共同目标只有一个：**让二次开发项目在持续合并上游的前提下不腐化**。其中：

- §3.4 是总原则 —— 当本文件、方案、需求或既有约束冲突时怎么裁决；
- §3.5 复用优先、§3.6 上游规范优先 —— 拦"另起一套"和"随手覆盖上游"；
- §3.7 人工确认清单 —— 列出机器测不出、但必须停下来问的情形；
- §3.8 单一入口与单一真相来源 —— 同一件事只能定义一次；
- §3.9 降级必须有界 —— 兜底路径必须可解释；
- §3.10 每条约束写明作用域 —— 防止"为保护 production 把开发能力也砍了"；
- §3.11 架构与可维护性优先 —— 当"能跑"与"结构正确"冲突时的排序。

### 3.0 架构与可维护性优先（本节的排序依据）

上面 §3.1–§3.11 全部是这一条的具体化。之所以单独写出来，是因为**二次开发项目最常见的失败不是写不出功能，而是每次都被"先让它跑起来"说服，最后结构不可维护、上游再也合不进来**。

**排序（从左到右，不可颠倒）**：

```text
架构与可维护性  >  可读性与一致性  >  功能范围  >  交付速度
```

含义是：**当上位与下位冲突时，永远牺牲下位**。具体到日常判断：

| 常见权衡 | 本项目的规定动作 |
|---|---|
| "先写个临时实现让功能跑起来，以后重构" | **不允许**。"以后"在二次开发里不会来 —— 上游还在动，临时实现会先变成合并冲突，再变成没人敢删的遗留。要么现在按结构做，要么现在就砍掉这个功能范围 |
| "这样写更少代码/更快" | 少代码不是目标。**代码少但结构错，是负收益**：它的成本在每次上游合并时复利 |
| "功能能跑就行，先上线" | 先砍范围，不降结构。范围是产品决策（可改），结构是工程约束（改一次要赔一次合并） |
| "上游就是这么写的，所以我照抄" | 上游写法是**事实依据**不是**正当性依据**。照抄上游前先按 §3.5/§3.6 判断它是否适用于本 fork 的约束 |
| "多加一层抽象会更灵活" | 反向同样成立：**无必要的抽象也是结构错**。抽象必须回答"它隔离了什么会变化的东西"，答不出就内联 |
| "评审时先放过，回头一起改" | 结构问题**必须在 PR 内解决**。它不像 bug 有复现路径，一旦合并就只会在上游合并时以冲突的形式浮现，成本翻倍 |

**判据（可直接用于 PR 描述与评审打回）**：说出这个改动**在半年后上游合并时**的代价。

- 如果答案是"不用改，它在 fork 自己的包里" → 通过。
- 如果是"要在每次合并时手动解冲突" → 按 §3.7 人工确认，并优先改成前者。
- 如果是"上游改了这个文件，我们会静默丢掉他们的修复" → **打回**。

**这条不是"追求完美"**：它允许为了不破坏结构而**缩小功能范围、推迟功能、甚至砍掉功能**，但不允许为了功能而破坏结构。范围可以下个版本再要，结构债没有偿还窗口。

**与 §3.4 的关系**：§3.4 管"冲突时怎么裁决"，§3.0 管"排序本身"。§3.4 的两个判定条件（A：正常开发会不会这么做；B：是不是没有别的路径）本质上就是本条在具体场景下的展开 —— 先问结构上正确的做法是什么，再问为什么做不到。

### 3.1 不许自己解析数据路径

```go
// ❌ 禁止
home, _ := os.UserHomeDir()
p := filepath.Join(home, ".octo", "sessions")

// ✅
p, err := datapath.Sub("sessions")
```

`datapath-guard` 扫 `internal/` `cmd/` `shared/`，两类命中分开处理：

| 命中 | 处理 |
|---|---|
| 字面量 `".octo"` | **零例外，直接失败**。产品里已经没有这条路径了（CLI 也一样），任何一处出现都是回潮 |
| `os.UserHomeDir()` | 失败，除非在 `scripts/homedir-allowlist.txt` 里。例外只给「真的要访问主机 home」的场景（展开用户输入的 `~/`、定位主机 Chrome 配置、sandbox 规则），**每条必须写理由**且要过一次 review |

理由：见 §1 第 2 点。这是本期唯一一条「在开发机上完全测不出来」的硬验收项 —— 开发机本来就有 `~/.octo`，写进去看不出任何异常。

顺带一提：`OCTO_DATA_ROOT` 是**显式指定**不是降级位置。测试、开发调试、CLI 装在只读目录这三种场景用它，别的地方不要碰。

### 3.2 不许写死品牌字面量

```svelte
<!-- ❌ -->
<h1>布丁盒子</h1>
<h1>Pudding Box</h1>

<!-- ✅ -->
<h1>{$t('product.name')}</h1>       <!-- 文案表里是 "{brand}" -->
```

所有品牌文字走 `{brand}` / `{brandShort}` 插值，取值只从 `branding/brand.json` 来（需求 §2.5「产品名已定」；品牌取值细则见 §5.2）。`brand-guard` 已在 CI 上。

两个**例外**要显式标注，否则会被 guard 误判：

| 例外 | 处理 |
|---|---|
| 端口占用提示里的 "Octo"（指上游那个产品，不是我们的品牌） | 该行加 `// upstream product name, not our brand` |
| ASCII 标识符 `BUDING-DEMO-0001`、模型 id `buding-*` | 常量旁注释说明它属于需求 §5.2.4「标识符例外」，**不随品牌名改** |

第二条尤其重要：已经有人想把它们改成 `PUDDING-*`。注释是唯一的防线。

**不得对 ASCII 标识符与数据键做本地化替换。** `BUDING-DEMO-0001`、`buding-*` 这类值会出现在**代码、协议字段、测试断言和配置文件**里；把它们翻译成中文短语（例如写成"固定本地激活码"）会让文档与代码分叉，而且从此无法用文本搜索定位常量 —— 2026-09-11 的批量替换就在本文件制造过 `ASCII 标识符 `固定本地激活码`` 这种自相矛盾的句子，并在 `P4-拦截页.md` 把一个「首尾空格通过 / 中间空格失败」的断言替换成了两个相同字符串、断言失去意义。**文档中引用这类值时一律写原字面量。**同理，`mock` / `stub` / `fixture` 等工作术语不要在一个批次里被机械替换成同义词 —— 术语一旦分叉，文档与代码注释（如 `product_login.go` 的 `fake verification code`）就再也对不上。

### 3.3 改上游文件要打标记

```go
// OCTO-FORK: 输出必须先过合规过滤再落盘（需求 §5.5.2）
// see dev-docs-usdable/需求/2260906/技术方案/P8-敏感词接入.md
sender = WrapSensitive(sender, engine)
```

`grep -rn "OCTO-FORK" .` 就是本 fork 相对上游的完整改动清单。合并时靠它区分「这是上游的」和「这是我们的」。

判断「是不是上游文件」：`git log --follow <file> | tail -1` 看首次提交是不是在 merge-base 之前。不确定就打标记，多打不扣分。

### 3.4 裁决原则：什么情况下可以突破既有约束

当一条既有约束（`internal/server` 零改、不删上游代码、不改上游公开签名、不加依赖、"保留既有功能"…）挡住需求实现时，用下面两个条件裁决。

#### 两个判定条件

| 条件 | 含义 | 如何自证 |
|---|---|---|
| **A 正常开发本该如此** | 不破例就会得到一个**反常**的设计：命名误导、层次颠倒、为绕开约束而多出一层无意义抽象、把该在一个地方的东西拆到两处。判断标准是「如果没有这条约束，任何一个合格工程师都会这么写」 | 能指出"照现状写会变丑/变怪"的**具体位置**，而不是"我觉得更好" |
| **B 无其他方案** | 已穷举替代方案（包括：换挂点、换装配层、改成让它到不了、用已有端口、放弃该功能），**没有一条能在满足需求的同时不破例** | 列出试过/排除的方案及排除理由，写进 PR 描述 |

#### 裁决矩阵

| A | B | 结论 | 处理 |
|---|---|---|---|
| ✓ | ✓ | **允许破例** | 按最符合 A 的方式实现，并走下面的登记流程 |
| ✗ | ✓ | **允许破例** | 同上 —— B 单独成立就够。此时不追求优雅，只求最小、可逆、可收敛 |
| ✓ | ✗ | **不允许破例** | 这是「这样写更好」，按 §5.3 属**建议**而非阻塞。按现状实现，把"更好的写法"记入 `未解决问题登记.md` |
| ✗ | ✗ | **不允许** | 直接拒绝 |

**只有 A 不算理由。** 这条最容易被滥用：绝大多数"改上游签名更干净"都只满足 A，而 §5.3 已经把"A 类改进"定性为非阻塞建议。反过来说，**只要 B 成立，就不必再为 A 犹豫** —— 需求实现优先于代码洁癖。

#### 破例时的强制动作

任一条不满足即视为未完成：

1. **最小化**：只做达成 B 所必需的那部分，不顺手重构。机械改动单独成 commit（§2.2）。
2. **标记**：上游文件加 `OCTO-FORK: <原因> — see <设计文档>`（§3.3）。
3. **可收敛**：写清"什么条件下可以撤回这个破例"（如上游支持了某能力、产品形态确定后）。
4. **登记与评审**：记入对应批次的 `开发计划.md` 决策表，并说明 A/B 各自为何成立；改动上游核心文件还需 P0-00 逐项批准。
5. **回归**：证明被破例的那条约束**其余部分仍然有效**（例：改了上游一个公开签名，就必须证明其余公开签名未动、且上游回归测试全绿）。

#### PR 里必须回答（模板）

```text
约束：<被突破的哪一条，引用章节号>
A（本该如此）：<照现状写会在哪里变反常>
B（无替代方案）：<排除的替代方案 + 各自的排除理由>
最小化：<本次只改了哪些行；哪些"顺带能改的"故意没改>
收敛条件：<什么时候能撤回这次破例>
其余约束仍有效：<如何证明>
```

前两行是硬要求：**填不出 B 就不该有这次破例**。

### 3.5 复用优先：新建一件事之前必须先举证"没有现成的"

**这是本 fork 最容易犯、代价最大的一类错误。** 二次开发项目里，"再写一个"永远比"先找到那个"便宜 —— 直到半年后两条实现开始分叉，行为不一致，而没人记得哪条是权威。

改任何方案、写任何新包/新接口/新 client 之前，必须先做一次**能力检索**并把结论写进方案：

| 要建的东西 | 必须先查 | 典型结论 |
|---|---|---|
| 模型/LLM 协议客户端（含 SSE、tool call、usage） | `internal/provider/*`、`internal/app/sender.go` | 已有 4 个 sender 接口 + 两个 wire 协议；新协议才需要新包 |
| 自定义 endpoint / 网关接入 | `app.ProviderCustom`、`config.Endpoint.Headers`、`Endpoint.RPM` | 已支持任意 BaseURL + 任意请求头 + 限流 |
| 某个能力是否已实现 | 全仓 grep + `CLAUDE.md` 架构章节 | 常见结论：已实现，只是没接上 |
| 新的数据路径 / 配置读写 | `internal/datapath`、`internal/config` | 数据路径必须走 `datapath`；配置有既有 schema |
| 新的权限/确认判断 | `internal/permission`、`internal/app/gate` | 已有 permission 引擎与 gate 装配点 |
| 新的品牌文案 | `branding/brand.json` + i18n 表 | 插值，不写字面量 |

**举证责任在"新建"一方。** 方案里写"新建 `XxxClient`"时，必须同时写出：

```text
既有能力检索：<查了哪些包/文件>
为什么不能复用：<具体到函数/字段；不是"不太适合">
复用后的形态：<在既有能力上加什么，而不是另起一套>
```

**只有"能复用却选择不复用"，无论理由多合理（性能、解耦、可读性），都属于 §3.7 的人工确认事项。** 因为这类决定的影响是复利的：它会同时把修复、安全补丁、协议变更的成本乘二。

**判据**：如果既有实现能满足需求的 **80%**，答案几乎总是"复用 + 补那 20%"。剩下的 20% 写在方案的"改动清单"里，而不是新建一个包然后重新实现那 80%。

**机制化（CI 层，已落地 2026-09-11）**：`scripts/reuse-guard.mjs` 对已识别的高风险重复实现位置做符号断言 —— `internal/productclient/gateway` 不得出现 `net/http`、`bufio`、`text/event-stream`、`[DONE]`、`json.NewDecoder`、wire-format token 字段（`prompt_tokens`/`completion_tokens`）或重试策略；`make reuse-check` + CI `reuse-guard` job。注意它刻意**不**禁止读取 `agent.Usage{InputTokens, CacheReadTokens}` —— 那是 agent 侧类型，observer 读它是正当的；被禁的是无线协议字段名。

新增一处"已知可由既有能力覆盖"的目录时，同时在该 guard 的 `REUSE_SCOPES` 里加一条断言 —— 规则只有变成断言才不会衰减。

### 3.6 上游规范优先（`.octorules` 与 `CLAUDE.md` 都是规范）

本仓库有两层规则，**优先级是明确**的：

```text
1. 上游规范（`.octorules` 与 `CLAUDE.md`）—— 默认遵守，不需要讨论
2. 本 fork 规则（本文件）—— 只在本项目有特殊性质时才覆盖上游（§1 的三条）
```

**`.octorules` 与 `CLAUDE.md` 是规范性文件（binding），不是参考资料，两者效力相同。** `CLAUDE.md` 是完整写版，`.octorules` 是精简索引；内容重叠处两者都适用，冲突时以更具体、更新的一条为准并在 PR 里说明。**改动其一必须同步另一份**（约定见 §7.3）。§3.6.1 把 `CLAUDE.md` 的要点摘入本文件，方便只读本文件的工具；**权威版本仍在 `CLAUDE.md`/`.octorules`，摘录与它们不一致时以它们为准。**

具体含义：

- 上游定的分层、命名、依赖方向、测试放置、注释语言、无新依赖等，**继续有效**，本文件不重复也不豁免它们。
- 本 fork 规则与上游规范冲突时，**以本文件为准**，但必须在 PR 里说明冲突点与被覆盖的上游条款。
- **不允许的第三种情况**：既不合上游规范，也不在本文件里登记，靠"这次先这样"混过去。这就是 §3.7 要拦的东西。
- 值得优先引用的上游条款：`internal/app` 是**构造 provider client 的唯一位置**；`provider → agent` 单向依赖；`*_test.go` 就近；`gofmt` 唯一格式化。

#### 3.6.1 上游规范要点（由 `CLAUDE.md` 摘入；权威仍在 `CLAUDE.md`/`.octorules`）

| 类别 | 要点 |
|---|---|
| 命令 | `make build` / `make desktop-portable`（Windows 便携，主交付物）/ `make desktop-portable-all` / `make portable-check` / `make test` / `make vet` / `make fmt-check` / `make fmt` / `make tidy`；单包 `go test ./internal/agent/`，单测 `-run TestXxx` |
| 分层（单向） | `cmd/octo` → `internal/app` → `internal/agent` ← `internal/provider`、`internal/tools`；`provider → agent` 是唯一方向，`agent` 不得 import `provider`；构造 provider client 只在 `internal/app` |
| 加能力 | 新 provider 放 `internal/provider/<name>/` 并实现 `Provider`（+可选 Streaming/Tool/ToolStreaming）；新 tool 放 `internal/tools/` 并注册进 `DefaultRegistry` / `DefaultTools()`；新 skill 是 `<data root>/skills/<name>/SKILL.md`，不新增 tool 代码 |
| 代码风格 | Go 1.25 语法；`gofmt -w` 是唯一格式化器，`gofmt -l .` 必须为空；`go vet ./...` 必须过；测试与源码同目录；HTTP 测试用 `httptest.NewServer`，`go test` 不接真实网络；注释只写 why；无正当理由不得加三方依赖 |
| 工作流 | 从最新 `v1` 切分支，功能/修复/文档 PR 一律合 `v1`，`main` 只接受上游合并；`merge` 不 `rebase`；一个特性 = 一个 PR = 一个 squash commit；提交信息与 PR 描述用英文 |
| 常见坑（事故复盘） | ① Bing HTML 端点不能带 `Accept-Encoding: gzip`；② OpenAI 流式要 `stream_options.include_usage=true`（DashScope / 真 OpenAI 否则不吐 usage）；③ cache token 语义按**协议**不按厂商，`InputTokens` / `CacheReadTokens` 互不重叠；④ OpenAI 工具参数按 `tool_calls[i].index` 分片拼接；⑤ `finish_reason: "tool_calls"` 必须在 provider 适配层归一为 `"tool_use"` |
| 文档位置 | 上游架构/事实 → `dev-docs/`；本 fork 需求/方案 → `dev-docs-usdable/需求/<批次>/`；规范与合并策略 → `dev-docs-usdable/`。**禁止把下游文档塞进 `dev-docs/`** |
| 不确定时 | 外部声明（endpoint、SDK、日期）先核实；环境问题导致测试失败要明说，不许注释掉测试；方案与需求冲突时停下来对齐，记入 `开发计划.md` §4.1 并改需求 |

### 3.7 人工确认清单（必须停下来问）

以下情形**不适用**"我觉得没问题"，必须在 PR 里标注并取得人工确认后才继续。它们都属于"机器测不出来、但会长期腐蚀项目"的类别：

| 情形 | 为什么必须问 |
|---|---|
| **能复用而不复用**（§3.5） | 会永久性地产生第二套实现，且成本随每次上游变更复利 |
| **破坏既有架构约定**（分层、依赖方向、单一构造入口、单一真相来源） | 一条被破例的架构约束，会变成下一条破例的先例 |
| **改动敏感面**：认证、凭证、数据根、品牌文案、积分/账务、权限判定、路由门 | 这些是验收会逐条查的硬项，出错的代价不是"改回来"而是"重新验收" |
| **非常规逻辑**：为绕开某约束而加中间层、同一概念存两处、静默降级、隐式回退、启动期写用户文件 | 通常能跑通，但下一个人读不懂，且容易在边界条件下变成 bug |
| **触碰上游核心文件**（`internal/server`、`internal/app`、`agent`、`tools`） | 合并冲突 + 上游回归双重风险；见 §3.4 的破例流程 |
| **"使用不得当"**：把某能力用在其设计意图之外（例如把 provider 通道当通用 HTTP 客户端用、把 productstate 当凭证存储用） | 短期可行，长期是 bug 温床 |
| **删改上游既有行为** | 见 `上游合并策略.md` §4.4「先问能不能让它到不了」 |

**登记方式**：PR 描述里写清「触发的是上表哪一行 + 事实 + 我选择怎么做 + 谁确认的」。不要只写"已确认"。

### 3.8 单一入口与单一真相来源

同一件事只有一个地方能定义，其他所有位置都是它的投影或引用：

| 一件事 | 唯一来源 | 禁止 |
|---|---|---|
| provider client 构造 | `internal/app` | 任何包直接 import `internal/provider/*` 自行构造 |
| 数据路径 | `internal/datapath` | `os.UserHomeDir()`、`".octo"` 字面量（§3.1） |
| 品牌取值 | `branding/brand.json` | 硬编码文案（§3.2） |
| 敏感词匹配 | `internal/sensitive` | 第二套匹配逻辑 |
| 词库内容 | `data/sensitive-words.txt` | 第二份存储；界面只是它的编辑器 |
| 合同方法签名 | 方案里的「合同骨架」一节 | 第二份文档复述签名（见 §3.5 举证） |
| 错误码与错误信封 | [中台交付包](需求/20260911/中台交付包.md) §3.2 | 第二份文档 / 前端 / 实现各自定义 `code` 取值或字段名（`messageKey`、`traceId` 之类） |
| DTO 字段名（catalog / 能力 / 用量） | 中台交付包 §3.2、§4.3 | 文档或页面层猜 JSON 层级、另起别名（如 `model[].modes` vs `model[].modeIds`） |
| 运行时 Profile schema | [运行时Profile配置](运行时Profile配置.md) §3 | 各方案自行增删字段却不更新 schema 文档与两份 JSON |
| 模式分组与投影 | `internal/chatmode` | 前端或 handler 自己算分组 |
| 模型展示名 | 中台签名目录的 `displayName`（经 P0-04 投影到成员） | `web/` 保留 `model.<id>` 一类本地名称表（会在同一 id 上覆盖服务端展示名；debug/test 回退除外） |
| 权限判定 | `internal/permission` | 各 handler 自己写 if |

新增"唯一来源"时要写进本表。**发现两处定义同一件事，按 §3.7 人工确认后再收敛，不要静默选一个。**

**文档里的派生陈述（本次评审补充）**：需求文档对同一事实的复述，只允许「一句话结论 + 引用 canonical 章节」，不得复制完整的理由段或表格 —— 复制出来的第二份会在下一次改动时静默过期（本次评审已在 mock 措辞、错误码、Profile schema 上各命中一次）。已识别的 canonical 位置：错误码/DTO 字段 → 中台交付包 §3.2；合同签名 → P0-01 合同骨架；Profile schema → 运行时Profile配置 §3；`ensureLocalEndpoint()` 删除的完整理由 → 01A §2 与 P9 §3.2。发现第二处完整复述即按 §3.7 收敛。

### 3.9 降级必须有界

任何"失败时兜底"的路径都要能回答三个问题，否则不得合入：

1. **兜到哪里**？（用最近一次**已验证**的缓存 / 内置词 / 只读模式；不能兜到"另一个模型来源"）
2. **要不要告诉用户**？（用户可感知的能力缺失必须可见；不得静默降级）
3. **什么时候恢复**？（重试条件、TTL、失效信号）

硬约束：

- **不得静默降级到未授权来源**（例：目录不可用时不得回落到本地模型 —— R4）。
- **不得把降级当授权**（例：策略过期不刷新时只允许低风险本地只读动作 —— P0-04）。
- **启动期不得写「用户可编辑文件」**（见下方 §3.9.1）。
- **fail-closed 优先**：签名、版本、audience、时钟窗口任一校验失败 → 拒绝，而不是"先用着"。

#### 3.9.1 启动期不得写用户文件（作用域与理由）

**这条规则不是为 `ensureLocalEndpoint()` 单独写的，也不会随它一起消失。** 它约束的是启动路径上的一整类行为，而 `ensureLocalEndpoint()` 只是被抓住的第一个实例。

**先分清两类落盘**（这是 §3.10 要求的"写明作用域"，混了就会把正常缓存也禁掉）：

| 类别 | 例子 | 启动期写？ |
|---|---|---|
| **用户可编辑文件**：用户能看到、能改、改完按它走 | `config.yml`、`chat-modes.json`、`data/sensitive-words.txt`、`product-state.json` | **禁止**（唯一例外见下） |
| **客户端自有缓存/日志**：用户不编辑，只是实现的内部状态 | `data/catalog.json`（目录缓存）、`data/logs/*.jsonl`、诊断/审计日志 | 允许。写的是自己的缓存，不受本条约束 |

**例外只有一个：首次运行的幂等种子。** 文件不存在时写入一次出厂内容，让用户看得见、能编辑；文件已存在时**绝不重写**。且失败不能阻塞启动（读不到就用手里的内存默认值继续跑）。

**为什么仍然必要** —— 三个理由，每一个都独立成立：

1. **它是读改写竞态的来源**。`ensureLocalEndpoint()` 的真实缺陷不只是"种了假模型"，而是它在启动时 **读 `config.yml` → 改 → 写回**。用户此时正在 onboarding 里保存 access key，两边各自读改写，后写的覆盖先写的。这是启动期写用户文件的结构性风险，与"种了什么内容"无关。

2. **它是唯一能解释"为什么这里不能写"的依据**。没有这条，评审时"顺手在启动时把默认值落盘"看起来永远是善意且无害的；有了它，就必须回答"这是幂等种子还是覆盖用户数据"。

3. **它解释了为什么缺失文件应等于"用默认"，而不是"把默认写出来"**。这是本项目已有两条实现给出的同一结论：`internal/sensitive` 的 `UserWords()` 对缺失文件返回空词表、**不写盘**；`internal/chatmode` 的 `Load()` 原先会种出 `data/chat-modes.json`，**已于 2026-09-11 改为不写**。后者的种出理由（"让用户能看到并编辑"）随着内置内容只剩三个固定模式 id 而失效，而在 P0-04 之后本地文件还可能变成"空覆盖"把选择器清空。

**当前状态（2026-09-11）**：仓库里**已无任何**启动期写用户可编辑文件的路径 —— `ensureLocalEndpoint()` 已删除，`chatmode.Load()` 的种出已移除。所以这条**当前没有活跃违规**，它是一条**前瞻性约束**：下一次有人想在启动时落盘默认值（例如目录缓存之外的用户可见配置），必须按下面的检查项自证。

**实践检查**（评审时逐项确认）：

- 这个写入是**幂等种子**（文件不存在才写）还是**每次启动都写**？后者直接打回。
- 判断是否需要种子时，先问：**缺失文件是否已经等价于默认值？** 等价 → **不写**（`sensitive` 与 `chatmode` 的现行做法）。只有当"用户必须看得见这个文件才能用"时才考虑种子。
- 写之前**读过用户可能刚改过的同一文件**吗？是 → 打回（读改写竞态）。
- 写入失败会**阻塞启动**吗？会 → 打回（必须降级为"内存默认值继续跑"）。
- 它是**用户可编辑文件**吗？不是（是缓存/日志）→ 本条不适用，但要按 §3.9 回答"兜到哪/是否可见/何时恢复"。

### 3.10 每条约束都要写明作用域

写规则或方案时，**必须写清它管的是哪个域**。本 fork 有三组最容易混淆的域，混了就会出现"为了 production 安全，把开发能力也砍了"或反之：

| 域 | 例子 | 写规则时必须说清 |
|---|---|---|
| **production vs developer** | `config.yml` 的 endpoint/URL/key | **developer/测试：完全允许**（本地联调、第三方模型验证、离线开发都要用它）。**production：可以读取/保存，但不得作为正式会话的模型来源**。所以正确的表述是"production 正式会话不得用 config.yml 作模型来源"，**不是**"config.yml 不得提供 URL/key" —— 后者会误伤开发 |
| **构建期 vs 运行期** | Profile 选择、构建标签 | 构建期决定；运行期的环境变量/配置/缓存/WebView 输入一律不能切换 |
| **本地 vs 远端** | 目录/策略缓存、词库 | 本地只做'已验证快照的缓存与投影'；权威在远端签名控制面 |

**判据**：一条规则如果没有写明作用域，它就会在评审时被两种方向引用。发现这类表述，按 §3.7 补全作用域，不要只在脑子里知道。

| 方案里出现「新建 XxxClient / XxxStore / XxxEngine」 | 先按 §3.5 举证：查过哪个既有包、为什么不能复用、复用后的形态。填不出就是重复实现 |
| 在 `internal/productclient/*` 里出现 HTTP/SSE/JSON 流解析 | 按 §3.5 打回：协议能力只在 `internal/provider/*`，构造只在 `internal/app` |
| 新增独立 `server.Config` 字段 / 逐路由改写路由表 | 违反 §3.7（触碰上游核心文件）+ §3.8（单一入口）；改走中性中间件 |
| 规则/方案里出现「不得提供 URL/key」类绝对表述 | 按 §3.10 补作用域：是 production 正式会话，还是所有环境 |
| 任何「失败就回落到…」 | 按 §3.9 回答「兜到哪 / 是否可见 / 何时恢复」；不得回落到未授权来源 |

### 5.3 评审规矩

- 至少一人 approve 才能合。
- Reviewer 只对**看懂了的**部分负责；看不懂就问，不要「看起来没问题」地 approve。
- 「这样写更好」属于建议，可以不采纳；「这样写是错的」属于阻塞，必须解决。评论里把两者说清楚。
- 作者不要在 review 中途 force push（除非 reviewer 同意），否则评论会丢上下文。

## 6. 测试要求

### 6.1 底线

- `make test`（`go test -race ./...`）必须绿。
- 前端 `npm test` 必须绿。
- **不许注释掉测试来让 CI 变绿**。环境问题导致失败就明说（`.octorules` 已有此条）。

### 6.2 本项目额外要求

**把验收项固化成测试。** 需求 §8 里凡是能写成断言的，都写成断言。本期至少这几条：

| 需求验收项 | 固化为 |
|---|---|
| 主机不出现新 `.octo` 业务数据 | `cmd/octo-desktop/portable_test.go` 的 tmpdir 隔离测试 |
| 代码里不存在 `".octo"` 字面量 | Go 测试里的全仓 grep 断言（本地 `make test` 就能发现，不用等 CI） |
| 隐私列无云端、智能列无本地 | `internal/chatmode` 的出厂配置断言 |
| 细条文案只提手机号，不提证件号/银行卡 | 前端字符串断言 |
| 本地确定性回复能被输出过滤命中 | `internal/provider/local` 的断言 |
| 用户把 `***` 改回原词仍不能发 | 前端行为测试 |
| 词库为空文件时内置词仍生效 | `internal/sensitive` 断言（P13 界面清空用户词的安全前提） |
| 未登录 + 无 window token 的请求放行（CLI 场景） | `internal/productgate` 测试 |

最后一条是个特例：它测的是一个**看起来像 bug 的有意行为**（需求 §9.8）。没有测试固定住，早晚有人「顺手修好」它。凡是这类反直觉的设计，都要有测试 + 注释双重固定。

### 6.3 手工验收

Windows 是唯一验收平台（需求 §6），但代码跨平台。所以：

- 每个 PR 的方案里都有手工验收步骤，合并前跑一遍并在 PR 里贴结果。
- **macOS / Linux 不能写坏**。任何 `runtime.GOOS` 分支都要有对应测试。为 Windows 验收引入 macOS 回归是开发计划 §5 明列的风险。

## 7. 需求与文档

### 7.1 需求有矛盾、或评审推翻了需求时

不要自己猜，也不要闷头按其中一种实现。流程：

1. 在技术方案里写一节说明矛盾或调整，引用需求的**章节号**（不要引行号 —— 需求一改行号就失效）。
2. 给出取舍与理由 —— 尤其是「为什么这样更好」，将来会有人问。
3. 记入 `开发计划.md` §4.1 表。
4. 评审拍板后**改需求正文**，并在需求的修订表里记一行。
5. 回头把技术方案里那一节改成「已回写，留档」，别让它读起来像还没解决。

**第 4 步最容易被跳过**，代价是几个月后验收时有人拿一条已作废的条款卡你，而当时在场的人都记不清了。本期 6 项已于 2026-09-07 一次性回写（Logo 字随语言变、账户面板形态、词库管理界面、内置词叠加语义、真模型验收、CLI 数据根），留档见 `开发计划.md` §4.1。

**跨文档取值改动**照 `开发计划.md` §4.2 的一致性矩阵同步——那张表列出了每个取值散落在哪几处。

### 7.2 已识别但暂不解决的问题

评审或真机测试中发现「有根因、有兜底、但决定先不做」的问题，**登记到
`未解决问题登记.md`**，别让它只存在于聊天记录里。登记格式与生命周期约定见该文件
文件头的「登记约定」。已立项进某个 PR 的功能不属于此类，那是 `开发计划.md` 的职责。

### 7.3 文档在哪

| 内容 | 位置 |
|---|---|
| 需求、开发计划、技术方案 | `dev-docs-usdable/需求/<批次>/`（当前 `2260906/`，方案在 `技术方案/`） |
| 本地开发 / 运行 / 端口分工 | `dev-docs-usdable/本地开发与运行.md` |
| 已识别但暂不解决（deferred）的问题 | `dev-docs-usdable/未解决问题登记.md` |
| 工程规范、合并策略 | `dev-docs-usdable/` |
| 上游架构设计 | `dev-docs/`（上游的，不要往里塞我们的东西） |
| 项目指引 | `.octorules` / `CLAUDE.md` —— **规范性上游文件，两者效力相同**（§3.6），改一份必须同步另一份 |
| 品牌取值 | `branding/brand.json` —— **唯一来源**，文档里的表格都只是摘录 |

**不要把下游文档塞进 `dev-docs/`** —— 那是上游目录，塞进去每次合并都冲突。

**文档之间用相对路径 + 章节号互链，不要用行号。** 行号在下一次编辑就失效，而失效的引用比没有引用更误导人。

### 7.4 规范对所有 AI 工具可见（已机制化）

`.octorules` 与 `CLAUDE.md` 只管得住读它们的那一类工具。要让**所有** AI 编程工具都读到并遵守本文件，仓库在每个工具各自的入口放一份指针：

| 工具 / 生态 | 入口文件 |
|---|---|
| 跨工具约定（Codex、Cursor、Gemini CLI、Aider、…） | `AGENTS.md`（**生成物**，内联 `.octorules` 全文） |
| Cursor | `.cursor/rules/dev-norms.mdc`（`alwaysApply: true`） |
| GitHub Copilot | `.github/copilot-instructions.md` |
| Claude Code | `CLAUDE.md` |
| 上游 agent 约定 | `.octorules` |

每个入口文件都必须指向 `dev-docs-usdable/开发规范.md`。`scripts/norms-guard.mjs`（`make norms-check`、CI `norms-guard` job、出包 `preflight` 的**硬失败**项）断言这一点，同时断言本文件把 `.octorules` 与 `CLAUDE.md` 都登记为规范性上游文件。**新增一种 AI 工具时，把它的入口加进该 guard 的 `ENTRY_FILES`** —— 规则只有变成断言才不衰减（§3.5 同理）。

**光有指针不够，必须内联。** Codex 没有 include 语法（`AGENTS.md` 里的 `@path` 只是字面文本，模型可以不理），且它对指令文件有字节预算（`project_doc_max_bytes`，默认 32 KiB，整条链**累计**）。本文件约 41 KB、`CLAUDE.md` 约 15 KB，都进不去；`.octorules` 约 10 KB 进得去，而它本身就是上游规则的精简索引（含三条硬规则）。所以 `AGENTS.md` 是**从 `.octorules` 生成的**：`make agents` 重新生成（改 `.octorules` 后必须重跑并一起提交），`make agents-check` + CI `agents-guard` job + 出包 `preflight` 断言它不漂移。

该 guard 还断言 `.octorules` **仍带着三条硬规则与合并策略的锚点** —— `.octorules` 是上游文件（Fork rules 一节是本 fork 加的，`git diff origin/main -- .octorules` 可见），上游合并一旦覆盖掉那节，重新生成会产出一个"看起来合规、却不含硬规则"的 `AGENTS.md`。这条断言把那种静默失效变成构建失败。

## 8. 定义完成（DoD）

一个 PR 算做完，要同时满足：

- [ ] 方案里的「改动清单」逐项做完，或方案已回写说明为什么不做
- [ ] 方案里的「测试」逐项通过（单测 + 手工）
- [ ] 方案里的「验收对照」中标记为「主责」的条目，能在 Windows 上开发验证
- [ ] CI 全绿（含四道 guard）
- [ ] Review 通过
- [ ] 若改了行为，`.octorules` / `CLAUDE.md` / 需求文档同步更新

一个**里程碑**算做完，额外要求：

- [ ] 需求 §8 中属于该里程碑的验收条目全部走过一遍
- [ ] 跑一次上游合并（上游合并策略 §3.2）
- [ ] `make desktop-portable` 产物在真机 U 盘上验一遍
