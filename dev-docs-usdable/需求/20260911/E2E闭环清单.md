## 0. 本轮目标（人工明确，2026-09-11）

> **在不真正接入正式中台的前提下，把全部 UI、交互与 Sandbox 接通，所有功能细节做完。**

拆成三条，缺一条都会让验收标准漂移：

1. **做：** 界面、交互、**全部本地逻辑**（数据根、门、词库、模式、便携、诊断）、**Sandbox 联调链路**。
2. **不做：** 正式中台地址与验签公钥（`D-001`）；需要中台共同签字的合同字段 —— `clientRequestId` / `toolPolicy`（`D-003`）、流中 `retract` 与账本终态帧（`D-002`）。
3. **不因此降级：** §0 原则的两条底线照旧 —— **失败关闭**、**不静默降级**。少做功能与放松安全是两件事，见 §0「不适用面」。

**"做完"的判据不是"页面能点"，而是本文档 §2 的 38 条闭环** `L-*` **各自能独立跑通并判定**。

## 1. 两套 E2E 依据的分工（不得混用）

## 2. 闭环总表（38 条）

> **2026-09-16（三）当前计数：✅ 30 ｜ 🔵 1 ｜ ⚠️ 1 ｜ 🟨 4 ｜ ⛔ 2 ｜ ⬜ 0**（`L-E3` 与 `L-F1` 各由 🟨 转 ✅ —— 前者随 `V-97` 收敛，后者随 `V-98` 收敛；`V-99` 新登记，只登记不改行为）。**2026-09-16 计数修正（二）：✅ 28 ｜ 🔵 1 ｜ ⚠️ 3 ｜ 🟨 4 ｜ ⛔ 2 ｜ ⬜ 0。** `L-E3` 由 ⬜ 转 ⚠️（壳侧冻结、写门与启动失败链已落地并有判据与变异，**可见半边仍等 `PR-8`/`G1`**）；`L-D5` 已于 2026-09-15 完成并从 ⬜ 转为 ✅；下方历史汇总段保留原始修订轨迹，当前状态以各行状态列与本条修正为准。

**状态列 —— 2026-09-12 起含义已改为「实现状态」（`V-23`）。** 此前它叫「规格状态」，定义是"这条闭环的规格够不够我照它写测试"，不回答"代码写完没有"。**但它的取值是 ✅，而全表末尾还有一个 `✅ 28` 的计数 —— 读起来就是"做完 28 条"。** 实际按代码核对，真正实现并验收的只有 **6 条**（`V-23`）。规格是否完整仍记录在「关键异常分支」「依据」两列里，不再占用状态列。

取值（当前）：✅ **已实现且验收合格**（按 `§2.1` 第 5 步：单元 + 端到端两条都过）｜ 🔵 **代码就绪，等中台/外部条件**（机制与钉子都在，判定所需的那个**外部前提不存在**；客户端侧无欠账，条件一到就能判，见下）｜ 🟨 **可走通但带已登记缺口**（端到端能跑通、用户看得见结果；判据里有**已登记**的欠账，逐条挂在本行并写明归属，见下）｜ ⚠️ **部分实现或不满足验收**（格内注明缺哪一条）｜ ⬜ **未实现**（格内注明归属 PR 与证据）｜ ⛔ **被外部件挡住**（合同层缺失，非实现问题）。

**🟨 的使用规则（2026-09-14 人工定，`开发规范` §6.4.6 纪律 4）。** 它存在的原因：本轮的目标是**先把流程走通**（§0），而"走通"与"判据全绿"是两件事 —— 只有 ✅ / ⚠️ 两个取值时，一条能跑但差个文案的闭环既不是 ✅ 也不是"不满足验收"，只能记成 ⚠️，读起来像没做完。三条约束，缺一条就不许标 🟨：

1. **必须真的能端到端跑通**，用户看得见结果；跑不通的一律 ⬜ 或 ⚠️。
2. **缺口必须逐条登记**在本行（缺哪一条、归属哪个 `V-n`/`PQn`、谁在什么时候补）。**没有归属的缺口不许留在 🟨 里** —— 那会退化成 `V-23` 那种"把规格当进度"。
3. **🟨 → ✅ 只差"把缺口清单清空"**：不重新实现、不重新设计、不改变已跑通的行为。

**与 ⚠️ 的分界：** ⚠️ = 那条闭环的**主路径**还没通或判据不成立（要写代码）；🟨 = 主路径**已经通了**，欠的是**补充项**（文案、某个分支、某条断言）。**判据：把缺口摘掉，这条闭环还叫这个名字吗** —— 还叫 ⇒ 🟨；不叫 ⇒ ⚠️。

**🔵 的用法（2026-09-15 人工要求："机制在，但判不了 —— 只个标记下"）。** 它必须与 ⚠️ 分开，因为**下一步的动作完全不同**：⚠️ 的下一步是"去写代码"，🔵 的下一步是"**去推外部**，客户端一行都不用改"。准入条件三条，缺一条就不许标 🔵：

1. **机制已落地且有自己的钉子**（不是"设计好了"，是代码在）；判据不成立的原因**不在客户端**；
2. **那个外部前提必须具名**（哪一条 `PQn`/`D-n`、谁的 owner）；
3. **条件一到就能判，不需要补代码**。若条件到了还要写代码，那它是 ⚠️。

**🔵 与 ⛔ 的分界：** ⛔ = **这件事本身不做**（能力矩阵）或**做不了**（`L-A1b` 缺幂等键，今天写不出合格闭环）；🔵 = **做完了，只是没法验收**。

### 2.0 为什么从 25 条拆成 33 条（2026-09-11 人工要求；后又补 2 条 → **35 条**；2026-09-13 补 `L-C8` → **36 条**；2026-09-14 按第 0 步拆 `L-C4` → **38 条**，见 §6 修订）

**人工要求：** 「每一个闭环最好别太大」。**拆分判据（`开发规范` §6.4 第 0 步）：** 一条闭环 = **一次可独立判定的用户可见行为**；能用一句话说清"用户看到什么变了"才算过关。按此复检，有 6 条实际上是**多个独立判据捆在一起**，拆开：

| 原 ID | 拆为 | 为什么捆着不对 |
| --- | --- | --- |
| `L-A1` | `L-A1a` 激活成功 ｜ `L-A1b` 响应丢失 | 成功路径**不该被 `PQ25` 拖住**；两者判据完全不同（一个判"进不进主界面"，一个判"幂等键有没有用"） |
| `L-B1` | `L-B1a` 界面门三态 ｜ `L-B1b` 窗口令牌与请求门 | **两套机制**：界面路由 vs HTTP 令牌。`PR-2b2b` 只关于后者 |
| `L-C1` | `L-C1a` 拉取与验签 ｜ `L-C1b` 缓存与投影 | 失败面不同（签名不过 vs 投影错）；**拆开后 `L-C1a` 不再被 `V-2` 挡住**（模式分组只属于 `L-C1b`） |
| `L-C3` | `L-C3a` 基础流式 ｜ `L-C3b` 思考块 ｜ `L-C3c` 工具调用 | 原来把**四个能力**（内容/思考/工具/usage）捆成一条，是本表最大的一条 |
| `L-D4` | `L-D4a` 读取与三层合并 ｜ `L-D4b` 用户词增删 ｜ `L-D4c` 导入 | 读 / 写 / 导入是**三种操作三种语义**（尤其导入是**合并非覆盖**） |
| `L-E4` | `L-E4a` 版本与缺字段 ｜ `L-E4b` 损坏与超前 | `PR-2a` 本来就是**两组独立测试**（缺字段不迁移 vs fail-closed 保留原文件） |

**拆分的净收益不是"看起来更细"，是两件事：** ① 阻塞被**隔离**（`L-A1` 原来因 `PQ25` 整条 ⚠️，拆开后只有 `L-A1b` 被挡，成功路径 `L-A1a` 可判）；② 每条闭环的"通了"变得**可以说清**，从而能变成断言。

**引用已同步**（`开发规范` §6.4.2："引用不同步 = 拆分没做完"）：本文档 §2 / §3 / §4、[`开发计划.md`](开发计划.md) 的 PR 归属与能力检索、[`需求基线.md`](需求基线.md)、[`README.md`](README.md)。

> **本次核对的方法（`PR-4b` 复核时再次执行，条数与上表逐格一致）**：不读文档、不读测试名，**只读 `v1` 的实际代码路径**，逐条回答"这条闭环的用户可见结果，今天在真机构建下能不能出现"。凡"函数在但无调用点""前端在但路由未注册""上游能力在但产品通道不存在"一律记为未实现（`§6.4` 第 5 步的"单元绿 ≠ 闭环合上"同理）。

> **`⬜` 的含义**：规格已写清、**实现尚未开始**（新增条目的初始态）。它与 `⚠️`（规格有缺口、无法判）不同 —— `⬜` 是**能判但还没做**，`⚠️` 是**做了也判不了**。

> **拆分后 ⚠️ 从 4 降到 3、并首次出现 1 条 ⛔ —— 这是进步不是退步。** 原来的 `L-A1` 因为`响应丢失`这一个分支整条挂在 ⚠️，而它的**成功路径其实完全可判**；拆开后成功路径独立成 ✅、被挡的那条独立成 ⛔，**阻塞不再污染它不属于的判据**。同理 `L-C1a`（验签）摆脱了 `V-2`。

## 3. 需要单独说明的闭环

### 3.1 `L-C4a` 余额刷新：口径冲突已由人工拍板收敛（`V-11` → 2026-09-14 新规则）

- `E9` 规则 2：**「余额更新唯一时机 = 收到终态帧」**。
- `C7` 抬头：**「账本终态帧收不到 ⇒『只有 `settled` 才更新余额』这条链路不通」**，兜底改为 `GET /v1/credits/ledger` **主动查询（拉模式）**。

**两处不能同时为真**，而 `L-C4` 的验收判据（"余额变化只在终态帧之后"）正是照 `E9` 规则 2 写的 ⇒ **本轮按这条判会必挂**（终态帧本批不交付）。

**处置（§3.8，结论只能有一个 owner）：** 以 `E9` 为 owner，把规则 2 改写为**两条并列的合法来源**，并写明本批取哪条：

1. 有终态帧时（`D-002` 交付后）：**只有 `settled` 才更新**，流中不预扣不回滚。
2. 无终态帧时（**本批**）：走 `GET /v1/credits/ledger` **拉模式**，且只在以下时机拉 —— 回合结束、界面重新获得焦点、用户手动刷新。**不得**流中轮询。

**2026-09-14 人工拍板，把上面那两个来源进一步收成一个（`E9` 规则 2 已按此改写，那一条是 owner）：**

> 「余额必须从服务器刷新，每次消耗啥的都需要从服务器同步，服务器来扣减积分，客户端只需要老老实实从服务器定时刷新余额就行了。」

于是**余额只有一个来源（中台账本）与一个写入路径（拉 `GET /v1/credits/ledger`）**；终态帧退化为"该去拉一次"的**触发器**、不再承载数字。这条收敛的连带效果有三：① 不存在"两个数谁说了算"，因此**没有两版验收判据**；② `D-002`（SSE 终态帧的接收形态）**不再是余额链路的阻塞项**（它仍阻塞 `retract` 与安全终态，属 `C6`）；③ `credits` 对象随之收敛为 `{balance}` —— 中台只给一个数，`monthUsed` / `monthKey` **既无来源又不许本地算**（`E9` 规则 7）。

**本批验收（`L-C4a`）：** 一个回合结束后（或手动刷新）余额能刷到中台的值；流中不出现余额跳变；拉取失败时保留旧值。**`402` 文案与充值入口分别归 `L-C4c` / `L-C4b`**（拆见 §2 与 §6 修订）。

**落地（`PR-5d1`，2026-09-14）：上面那三条判据各有钉子，且"触发器 ≠ 载体"这条被单独钉住。** 最值得留的是**触发器清单** —— 它同时也是"**不**该发生什么"的清单：登录后、回合结束、窗口重获焦点、积分页打开、手动刷新**五处都只是"去拉一次"**，任何一处直接把数字写进界面都是缺陷（`App.svelte` 的 `credits_update` 此前正是这么做的：它把 `ev.credits` 拷进 store，即**第二个写入方**）。判据形式：**改盘上其它任何字段、或只收到事件而不拉账本，界面上的数不变**。另外两处只有写测试才会遇到的事实：① **"0"与"没给"必须分得开**（`BalanceMicroCredits` 从 `int64` 改指针）—— 0 在本产品里是最常见的合法值（它就是让网关回 `402` 的那个值），把畸形应答读成 0 会让界面无声地告诉一个有余额的用户"你没钱了"；② **替身看不见 json tag**（`V-57` 的族属）—— 替身的 bootstrap 应答是**用客户端自己的 DTO 序列化**的，tag 写错时往返自洽、经替身的钉子全亮，所以那条钉子必须解**手写的字面 JSON 体**。

### 3.2 `L-F1` 四事件 vs `L-E3` 拔盘：两套机制管同一件事？

- `F2` 的**拔盘冻结**：桌面壳层，程序目录消失 → 冻结界面。
- `datastore:lost` / `datastore:restored`：服务端经 WS 推出的**产品事件**。

**两者是否同一状态的两个视角、谁先谁后、只出现一个时算不算通过 —— 当时都没写。** 这是 `N-5` 的一部分，但影响 `L-E3` 与 `L-F1` 两条闭环的判定，所以单列。

**已定（2026-09-16，`PR-8`；四条见 `开发计划` §4.1 第 45 行）：两者都要，且分工是「门」与「看得见的那半」，不是两个视角。** 事实是**壳与服务端同一个进程**（`cmd/octo-desktop/main.go:633` 起 server、`:738` 起 watchdog），所以答案是**一个检测器**（`watchdog.go`，含 2 次失败的迟滞与一次性去重）、**一个门**（`internal/datapath.Freeze`，写拒绝、fail-closed）、**一个事件**（`datastore:lost`/`restored`，壳经导出缝广播）、**一个 UI owner**（`FrozenOverlay`，由 `frozen` store 驱动）。**顺序**：先冻门，再广播。**只出现一个都不算通过** —— 缺门是"显示冻结而写入照跑"，缺事件是"写被拒而用户看不见"。**上面那条"壳负责冻结 UI"的建议要更正**：壳负责冻结**写入**，冻结**界面**是 Web 的遮罩、且只由这个事件驱动 ⇒ **事件必须在新连接时重放**，否则冻结期间刷新/重开窗口会让遮罩消失而写入仍被拒。**是否带 `reason`：不带** —— 今天只有一种原因，而 `frozen.desc` 已是一句完整措辞，再加一个 reason 就是同一句话的第二个 owner（§3.8）。

### 3.3 `L-A1b` / `L-A4`：`PQ25` 与 `PQ26` 是这两条的**判定前提**，不是装饰

**一次性激活码 + 响应丢失 + 无客服载体**，三者叠加卡住两条闭环，且**卡的是不同环节**：

- **`L-A1b`（响应丢失）卡在 `PQ25`：** 合同没有幂等键 ⇒ 用户重试时，中台无法回答"这个激活码是已成功还是没成功"。**这条不是实现能补的**，要中台在合同里加幂等键（或明确"重复提交同一激活码返回原结果"）。在此之前它只能是 ⛔。
- **`L-A4`（失败分流）卡在 `PQ26`：** 界面会说"请联系客服"，而用户无处可联系。**这两条在 `PQ26` 落地前只能判「文案正确」，不能判「闭环成立」。**

**拆分带来的好处在这里最明显：** 原来 `L-A1` 把"激活成功"和"响应丢失"捆在一起，于是 `PQ25` 这个合同层缺陷**污染了成功路径的判定**（整条挂 ⚠️）。拆开后 `L-A1a` 独立判 ✅ —— 它可以先做完、先验收，不必等中台加字段。

### 3.4 `L-D2` 输出打码：三个「判据看不见的地方」（`PR-6a`，2026-09-14）

`L-D2` 从 ⬜ 直接到 ✅，是因为它这一轮的形状特殊：**引擎是整包搬来的、判据也大多是搬来的**，而真正会出错的地方**一条搬来的判据都照不到**。三处写在这里，因为它们是"这条闭环凭什么 ✅"的实质。

**① 装配位置：归档那一处今天接不上，而照抄它全套测试仍是绿的。**

归档实现在**启动时装配的那个默认 sender** 上包一层。今天产品回合**不走那个 sender**：网关绑定的回合由 `GatewayEndpoint.Sender(tuning)` **每回合现造**（`PR-5a`），IM 回合另从 `channelModelOps().Resolve` 取。照抄归档 ⇒ **产品自己的路径上一个字都不打码**，而引擎的测试、装饰器的测试、路由的测试**全部照旧全绿** —— 与 `V-57`（json tag 写错、替身往返自洽）是同一族：**错在接线，而判据全在线的另一端**。

落点因此改成**三处 agent 构造点**（`buildAgent` 主路径、子代理模板、IM 通道）。**不放在 `senderForSession` 里**，理由是实测的：**四处上游断言钉住了那个函数的身份**（普通路径必须原样返回 `srv.sender` 本身、网关路径必须返回注入的那个 sender），而它们判的是**路由**、不是打码 —— 为一层装饰去改四条路由判据，是把判据改来迁就实现。同一族的旁证：**lite sender**（`liteSenderFromConfig`）也会产生**用户可见文字**（会话标题、压缩摘要），故一并包上；它是配置了 lite 模型才存在的路径，**任何回合级测试都照不到**。

**② "落盘即打码"必须读文件的字节，不能读重载后的结构体。**

判据是 `G2` 拍板的那一句：装饰在 sender 上 ⇒ agent 写进 history 的就是打码后文本。但"写盘时打码、读回时打码"与"写盘明文、读回才打码"**在结构体上无法区分**，而后者在**换机 / 用编辑器打开会话文件**时就露馅。所以那条钉子读 `SavePath()` 的**原始字节**，并断言里面**不含原词**。

**③ 跨 chunk 的词：这是"接线"与"引擎"唯一的交界处。**

引擎自己会缓存 `maxLen-1` 个字（`StreamFilter`），所以词被切成两半时**它**是对的 —— 但如果装饰器只滤完整回复、不滤流式增量，或者忘了 `Flush` 尾部，用户就会**先看到半个词、后看到 `***`**。判据因此让替身**把词切成两半分两个 delta 发**，并断言**上屏文本与落盘文本一致**（刷新页面时不会从 `***` 变回原词）。

**两个「有意不打码」也在这里说明，因为它们看起来像漏做：**

| 不打码的地方 | 为什么 | 判据 |
| --- | --- | --- |
| `tool_use` 的入参 JSON | 那是 agent 要 dispatch 的参数；打码会**改坏工具调用本身** | 反钉：入参里的命中词**逐字未变** |
| `Reply.Blocks` 里的 `thinking` 块 | 它要**带签名原样回传**供应商，供应商会校验 | 反钉：块内文本**逐字未变**（只有上屏的流式思考增量被打码） |

`V-71` 登记的正是这两个"有意不打码"**之外的**一处：任务清单与工具输出（它们经 `tool_result.ui_payload` / `todo_update` 上屏）**今天仍是明文**。**2026-09-14 已拍板（用户）：不扩展。** 结论写在 `需求基线` `V-71`：两处「不打码」是**明处的例外**，各配一条**反钉**（断言命中词**逐字不变**地落进会话 JSON）—— 将来有人顺手给它们打上码时，那条钉子转红，逼他回来读这一行的理由。判据是「**没有任何验收口子要求它**」：`P8` §3.4 只对「模型答话」下了结论；用户自己敲进输入框的字走 `L-D1` 的输入检测（`PR-6b3`），不是同一条要求。

> **`P1` 是本轮最容易被漏掉的一件。** 目标既然定为"不真正接入正式中台"，那么 E2E 就必须能**不依赖远程**地跑 —— 否则"闭环"退化成"某天有人手动点过一次"。`P1` 与 `devBackend.ts` **不是一回事、也不能互相替代**：`devBackend` 顶替的是**本地 Go 服务**，`P1` 顶替的是**中台**。这两层必须分开说，混为一谈会得到"有 Sandbox 就不用 P1"的错误结论。
>
> **`P1` 也不能在"被它镜像的东西"之前写出来。** 替身是 `internal/productclient` 的镜像 —— 而该包在 `v1` 上并**不存在**（8 个中台侧包一个都没有，2026-09-11 核实）。先写替身会发明一份契约，再写客户端又发明一份，两份必然漂移（`§3.8`）。因此正确顺序是**一份 Go 类型、两个实现**，这也是 `PR-1` 把「契约层 + 替身 + 客户端骨架」放在同一个 PR 的原因。详见 [`开发计划.md`](开发计划.md) §2。
