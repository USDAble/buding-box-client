# 完整身份迁移预留方案

## 1. 目的与适用范围

本方案不要求现在迁移，而是为未来把当前展示品牌进一步升级为完整独立产品身份提供安全边界。

适用仓库：`E:\zxy\work-code\buding-box-client`

可能涉及的旧身份包括：

- CLI：`octo`
- 数据目录：`~/.octo`
- 环境变量：`OCTO_*`
- Web/配对协议：`octo-ui`、`octo-pair`
- Go module：`github.com/open-octo/octo-agent`
- 桌面和服务标识：`dev.octo.*`
- 官网、下载、Release 和升级地址
- Capacitor、Android、iOS、macOS、Windows 的系统标识

核心原则：**完整迁移不是替换字符串，而是一次带兼容层、数据迁移、回滚和发布策略的身份变更。**

## 2. 迁移对象与推荐策略

| 迁移对象 | 当前阶段 | 未来推荐策略 |
|---|---|---|
| CLI 命令 | 保留旧命令 | 新命令作为主入口，旧命令保留兼容别名并给出迁移提示 |
| Go module/import | 保留旧路径 | 新 module 发布新路径；旧路径通过兼容版本或迁移说明过渡 |
| 数据目录 | 保留 `~/.octo` | 新目录优先；首次启动检测旧目录、备份后迁移，失败自动回退 |
| 环境变量 | 保留 `OCTO_*` | 新前缀优先、旧前缀回退；冲突时明确优先级并提示 |
| API/WS | 保留现有行为 | 增加协议版本与能力协商，不直接删除旧字段 |
| 配对协议 | 保留旧解析 | 新旧协议并行解析；新客户端默认生成新格式但可识别旧格式 |
| Mobile ID | 当前不破坏切换 | 新包标识作为新应用发布；旧应用提供迁移/导入流程 |
| Desktop ID | 当前保留兼容 | 新 Bundle/AppUserModelId 与旧服务并行过渡，确认升级策略后再下线 |
| Release/下载 | 当前兼容旧地址 | 旧地址长期重定向或返回迁移版本，新地址成为主入口 |

## 3. 迁移前必须建立的身份映射表

实施前建立版本化映射文件或等价配置，至少记录：

- 旧展示名与新展示名
- 旧 CLI 与新 CLI
- 旧目录与新目录
- 旧环境变量与新环境变量
- 旧协议名、协议版本与新协议名、版本
- 旧 URL Scheme、深链、Universal Link、App Link 与新值
- 旧 macOS Bundle ID、LaunchAgent、pkg identifier 与新值
- 旧 Windows AppUserModelId、安装目录、卸载键与新值
- 旧 Release artifact、下载域名、升级 API 与新值
- 各迁移项的首次引入版本、停止写入版本、停止读取版本

映射表必须成为测试输入，不能只存在于口头约定或一次性脚本中。

## 4. 推荐迁移阶段

### M0：冻结与盘点

- 冻结当前版本的身份常量和数据格式。
- 保存一份可运行的旧版本安装包。
- 建立旧目录、旧配置、旧会话、旧配对码和旧环境变量的测试样本。
- 记录升级地址、签名、安装器和商店发布状态。

### M1：兼容准备版

- 引入集中身份配置和映射表。
- 新旧名称可以同时显示在诊断信息中，但用户界面只使用新展示名。
- 增加协议版本、配置版本和迁移状态字段。
- 新版本继续读取旧目录、旧环境变量和旧协议。

### M2：双读单写

- 新目录优先写入；旧目录只读。
- 新环境变量优先，旧环境变量回退。
- 新协议优先发送，同时可解析旧协议。
- 每次迁移前自动备份并记录迁移日志。
- 用户可选择跳过迁移，保留旧数据不被删除。

### M3：显式迁移

- 提供 CLI 和 UI 迁移入口。
- 展示将迁移的文件、权限、风险和备份位置。
- 迁移成功后保留旧目录只读副本一段兼容周期。
- 失败时恢复备份，继续使用旧目录或旧协议。

### M4：双品牌/双入口过渡

- 新 CLI、下载地址、深链和应用标识成为主入口。
- 旧命令、旧链接、旧配对码仍能跳转或解析。
- 升级器可以从旧渠道升级到新渠道，但不能反向覆盖不兼容版本。
- 通过发布说明明确迁移行为和回滚方法。

### M5：停止写入旧身份

- 旧目录、旧变量和旧协议不再写入，只保留读取。
- 在日志或 UI 中给出明确但不过度打扰的迁移提示。
- 只有在兼容数据仍能导出、备份和恢复时，才考虑停止读取旧身份。

### M6：停止读取旧身份

此阶段是破坏性变更，必须满足：

- 至少一个明确的兼容周期已经结束。
- 旧数据已有稳定迁移工具和恢复方案。
- 旧客户端、旧移动端和旧服务的互操作性已评估。
- 下载、升级、安装器、商店和文档已同步切换。
- 有明确的版本公告、迁移指南和人工支持入口。

## 5. 各类对象的技术预留

### 5.1 CLI 和 Go module

- 新 CLI 先作为别名或新构建目标发布，不立即删除旧命令。
- 帮助和版本输出明确显示新品牌，诊断信息保留兼容标识。
- 新 module 迁移使用可编译的兼容版本、清晰的 import 迁移指南和自动化构建验证。
- 任何 public API、配置结构和插件接口都要先做版本化。

### 5.2 数据目录和配置

- 迁移前检查目录权限、文件锁、正在运行的进程和磁盘空间。
- 先复制或快照，再校验，再切换；不在原目录上直接破坏性移动。
- 迁移清单应包含配置、会话、技能、密钥引用、缓存和用户自定义内容。
- 新旧目录都要处理路径大小写、符号链接、跨平台路径和并发启动。
- 迁移完成后保留可导出的备份，明确删除条件。

### 5.3 环境变量

- 新变量优先级高于旧变量；同名冲突时输出一次性迁移警告。
- 对敏感值不要把完整内容写入日志、诊断报告或遥测。
- 文档和示例同时说明新变量与旧变量的兼容期限。
- CI、安装脚本、systemd、launchd、桌面启动器和移动端构建配置都要覆盖。

### 5.4 API、WebSocket 和配对协议

- 增加明确的协议版本或能力协商字段。
- 服务端在兼容期内同时解析旧、新标识；客户端按能力选择发送格式。
- 配对二维码、深链和短链接保留旧格式解析入口。
- 协议迁移必须覆盖旧客户端、新客户端、旧服务、新服务的组合测试。
- 不依赖改 User-Agent 或界面文案来判断协议版本。

### 5.5 移动端标识

Android、iOS 的 Application ID/Bundle ID 变化通常会影响升级、签名、商店应用身份、Keychain 和本地数据。推荐：

- 先决定是“同一应用改展示名”还是“新应用重新发布”。
- 如果必须更换 ID，提供旧应用导出/导入或深链迁移路径。
- 新旧 App 并存期间，旧 App 的配对和数据导出能力不能提前删除。
- 重新检查 URL Scheme、Universal Link、App Link、通知和系统权限说明。

### 5.6 桌面系统标识

- macOS Bundle ID、LaunchAgent、pkg identifier、签名和 Keychain service 需要一起评估。
- Windows AppUserModelId、安装目录、卸载信息、快捷方式和协议注册需要一起评估。
- Linux desktop entry、systemd service、配置路径和 MIME/URL 注册需要一起评估。
- 新旧服务并行时必须避免端口、锁文件、后台进程和自动启动重复运行。

### 5.7 Release、下载和升级

- 旧下载域名和升级 API 至少在兼容周期内保留重定向或兼容响应。
- artifact 名称可以先变，但升级器应理解旧名称和新名称。
- 校验和、签名、公钥、镜像路径和 CDN 缓存策略必须单独验证。
- 安装脚本不能假设用户永远从新域名下载。
- 发布说明要写清楚“品牌变化”和“技术兼容变化”是两件事。

## 6. 数据迁移与回滚要求

每次迁移必须具备：

1. 迁移前检测。
2. 自动备份或用户确认的备份位置。
3. 可重复执行且不会重复破坏数据。
4. 校验迁移前后关键文件数量、权限和内容摘要。
5. 失败时恢复旧状态。
6. 用户可跳过、稍后重试或导出数据。
7. 迁移日志不包含密钥和隐私内容。
8. 迁移后的旧数据保留策略和删除条件。

## 7. 未来可继续修改的预留清单

除名称和 Logo 外，未来还可以独立调整：

- 品牌色、字体、圆角、间距和暗色主题
- 首次启动流程、产品定位和功能命名
- About、隐私、安全、支持和反馈页面
- 埋点、错误报告、崩溃报告和遥测开关
- User-Agent、诊断信息和日志格式
- 默认工作目录显示名、导出文件命名和通知标题
- 桌面托盘、快捷键、系统服务和自启动策略
- 移动端权限说明、推送、深链和分享卡片
- 商店名称、截图、描述、分类和隐私标签
- 官网 SEO、Open Graph、博客页脚和下载页
- Release artifact、安装脚本、镜像、CDN 和升级策略
- 第三方许可证、版权页、贡献指南和安全响应入口
- 多语言术语表、无障碍标签和屏幕阅读器文案
- 配置 schema 版本、协议能力、迁移工具和兼容期限

这些项都应通过集中配置、资源清单、版本化映射表或独立文档预留，不应散落为难以追踪的硬编码。

## 8. 迁移验收矩阵

至少覆盖：

| 场景 | 验收内容 |
|---|---|
| 新安装 | 新名称、图标、About、目录、服务和升级地址正确 |
| 旧版本升级 | 旧数据、旧脚本、旧服务和旧配对仍可用 |
| 新版本回滚 | 回滚后旧配置、旧协议和旧客户端可继续工作 |
| 跨端配对 | 旧/新 Web、桌面、移动端与 Relay 组合互通 |
| 数据迁移失败 | 自动恢复，用户数据不丢失 |
| 环境变量冲突 | 新旧变量优先级明确，敏感值不泄露 |
| 协议不匹配 | 能力协商或明确报错，不静默损坏数据 |
| 离线升级 | 安装包校验、签名和本地升级流程正常 |
| 卸载重装 | 是否保留数据、是否能恢复、提示是否清楚 |
| 法律信息 | 版权、许可证、第三方声明和来源信息完整 |

## 9. 迁移决策门

只有在以下问题都有明确答案后，才允许开始完整身份迁移：

- 新身份是否已经有合法授权和真实归属说明？
- 新旧数据目录如何备份、迁移和回滚？
- 旧 CLI、旧协议和旧客户端兼容多久？
- 移动端 ID 变化采用同应用升级还是新应用发布？
- 旧下载地址、签名、公钥和升级服务如何保留？
- 用户如何知道发生了品牌变化、是否需要操作？
- 如何验证所有平台和第三方集成没有被破坏？

如果任何一个问题没有答案，继续保持当前“新展示品牌 + 旧运行时兼容”的路线，不进入破坏性迁移。
