## 1. 这个进程是什么

`cmd/octo-desktop` 同时是**两个东西**，这是理解启动顺序的前提：

- **本机唯一的后端**：绑定固定回环地址 `127.0.0.1:8088`（`hubAddr`），在进程内跑与 `octo serve` **同一个** Web 服务，于是 Web UI / VS Code / Obsidian / CLI 全都连到这一个实例，`/api` 与 `/ws` 处理器一行不改地被复用。
- **一个原生窗口**：Wails 窗口指向该地址，提供浏览器给不了的那一层（系统文件夹对话框、托盘、开机自启、原生通知）。

它加入 `internal/serveproc` 的 `serve.pid` 协议 —— 与 `octo serve -d` 同一套 —— 这样两者不会抢端口，而是**互相接管**。

## 2. 启动顺序

顺序不是随意的：每一步之所以在那个位置，都是为了让后一步能用上前一步的结果。按 `main()` 的实际次序：

| # | 步骤 | 代码 | 为什么必须在这个位置 |
| --- | --- | --- | --- |
| 1 | 清掉不可用的 `$TMPDIR` | `ensureValidTempDir` | macOS 的 postinstall 会用 `open` 从 `installd` 的临时沙箱里拉起应用，那个沙箱早已不存在；托盘常驻进程之后任何 `os.MkdirTemp`（含更新器）都会失败 |
| 2 | stderr → `data/crash.log` | `setupCrashLog` | 该进程没有可用 stderr（Windows 是 `-H windowsgui`、macOS 从 Finder 起）。**必须在任何可能 panic 的东西之前**，且**必须在更新器辅助模式之前** —— 原地替换正在运行的安装正是那种失败需要留痕的文件操作。接在终端上时跳过（终端比无人 tail 的文件好） |
| 3 | 更新器辅助模式 | `updater.HandleHelperMode()` | 被派生的辅助子进程只负责把已暂存的更新换上去然后退出。**排在下面所有启动副作用之前**，避免在一个只为拷文件而存在的进程里做 chdir、播种 CLI、读设置 |
| 4 | cwd 钉到程序目录 | `ensureWorkingDir` → `datapath.ProgramDir()` | GUI 启动会继承 `/` 或盘符根。上游原本 chdir 到**用户主目录**，便携版钉到**程序目录**（数据根的父级），与 CLI 一致 —— 见 `P1` §3.3 |
| 5 | PATH 同步登录 shell | `shellpath.SyncToLoginShell()` | GUI 启动继承的环境往往缺 `~/.local/bin`、`/opt/homebrew/bin`。服务器在本进程内跑，stdio MCP 子进程与 shell 工具**直接继承本进程的 PATH** |
| 6 | 读 `data/serve.env` | `serveenv.Load()` | 登录 shell 给不了的变量（provider key 等）。与 `octo serve` 同一条路径，两个后端解析出同一组环境变量；缺失即 no-op，显式环境变量优先 |
| 7 | 选原生文案语言 | `applyLang()` | 原生对话框与托盘文案跟随系统 UI 语言 |
| 8 | 读 `data/desktop.json` | `loadDesktopSettings()` | 下面的 `KeepRunningInBackground`、CLI 播种版本都要用 |
| 9 | 播种 `data/bin/uv` | `ensureBundledUv()` | 需要 Python 的 skill 在"只要下载解压"的形态下也得能用 |
| 10 | 播种 `octo` CLI | `ensureBundledOcto(&settings)` | macOS 还会把该目录加进 PATH。**可能改 `settings.SeededOctoVersion`，所以必须早于第 11 步**（桥要持有设置的副本） |
| 11 | 造 `nativeBridge` | `nativeBridge{...}` | `allowQuit` 初值取 `!settings.KeepRunningInBackground` —— Windows/Linux 上关窗口默认**不许**退出 |
| 12 | 注册原生通知服务 | `notifications.New()` | macOS 的 UNUserNotificationCenter 需要 bundle id，**没有 bundle 会硬失败** ⇒ 只在 `.app` 里注册（`notificationsAvailable()`）；裸 `make desktop` 二进制只是没有原生通知 |
| 13 | `application.New` ＋ 单实例 ＋ `ShouldQuit` | `application.New(application.Options{...})` | 见 §3。产品名/口号/单实例 id 全部从 `brand.Load()` 取，代码里没有品牌字面量 |
| 14 | 配置原地更新器 | `bridge.inplaceUpdate` ← `canInplaceUpdate()` | 决定托盘的更新项走 `app.Updater` 还是下载页。**本仓不装配**（门控在 `productUpdatesEnabled`，见 §5 第 13 条）⇒ `inplaceUpdate` 恒为 `false`，于是即便有路径调到 `startUpdateFlow`，它也只会打开下载页 |
| 15 | 注册更新重启事件与通知回调 | `app.Event.On(updater.EventUserRestart, …)` | 用户的"重启以完成更新"要置 `updateRestart`，供第 13 步的 `ShouldQuit` 读到 —— 所以**必须在任何更新会话开自己的重启处理器之前**注册 |
| 16 | 造托盘 ＋ 常驻刷新 | `app.SystemTray.New()`、`go refreshTrayLoop(...)` | 无图标也无文字的状态项在 macOS 上**根本不渲染**，故明确设图标（darwin 用模板图，其它用彩色图） |
| 17 | 等 `ApplicationStarted` 再起后端 | `app.Event.OnApplicationEvent(events.Common.ApplicationStarted, …)` → `startHub` | 接管询问是**模态对话框**，需要活的事件循环。放在这里就可以"先问用户、再停别人的后端" |
| 18 | 自动更新循环 | `go autoUpdateLoop(bridge)` | 启动后 30 秒首查，之后每 24 小时。**本仓不启动**（门控在 `productUpdatesEnabled`，见 §5 第 13 条）—— 没有它就没有"新版本"通知，托盘的更新项也随之没有来源 |
| 19 | `app.Run()` | — | 事件循环 |
| 20 | 退出清理 | `serveproc.ReleaseOwned` → `srv.Shutdown`（5 秒超时）→ `closeLog` | pid 文件只在仍属于自己时才释放 —— 已经接管过端口的后继进程必须保住它自己那份 |

`startHub` 内部（第 17 步）再展开一层：

| 步骤 | 代码 | 说明 |
| --- | --- | --- |
| 已有后端在跑则先问 | `serveproc.Running()` → `bridge.confirmTakeover(pid)` → `serveproc.Stop()` | 拒绝即 `app.Quit()`。**本机只有一份后端**这条规则在这里执行 |
| 绑端口（接管后给 8 秒宽限） | `listenHub(hubAddr, grace)` | `serveproc.Stop` 只是发信号，监听器要迟一拍才关；冷启动真冲突则立刻失败 |
| 失败即对话框 ＋ 退出 | `bridge.showError(L().errBindFmt, …)` → `app.Quit()` | 需求第 6 条要的提示落在这里，**但文案与规定不同，见 §5** |
| 写 `serve.pid` | `serveproc.WritePid` | 与 `octo serve -d` 共用 |
| 打开 `data/logs/serve.log` | `setupHubLog()` | **必须等接管完成**：在接管前打开/轮转，可能在 Windows 上因文件被活着的守护进程持有而改名失败。放在 `server.New` 之前才能收住后端自己的启动日志 |
| 附件老化 | `server.StartUploadsHousekeeping()` | 桌面壳不走 `cmd/octo` 的 `runServe`，不在这里调就永远不会跑 —— **这个进程就是那件housekeeping 的长期实例** |
| 一次性装配 | `mountProductAPI()` → 5 个值 | 本地产品路由、内置网关的 sender 工厂、回合守卫的目录谓词、合规词引擎、输入门。**必须一起造**：它们要共用**同一个** `CredentialHolder`（两个就会出现网关拿着过期令牌），且谓词读的正是这里挂上路由的那份目录存储 |
| `server.New` | `server.Config{...}` | 失败同样对话框 ＋ 退出 |
| 起服务 ＋ 开窗 | `srv.ServeOn(ln)`、`bridge.showWindow()` | 窗口在服务已经接受连接之后才开 |

## 3. 单实例、端口、接管

三件事容易混，各自的机制不同：

| 要防的情况 | 机制 | 行为 |
| --- | --- | --- |
| 用户**又双击了一次**同一份程序 | Wails 单实例，锁名取 `identifiers.singleInstanceId`（`app.puddingbox.desktop`） | 第二个进程退出，已有窗口被激活（`OnSecondInstanceLaunch` → `showWindow()`） |
| 本机装过 **Octo** | 同上：单实例 id 与上游的 `dev.octo-agent.desktop` **不同** | 布丁盒子与已装的 Octo 是两个单实例，第二次双击不会把用户带到 Octo 窗口。**但端口 8088 只有一个**，于是落到下一行 |
| `octo serve -d` 或别的程序**占着 8088** | `serveproc` 的 pid 协议 | 若是本产品的前一个后端 → 问过用户后接管；若是别的程序 → 绑不上，对话框 ＋ 退出，**不改端口、不改数据根、不起第二份** |

**单实例标识的值不在这份文档里，owner 是 `branding/brand.json`** 的 `identifiers.current.singleInstanceId`（今天 `app.puddingbox.desktop`），并由 [`品牌升级方案.md`](../品牌升级方案.md) 的 `identifiers.current` / `identifiers.future` 两段机制管理"现在不动、正式发布再换"。**注意需求第 5 条正文写的 `app.budingbox.desktop` 是 §5.2.4「本期 mock 资产」里的值，而那一节自己声明「正式稿只换文件」** —— 同理 `exeName` / `portableDirName` 的 mock 是 `BudingBox.*`、实际是 `PuddingBox.*`。所以**不要照需求里那几个字面量去"对齐"代码**（那是把一份已声明为 mock 的拷贝当成了 owner，§3.8）。

## 4. 生命周期：三种离开

需求 §5.1.2 的三种离开在代码里的落点：

| 动作 | 进程 | 登录态 | 界面 | 代码 |
| --- | --- | --- | --- | --- |
| 点窗口关闭 | 仍在（托盘） | 不变 | 窗口隐藏 | `ShouldQuit` 非 darwin 时读 `allowQuit`（初值 `!KeepRunningInBackground`）；darwin 用 `ApplicationShouldTerminateAfterLastWindowClosed`；Windows 另需 `DisableQuitOnLastWindowClosed` —— 否则 Wails 的 Windows 后端在窗口表清空时**不咨询 `ShouldQuit`** 就发退出消息 |
| 托盘「退出」 | 先落盘再结束 | 保留 | 无 | `requestQuit()`：有 IM 渠道在跑时先确认（停掉会断开别的客户端），然后 `allowQuit = true` ＋ `app.Quit()` |
| 个人中心「退出登录」 | **仍在** | 清除 | 回拦截页 | 属产品门（`P3`），不经本文 |

macOS 另有一条：窗口已隐藏到托盘后点 Dock 图标触发 `ApplicationShouldHandleReopen` → `showWindow()`，否则那次点击会无反应。

- **打包形态**：便携目录里有哪些文件、图标与文件属性怎么注入、exe 叫什么 —— `P12`。本文只从"双击之后"开始讲。
- **CLI 的启动**（`octo serve`、`octo serve -d`）：本文只在"谁占着 8088"这一点上提到它。
- **开发者启动路径**（热重载、`make desktop-dev`）：见 `TODO-01`。
