### 0.2 三条被本次评审判定为「之前定错了」的事

1. **P0-00A 不能"先完成"** —— 原文结论要求"完成 P0-00A 的 UI 可见性边界"再进 P0-01，但 00A 自身的入口可见性是**由 P0-04 的能力矩阵驱动的**（`visible=false`）。所以 00A 现在能交付的只有**规则**（哪些入口首发隐藏、保留其实现），`visible` 的接线必须等 P0-04 的 capability contract 冻结。修正：§0 结论与波次表均已按此调整，00A 拆成「规则（现在）」+「接线（随 P0-04）」。

2. **M7 前端此前没有 owner，`web/` 也不在文件所有权表里** —— 模块地图把 M7 列为独立模块并说"应当尽早并行"，但工作包清单（00/00A/01/01A/02/03/04/05/06/07/08/09/10）里**没有任何一个文件承接前端**，§3 文件所有权表（P0-开发顺序与协作计划.md §3）的六行里也没有 `web/`。后果是两个 owner 可以同时改 `web/src/lib/chatMode.ts` 而无人裁决 —— 这正是本文件 §2「排期冲突判定规则」警告的情形。修正：§3 增加前端所有权行，并把 M7 的 owner 明确为**独立于后端各包**的一位前端负责人。

     > **已拍板（2026-09-11）：新增 `11-前端投影与文案.md`。** 理由是一个模块一个文件，M7 与其它工作包同构，冲突面从"§3 里一行所有权"变成"一个 owner 一个文件"。代价是编号约定从 10 扩到 11（已登记在"文件即工作包"清单与 §3）。原"先用 §3 的所有权行把冲突面消灭"的临时做法**已被 `11` 取代**；§3 的所有权行保留，用于声明"后端包不得改 `web/`"这条**反向**约束。

3. **M2 的共享信封（验签/缓存/刷新）没有单一 owner** —— §2 已经正确指出"信封验签/缓存/刷新机制只实现一次，建议放 `internal/productclient`"，但工作包清单里 `internal/productclient` 属于 P0-02，而 P0-04（目录）与 P0-06（词库）是**另外两个 owner**。这恰好命中本文件自己列的"两个 owner 要改同一份存储格式 → 模块边界划错"。修正：§3 明确 **P0-02 是信封机制的 owner**，P0-04/P0-06 只提供各自的 DTO 与合并规则，并**不实现验签**。**但 crypto 不能直接落在 `productclient` 并返回 `productpolicy.Signed`** —— `productpolicy` 已 import `productclient`（`Signed` 含 `productclient.Catalog`），会构成 import 环。因此分工是：crypto 唯一实现在 `productclient`，`Verifier` 端口留在 `productpolicy`，由 `productruntime` 的 adapter 连接（见 §3 的补注与 [P0-01 落点表](01-运行时Profile与窄端口抽象.md#合同在代码中的落点b0-已冻结2026-09-11)）。

## 2. 按功能模块切分（决定并行顺序的依据）

**并行顺序按「功能模块 + 前后端边界」切，不按文件切。** 一个模块 = 一个对外只有一处接口的职责单元；只要两个工作包要改同一份契约或同一个存储，它们就不能真并行，必须串行或在接口冻结后并行。若发现"必须改文件才能排期"，那说明模块边界划错了，应先改边界，不要改文件去迁就排期。

### 模块地图（每个模块只有一个 owner，接口只有一个）

| 模块 | 层 | 职责 | 对外唯一接口 | 工作包 |
| --- | --- | --- | --- | --- |
| **M1 身份与凭证** | 后端 client | 登录、刷新单飞、轮换、撤销、`credentialstore` | `AuthClient` + `credentialstore`（`Load`/`Save`/`Clear`；方法名以 `internal/credentialstore/store.go` 为准） | P0-02、P0-08 |
| **M2 控制面投影** | 后端 client | bootstrap、目录、能力/策略、词库、legal 的拉取、验签、缓存与刷新 | `ControlPlaneClient` + `data/catalog.json` / 词库缓存信封 | P0-02、P0-04、P0-06 |
| **M3 策略执行** | 后端 policy | 本地 PEP、`allow`/`ask`/`deny`、审计字段 | `CapabilityPolicy.Evaluate` | P0-04、P0-10 |
| **M4 模型出口** | 后端 client（在 `internal/app` 之上） | 装配网关 sender、`clientRequestId`、终态/取消/补查 | `gateway.ControlClient` + 既有 `agent.Sender` | P0-03、P0-05 |
| **M5 产品运行时** | 后端装配 | 产品 HTTP、会话前置策略、desktop 装配 | `internal/runtimeport`（中性）+ productruntime HTTP | P0-01、P0-01A、P0-05 |
| **M6 本地数据与迁移** | 后端 | `product-state.json` 拆分、`installId`、诊断白名单 | `datapath` 路径约定 + secret scanner | P0-08、P0-09 |
| **M7 前端投影与文案** | 前端 | 模型选择器、能力可见性、状态/错误码文案、legal 展示 | machine code → 文案映射表；`visible`/`entitled` projection | P0-04、P0-06、P0-10 提供数据；**实现面是 `web/`，工作包为 [`11-前端投影与文案.md`](11-前端投影与文案.md)，owner 是独立的前端负责人**（见 §3） |
| **M8 发布与验收** | 工程 | 构建标签、打包、更新/回退、contract suite、E2E、fork-drift 守卫 | `release-profile-guard`、`server-diff-guard`、`reuse-guard`（三者均已落地，`make release-profile-check` / `server-diff-check` / `reuse-check`） | P0-00、P0-07、P0-09 |

**前后端边界**：M1–M6 是后端（Go），M7 是前端（Svelte），M8 是工程。前端只能消费"machine code + projection 字段"，不得解析后端结构或自然语言消息；后端不得为迁就前端而改变状态机。这条边界已经在 DTO/错误码层面固定，不需要额外沟通。

### 依赖顺序（由模块边界推出，不是人为排期）

```text
        │
        ▼
M5 的 contract 骨架（P0-01 B0，模块接口冻结）
        │
        ├──────────────┬──────────────┬──────────────┐

        │              │              │             用 contract sample 假数据)
        └──────────────┴──────┬───────┘

                              │
                              ▼

```

**必须串行的三处（不要试图并行，否则会出现两份契约）**：

1. **M1 内部**：P0-02 的 `AuthClient` 与 P0-08 的 `credentialstore` 共管 token 生命周期 —— 先冻结 `credentialstore` 接口（P0-01 B0），再由一个 owner 串行做实现；两人分别做会得到两套刷新语义。
2. **M2 内部**：目录（P0-04）与词库（P0-06）都走控制面的签名信封 + 缓存 + TTL。**信封验签/缓存/刷新机制只实现一次**（建议放 `internal/productclient`，由目录与词库共用），P0-06 只加词库特有的合并规则与文案。分别实现会出现两套验签，其中一套必然漏掉 `audience` 或版本单调。
3. **M4 与 M3 的交接**：模型资格（`eligible`/`transport`）由 M2 产出、M3 判定、M4 执行。三者顺序固定，不要为了并行把 `eligible` 检查复制到 M4。

**可以真并行、且应当尽早并行**：M7 前端（用 contract sample 的假数据先做投影与文案）、M6 的 `installId`/secret scanner、M8 的 guard 与 CI。它们不依赖真实中台，也不改上游文件。

### 排期冲突的判定规则

| 症状 | 说明 | 处理 |
| --- | --- | --- |
| 两个 owner 要改同一个 DTO/接口 | 契约未冻结 | 回到 P0-01 B0 冻结后再开 |
| 两个 owner 要改同一份存储格式（如缓存信封） | 模块边界划错 | 抽成共享机制（如 M2 的验签/缓存），由一人实现 |
| 一个 owner 被要求"顺便改一下 server" | 越过了 M5 的 `runtimeport` 边界 | 按 §2 单一 owner 规则走例外批准 |
| 前端要等后端联调才能开工 | 前后端边界没写清 | 用 contract sample 假数据先做前端投影 |
| **为了让两个 owner 能同时开工，把同一方案拆成两份实现** | **最危险的一类**：排期压力被转嫁成架构债 | **拒绝。** 按[开发规范](../../../开发规范.md) §3.5/§3.7：先收敛为一份共享实现（如 M2 的验签/缓存），把第二个 owner 转到不重叠的模块（如 M7 前端 / M8 guard）。**调整 owner 与模块划分，不调整技术方案。** |

**元规则（本文件所有排期的约束）**：本文件的顺序、波次和 owner 划分都是**从模块边界与前后端边界推导出来的结果**，不是独立目标。

**方向不可颠倒**：本文件**不得**作为技术方案与开发计划的制定依据 —— 它不能要求"为了配合排期而改方案/改契约/复制实现"。当它与需求或方案冲突时，**改本文件**。反过来说，下面第 3 条是**唯一**允许的"排期影响开发计划"的方向，而它之所以成立，是因为**前后端边界是架构边界**（对外接口 + 数据所有权都不同），不是排期造出来的概念。

当排期与技术方案冲突时：

1. 先问"能否让 owner 去做另一个模块"（人可重排）；
2. 再问"能否用 contract sample 让下游先开工"（接口可先冻结）；
3. **为了前后端真正并行，可以适当调整开发计划本身** —— 具体做法是把接口**提前冻结**（先定 DTO / error code / projection 字段），让前端用 contract sample 的假数据先做投影与文案，后端随后补实现。这属于**调整交付顺序与接口冻结时点**，不改变契约内容。
4. **不得**为了并行而复制实现、放宽验签、绕过单一入口或新增第二套真相来源 —— 这些会保留到发布之后，而排期不会。第 3 条的正当性来自"前后端边界真实存在"，不是"两个人都要同时开工"；把第 3 条套用到"两个后端 owner 都要改同一份契约"上，就是本表最后一行警告的那种排期转嫁。

### `internal/server` 的单一 owner（消歧）

`00`（零改预算）与 `01A`（迁移 + `apiProduct` 折叠）都声明触及 `internal/server`，必须明确不冲突：

| 角色 | 职责 | 不负责 |
| --- | --- | --- |
| **profile 核心负责人（`00`）= server 写权限的唯一 owner** | 审批并合并所有对 `internal/server` 的改动；维护零改预算与 `server-diff-guard` 的登记上限 | 不实现产品业务迁移本身 |
| **`01A` 负责人** | 产出迁移与折叠的**具体 diff**，提交给 `00` owner 合并 | 不自行绕过预算、不在未登记的情况下扩大 server 改动 |

规则：`01A` 的每个 server 改动 PR 都必须由 `00` owner 在同一 PR 上确认「这是已登记的例外、行数在上限内」。`apiProduct` 折叠是**已预先批准**的例外（它的净效果是删掉 157 行改写，只增加 1 个中间件挂点），因此不需要逐次再申请；其他 server 改动仍需逐项批准。

**棘轮与迁移期的交互（本次评审补充）**：`server-diff-guard` 的上限基线**就是当前值**（`apiProduct` 161、`server.go` 484…），因此它对 `internal/server` 的**任何净增长**都会失败。这对 `01A` 是顺的（迁出与折叠只会让数字下降），但会出现一种中间态：**"先把新实现写进 server、再搬走"**。这种写法不允许 ——

- 迁出类改动要么**同 PR 内完成"加入新包 + 从 server 删除"**，让净变化为负；
- 要么先在新包里把实现做好，**最后一步才动 server**（删旧），避免出现"两处都在"的中间提交。

确实需要一次净增长时（例如某个中性中间件挂点），按 §3.4 破例流程在同一个 PR 里**下调其他上限或说明为什么该文件必须增长**，并取得 `00` owner 确认 —— 而不是直接改高上限把 CI 哄绿。**改高上限本身就是要人工确认的动作。**
