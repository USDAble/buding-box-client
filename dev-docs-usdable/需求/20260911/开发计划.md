## 2. 逐个 PR

### `PR-1` 契约层 + 中台替身 + 客户端骨架（最小范围）

**为什么三者必须同一个 PR：** 替身是客户端的**镜像**。先写替身会发明一份契约，再写客户端又发明一份，两份必然漂移 —— 正是 `§3.8` 禁止的"同一件事两处定义"。**一份 Go 类型，两个实现**，替身才具备证明力。

> **⚠️ 实施期范围修正（2026-09-11，落代码时发现，已按此实现）。** 本节原先把 JCS + ed25519 验签列在 `PR-1`。**这是错的**：`PR-1` 的四个端点（发码 / 登录 / 刷新 / bootstrap）**没有任何签名要验** —— 需要验签的是**签名目录与策略信封**。而 bootstrap 在合同里**同时返回目录**（`中台交付包` §4.1 第 5 行：账户摘要 + 权益 + 余额 + **模型目录** + 能力矩阵 + 策略版本），所以正确做法是**把 bootstrap 收敛为「账户 + 激活 + 余额」，目录与能力矩阵留到 `PR-4`**，签名代码整体下沉到 `PR-4`。理由有二：① 让 `PR-1` 不包含本题**唯一没有现成实现**的一处，符合"先走通流程、别太复杂"；② JCS 是 RFC 8785，手写一份不合规的实现比不写更危险，它应当与目录一起一次做对。**bootstrap 不带目录是合法状态，不是错误**（`B4`：目录未就绪时选择器为空 + 不可用提示）。

**做：**

1. `internal/productclient/` —— **契约层**：`dto.go`（请求/响应类型 + 错误码常量，是字段名与错误码的**唯一 owner**）+ `client.go`（4 个端点 + 内存凭证持有者 + 401 单飞刷新与一次重放，即 `PR-1` 即已落地 `L-A6`）。
2. `internal/productclient/clienttest/` —— **中台替身**：真 HTTP handler、可编排场景、含测试码重置，**与客户端共用上面那份类型**。
3. 测试：用替身驱动客户端，覆盖 `L-A1`–`L-A6` 的**客户端侧**分支。

**不做（留到后续 PR）：** **JCS + ed25519 签名/验签（下沉 `PR-4`）**、模型目录与能力矩阵（`PR-4`）、网关 SSE（`PR-5`）、词库（`PR-6`）、`/api/product/*` 本地服务（`PR-2`）、前端接线、`devBackend` 拆除、可执行替身文件。

**验收：**

- 用替身跑通 `L-A2`（二次登录**不需要**激活码与盒子编号）、`L-A5`（bootstrap 回填 `boxCode`；缺失时是空值而非报错）、`L-A6`（401 单飞刷新一次 + 重放一次；刷新被拒 → 清凭证 + `ErrSessionExpired`，不重试）。
- 四个激活错误码（`activation_invalid` / `activation_code_used` / `box_code_unknown` / `box_code_mismatch`）**各自**可被触发并断言（`L-A4`）；`phone_mismatch` 亦单列。
- 同一盒子编号 + 两个不同激活码 → **两次都成功**（`L-A1` 的一对多回归）。
- 平台完全不可达 → `network_unavailable`（与上游 5xx 区分，且**不**回落本地模型源）。
- `L-A1` 的"响应已送达但响应丢失"分支 **不实现**，登记为 `PQ25` 的未决面。

**替身的形态：**

| 项 | 定 |
| --- | --- |
| 落点 | 库 `internal/productclient/clienttest`（仓库内，测试可用），暴露 `Handler()` 由调用方用 `httptest.NewServer` 包起来。**不做**独立的可执行替身文件 —— 最小范围内它只服务 Go 测试；前端 E2E 需要它时再补（那是 `PR-2` 之后的事） |
| 隔离 | 仅被 `_test.go` 引用 ⇒ 不可能进入便携包；`PR-9` 的 preflight 加一条断言兜底 |
| 契约来源 | **import `internal/productclient` 的类型**，不重写 JSON schema |
| 签名 | **`PR-1` 不需要签名**（四个端点都不验签，见上方范围修正）。测试密钥与签名能力随 `PR-4` 的目录/策略一起引入 |
| 场景编排 | 用特定手机号 / 激活码触发特定错误码，使每个分支**按需到达**（Sandbox 做不到这点）。已内置：同一盒子编号的两个激活码（一对多）、只发给特定手机的激活码（`phone_mismatch`）、未知盒子编号、真实但对不上的盒子编号、失效访问令牌、被撤销的刷新令牌、平台不可达 |
| 重置 | `New()` 每次都是干净状态，等价于重置测试激活码，对应 `S-8` 要中台提供的那一项 |

### `PR-3` 拆除 `devBackend.ts`

**触发条件（写死，不留解释空间）：** `developer` 构建下，本地 Go 服务能真实应答 `/api/product/*`，且 `/api/product/*` 的链路可跑通 —— **即 Sandbox（或替身）通了之后**。这正是 `G5` 的判据：`rg devBackend web/src --glob '!dev/**'` 无命中。

**保留期的硬约束（`G5`）：** 若为纯 UI 开发保留，必须是**显式且默认关闭**的开关，开启时界面/日志可见；**4 个 WS 事件在它下面不可测**。

## 3. 能力检索（§3.5，强制）

**每个"新建 X"的举证责任在新建一方。** 以下四处是本题的全部"新建"。

### 3.1 中台 HTTP 客户端（`internal/productclient`）

```text
既有能力检索：internal/provider/*（4 个 sender 接口）、internal/app/sender.go、
              internal/app/provider.go（ProviderCustom = "custom" 任意 BaseURL）、
              internal/config/config.go:105 Endpoint{BaseURL, Protocol, Headers, RPM}
为什么不能复用：**【可复用，已选择复用】** 见 3.2 —— 模型通信整条链路复用既有 provider 栈。
              productclient 只承载 provider 覆盖不到的那一层：登录/激活/bootstrap 的
              信封、业务错误码、目录验签、凭证生命周期。它不是第二个 HTTP 客户端。
复用后的形态：productclient 持有 agent.Sender 的装配参数（baseURL + token），
              401 刷新后重建 sender；**不自己写 SSE、不自己写 tool-call 聚合、不自己写 usage 归一**。
参考：需求基线 C2（动态凭证注入）与 C3（复用既有 provider 栈）已写明此结论，本文不复述推理。
```

### 3.2 网关流式调用 —— 本题最容易写重的一处

```text
既有能力检索：internal/provider/openai/{client.go,stream.go}（SSE 分帧、tool_calls[i].index
              碎片拼接、stream_options.include_usage、usage 归一）、
              internal/app/sender.go:228 openai.New(apiKey) + Client.BaseURL 覆盖
              （client.go:103 "optional override"）、Client.Headers（config 静态头）
为什么不能复用：**能复用，复用**。网关说 OpenAI 协议 ⇒ `BaseURL` 指向网关 + `Headers` 带网关头，
              就是一个标准 chat/completions。**不新建 SSE 解析器**（`finish_reason` 归一、
              工具调用碎片、`prompt - cached` 都已在 stream.go 里做对）。
              唯一缺口见下。
复用后的形态：**一处窄增量** —— `Endpoint.APIKey` 与 `Headers` 都是**构造期静态明文**
              （config.go:126 明写 "Values are static plaintext；no env-var interpolation"），
              而网关需要**每请求注入轮换的会话令牌**。故需一处"动态认证注入"口子，
              按 C2 规则 2 用「用当前内存 token 装配 sender」实现，**不改 provider 的解析逻辑**。
```

> **这直接回答了一个反复出现的问题**：「不是已经有 Claude / OpenAI 的对接机制了吗，直接用不就行了？」——**是的，就是直接用**，`BaseURL` + `Headers` 已经支持任意网关。本题**只有一处**真正需要新写：动态令牌注入（C2）。其余全是复用。

### 3.3 JCS 规范化 + ed25519 验签（**唯一没有现成实现的一处**）

```text
既有能力检索：internal/productprofile/profile.go —— 已是信任锚的 owner：
              TrustedKeyIDs map[string]string（keyId → base64 ed25519 公钥）、
              validateTrustedKeyIDs()（profile.go:191，校验 base64 与 ed25519.PublicKeySize）。
              internal/upgrade/upgrade.go:6 —— "there is no signature layer"（升级清单不验签）。
              全仓 grep：**无 JCS / RFC 8785 规范化实现；无 ed25519 验签调用**。
为什么不能复用：信任锚可复用，**规范化与验签无可复用实现**。但**不得**让签名方与验签方
              各写一份 —— 两份会漂移，结果是"替身测试全绿、生产验签失败"。
复用后的形态：复用 productprofile.TrustedKeyIDs 作信任锚；JCS+ed25519 只写**一份**
              （`internal/productclient/signing.go`，**随 `PR-4` 的目录/策略落地**），
              **替身签名与客户端验签共用同一实现**。
```

### 3.4 中台替身（`clienttest`）

```text
既有能力检索：web/src/dev/devBackend.ts（前端假后端，替换 globalThis.fetch）、
              httptest（.octorules 指定的 HTTP 测试方式）、
              internal/productclient（PR-1 新建，替身的类型来源）
为什么不能复用：devBackend 顶替的是**本地 /api 边界**，替身顶替的是**中台边界** ——
              不同层，不可互换（E2E闭环清单 §4 已写明这处易混淆点）。
              devBackend 是 TS/前端，无法驱动 Go 侧代码路径。
复用后的形态：**import productclient 的类型**做服务端，不重写 schema。
```
