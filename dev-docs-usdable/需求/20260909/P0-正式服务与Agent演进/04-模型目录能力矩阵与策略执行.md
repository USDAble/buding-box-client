## 开工前置（第一条就是检查公钥已注入）

本工作包**不能**在 `trustedKeyIDs` 为空时开工 —— 没有受信公钥就无法验签，整个"本地策略执行点"退化成"什么都验证不了"。因此开工前逐条确认：

1. **[ ] `internal/productprofile/profiles/production.json` 的 `trustedKeyIDs` 已注入中台签名服务的公钥**（至少一把、建议两把以备轮换），且 `make release-config-check` 不再报空 store。**owner 是中台/服务端**（公钥内容不是客户端研发能决定的），时间点就是这里 —— 而不是等出包时被 advisory guard 提醒。注入 owner/时间点/未注入时的行为见 [P0-01 §1 的「注入 owner 与时间点」表](01-运行时Profile与窄端口抽象.md)。
2. [ ] 中台已按「发给中台的控制面交付要求」给出 policy contract sample（含**真实版本串格式**）。注意版本号是 `2026-09-10.1` 这类**日期点分数字**而非 semver —— 比较器的语义见 `internal/productpolicy/policy.go` 的 `CompareVersions`，拿到 sample 后先确认它。
3. [ ] 确认 `publicKeys` 的轮换语义：新公钥入表后，老客户端在**旧 policy 未过期**期间是否仍被接受（轮换不能造成一次全量失效）。

## 目标

让模型、隐藏菜单、MCP、技能、连接器、后台任务等都由同一份外部能力矩阵驱动，并在客户端的本地策略执行点完成最终判定。功能可保留而菜单暂不出现；但隐藏 UI 不可以成为权限边界。

## 发给中台的控制面交付要求（本仓库不实现）

1. bootstrap/catalog 以签名 policy envelope 下发 `available`、`visible`、`entitled`、`permissionPolicy`、`minClientVersion`、`policyVersion`。
2. model 仅下发 `id`、能力、上下文/输出上限、模式、资格、价格版本、展示字段；`transport` 固定 `gateway`。任何 provider URL/key 出现都视为协议错误。
3. 策略 scope 预留 `user`、`team`、`org`，P0 先实现 `user`；所有配置变更应有操作者、时间、策略版本和灰度条件审计。
4. 词库版本与能力策略同属控制面但独立 TTL；词库失败不影响菜单，菜单/策略失败不影响本地安全默认拒绝。

## 当前仓库开发任务：本地策略执行

1. 在工具调用前统一调用 `CapabilityPolicy.Evaluate`，输入包含会话、能力、目标路径/域名、是否后台、策略版本；返回 `deny`、`ask` 或 `allow`。
2. 文件写、终端执行、新域名外发、安装扩展、后台/定时任务默认 `ask` 或 `deny`。模型输出的 tool call 永远不是用户授权。
3. 对运行中的长任务记录启动时策略版本；每个高风险步骤按当前有效策略再次校验。策略过期且不能刷新时，只允许低风险本地只读动作。
4. UI 读取 `visible` 决定露出，执行层读取 `entitled + permissionPolicy` 决定能否做。两者必须有独立单测。
5. 落地「模型目录的本地缓存与刷新」（见下节）：验签、原子写、启动异步刷新 + TTL 周期刷新 + 陈旧时按需刷新，并把目录 `model[].modeIds` 投影为 `chatmode` 分组。

## 模型目录的本地缓存与刷新

正式模型列表**只**来自中台签名目录（`ControlPlaneClient.Models()`）；客户端不内置名单、不从 `config.yml` 读取、不回落到 `internal/provider/local`。但目录必须能在断网/首次启动竞态下可用，因此在本地保存一份**已验证的签名快照**。

### 存什么、存哪里

```text
data/
├── catalog.json            ← 受信目录快照（原始签名信封，未解包的密文/签名字节按中台格式原样保存）
└── chat-modes.json         ← 不再由出厂预置；由目录的「模式」字段投影生成，只作为用户可编辑的分组覆盖
```

- **不进 `config.yml`**：`config.yml` 是用户可写的普通配置，不能承载"受信快照"。目录缓存必须是独立文件，且**写入只由验签通过后的客户端逻辑发起**（用户手改它无效 —— 验签会失败）。
- **保存原始信封**，不保存解包后的结构：验签需要原始字节；只存解包结果会让"重新验签"变成不可能。
- 写入用**临时文件 + rename** 的原子替换，避免断电留下半份 JSON。
- 单文件带 `schemaVersion`，便于后续迁移。
- **验签不由本包实现**：crypto（ed25519 + JCS 归一 + `signature` 剥离 + `keyId` 查表）的唯一实现在 `internal/productclient`（owner 02）；`productpolicy.Verifier` 只是端口，由 `productruntime` 的 adapter 装配。本包保留 audience / 时间窗口 / 版本单调判定，不得再写第二套验签（[P0-01 落点表](01-运行时Profile与窄端口抽象.md#合同在代码中的落点b0-已冻结2026-09-11)）。

### 归属定案：五段，各一个唯一 owner

早先 `04` / `09` / `架构演进评审` 对 `data/catalog.json` 的"载体包"给了三种说法（`internal/productclient` / `internal/productpolicy`），后果是 P0-02 与 P0-04 都会认为对方该写文件。定案如下，**其他文档只引用本节，不得再声明归属**（§3.8）：

| 段 | 干什么 | 代码位置（唯一 owner） |
| --- | --- | --- |
| ① 取 | 条件请求（`If-None-Match` / `knownVersion`）、信封解码 | `internal/productclient`（owner 02） |
| ② 验签 | ed25519 + JCS 归一 + `signature` 剥离 + `keyId` 查表 | `internal/productclient`（owner 02，**唯一实现**） |
| ③ 判定 | `audience` / 时间窗口 / 版本单调 / 过期语义 | `internal/productpolicy`（owner 04，不含 crypto） |
| ④ 落盘 | 原始信封的原子写（临时文件 + rename） | **端口声明在 `internal/productclient`（`SnapshotStore`），文件系统实现与路径在 `internal/productruntime`** |
| ⑤ 刷新调度 | 启动异步 / TTL 周期 / 陈旧按需 / 换账号强制（见下节时机表） | `internal/productruntime`（由 owner 04 交付，位置固定在装配根） |

**路径怎么进来**：`productclient` 是叶子包，**不解析数据路径**（[开发规范](../../../开发规范.md) §3.1 —— 不许自己解析数据路径，一律走 `internal/datapath`）。数据根由装配根用 `internal/datapath` 解析后注入 `SnapshotStore` 实现。所以"谁把 data root 注入进来"的答案是**装配根，不是 02**。

### 缓存信封（客户端侧记录，附加在原始信封旁）

| 字段 | 用途 |
| --- | --- |
| `catalogVersion` | 用于 `Models(ctx, knownVersion)` 的条件请求（`If-None-Match` / 版本比较） |
| `fetchedAt` | 刷新调度与"asOf"展示 |
| `expiresAt` | 中台下发的有效期；**这是能否在离线时使用的唯一依据** |
| `signature` / `keyId` | 验签；`keyId` 用于密钥轮换 |
| `audience` | 必须等于本产品的受信标识，防止跨产品重放 |

### 刷新时机

| 时机 | 行为 | 失败处理 |
| --- | --- | --- |
| **启动** | **异步**触发一次刷新（不阻塞窗口/首屏；有缓存就先用缓存） | 静默重试；不阻塞启动，不写用户文件 |
| **定时** | 按 `expiresAt` 的 TTL 调度（建议 TTL 的 1/2，带抖动），进程存活期内周期刷新 | 指数退避；连续失败只上报诊断，不降级到本地模型 |
| **按需（陈旧时）** | 新会话/换模型前若缓存已过期，先尝试刷新，成功再用 | 刷新失败 → **不得**用陈旧目录开新回合，按下方"过期语义"处理 |
| **登录/换账号** | 强制刷新（不同账号 `entitled` 不同） | 未刷新成功前不展示模型选择器，展示"目录暂不可用" |

刷新是**幂等**的：拿到 304 或同一 `catalogVersion` 时不重写文件。

### 过期语义（与 §3.9 一致）

| 缓存状态 | 允许的行为 |
| --- | --- |
| 有效（未过期 + 验签通过） | 正常使用；离线也可用（R4：只可使用最后一次有效缓存所允许的能力） |
| 已过期、刷新失败 | **不开启新回合**；只允许低风险本地只读动作；UI 明确提示目录过期 |
| 验签失败 / `audience` 不符 / 时钟窗口异常 | **fail-closed**：直接拒绝（视为无目录），不得使用该快照 |
| 无缓存（首次启动且未联网） | 模型选择器不可用；不回落到 `internal/provider/local` 或 `config.yml` |

**硬规则**：任何一条降级路径都不得把"目录不可用"变成"使用本地模型"。这是 R4 的核心断言，P0-05 与 P0-07 各有一条用例覆盖。

### 与 `chatmode` 的关系

**现状（2026-09-11 已改）**：`chatmode.Builtin()` 现在**不含任何模型 id** —— 只返回 `privacy` / `smart` / `default` 三个模式 id。原因与后果见 `P0-开发顺序与协作计划.md` §5.1：原来的 4 个 `buding-*` 依赖已删除的 `ensureLocalEndpoint()` 种入，出厂态因此列出 4 个选不中的模型（含 `default` 的 `defaultModel`），属于缺陷而非过渡态，故已删除。

因此 P0-04 **不是"顺手清理假 id"，而是补上唯一缺失的一环**：把模型填回模式里。

**投影规则（P0-04 实现规格）**：

```text
目录 model[].modeIds    →  模式分组成员（privacy/smart/default）
目录 model[].id         →  模式成员 id（即请求时上报的 `modelId`，同一个值）
目录 model[].displayName →  模式成员展示名（**唯一来源**，见下）
目录 model[].default?   →  模式默认项（目录里标了默认的那个）
用户 data/chat-modes.json（若存在）  →  仅覆盖分组顺序/默认项，不得引入目录外的 id
```

> 字段名只有一套：**目录 DTO 里叫 `id`**（[中台交付包 §4.3](../产品客户端与中台对接/中台交付包.md)），**网关请求体里叫 `modelId`**（同文件 §5.1）—— 同一个值在不同报文里的名字，不是两个字段。文档与实现都不得再造 `model[].modelId`、`model[].modes` 一类别名（§3.8）。

具体约束：

1. **模式 id 不变**：`privacy`/`smart`/`default` 仍是产品固定的三个组（`internal/chatmode` 的常量是唯一来源，§3.8）。投影只填 `Models`、`DefaultModel` 和每个成员的 `DisplayName`。
2. **成员来自目录，不来自本地**：模式里的每个 id 都必须在**当期签名目录**中存在；目录里没有的 id 一律**丢弃**，不得展示为可选模型。
3. **展示名只来自 `displayName`**：`internal/chatmode` 的投影必须把目录的 `displayName` 带到成员的 `DisplayName`，前端**原样渲染**。前端**不得**保留按模型 id 查本地 i18n 的名称表 —— 中台改名后本地表会继续显示旧名，且它会在同一 id 上覆盖服务端展示名（[中台交付包 §4.3](../产品客户端与中台对接/中台交付包.md)）。**唯一例外是 debug/test**：developer 构建、契约测试在无可用目录时回退到 `id`，该回退不进 production 渲染路径。**模式的展示名不受此约束**，仍走本地 i18n（`mode.<id>`）：模式是产品固定的三个组，不是中台下发的数据。
4. **用户文件只做覆盖，不做新增，且不得清空投影**：`data/chat-modes.json` **只在用户自己创建时存在**（客户端不再种出它，见 §3.9.1），其作用是调整分组顺序与默认项；其中出现目录外的 id 时，记录一次提示（沿用 P9 §9 的"损坏/异常提示一次"策略），**不写入投影结果**。关键边界：**用户文件的空 `models` 不得把投影结果清空** —— 投影以目录为基线，用户文件只在目录 id 范围内做筛选/排序/定默认；否则一个新装的空文件会表现为"选择器全空"。
5. **`CompositeID` 继续由 endpoint 解析**：`handleGetChatModes` 现有的 `compositeIDForModel()`（`<endpoint>::<model>`）保持不变 —— 它是"这个模型当前能不能被选中"的唯一判定，不要为投影另写一套。
6. **出厂默认模型**：需求 §8「出厂默认模型为云端智能」的验收**转移到本任务**。在目录尚无数据时，模式成员为空、`DefaultModel` 为空，这是正确状态（selector 显示空组），**不得回退到任何硬编码 id**。
7. **不为投影新起一套包**：投影逻辑放 `internal/chatmode`（它已是模式分组的唯一 owner），目录读取走 M2 的 `internal/productclient`。`internal/chatmode` 不得自己发 HTTP、不得自己验签（§3.5 / §3.8）。

## 验收

- `visible=false, entitled=true` 时功能代码保留但菜单不显示；灰度后可显示。
- `visible=true, entitled=false` 时用户能看到入口但服务/本地执行被拒绝并有可理解提示。
- 外部网页/附件中的提示注入无法改变 policy 或让工具越权。
- 签名错误、过期、低版本不兼容的策略不扩权；MCP/技能/cron 均覆盖。
- **目录缓存覆盖四种状态**：有效（含离线可用）、已过期且刷新失败（不开启新回合）、验签失败（fail-closed）、无缓存（不回落到本地模型/`config.yml`）。
- **刷新调度覆盖三种时机**：启动异步刷新不阻塞首屏、TTL 周期刷新、陈旧时按需刷新；304 不重写文件。
- 模式分组来自目录投影：用户 `chat-modes.json` 中的目录外 id 不出现为可选模型。
- **展示名只来自目录 `displayName`**：目录改名后选择器立即显示新名（无需改前端）；全仓检索证明 `web/` 里不存在按模型 id 查本地名称的表（`model.<id>` 一类），且投影出的成员带 `DisplayName`；无目录时（debug/test）回退到 `id`，该回退不出现在 production 渲染路径。

## 合并策略与外部依赖

P0-01 先冻结 capability DTO 和接口边界；客户端先定义 capability ID 常量表（**id 的唯一登记表是[中台交付包 §4.4](../产品客户端与中台对接/中台交付包.md)，本文件与代码常量表都只引用它，不另列清单**）、已签名 policy contract sample、`productpolicy` mock 与 PEP 单测。中台按同一份 contract sample/签名规则在其仓库实现控制面。菜单改动、工具 PEP 改动、catalog client 分 PR 合并，最终由 P0-07 使用 sandbox 做组合验证。
