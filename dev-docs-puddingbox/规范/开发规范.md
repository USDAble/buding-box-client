# 开发规范

> 本 fork 的工程边界。`.octorules`、`CLAUDE.md` 与本文件同等生效：前两者规定上游项目的通用工作方式，本文件只补充本 fork 的约束。冲突、范围不清或需要扩大改动时，先说明选项并等待确认，不凭猜测推进。

## 规则放在哪里

- 上游项目结构、代码风格、通用测试、分支和提交流程：`.octorules`、`CLAUDE.md`。
- 本 fork 的数据、品牌、上游同步边界：本文件。
- 新建或重写 fork 文档的写法：`文档规范.md`。
- 上游同步流程：`上游合并策略.md`。

不要复制这些文档的内容来“补充说明”；规则只保留一个权威版本。

## 三条硬规则

### 数据路径只能由 `internal/datapath` 决定

业务代码不得自行用用户目录、可执行文件目录、当前目录或环境变量决定产品数据位置。读取、创建、迁移和清理产品数据都经 `internal/datapath` 的公开接口；只读查询不能意外创建用户文件或目录。

测试夹具、构建脚本或明确的非产品数据是唯一例外，必须在变更说明中写清原因和范围。运行 `make datapath-check`。

### 用户可见品牌只能来自品牌配置

不得在产品代码、UI、脚本或发布物中新增硬编码品牌名、域名、Logo 路径或产品文案。使用 `branding/brand.json`、生成的访问器和本地化资源；仅当它是上游协议或兼容标识时才保留共享上游名称。

例外必须说明为何不能配置化。运行 `make brand-check`。

### 改上游文件必须标记 fork 原因

只要本 fork 改变上游基线文件的行为或内容，就在改动附近以该语言的原生注释写：

```text
OCTO-FORK: <保留此改动的具体原因>
```

标记写原因，不写文档路径或章节号；一个标记只覆盖相邻、同一目的的改动，不能掩盖无关变更。运行 `make marker-check`。

## 设计与实现

- 架构和可维护性优先于功能范围和交付速度；结构不成立时缩小范围或先澄清，不以“先能跑”为理由留下第二套实现。
- 先找既有实现、模型和入口。能扩展现有所有者时，不新建第二套状态、路由、配置或降级逻辑。
- 每项可见行为只有一个事实源和一个所有者；跨层传递依赖，不让低层反向读取产品状态。
- 降级必须有明确触发条件、用户可见结果和可测试边界；不能吞错后静默换路径。
- 测试替身只表达真实契约；仅用于人工调试的开关、转发和故障注入留在开发工具，不进入产品或契约实现。
- 改上游文件时，优先把 fork 逻辑放进新增文件或独立区块，让上游文件只保留薄接线；需要隐藏上游功能时，优先让它不可达而非删除代码。

以下情形先写方案并与用户确认：数据迁移、权限或安全、账户/积分、公开 API、破坏兼容性、跨端体验、大范围重构，或无法复用既有实现。方案至少说明范围、非目标、备选项、风险、上游影响和验证方式；实现改变方案时，同步回写当前结论。

需求、代码和测试互相矛盾时，先暴露矛盾，以用户确认的行为为准；不得只改其中一个位置让矛盾暂时消失。

## 评审与验证

每个变更在提交前回答：

1. 单一所有者和入口是什么？为什么不能复用现有实现？
2. 是否触及硬规则、上游文件或公共行为？例外、标记和守卫是否齐全？
3. 失败、迁移和降级时用户会看到什么？
4. 哪些自动测试和必要的端到端或手工路径证明它可用？

运行与改动相称的定向测试；涉及 Go 行为时运行相关包测试，交付前运行 `go test ./...`。首次在一个 clone 开发时运行 `make hooks-install`：提交执行快速守卫 `make quick-check`，推送执行完整 `make gate`。同时运行受影响的守卫；触及数据路径、品牌、文档引用或上游标记时，分别运行对应的 `make *-check`。不能运行的验证必须说明原因和影响，不得伪造“已通过”。

## 完成定义

完成不是“代码能编译”，而是：行为符合已确认范围；所有者清楚；测试和守卫通过；用户可见变化已验证；相关主题文档按 `文档规范.md` 更新；没有无说明的兼容性、数据或安全风险。

## 非目标

- 不取代 `.octorules`、`CLAUDE.md` 的上游规则。
- 不重复分支命名、提交格式、PR 模板或历史决策台账。
- 不用规则替代需要用户确认的产品判断。
