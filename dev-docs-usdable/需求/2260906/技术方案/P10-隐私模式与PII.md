## 1. 目标与非目标

**目标**

1. 隐私模式下三处持续提示（输入框上方细条、模型芯片标签、侧栏会话盾牌），切走全部消失。
2. PII 脱敏：仅隐私模式，仅 11 位大陆手机号，仅作用于「发给模型的副本」。

**非目标**

- 不做身份证 / 银行卡（需求 §7、§10 T12 明确本期不做，**文案上也不能承诺**）。
- 不做敏感词（P7/P8，两套独立）。
- 不做 Toast 式提示、不做可关闭的提示（需求 §5.6.1 三个「不得」）。

## 3. 设计

### 3.1 三处提示

需求 §5.6.1 要求「持续可见、不得用会消失的 Toast、不得让用户永久关闭、不得用挡住输入的全屏条」，三处同时存在，切到智能/默认全部去掉。

```
┌─────────────────────────────────────────────┐
│ 侧栏                │ 主聊天区                │
│  ┌───────────────┐  │                        │
│  │🛡 关于报销的会话│  │  …气泡…                │
│  └───────────────┘  │                        │
│   ↑ ③ 会话标题盾牌  │ ┌──────────────────────┐│
│                     │ │🛡 隐私模式：发送前会 ││ ← ① 细条
│                     │ │   处理手机号等个人信息│ │
│                     │ ├──────────────────────┤│
│                     │ │ [ 输入框            ]││
│                     │ ├──────────────────────┤│
│                     │ │ [🛡隐私 本地通用 ▾] ││ ← ② 芯片标签
│                     │ └──────────────────────┘│
└─────────────────────────────────────────────┘
```

三处都由同一个 `$sessionMode === 'privacy'` 驱动，不各自判断。

**① 细条**（`PrivacyBar.svelte`）：

- 位置：输入框**正上方**，走 P6 的 `ComposerNotices` 的 `slot: 'above'`。
- 主文案（需求逐字）：「隐私模式：发送前会处理手机号等个人信息。」
- 可展开一行（需求逐字）：「只处理随后发给模型的内容；你在对话框里看到的仍是原文。本期演示 11 位手机号。」
- 展开/收起是**展示细节**，不是关闭 —— 收起后细条主体仍在。
- 不可关闭：不渲染任何关闭按钮。

文案里**只提手机号**，不能出现「证件号」「银行卡」（需求 §5.6.2 末句 + §8 验收「细条文案只提手机号，不提证件号/银行卡」）。在 `i18n.ts` 该行加注释说明这是验收项，防止后来有人「补全」。

**② 芯片标签**：芯片上加「隐私」标签；选择器里当前分组同样可见（P9 的 `ModeMenu` 已有分组头，加盾牌图标即可）。

**③ 侧栏盾牌**：会话标题旁小盾牌，用于区分多会话。需要会话列表数据里带 `chatMode` —— `GET /api/sessions` 的响应加该字段。

### 3.2 PII 脱敏规则

需求 §5.6.2：「在文本中找出连续 11 位数字（**先按 §5.3.2 去掉空白与短横线**，再认 `1` 开头的 11 位），将中间 4 位改为 `****`」。

这里有个坑：需求说「先去掉空白与短横线」，但输出必须是**用户原文的脱敏版**，不能把空格和短横线也一并删掉 —— 那样发给模型的文本就变形了。所以和 P7 一样，需要**索引映射**：

```
原文:      "我的电话 138-0000-1234 请存"
                     │
        ① 去空白与短横线（记录映射）
                     ▼
规范文:    "我的电话13800001234请存"
                     │
        ② 找 1 开头的连续 11 位数字
                     ▼
命中:      规范位 [4,15)
                     │
        ③ 映射回原文 → 原文区间，中间 4 位数字替换为 ****
                     ▼
输出:      "我的电话 138-****-1234 请存"
```

「中间 4 位」指的是这 11 位数字里的第 4–7 位（0-based `[3,7)`），按需求给的例子 `138****1234` 确认：前 3 位 + 4 个星 + 后 4 位。原文里这 4 位数字可能被短横线分开，逐个数字替换、保留其间的分隔符是最忠实的做法。

> **已定（2026-09-07）**：`138-0000-1234` 脱敏后是 `138-****-1234`（保留短横线）。因为需求要求的是「将中间 4 位改为 `****`」，改的是数字不是整段。

同一条文本里多处手机号都处理（需求明确）。

**复用 P7 的索引映射基础设施**：`internal/sensitive/normalize.go` 里的映射逻辑抽成可复用的小工具，PII 用不同的「删除字符集」（只删空白与短横线）调用它。两套规则独立（需求 §5.5 末段），但底层的「规范化 + 映射回原文」机制共享，避免写两遍最容易出错的代码。

### 3.3 三份文本的去向

需求 §5.6.2 的表是本 PR 最容易实现错的地方：

| | 合规敏感词（P8） | 隐私模式 PII（本 PR） |
|---|---|---|
| 用户气泡 | 替换后的文本 | **用户原文** |
| 交给模型 | 替换后的文本 | 脱敏后的文本 |
| 本地历史 | 与界面一致（替换后） | **原文** |

即：敏感词是「三处一致地替换」，PII 是「**只有发给模型的那一份**被改，气泡和历史都是原文」。

实现上意味着 PII 脱敏必须发生在**构造 provider 请求的那一刻**，而不是在写入 `Message` 之前：

```
用户输入原文
  → P8 敏感词检查（命中则停）
  → 写入 Message（原文）→ session.Save() 落盘（原文）→ 推给前端渲染气泡（原文）
  → 【本 PR】构造发给模型的消息副本时脱敏  ←── 唯一的脱敏点
  → provider
```

放在 `internal/app` 的 Sender 装饰器里（与 P8 的 `filteringSender` 同一层，但方向相反：P8 过滤**入站**的模型输出，本 PR 脱敏**出站**的用户输入）。两个装饰器叠加：

```go
sender = WrapPII(WrapSensitive(base, engine))
```

装饰器需要知道当前会话是不是隐私模式 —— 通过一个 per-turn 的上下文值传入，而不是让装饰器去查会话（装饰器不该依赖 session 包）。

### 3.4 与敏感词的执行顺序

需求 §5.5 末段：「先做输入合规检测（用户可关）；通过后，若当前会话是隐私模式，再对『发给模型的副本』做 PII（用户不可关）。两套独立，关敏感词不会关掉 PII。」

顺序固定，且 PII 无开关。`prefs.inputSensitiveCheck`（P8）**不影响** PII —— 这条要有测试固定住（需求 §8 明确验收「关输入检测后隐私模式 PII 仍在」）。

## 6. 测试

**Go 单测**

| 输入 | 期望 |
|---|---|
| `13800001234` | `138****1234` |
| `138 0000 1234` | `138 **** 1234`（保留空格） |
| `138-0000-1234` | `138-****-1234`（保留短横线） |
| `138-00-00-1234` | `138-**-**-1234`（中间 4 位被短横线拆开，逐个数字替换、保留分隔符） |
| `我的是13800001234，他的是13900005678` | 两个都脱敏 |
| `23800001234` | 不变（非 1 开头） |
| `1380000123` | 不变（10 位） |
| `138000012345` | 不变（12 位连续数字，不是 11 位手机号） |
| `+8613800001234` | `+86138****1234`（`+86` 前缀保留，中间 4 位打码。已定 2026-09-07） |
| `""` | 不变 |

- `WrapPII` 在非隐私模式下**完全不改动**文本（逐字节相等断言）。
- 隐私模式下：发给 provider 的消息脱敏，而 `session.Messages` 里存的是原文（这条是需求表格的直接验收）。
- `inputSensitiveCheck: false` + 隐私模式 → PII 仍生效。
- **装饰器叠加顺序**：`WrapPII(WrapSensitive(base))` 组合后，出站请求的用户文本被 PII 脱敏（手机号 `138****1234`）、入站模型输出被敏感词打码，两者各司其职、互不串扰（含手机号的模型输出不被 PII 改写，含敏感词的用户输入不被输出过滤器改写）。此条把 §9「顺序写进测试固定」落到实处，防止将来有人调反。

**前端单测**

- `sessionMode === 'privacy'` → 三处提示都在；切 `smart` / `default` → 三处都消失（一次断言三个，防止漏掉某一处）。
- 细条无关闭按钮。
- 细条文案不含「身份证」「银行卡」/ "ID card" / "bank card"（**字符串断言**，把验收项固化成测试）。

**手工验收**

1. 隐私模式下发一条含手机号的消息 → 气泡里是原文。
2. 抓请求（或看日志）→ 实际发给模型的是 `138****1234`。
3. 重启后看历史 → 仍是原文。
4. 切到智能 → 三处提示全消失。

第 2 条的**权威验证是 Go 单测**（上方「隐私模式下：发给 provider 的消息脱敏」已直接断言装饰器出站副本）。手工验收的可视化手段**可选**：P11 已合入则看 `data/logs/local-provider.jsonl`；未合入则用任意抓请求的代理或临时日志。**P10 验收不依赖 P11**。

## 9. 风险与决策

| 项 | 处理 |
|---|---|
| `138-0000-1234` 的脱敏形态 | 已定（2026-09-07）：保留分隔符，见 §3.2 |
| `+86` 前缀号码是否脱敏 | 已定（2026-09-07）：是（去掉空白短横线后 `+8613800001234` 里含 1 开头的 11 位） |
| 误伤 11 位数字（订单号等 1 开头） | 需求只定义了这一条规则，接受误伤。用户气泡里是原文，损失有限 |
| 装饰器叠加顺序 | `WrapPII(WrapSensitive(...))` —— PII 在最外层，最后作用于出站请求。顺序写进代码注释并测试固定 |
| 三处提示漏掉一处 | 前端测试一次断言三处，且切模式时断言三处都消失 |
