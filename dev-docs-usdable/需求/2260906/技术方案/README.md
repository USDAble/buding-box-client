## 2. 每份方案的固定结构

写方案和评审方案都按这七节走，缺节视为方案未完成：

1. **目标与非目标** — 非目标要写，防止 PR 越界。
2. **现状（代码事实）** — 必须给出 `文件:行号`，禁止凭印象描述上游行为。
3. **设计** — 结构、时序、状态机。
4. **接口与数据结构** — Go 签名 / TS 类型 / JSON schema / HTTP 路由，落到可直接编码的粒度。
5. **改动清单** — 逐文件列「新增 / 改写 / 删除」，这份清单就是 PR 的自查表。
6. **测试** — 单测点 + 手工验收步骤。
7. **上游合并影响** — 见下节，这是本项目区别于普通项目的必填项。

另加「验收对照」小节，把需求 §8 的验收条目一条条映射到本 PR，避免验收时找不到责任人。

## 3. 上游合并影响分级

本仓库是 `octo-agent` 的 fork，会持续从上游拉更新。每份方案必须自评一个等级并写清缓解手段：

| 等级 | 含义 | 要求 |
|---|---|---|
| 低 | 只新增文件 / 新增包，几乎不碰上游文件 | 写明新增路径即可 |
| 中 | 改上游文件，但改动集中在少数几个函数 | 列出被改函数，加 `OCTO-FORK:` 注记 |
| 高 | 改动散布在几十个上游文件里 | **必须**先做一层收口抽象，再机械替换；并配 CI guard 防回潮 |

判定为「高」而没有收口抽象的方案不予通过评审。P1 与 P8 是本期仅有的两个高等级项，也是最容易在下一次上游合并时被整体冲掉的两处。

## 4. 术语

沿用需求 §3。本目录额外约定：

- **数据根** — `data/`，代码里一律通过 `internal/datapath` 取。`~/.octo` 与 `os.UserHomeDir()` 决定业务路径的写法**全部删除**，CLI 也一样（P1 §1 决策）。
- **程序目录** — 可执行文件所在目录，`datapath.ProgramDir()`。
- **账户面板** — 需求里叫「个人中心」。2026-09-07 评审把形态从「右侧滑出三分之一」改成「左侧同宽浮层覆盖 Sidebar」，代码与本目录用「账户面板 / AccountPanel」这个名字，引用需求条款时仍写「个人中心」。见 P5 §2.1。
- **窗口令牌（window token）** — 桌面 webview 与后端之间的进程内随机凭证，产品门用它区分「桌面窗口发起的请求」与「本机其它 loopback 进程」，见 P3。
- **机器门 / 产品门** — 需求 §1.2，代码里分别是 `internal/server/auth.go` 与新增的 `internal/productgate`，两者是并列中间件，不互相替代。
