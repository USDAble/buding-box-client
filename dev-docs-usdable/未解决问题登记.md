## 登记约定

- **什么该登记**：评审或真机测试中发现的行为偏差 / 边界场景，当前有兜底方案、
  但不满足「最正确」的实现，且不值得为此引入新依赖或新复杂度。
- **什么不登记**：已经立项进某个 PR 的功能（那属于需求，进 `开发计划.md`）；
  已经修完的 bug；纯代码风格问题。
- **每条的格式**：`编号`、`标题`、`发现日期`、`状态`、`根因 / 影响`、`当前兜底`、
  `何时重新评估`。
- **状态**：`待评估` → `已解决（见 commit）` → `不再适用（原因）`。解决时把条目
  标记为已解决并保留，不删除，方便追溯。
- **何时重新评估**：相关 PR 合入、或上游合并带回新信息、或真机测试复现时。

## 登记列表

### U-001 WebView2 检测依赖注册表，存在误判

| 项 | 内容 |
|---|---|
| 发现日期 | 2026-09-08 |
| 状态 | 待评估 |
| 位置 | `cmd/octo-desktop/webview2_windows.go` 的 `webview2Available()` |

**根因 / 影响**

当前检测读注册表
`HKLM\SOFTWARE\Microsoft\EdgeUpdate\Clients\{F3017226-FE2A-4295-8BDF-00C3A9A7E4C5}`
的 `pv` 值判断 WebView2 Evergreen Runtime 是否安装。注册表读取在两种边界场景会误判：

1. **key 存在但运行时已损坏 / 卸载残留**：注册表项还在、`pv` 非空，但实际 runtime
   DLL 已被破坏 → 误判「已安装」，boot 链放行，最终窗口打开失败（由正常启动路径兜底）。
2. **per-app fixed-version 部署**：把 WebView2 loader 直接放在 app 目录、不写注册表
   的部署方式 → 误判「未安装」，即使 app 自带 runtime 本可正常打开。

更准确的判定是官方 SDK 的 `GetAvailableCoreWebView2BrowserVersionString`
（或直接尝试创建 `CreateWebView2EnvironmentWithOptions`，但后者在缺失时会弹出
runtime 安装 UI，正是 boot 链在显示可读错误前必须避免的行为），而 SDK 方案需要
引入 WebView2 loader 依赖（DLL 或包引用），对便携单二进制交付是额外负担。

**当前兜底**

沿用 P2 §9 的决策：检测**宁可信「可用」**——注册表读失败按「已安装」处理，由
`FatalDialog` 之外的正常启动路径兜底「窗口起不来」的失败模式，而不是用一个可能
错的 gate 挡住一台实际能用的机器。`webview2_other.go` 在非 Windows 恒为可用。

**何时重新评估**

- 真机测试出现「误拦可用机器」或「放行后闪退」的复现时；
- 便携打包（P12）确定交付形态后，若采用固定版本（fixed-version）运行时部署，
  需重新设计检测逻辑以兼容无注册表项的场景；
- 决定引入 WebView2 loader 依赖时。
