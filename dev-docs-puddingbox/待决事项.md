## 生产控制面需要交付真实配置

生产构建选用 `internal/productprofile` 的 production Profile；当前其中的控制面与网关主机仍为 `.invalid` 占位值，可信签名公钥为空。因此构建和结构校验可以通过，但产品门会把该包呈现为未配置，不能完成真实中台登录或取得可信目录。开发 Profile 与 `productstub` 不能替代生产交付。

需要确认：真实的控制面和网关地址、签名 key ID/公钥及其交付渠道是否已具备；若尚未具备，发布流程应明确限制为内部验证，而非对外生产包。结论应回写 [运行时 Profile 配置](运行时Profile配置.md)、[中台接口契约](中台接口契约.md) 与 [便携打包](便携打包.md)。

## 数据根环境覆盖暂不接入 Profile

`allowDataRootOverride` 声明开发 Profile 允许数据根覆盖，但当前没有运行时代码读取它，`internal/datapath` 仍直接接受 `OCTO_DATA_ROOT`。本轮明确暂不改变该行为，因此生产构建尚不能把该字段当作环境覆盖禁令。

未来若要使生产版禁止数据根环境覆盖，需先定义对便携使用、已有脚本和用户数据的兼容性，再改代码和测试。详见 [运行时 Profile 配置](运行时Profile配置.md) 与 [便携数据根](便携数据根.md)。

## 官网真实地址需要在帮助入口上线前确认

品牌事实源已有 `links.external.website`，但当前值仍是上游迁移站点，不能作为布丁盒子的官网对用户展示。帮助与反馈页已约定只读此字段、在真实地址缺失时禁用外跳；不应在 UI 中硬编码或临时猜测一个域名。

需要确认：正式 HTTPS 域名、归属与对外上线状态。确认后更新 `branding/brand.json` 和派生产物，并让品牌校验拒绝上游/占位 URL；结论回写 [品牌与标识](品牌与标识.md) 与 [个人中心](个人中心.md)，再启用帮助页的官网链接。

## 跨平台产物命名要确定品牌迁移策略

Windows 便携目录和可执行文件由品牌配置派生；macOS 打包脚本仍输出 `Octo.app`，Linux 输出 `Octo-<arch>.AppImage`。这不是文档命名问题，而是不同平台已经对文件名作出了不同承诺。

需要确认：是否统一到品牌名；若统一，旧下载链接、更新识别、签名/安装说明与用户脚本如何兼容。确认前保持现状并在发布说明中使用实际名称，详见 [便携打包](便携打包.md) 与 [品牌与标识](品牌与标识.md)。

## 手动检查更新缺少一致的信任边界与本地错误契约

当前三处结论彼此冲突：[个人中心](个人中心.md) 和 [本地 API 契约](本地API契约.md) 允许账户角主动调用 `POST /api/product/check-updates`；[启动与生命周期](启动与生命周期.md) 仍写“相关 UI 不应发起出站版本检查”。实际桌面壳已注册该路由，并直接调用 `internal/upgrade.Check`。后者查询上游 GitHub 与镜像，既不从 Profile 读取版本来源，也没有使用 Profile 信任 key 或已签名发布清单；查询失败时还以 `http.Error` 返回纯文本 `503`，偏离本地 API 的 JSON 错误信封。

需要确认：便携产品是否保留“仅用户主动、只查询不下载”的能力。若不保留，应删除账户角入口和本地路由；若保留，版本来源、渠道与完整性校验必须由 Profile 或其可信 key 验证的发布清单拥有，并把失败统一为可本地化的 JSON machine code。结论应同时回写 [配置治理](配置治理.md)、[启动与生命周期](启动与生命周期.md)、[个人中心](个人中心.md)、[本地 API 契约](本地API契约.md) 与 [运行时 Profile 配置](运行时Profile配置.md)，再补桌面壳路由的成功、失败和“不触发下载/安装”测试。

需要确认：测试环境人工联调矩阵和回滚演练是否仍是本主题未完成的发布门。若仍未完成，应把尚未验收的项目显式收敛为唯一的当前阻塞清单；若已完成，应按本文自身完成定义移除阶段性叙述，只保留最终架构、迁移/回滚边界和验证入口。

## 品牌链接仍有消费者绕过品牌事实源

`web/src/components/overlays/SettingsModal.svelte` 的“查看许可”仍硬编码上游 GitHub URL，而 `branding/brand.json` 已拥有同一 `links.external.license`。这使修改品牌配置无法完整生效，也违反“用户可见品牌链接只能来自品牌配置”的硬规则；[品牌与标识](品牌与标识.md) 与 [配置治理](配置治理.md) 对“公开链接唯一事实源”的描述因此不完全成立。

需要确认：许可链接是否继续指向上游许可证，还是改为布丁盒子的对外许可页。确认后只在 `branding/brand.json` 保留该事实，并让设置页通过品牌访问器读取；同时增加品牌守卫或组件测试，防止重新写入硬编码链接。

## 已核实的低风险文档漂移

[开发与联调](开发与联调.md) 把 `productstub` 的健康手机号写成“任意以 `1` 开头的 11 位手机号”，实际前后端共同的 `productphone.Normalize` 只接受大陆号段 `1[3-9]`（或合法 E.164）。这会使按文档使用 `10000000000`、`12000000000` 的联调直接得到 `invalid_phone`。这是无需产品取舍的文档修正：应将示例和描述改为 `1[3-9]` 开头的 11 位大陆号码或合法 E.164，并保留现有国际号码测试口径。
