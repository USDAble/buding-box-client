# 工具名称与技能参数兼容

写作参照：`dev-docs/m7-skills-design.md`

模型返回的工具名称允许与当前回合已提供的工具名称仅有大小写差异，也允许使用工具定义中明确声明的本地别名。例如 `Skill`、`Glob` 分别执行现有技能加载和文件匹配工具，`Bash` 执行 `terminal`。该规则由共享 agent 循环处理，CLI、桌面、Web 和定时任务复用同一入口。

## 在权限检查之前确定名称

`internal/agent/tool_names.go` 的 `canonicalToolName` 只查询本回合传入的 `ToolDefinition` 列表：标准名称精确匹配优先，其次是唯一的忽略大小写匹配，最后才查询各定义的 `Aliases`。别名同样忽略大小写，多个不同工具声明同一别名时不转换。未知名称和存在歧义的名称保留原值，不猜测工具，也不扩大工具目录。

`ToolDefinition.Aliases` 只供本地解析，JSON 序列化及供应商请求仍只提供标准名称和原有参数 Schema，避免向模型重复提供同一工具。当前声明 `Bash → terminal`、`WebFetch → web_fetch`、`WebSearch → web_search`；目标工具未提供给本回合时，其别名不会被启用。别名只代表名称兼容，参数仍遵循本地 Schema，不把其他产品的超时单位、后台模式或过滤参数自动套入本地工具。

`Agent.runLoop` 在发送工具开始事件和执行权限检查之前调用 `canonicalizeToolCallNames`。PreToolUse / PostToolUse hooks、权限规则、执行器、读后写检查和完成事件使用同一个标准名称；发回模型的历史保留供应商返回的原始名称，不把 `Skill` 或 `Bash` 改写成另一个调用。工具调用 ID、参数、参数解析错误和结果配对保持原有语义；不修改供应商返回的原始切片。

本地问题的触发记录是定时任务创建会话返回了 `Skill` 与 `Glob`，而客户端注册名称为 `skill` 与 `glob`，导致严格名称分发返回 unknown tool。技能文件已经存在，错误发生在进入技能加载前。修复不改变任务创建流程或调度规则。

专家创建的后续调用实际使用了 `Bash` 和已有的 `command` 参数；这与 `terminal` 不是大小写差异，因此需要显式别名。修复继续执行现有终端工具，权限规则、hooks 和终端读后写跟踪都接收标准名称，不新增 shell 执行入口。

## 技能加载兼容 `skill` 参数

`SkillTool.Execute` 继续以 `name` 为标准参数；仅在请求中没有 `name` 字段时，接受 `skill` 字段作为技能名。例如 `{"skill":"skill-creator"}` 和 `{"skill":"expert-agent-manager"}` 沿用现有技能加载流程。显式传入的空值、非字符串或未知 `name` 仍报错，不用别名覆盖；别名同样不能绕过技能启用状态、专家允许列表和系统技能限制。

创建技能和专家的本地失败记录中，模型均使用了 `skill` 字段。本地加载器返回 `skill: name is required` 后，网关在下一轮返回 `PROVIDER_CONTEXT_UNAVAILABLE`。兼容处理只读取参数，不修改原始调用、会话历史或工具调用 ID，也不增加模型重试。它解决已确认的参数不匹配；其他网关上下文故障仍需根据网关侧记录排查。

## 验证

`internal/agent/tool_names_test.go` 覆盖标准名称、大小写变体、未知名称、未提供工具、名称碰撞，以及流式和非流式循环中的权限拒绝、历史、事件和调用 ID。

`internal/tools/tool_names_test.go` 以真实 agent 循环和 `DefaultRegistry` 加载隔离的 `cron-task-creator` 技能并执行 `Glob`，同时验证大小写变体不能绕过已有文件的读后写检查。测试只使用临时文件和模型回复夹具，不调用真实模型、不创建定时任务。

`internal/tools/skill_arguments_test.go` 覆盖标准参数、别名、参数优先级、无效参数和原始参数保持不变；通过真实 agent 循环验证两个创建入口的技能能加载并继续下一轮，同时验证专家技能限制继续生效。

`internal/tools/tool_catalog_test.go` 遍历完整 `allTools`，包含默认不可用而被门控的工具，检查名称及别名不冲突、参数 Schema 中的必填字段有定义，并以无副作用执行器验证所有名称与别名的大小写变体。另通过真实 `DefaultRegistry` 验证 `Bash` 执行一条回显命令。agent 测试验证别名不能绕过 `terminal` 拒绝规则、未提供工具不启用别名，以及别名不进入模型工具 Schema。

## 新工具和新技能沿用现有契约

新增内置工具只加入 `allTools`，工具列表和执行器都读取同一个注册表；大小写兼容自动覆盖它。需要兼容不同拼写时在该工具的 `Definition` 中显式声明 `Aliases`，并运行目录检查；不要另加一套注册表或在执行器分发后才改名字。MCP 工具按当前回合发现的定义处理，不猜测其服务端接口。

新建技能只组合现有工具，不会自动注册新的工具。`skill-creator` 要求生成步骤遵循当前会话实际提供的名称和参数 Schema，并在测试中检查相关调用。`Read/Write/Edit` 与本地文件工具不仅名称不同，常见的 `file_path` 与本地 `path` 也不一致；`Task/Agent` 的能力及参数同样不能只按名字推断，因此不声明这些语义不完整的别名。缺失能力或错误参数仍需明确报错，不能承诺模型永远不会生成无效调用。

本地开发使用 `make desktop-dev` 时，该 Go 行为需要重新构建并重启开发桌面进程，Vite 热更新不能替换已运行的后端代码。

## 非目标

- 不模糊推断未声明的别名，也不重写已记录的工具参数或自动转换其他产品的参数语义。
- 不增加重试、额外模型请求或备用执行器。
- 不修改权限策略、技能可用范围、MCP 配置或任务数据。
