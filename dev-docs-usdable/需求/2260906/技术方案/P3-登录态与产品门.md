## 1. 目标与非目标

**目标**

1. 定义并落地 `data/product-state.json` —— 本期所有本地确定性数据（登录态、激活、积分、开关、默认模式）的唯一状态文件。
2. 新增**产品门**：拦桌面窗口渲染 + 该窗口发起的聊天相关请求。
3. 与上游 access key **机器门**并存，不替代、不拆除。

**非目标**

- 不做拦截页 UI（P4）。
- 不拦 CLI，不拦本机其它 loopback 进程（需求 §9.2 / §9.8 已列为已知限制）。
- 不做真实鉴权、不做 token 过期（需求 §5.3.5）。

---

## 2. 现状（代码事实）

- 机器门：`internal/server/auth.go`，`requireAuth` 中间件；cookie 名 `octo_access_key`（`:28`）；loopback 豁免（同文件头注释）。前端 `web/src/lib/auth.ts` 负责 401 时弹 `AuthGate.svelte`。
- 权限门：`internal/app/gate.go` `NewPermissionGate` —— 这是**工具调用**权限引擎，与产品门作用面完全不同，不要混。
- 没有任何「用户身份」概念。上游是单机单用户，`internal/server` 里没有 session/user 中间件可复用。

> **计划修正**：开发计划 §4 第 2 条建议「新增独立 gate，不污染现有权限引擎」——方向对，但没说清**产品门如何识别「桌面窗口发起的请求」**。这是本方案要解决的核心问题：如果只在前端 gate，用户 F12 或外部 curl 就能绕过；如果按 loopback 判定，CLI 也会被误拦（需求 §2.3 禁止）。

## 3. 设计

### 3.1 窗口令牌：产品门的识别依据

```
桌面进程启动
   └─ 生成 windowToken = 32 字节随机（仅存内存，不落盘）
        ├─ 注入 webview：加载 URL 带 ?window_token=…，前端立刻存入 sessionStorage 并清地址栏
        └─ 交给 productgate 中间件作为唯一有效值

请求到达 /api/chat…
   ├─ 无 X-Octo-Window-Token          → 放行（CLI / 其它 loopback 进程，需求 §9.8 已知限制）
   ├─ 有且匹配 + 已登录                → 放行
   └─ 有且匹配 + 未登录                → 403 {"error":"product_gate","reason":"not_logged_in"}
```

这个设计的取舍要说清楚：**它拦的是「窗口」不是「机器」**。带错 token 的请求不放行，不带 token 的请求放行 —— 后者正是 CLI 场景。这与需求 §1.2「产品门拦的是桌面窗口里的界面，以及该窗口发起的聊天相关请求」和 §9.8「本机其它进程仍可能访问 loopback API」完全一致，不是漏洞而是明写的边界。

token 只存内存，进程重启即换，因此不需要考虑泄露后的吊销。

### 3.2 两道门的关系

```
HTTP 请求
   │
   ├─ requireAuth（机器门，上游）      ── 防远程连接，判 access key / loopback
   │
   └─ requireProduct（产品门，新增）   ── 防未登录使用，判 window token + 登录态
```

两者是**串联的独立中间件**，各自可以单独失败，错误码不同（401 vs 403），前端处理路径也不同（弹 AuthGate vs 切拦截页）。绝不把登录态塞进 access key 体系 —— 需求 §7「不做：用产品登录替换 access key」。

### 3.3 受产品门保护的路由

需求要求拦「聊天相关请求」。按白名单反向定义更安全（新增路由默认被保护）：

**豁免**（未登录也能调）：

| 路由 | 理由 |
|---|---|
| `/api/health` `/api/version` | 上游已豁免机器门，保持一致 |
| `/api/product/state` (GET) | 前端要靠它判断该渲染拦截页还是主界面 |
| `/api/product/login` `/api/product/send-code` `/api/product/activate` | 登录动作本身 |
| `/api/product/locale` (PUT) | 需求 §5.3「未登录允许切换界面语言」 |
| `/api/product/legal/*` | 协议与隐私待接入页面 |
| 静态资源 `/`, `/assets/*` | 页面本身要能加载 |

**其余全部保护**，含 `/api/sessions*`、`/api/chat*`、`/ws`、`/api/mcp*`、`/api/channels*`、`/api/lightapps*`（需求 §5.4.3 末条：未登录时这些能力同样不可从窗口调用）。

WebSocket `/ws` 的 token 走查询参数（浏览器 WS 握手不能自定义 header），与上游 access key 的做法一致。

### 3.4 状态文件

`data/product-state.json`，单一文件，原子写（写 `.tmp` + `os.Rename`）。U 盘上 rename 是原子的，比就地改写安全。

```json
{
  "schemaVersion": 1,
  "account": {
    "phone": "13800001234",
    "phoneMasked": "138****1234",
    "nickname": "用户1234",
    "token": "local-8f3a…",
    "lastLoginAt": "2026-09-07T10:00:00+08:00"
  },
  "activation": {
    "activated": true,
    "code": "固定本地激活码",
    "activatedAt": "2026-09-07T10:00:00+08:00",
    "expiresAt": "2027-09-07T10:00:00+08:00"
  },
  "credits": { "balance": 1280, "monthUsed": 0, "monthKey": "2026-09" },
  "plan": { "name": "trial" },
  "prefs": {
    "locale": "zh",
    "inputSensitiveCheck": true,
    "defaultChatMode": "default"
  }
}
```

字段归属：`account`/`activation` 本 PR；`credits` P6；`prefs.inputSensitiveCheck` P8；`prefs.defaultChatMode` P9。**schema 在本 PR 一次定完**，后续 PR 只填值不改结构，避免三个 PR 各自加字段导致的合并冲突。

- `account == null` → 未登录。
- `activation.activated == false || activation == null` → 首次激活（拦截页显示激活码字段）。
- 「退出登录」只清 `account`，保留 `activation` / `credits`（需求 §5.3.5）。
- `token` 无过期字段 —— 需求明确本期不做过期，不要预留一个没人维护的 `expiresAt`。
- `phone` 存规范化后的 11 位明文。这是本地确定性数据、在用户自己的数据根里，需求 §6「安全：登录态仅存数据根；本地 token 即可」。二次登录要比对绑定号（§5.3.4），存掩码就比不了。

### 3.5 并发与一致性

`internal/productstate` 包内用一把 `sync.RWMutex` 保护内存副本，写操作同步刷盘。所有读走内存，避免每次请求读盘（U 盘上很慢）。

冻结状态（P2 的 `frozen`）下写操作直接返回错误，不尝试落盘。

## 4. 接口与数据结构

```go
// internal/productstate/state.go
package productstate

type State struct {
    SchemaVersion int         `json:"schemaVersion"`
    Account       *Account    `json:"account"`
    Activation    *Activation `json:"activation"`
    Credits       Credits     `json:"credits"`
    Plan          Plan        `json:"plan"`
    Prefs         Prefs       `json:"prefs"`
}

type Store struct{ /* mutex + State + path */ }

func Open(path string) (*Store, error)      // 文件缺失 → 零值 State，不报错
func (s *Store) Snapshot() State            // 值拷贝，读方不持锁
func (s *Store) Mutate(fn func(*State) error) error  // 改 + 原子落盘
func (s *Store) LoggedIn() bool
```

```go
// internal/productgate/gate.go
package productgate

type Gate struct{ /* token + *productstate.Store */ }

func New(windowToken string, st *productstate.Store) *Gate

// Middleware 包住受保护路由。豁免清单由调用方（internal/server）决定，
// 这样 gate 包不需要知道任何路由字面量。
func (g *Gate) Middleware(next http.Handler) http.Handler

// Allow 供 WebSocket 升级前单独调用（WS 不走普通中间件链）。
func (g *Gate) Allow(r *http.Request) (ok bool, reason string)
```

**HTTP**

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/product/state` | 返回脱敏后的状态（不含 `phone` 明文、不含 `token`），前端据此路由 |
| POST | `/api/product/logout` | 清 `account`，200 |
| PUT | `/api/product/locale` | `{"locale":"zh"\|"en"}`，未登录可调 |

登录 / 发码 / 激活三个接口在 P4 定义（它们的校验规则属于拦截页表单）。

**前端**

`web/src/lib/product.ts` 新增：

```ts
export type ProductPhase = 'unknown' | 'blocked' | 'ready'
export const productPhase: Writable<ProductPhase>
export const productState: Writable<ProductStateDTO | null>
export function windowToken(): string | null    // 从 sessionStorage 读
export async function refreshProductState(): Promise<void>
export async function logout(): Promise<void>
```

`web/src/lib/api.ts` 的统一 fetch 包装里加两件事：请求带 `X-Octo-Window-Token`；响应 403 且 `error === "product_gate"` 时把 `productPhase` 置 `blocked`（处理「另一个窗口退出登录」这类状态漂移）。

## 6. 测试

**单测**

- `productstate`：缺文件 → 零值；`Mutate` 后重开读回一致；写失败（目录只读）不破坏原文件。
- `productgate`：四种组合（有/无 token × 已/未登录）返回正确；豁免路由恒放行；`/ws` 走查询参数。
- 退出登录后 `activation` / `credits` 仍在。

**集成**（`httptest`）

- 未登录 + 正确 token 请求 `/api/sessions` → 403 `product_gate`。
- 未登录 + 无 token（模拟 CLI）→ 200。**这条要显式写测试**，因为它看起来像 bug，必须有测试固定住这个有意为之的行为，防止后来的人「修复」它。
- 机器门与产品门同时不满足时，先返回 401（机器门在外层）。

**手工验收**

1. 未登录状态下 F12 手动 `fetch('/api/sessions')` → 403。
2. 同一时刻用 `octo` CLI 操作 → 正常。
3. 「退出登录」后进程仍在、托盘仍在、回拦截页；会话与积分文件仍在 `data/`。

## 7. 上游合并影响

**等级：低。** 两个新包 + `server.go` 里几行中间件挂载 + `api.ts` 里的 fetch 包装。

风险点只有一个：上游新增路由时不会知道产品门的存在。因为豁免采用**白名单**（默认保护），新路由自动被保护，方向是安全的 —— 最坏情况是某个新路由被误拦，属于可见的功能问题，而不是静默的安全漏洞。这个取舍要在 `server.go` 的注释里写明。

## 9. 风险与决策

| 项 | 处理 |
|---|---|
| window token 通过 URL 传递会进 webview 历史 | 前端首屏立即 `history.replaceState` 清掉，与上游 `?access_key=` 的既有做法一致（`web/src/lib/auth.ts` 头注释） |
| 状态文件损坏（拔盘写一半） | 原子 rename 保证不会读到半个文件；真读不出来时按「未登录 + 未激活」处理并提示，不静默重置已激活状态 —— 宁可让用户重新激活也不要让他以为数据没丢 |
| 两个门的错误码被前端混淆 | 401 → AuthGate；403 + `error:"product_gate"` → 拦截页。写进 `api.ts` 注释 |
| 需求 §9.8 的已知限制被误当作 bug 上报 | 在帮助待接入页面与本文档各写一句；测试里固定住该行为 |

**已拍板**（回答开发计划 §4 第 3 条）：本地确定性数据落在**数据根内单一状态文件** `data/product-state.json`，不进 `brand.json`。理由：`brand.json` 是编译期品牌配置、要进 CI guard、要跟着 `make brand` 同步；而积分/登录态是运行期用户数据，两者生命周期完全不同，混在一起会让 `brand-check` 因用户数据变动而失败。
