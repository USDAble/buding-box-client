# 本地编译、打包与人工验收手册

- **适用仓库：** `E:\zxy\work-code\buding-box-client`
- **唯一开发分支：** `dev-zxy`（不得在 `main` 开发或合并）
- **PR 目标：** `origin/buding`
- **最后更新：** 2026-09-04
- **用途：** 在创建 `dev-zxy -> buding` PR 前，由人工复现构建、安装和功能验收。

> **结论先说清楚：一个 EXE 不能覆盖所有 CPU 架构和所有 Windows 系统。**
>
> - `octo-setup.exe` 是 **Windows x64（amd64）** 安装器，只能用于 64 位 Intel/AMD Windows。
> - Windows ARM64 应使用单独构建的 `octo-setup-arm64.exe`，并在 ARM64 真机验收。
> - 32 位 Windows（x86）不在 Desktop 发布支持范围内；x64/ARM64 安装器均不能在其上运行。
> - Windows 的成功不能代替 macOS、Linux、Android、iOS 的构建或运行验收。

除非章节明确要求，否则不要把 `GOARCH=amd64` 写入仓库配置、脚本或 CI。本手册中的目标架构变量仅用于**一次目标包构建**，不会改变项目默认行为。

## 1. Windows Go 工具链：官方 x64 安装与 PATH 修复

### 1.1 当前机器状态

本机是 64 位 AMD Ryzen 9 5900X，适合 **Windows x64 Go**。官方 Go 已通过 winget 安装：

```powershell
winget install --id GoLang.Go --exact --silent --accept-source-agreements --accept-package-agreements
```

当前官方安装应满足：

```powershell
$go = 'C:\Program Files\Go\bin\go.exe'
& $go version
& $go env GOHOSTARCH GOARCH GOOS GOROOT
```

预期至少包括：

```text
go version go1.27.0 windows/amd64
GOHOSTARCH=amd64
GOARCH=amd64
GOOS=windows
GOROOT=C:\Program Files\Go
```

### 1.2 必须处理遗留 x86 Go PATH

机器上仍可能存在旧路径：

```text
C:\Program Files (x86)\Go\bin
```

若它排在 `C:\Program Files\Go\bin` 前面，普通 PowerShell 的 `go` 会错误命中 `windows/386`，Desktop/Wails 的 Windows callback 可能报：

```text
panic: compileCallback: argument size is larger than uintptr
```

这不是品牌代码问题，也不是 CPU 不支持。请以**管理员身份**打开“编辑系统环境变量”，在系统 `Path` 中：

1. 删除 `C:\Program Files (x86)\Go\bin`；
2. 保留并优先放置 `C:\Program Files\Go\bin`；
3. 关闭全部终端，重新打开 PowerShell；
4. 验证：

```powershell
where.exe go
go version
go env GOHOSTARCH GOARCH GOOS GOROOT
```

在管理员 PATH 修复前，仍可安全地在本手册命令中使用 `$go = 'C:\Program Files\Go\bin\go.exe'`。这只是明确选择已安装的官方 x64 编译器，**不是**向仓库写入架构硬编码。

## 4. Windows：一键生成本地验收安装器

> 一个安装器不能覆盖所有 Windows CPU：`amd64` 与 `arm64` 必须分别打包、分别在对应真机验收；32 位 Windows 不在 Desktop 支持范围内。

唯一的 Windows 打包入口是：

```text
scripts\package-desktop-windows.ps1
```

它会从脚本自身的位置定位仓库，因此无需依赖当前 PowerShell 的工作目录；依次执行品牌同步检查、Web 依赖安装和构建、目标架构 `rg` 嵌入、Windows 图标资源生成、Desktop/CLI 构建、`uv.exe` 下载、Inno Setup 编译，并在成功时打印安装器绝对路径、大小和 SHA-256。

### 4.1 第一次准备：Go、Node/npm 和 Inno Setup

- **AMD/Intel x64 Windows：** 安装官方 Windows x64 Go；本机建议使用 `C:\Program Files\Go\bin\go.exe`。
- **Windows ARM64：** 安装官方 Windows ARM64 Go。x64 Go 在 ARM64 Windows 的模拟层中可能能启动，但并非原生、没有必要，也不应作为常规打包方案。
- **x64 构建机交叉编译 ARM64 包：** 本项目 Desktop 在 Windows 使用 `CGO_ENABLED=0`，所以官方 Windows x64 Go 可构建 `-Arch arm64`；这不替代 ARM64 真机安装与功能验收。
- 脚本会优先找官方 Go 安装位置，也可通过 `-GoExecutable` 指定其他已验证的 Go；它拒绝 `windows/386`，并且不会修改系统 PATH、`GOARCH` 或仓库配置。
- 安装 Inno Setup 6（首次一次）：

```powershell
winget install --id JRSoftware.InnoSetup --exact --accept-source-agreements --accept-package-agreements
```

若程序未被自动找到，可用 `-IsccExecutable 'C:\path\to\ISCC.exe'` 显式指定。脚本需要可用的 `node`、`npm`、Git、网络；网络用于 npm、ripgrep 和 uv 的锁定版本下载。

### 4.2 x64 安装器：推荐的一条命令

```powershell
Set-Location E:\zxy\work-code\buding-box-client
pwsh .\scripts\package-desktop-windows.ps1 -Arch amd64 -Version 0.0.0-local
```

如需避免覆盖一个正在运行或被人工检查占用的旧安装器，可增加 `-OutputDirectory '.\staging-verify'`；不传时仍使用默认的 `staging`（x64）或 `staging-arm64`（ARM64）。若机器无法访问 GitHub，可将已有对应架构的 `uv.exe` 通过 `-UvExecutable 'C:\path\to\uv.exe'` 传入，脚本会跳过下载；否则脚本会自动下载 Makefile 锁定版本，并对网络下载设置 120 秒超时。

成功后，安装器位于：

```text
E:\zxy\work-code\buding-box-client\staging\octo-setup.exe
```

`0.0.0-local` 仅用于本地验收，不能作为正式发布版本。对外名称会来自 `branding\brand.json`；内部可执行文件仍为 `octo-desktop.exe` 和 `octo.exe`，不得为了改名破坏旧数据、深链或协议兼容。

只在确认 `internal\server\webdist` 已由当前源码构建且想节省时间时，才使用：

```powershell
pwsh .\scripts\package-desktop-windows.ps1 -Arch amd64 -Version 0.0.0-local -SkipWebBuild
```

这不是日常验收的默认命令。默认流程始终重建 Web UI，避免把旧页面嵌入新安装器。

### 4.3 ARM64 安装器：独立包、独立真机验收

可在 Windows x64 构建机交叉编译：

```powershell
Set-Location E:\zxy\work-code\buding-box-client
pwsh .\scripts\package-desktop-windows.ps1 -Arch arm64 -Version 0.0.0-local
```

成功后输出为：

```text
E:\zxy\work-code\buding-box-client\staging-arm64\octo-setup-arm64.exe
```

不要把 x64 包在 ARM64 上的模拟运行当成 ARM64 发布验收；必须将该 ARM64 安装器复制到 ARM64 Windows 真机，完成下面的清单。

### 4.4 Windows 人工验收清单（每个目标架构均必须逐项记录）

建议在新的 Windows 测试账户执行；先备份现有 `~\.octo` 数据。

- [ ] 双击目标包：x64 为 `staging\octo-setup.exe`，ARM64 为 `staging-arm64\octo-setup-arm64.exe`；安装向导、发布者、开始菜单和卸载项显示布丁盒子 / Pudding Box 资料；
- [ ] 首次启动 Desktop，确认窗口标题、欢迎页、设置、关于我们、通知与托盘图标；
- [ ] 中文/英文切换后，产品名称、标语和 About 信息一致；
- [ ] 创建任务、启动本地工具、运行一个 Agent/聊天流程、保存后重启，确认基础功能；
- [ ] 使用一份已备份的旧 `~\.octo` 数据验证读取；不要把该兼容目录重命名为品牌名目录；
- [ ] 在同一账户执行覆盖安装，确认应用可启动且数据未被无提示清空；
- [ ] 卸载后确认程序移除；用户数据不得被无提示删除；
- [ ] 保存安装器、关于页面、托盘、开始菜单、故障日志的截图；记录版本、机器 CPU 架构、SHA-256、步骤与结果。

本地包未签名时，Windows 可能提示“未知发布者”。这是正式发布阻断项，但不等同于功能测试失败。

### 4.5 失败排查与临时产物

- 报 `pattern binaries/rg: no matching files found`：必须通过本脚本运行；它会先调用 `scripts\embed-rg-windows.ps1`。不要手工跳过此步骤。
- 报 Go 的 `compileCallback: argument size is larger than uintptr`：检查 `where.exe go`，移除旧的 `C:\Program Files (x86)\Go\bin`，并安装/使用原生 64 位官方 Go；也可暂时给脚本传入 `-GoExecutable 'C:\Program Files\Go\bin\go.exe'`。
- 找不到 `ISCC.exe`：执行本节的 winget 命令，重新打开 PowerShell，或使用 `-IsccExecutable`。
- 需要保留 uv 下载现场排查：增加 `-KeepDownloads`；默认仅清理本脚本自己的 `dl\package-desktop-windows-*` 临时目录。`embed-rg-windows.ps1` 的 `dl\rg*` 缓存可在人工验收后再自行删除。
- `staging\`、`staging-arm64\` 与 `dl\` 已在 `.gitignore` 中，属于本地构建产物；先检查内容后再清理，绝不提交到 PR。

## 6. macOS：必须在 macOS 上构建和验收

Windows 无法替代 macOS 的签名、Universal 二进制、Finder/Dock/托盘视觉检查。项目脚本会构建 Intel + Apple Silicon Universal `Octo.app`，最低目标为 macOS 11.0。

在 macOS 的仓库根目录执行：

```bash
xcode-select --install
# 安装与项目要求匹配的 Go、Node/npm 后：
npm --prefix web ci
npm --prefix web run build
bash scripts/package-desktop-macos.sh

mkdir -p staging
go build -o staging/octo ./cmd/octo
cp LICENSE.txt staging/LICENSE.txt
AppVersion=0.0.0-local SourceDir="$PWD/staging" OutDir="$PWD/staging" \
  packaging/macos/build.sh

installer -pkg staging/octo-setup.pkg -target CurrentUserHomeDirectory -dominfo
pkgutil --expand-full staging/octo-setup.pkg expanded-pkg
```

预期包：

```text
staging/octo-setup.pkg
```

macOS 人工验收：Finder 中应用名和 `icon.icns`、Dock、菜单栏/托盘、窗口标题、About、中文/英文、首次启动、覆盖安装、卸载/删除重装、旧数据读取。脚本的 ad-hoc 签名只适合本地测试；正式发行需要 Developer ID 签名和 Apple notarization。

## 7. Linux：必须在原生 Linux 目标架构构建和验收

Linux AppImage 是 native-only：x86_64 应在 amd64 Linux 构建，aarch64 应在 ARM64 Linux 构建。GTK4、WebKitGTK 6.0、libsoup 3.0 是宿主依赖，不能因生成 AppImage 就假设所有发行版可运行。

```bash
sudo apt-get update
sudo apt-get install -y libgtk-4-dev libwebkitgtk-6.0-dev libsoup-3.0-dev
cd /path/to/buding-box-client
npm --prefix web ci
npm --prefix web run build
bash scripts/package-desktop-linux.sh 0.0.0-local

chmod +x Octo-*.AppImage
./Octo-*.AppImage
```

预期输出按宿主机架构为：

```text
Octo-x86_64.AppImage
# 或
Octo-aarch64.AppImage
```

验收应用菜单/desktop entry、图标、窗口名、启动、WebKitGTK、中文/英文、升级/旧数据兼容。若手动携带 CLI，`OCTO_CLI` 必须与 AppImage 同一架构。

## 8. Android 与 iOS：原生工程、打包与人工验收

Windows 可做第 3 节 Mobile 检查，但不能生成并真机验证 iOS；Android 需要 Android SDK、JDK、ADB；iOS 需要 Mac、Xcode 和 iOS SDK。以 `mobile\README.md` 为工程生成权威说明。

```bash
# 仓库根目录
make web-build
cd mobile
npm ci
npm run bundle-web
npx cap add android
npx cap add ios
npm run wire-native -- --local
npx cap copy
```

Android Debug 示例：

```bash
(cd android && ./gradlew assembleDebug)
adb install -r android/app/build/outputs/apk/debug/app-debug.apk
```

macOS 上的 iOS Simulator 示例：

```bash
xcodebuild -project ios/App/App.xcodeproj -scheme App \
  -destination 'platform=iOS Simulator,name=iPhone 15 Pro' build
```

每次 Web 改动后都需要重新执行 `npx cap copy`。`npm run wire-native -- --local` 只能用于本地模拟器/真机调试，不可作为 Release 环境配置。

移动端人工验收：主屏图标、应用名、欢迎/关于页面、中文/英文、配对/Deep Link、任务/聊天/审批、重启后的数据、覆盖安装。推送唤醒属于单独的移动平台能力，不应由品牌验收推断为已完成。
